# Extending garden

Step-by-step checklists for adding a command, dashboard tmux hook, config key, garden-level setting, workflow, or harness. Each names the call sites that do NOT follow automatically from registration — the places a new extension silently degrades if missed. Architecture lives in `DESIGN.md`; this file is the how-to.

## Adding a new command

1. `src/commands/<name>.ts` — export an async `(args: string[]) => Promise<void>`
2. Register in `src/commands/index.ts`
3. Add to the help text in `src/cli.ts`
4. Use `output()` and `resolveProject*()` per the Conventions in `AGENTS.md`

## Adding a dashboard tmux hook

Install visual status hooks in `setupStatusBar` (`src/dashboard/header.ts`), which runs on creation and runtime refresh. Keep work tmux-native when possible; a focus hook can use `refresh-client -S` with the event client as its default target. Hooks requiring Garden logic follow the `create.ts` hooks: invoke an internal `dashboard` route through `run-shell` and shell-escape its arguments. Test command wiring and any format or redraw behavior against an isolated tmux server; `test/integration/status-focus.real.test.ts` uses a Python standard-library PTY fixture to exercise terminal focus reports.

## Adding a new project config key

Add the field to `ProjectConfig` and `VALID_CONFIG_KEYS` in `src/config.ts`. A scalar key also belongs in `SETTABLE_KEYS` and the validation/mutation switch in `src/dashboard/project-config-mutate.ts` so the CLI has one authoritative writer; a list-valued key with verbs needs a dedicated dispatch and shared mutators instead (`sandboxWriteRoots` is the example). Update `src/cli.ts` help plus the Projects summary above; add a dashboard menu row only when the key is an everyday interactive control. Cover set, clear, invalid, and read-back behavior in `test/config.test.ts`, and update `DESIGN.md` when the key changes runtime architecture.

## Adding a garden-level setting

Add an optional field or typed block to `GardenConfig` in `src/config.ts`, with a defaulting getter and a validated setter using `mutateConfig`. For a menu control, add its view field, plan builder, and apply handler in `src/dashboard/garden-menu.ts`, then wire the internal route in `src/dashboard/index.ts`. Await any live update before reopening the menu: `runMenu` blocks until the menu closes. Route all consumers through the same getter; for column split changes, use `reconcileColumnSplit`, which reuses `rebakePanesOnResize` and `presizeHiddenWindows` and records successful application under the dashboard state lock. Cover set, unset, invalid values, and live application, and update the settings summaries here and in `DESIGN.md`.

## Adding a new workflow

See `WORKFLOWS.md`. Short version: define a poller-only `WorkflowDefinition` in `src/dashboard/workflows/<name>.ts`, register it in `workflows/index.ts`, and reuse `default.ts`'s state handlers wherever possible. Agent activity hooks are shared lifecycle plumbing; do not import the workflow registry from `hook-dispatcher.ts` or `hooks/default.ts`. Tests: `test/workflows.test.ts` + an integration test on the real external boundary the workflow drives. Concrete examples in the registry: `trellis.ts` (full-spec divergence — own reviewer prompt, verdict vocab, model pinning, post-merge dispatch), `grow.ts` (minimal loop divergence), and the designer/planner pair (data-only definitions that reuse default handlers and invert worker posture through rules/skills). If your workflow shares the cold-respawn-per-iteration mechanics, supply a `LoopHooks` instance (see `src/dashboard/loop.ts`) instead of forking the dance.

**Per-workflow runtime data** (the trellis pattern). Anything the workflow accumulates per worker goes under an optional sub-object on `WorkerEntry`, not as flat fields — `entry.trellis?: TrellisData` and `entry.grow?: GrowData` are the two concrete examples (`registry.ts`). `updateWorkerFields({ <subObject>: { <field>: ... } })` deep-merges that sub-object so callers don't clobber sibling fields. Add a legacy-shape migration to `readRegistry` so on-disk entries from earlier shapes get rebuilt at next read. Don't add flat per-workflow fields to `WorkerEntry`; the flat-fields path was deliberately removed (the migration in `readRegistry` exists to scrub stragglers from old on-disk entries).

## Adding a new harness

See `docs/MULTI-MODEL.md` "Layer 3". Short version: implement `HarnessCore` in `src/dashboard/harness/<name>-core.ts` (command dialects, prompt delivery, transcript reader, transient-error shapes — keep its import closure light; it is reachable from `dist/hook.js`), add `installRuntimeConfig` in `harness/<name>.ts`, and register in both `harness/core.ts` and `harness/index.ts`. Registering makes the harness a crew **member** and so a `⌥⇧N` provider choice for free; add its strong/middle pair to `SEAT_MODELS` (`crew.ts`) or its builtin crew seats stay unpinned. But the composer's **model and effort vocabularies** are per-harness and do NOT follow: `composerModels`/`composerEfforts` (`trellis-picker.ts`) branch explicitly, so an unhandled harness silently offers the Anthropic aliases and the claude-code effort rungs. Add a branch (see `codex-models.ts` for the read-the-harness's-own-catalog shape, fallback-list included) or the operator picks names the new harness cannot run. Launch **tuning defaults** are per-harness in the same way: `harnessTuning` (`launch-plan.ts`) is what pins codex's unpinned model/effort, and a harness with no branch there launches on whatever its own CLI defaults to. That may well be right — decide it deliberately rather than inherit it by omission. A new **provider** needs none of this — it is config, not code: `garden provider add` makes it a member and its `modelMap` keys become its model vocabulary automatically (`providerModelAliases`). Add a row to the `READERS` table in `prompt-verify.ts` too: delivery verification reads back the newest prompt from the harness's own transcript, and because that table is a hook-bundle leaf rather than a `HarnessCore` method, registering does NOT opt a harness in — an unlisted harness silently loses verification (`prompt-verify.test.ts` fails until the row exists). The reader must skip the harness's injected user-role records and return the text verbatim: the caller compares it against what garden pasted, so any condensing manufactures a mismatch. `task-title.ts`'s `OPENING_READERS` is a second such table, for the same bundle reason and with the same consequence: an unlisted harness can never be given a written thread title, so a row its own title source leaves blank stays blank (`task-title.test.ts` fails until the row exists). Its reader returns the first task prompt, including peer-delivered task messages that delivery verification skips. A harness without a turn-end signal cannot be registered — `capabilities.turnEnd` is typed `true` because STATUS.md's no-polling invariant is preserved by refusing such harnesses, not polling around them. Worker capabilities are **enforced at spawn/resume** by `resolveWorkerLaunchPlan` (`launch-plan.ts`, delegating tuple checks to `workerLaunchCompatibilityError`), so declare them deliberately rather than copying a sibling adapter: `workerWorkflows` is a fail-closed allowlist of the worker workflows whose launch/resume semantics the adapter actually implements (a workflow missing from it is refused, so registering does NOT opt a harness into future workflow protocols), and `providerProfiles` says whether the harness consumes garden's `ANTHROPIC_*` provider contract — false means a provider-backed worker is refused rather than silently launched against the harness's own backend. `sandbox` and `resume` are enforced at the same boundary; `headlessRoles` separately opts the adapter into each review-family role. The event side: translate the harness's native lifecycle onto the normalized `WorkflowHookHandlers` methods (`onTurnEnded` etc.) — for claude-code that translation is `hook-dispatcher.ts`'s wire-name switch. Check what the harness's terminal title says while it works: if it is not a rolling summary of the agent's activity, implement the optional `readActivity` too, or the status pane's detail column shows whatever the title happens to be (for Codex that was the worktree basename, i.e. the worker's own name). Check whether the harness can move a session OFF the model garden pinned with its launch flags: if it can, and if it names models in the same vocabulary the pin uses, implement the optional `readRunningModel` so `model-drift.ts` can flag the divergence — a harness that omits it is simply never checked, and garden goes on asserting a pin it cannot verify (which is what let codex 0.153.4 run a worker on `gpt-6-astra` for 13 minutes under a row reading `gpt-5.6-sol`). The caller compares the reading to the pin for exact equality, so a harness whose pin is an alias its transcript never echoes back (claude-code pins `opus`; the transcript records `claude-opus-5`) must normalize inside the reader — answer in the pin's own words when the two name the same model, and return null for an id it cannot place, rather than handing up a spelling that reads as drift on every healthy worker. Check WHEN the harness's SessionStart-equivalent fires, too: garden's seed wait treats `agentStatus` leaving `loading` as "the TUI is up", which holds only for a harness that reports boot. One that fires at the first *turn* instead (Codex) deadlocks that wait — nothing clears `loading` until a prompt lands, and the wait is what withholds the prompt — so it must implement the optional `promptReady`, which reads boot off the pane. Two call sites outside the adapter name the harness explicitly and do NOT follow from defining it: `newWorker` (`workers.ts`) stamps codex's `awaiting task` creation placeholder (or a seed's first line) so a fresh row is not blank before the first prompt, and `applyAndLog` (`hooks/default.ts`) exempts a worker still carrying that placeholder from the heartbeat throttle so the derived summary lands on the first hook rather than up to 10s later. A harness with no branch there starts blank and heals a heartbeat behind. The pane's **status line** is a third such site: garden names the worker's model, effort, and remaining context on every pane, but each harness expresses that in its own dialect (claude-code: a `statusLine` command in garden's settings file; Codex: a `-c tui.status_line=[…]` launch override), so a new adapter shows whatever its CLI shows by default until it renders its own. `readTurns` owes a **summary**, not a transcript dump: accumulate activity between operator prompts and flush ONE assistant turn per prompt through `summarizeTurn` (`conversation.ts`), mapping the harness's tool vocabulary onto the neutral names it reads — and route operator prompts through `promptTurn` so garden's own continuations collapse to markers. A reader that emits one turn per assistant message produces a worse-formatted copy of the agent pane.

Two model details do not follow automatically from registering the adapter. If the harness accepts both aliases and concrete model IDs, normalize only aliases whose transcript spelling differs; concrete pins must stay exact or a substitution within one family is hidden. If `harnessTuning` supplies a Garden-owned default model, add that same default to `pinnedModel` (`model-drift.ts`) and `projectWorkerModel` (`crew.ts`), or the drift detector and override-only status badge disagree with the launch plan.
