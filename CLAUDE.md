# Garden

Garden is a CLI orchestrator for managing interactive Claude Code sessions across multiple projects via a tmux dashboard.

**Authoritative docs.** This file is a quick-start. Depth lives elsewhere — when something here disagrees with one of these, the spec wins:

- `DESIGN.md` — full architecture
- `rules.md` — coding rules loaded into every Claude session (commit/test/scope discipline)
- `WORKFLOWS.md` — workflow registry design, "how to add a new workflow", and trellis/grow workflow specs
- `docs/STATUS.md` — worker status state machine (spec)
- `docs/MULTI-MODEL.md` — multi-model / multi-harness architecture (Phases 1-3 shipped — provider layer, neutral core, harness adapter registry; Phase 4 in progress — Codex adapter shipped and reachable **as a reviewer** via per-role resolution (`config <p> role reviewer harness codex`) and **as a worker** via `workers new --harness codex`; a Codex worker's session-id capture and history/continue routing now ship — the remaining gaps are live-verifying `codex resume` and Codex-aware unsent-draft detection)
- `docs/TRACKS.md` — multi-track / promotion pipeline (design target, no code yet)
- `docs/` — additional design docs and behavioral specs; see `docs/README.md` for the index

## Build and run

```bash
npm install
npm run build          # esbuild → dist/cli.js + dist/hook.js
npm run dev -- help    # tsx during development
npm test               # vitest unit + integration; tsc --noEmit
```

`npm link` makes `garden` global. `dist/cli.js` is the symlink target — `npm run build` is all you need after edits. `package.json` sets `"sideEffects": false` so esbuild tree-shakes imported-but-unused modules (load-bearing for keeping `dist/hook.js` lean); modules must stay free of import-time side effects — only the entry points (`cli.ts`, `hook-entry.ts`) execute at top level. The build emits a second minimal bundle, `dist/hook.js` (from `src/hook-entry.ts`), that serves the per-tool-call Claude hook: it bundles only the hook dispatcher's import closure (~60% smaller than `cli.js`) so each fire's node cold-start is cheaper. Worker `settings.json` hook commands invoke it via `resolveHookRunner()` (`dashboard/runner.ts`), prefixed with a `NODE_COMPILE_CACHE=~/.cache/garden/node-compile` assignment (`hookCompileCachePrefix`) so each cold start reuses the bundle's cached V8 bytecode (~8% faster, measured; the dir is a sandbox-writable root shared fleet-wide, and node self-invalidates it on version/content change). The prefix is applied only on the claude-code path (`buildSettingsJson`), whose hook commands run through a shell — deliberately not folded into `resolveHookRunner()`, since the Codex adapter embeds that string in a TOML `command` value with different exec semantics. `cli.js` keeps its own `_claude-hook` route for workers whose settings predate it.

Best-effort + THIN (fs/path/crypto/config only, dir resolved lazily) so it is safe in the `dist/hook.js` closure `registry.ts` reaches; callers pass already-primitive payloads. Phase 1 (lifecycle): `worker.created` (full config snapshot + `rulesHash` + `gardenVersion`, from `workers.ts`), `state` (every real prState move, from `transitionState`), `merge` (terminal state + `mergeCount` + changed-file count, from `transitionToTerminal`). Phase 2 (review-cycle quality): `review.verdict` (verdict + duration + reviewer fix magnitude via `getDiffNumstat` over `preReviewSha..tipSha`, from `handleReviewing`), `resolve.outcome` / `cifix.outcome` (advisory verdict + ground-truth `verificationPassed` + `attempts` + duration, from `poller-resolve`/`poller-ci-fix`). Phase 3 (autonomy): `continue.dispatched` (garden-initiated pastes with `kind`, from `continueWorker` — operator prompts arrive via UserPromptSubmit and are NOT recorded, so operator work = all prompts − these), `operator.action` (hold/bounce from `workers.ts` shared cores, kick from `commands/kick.ts`). Phase 4 (cost): `worker.tokens` (cumulative transcript token usage at each merge, from `transitionToTerminal` via `sumTranscriptUsage` in `conversation.ts` — **dedupes by `message.id`** since Claude re-emits each message per stream update, else ~2.7x overcount; per-cycle cost = read-time diff of consecutive samples). Join key `workerId = project/name/createdAt`. Phase 5 (read surface): `readTelemetryEvents` (sole reader, scans all shards) + the `garden stats` command aggregating by config (config join built from the full `worker.created` history so `--since` windowing never orphans config; unjoinable pre-ledger workers bucket to `(unknown)`). Spec: DESIGN.md "Telemetry ledger"
  - `usage.ts` + `usage-poller.ts` — Claude quota meter (5h/week/model-scoped). **Two sources split by cadence** (mirrors Claude Code itself): the 5h + weekly bars come every poll from the `anthropic-ratelimit-unified-{5h,7d}-*` headers on a 1-token `/v1/messages` completion (`fetchUsageHeaders`→`parseUnifiedHeaders`; utilization is a 0..1 fraction, reset is epoch seconds) — the documented, generously-limited surface; the model-scoped bar (`fable`) + extra-usage credits come at most hourly from the throttled `/api/oauth/usage` endpoint (`fetchUsageRaw`→`normalizeUsage`, gated by `scopedFetchDue`). A scoped 429 is silent — the header bars stay live, the scoped bar keeps its last value. `assembleSnapshot` folds both fetch outcomes + prior into the snapshot: `dataAt` tracks primary-bar freshness (drives the stale tag), `scopedAt`/`scopedAttemptedAt` track the scoped bar's freshness + hourly cadence so it never trips the stale warning. This replaced polling the throttled endpoint for all three bars, which chained hour-long freezes when fleet activity pushed request volume past the endpoint's ~10-12/hr budget. `renderUsagePane` draws a second **Codex** meter in the empty space to the right when a Codex worker has reported usage: `codex-usage.ts` parses the `rate_limits` object Codex writes into its rollout JSONL each turn (primary/secondary rolling windows + credits — same shape as Anthropic's), captured at Stop-hook time (no new auth/endpoint/poller; the data is already on disk at `transcript_path`). Windows sort smaller-first (5h above 30d) to match Claude's ordering; a subscription account typically reports only the 30d (`window_minutes=43200`) window. Two-column layout is gated on Codex data existing, so an all-Claude fleet's pane is byte-unchanged.
  - `watchdog.ts` — liveness watchdog: recurring tick that recovers lost event delivery — re-pokes workers stranded in active states by a lost one-shot event, keeps each project's poller window healthy (respawns it if it died, collapses duplicates to one if a spawn race left several — resolving windows by index, since tmux name targets are ambiguous across duplicates), and alerts on orphaned worker windows (a live tmux worker window with no registry entry — the create/sweep race casualty; detection only, never reconstructs the entry). It also discounts machine-sleep/clock-jump time from live review/resolve/ci-fix timeouts (`absorbSleep`): the watchdog is the fleet's one fixed-cadence process, so a loop iteration that overran a full tick of slack measures suspend time — it shifts `reviewStartedAt` forward by the slippage on live-windowed workers so a laptop that slept mid-review doesn't wake to a spurious `REVIEW_TIMEOUT_MS` kill. It also re-bakes the status pane each tick (`refreshStatusElapsed`, `header.ts`) so the time-in-state suffixes advance — the sole recurring driver of the otherwise event-driven status pane, content-deduped so an idle fleet never repaints. On an hourly throttle it runs disk housekeeping (`housekeeping`): `truncateLog` enforces the 10MB `dashboard.log` cap on a recurring cadence (it was previously only called on fresh dashboard creation, so a long-lived session's log grew unbounded between restarts), and `sweepBootstrapScripts` deletes spent `bootstrap-<project>-<branch>.sh` scripts older than 6h from `SESSIONS_DIR` (each worker launch writes one, the pane consumes it within seconds and never touches it again, but nothing removed them — one orphan accrued per worker ever created). Transitions nothing (delivery-time and disk bookkeeping only).
  - `conversation.ts` — transcript parser feeding the per-worker history view (`⌥h`): tail-reads the worker's Claude transcript JSONL into turns (operator prompts + verb-tagged assistant summaries) and formats the pane; transcript path captured from the hook input (`WorkerEntry.transcriptPath`) or derived from worktree cwd + session id. Keeps the view a summary, not a raw dump: system-injected user-role messages (background-task `<task-notification>`s, slash-command echoes — detected via the transcript's `promptSource` field, wrapper-tag denylist for legacy transcripts) are skipped so surrounding agent activity folds into one summary; garden's own `[garden]` continuation prompts collapse to a compact dim `garden · <kind>` marker (`gardenLabel`) with the response kept visible. Operator prompts are shown uncapped. (The view is "history"; the module parses the underlying conversation transcript.)
  - `sandbox.ts`, `credentials.ts`, `claude-env.ts` — Claude profile / Keychain / sandbox config
  - `alerts.ts`, `log.ts`, `git.ts`, `names.ts`, `runner.ts`, `plot-status.ts` — utilities

## CLI surface

Run `garden help` for the full command list with arguments (`garden <cmd> --help` prints the same — there are no per-command flag pages). High-level groupings:

- **Projects**: `add` / `create` / `remove` / `config` (keys: `baseBranch`, `checks`, `postMerge`, `sandboxDomains`, `claudeProfile`, `provider`, `harness`, `logColor`, `requireCiSuccess`, `holisticReview`). `baseBranch` is the authoritative merge target for new workers (`resolveSpawnBase`: `--base` > `baseBranch` > checkout); unset keeps the legacy checkout-follows behavior. `register`/`unregister` aliased. **Per-role review selection** via the `config <p> role [<role> [harness|model] [value]]` subcommand (roles: reviewer/resolver/ci-fix) — `resolveReviewRole` (`roles.ts`) independently resolves each role's `{harness, model, env}`, defaulting to strong first-party Anthropic Opus, overridable to e.g. `role reviewer harness codex`. Review-family provider is deliberately not a knob (a provider only defeats the safety net); the worker keeps the flat `provider` key. The `harness` key is the worker default (axis 2, the `provider` analog for axis 1); absent = claude-code, `workers new --harness` overrides per worker.
- **Crews**: `config <p> crew [<name>]` (`src/dashboard/crew.ts`) — sugar that sets the worker harness/provider *and* the review-role harnesses together, so composing a fleet is one word. A crew is a pair of **members** named `<worker>-<reviewer>` (with `all-X` sugar): a member is *data* — the registered harnesses (`claude`, `codex`) plus one per configured provider (`deepseek` → claude-code against that backend), so a new provider/harness expands the crew set with no crew code. The load-bearing asymmetry: any member may build, but only harness members review (a provider on review defeats the safety net) — hence `deepseek-claude`/`deepseek-codex` exist but no `*-deepseek`. `deriveCrew` reports a project's current crew (null when hand-tuned); `applyCrew` is authoritative over the worker harness/provider + the three review harnesses. Dashboard surface: the **`⌥⇧C` crew picker** (`crew-picker.ts` — its own key, not the per-spawn `⌥⇧N` workflow picker, since a crew reconfigures the whole project) applies a crew to the focused project, and a quiet grey crew badge rides each project header in the status pane (`formatCrewBadge`, `commands/status.ts`; hidden for the default `all-claude` crew — identity default is invisible). Spec + verified findings: `docs/future/CREWS.md`.
- **Plots**: `plot` (alias `p`) — named ordered subsets of projects (max 9). `⌥1–⌥9` index into the active plot, `⌥p` cycles focused plots. `focus` / `unfocus` / `reorder` toggle and order ⌥p inclusion. Storage: `~/.garden/config.yml`.
- **Diary**: `diary [project] [--path]` — per-project diary (free-form operator notes) opened in `$EDITOR`; `--path` prints the file path. Storage: `~/.garden/diary/<project>.md` — operator-private, outside any repo, invisible to workers and reviewers. In the dashboard, `⌥d` opens the focused project's diary in the garden pane, and switching projects (`⌥1–9` / `⌥p`) reloads it on the newly-focused project — driving nano's save+exit (`^O Enter ^X`) first so unsaved notes survive (`reloadDiaryEditor` in `navigate.ts`; nano/pico-only, since a custom `$EDITOR`'s save keys can't be driven blindly). This reloads whether the diary is the active garden pane *or* parked in the hidden `_garden-diary` window (the operator switched the garden pane to another view): re-entering the diary view does not restart the editor, so a parked editor would otherwise show whatever project was focused when it parked. nano/pico are launched with `-b` (word wrap) so long lines wrap to the pane width; detection is `editorIsNano` (`src/diary.ts`). (`src/diary.ts`, `src/commands/diary.ts`).
- **Claude profiles**: `claude-profile add|login|list|remove`. Per-project `claudeProfile` config injects `CLAUDE_CONFIG_DIR` for that project's worker / reviewer / resolver. macOS Keychain footgun: every Claude `/login` overwrites one shared entry, so always re-auth via `garden login` (it strips `CLAUDE_CONFIG_DIR` and captures Keychain → file for profiles).
- **Providers**: `provider add|list|remove` — Anthropic-Messages-compatible backends (DeepSeek `/anthropic`, local Ollama, gateways) that a project's WORKERS reach via env swap (`ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN="$<tokenEnv>"`, model aliases via `ANTHROPIC_DEFAULT_*_MODEL`). Set per project with `garden config <project> provider <name>`; applies to new/bounced workers. The key travels via the tmux *session env* (the server env is frozen at start): operator-shell commands sync it with `set-environment`, `workers new` refuses to spawn without it, and `garden auth status` reports shell + session presence (syncing as it reads). Reviewer/resolver/ci-fix never use the provider — `reviewerEnvPrefix` empties inherited `ANTHROPIC_*` env and all three default to Opus on the claude-code path (every project, not just provider-backed), each overridable per role via the `role` config surface. Provider-only fleets switch the usage meter/poller/`garden usage` off with an explanatory line. API keys are env-var references — no login flow. Spec: `docs/MULTI-MODEL.md`.
- **Auth**: `login [profile]`, `auth status` (presence/expiry/Keychain displacement diagnostic; provider rows report token env-var presence in shell + dashboard session, syncing as they read).
- **Operator inspection**: `queue [project]` (`src/commands/queue.ts`) shows the merge pipeline — merge-pending workers numbered by serial merge order (earliest `mergePendingAt` merges next), then in-review/resolving/ci-fixing, then blocked, with CI markers (`CI fix N/3`, `CI ✗ <sha>`) from persisted prState/`failingReason`. `alerts` (`src/commands/alerts.ts`) splits unread (added since the last `⌥l` ack — `lastSeenAt`) from read, with level glyphs (`✖`/`⚠`) and relative age. `stats` (`src/commands/stats.ts`) aggregates the telemetry ledger into a per-config comparison — quality (clean-review rate, reviewer fix magnitude, fail rate, review duration), cost (output tokens per merge), autonomy (interventions per merge); `--by config|model|provider|harness|workflow|crew|rules|version`, `--since Nd|Nh|Nm`, `-p <project>`; JSON when piped, table in a TTY. `doctor` (`src/commands/doctor.ts`) is an environment preflight (tmux/claude required, gh optional + auth, node, and the unverifiable Option-as-Meta terminal setting).
- **Workers**: `whoami`, `review`, `kick`, `bounce`, `hold`, `pause`, `resume`, `health [--fix]`, `logs [-w <worker>]`, `checks [project]` (run the project's checks command under the machine-wide checks semaphore — see `src/checks-semaphore.ts`). The five worker-targeting commands (`kick`/`bounce`/`hold`/`pause`/`resume`) resolve their `<worker>` argument through the shared `resolveWorkerArg` (`src/commands/resolve-worker.ts`): exact name → unique case-insensitive prefix → unique substring, plus `.` for the dashboard's focused worker — so `garden kick blea` finds `bleak-hoar-glow`. `review [worker]` (also via `resolveWorkerArg`, default `.`) prints a worker's last review — the verdict, the review-window diff (`git diff --stat preReviewSha..tipSha`, the reviewer's edits plus any base advancement if it rebased mid-review), and the review body — read from the durable `entry.lastReview` snapshot (`LastReviewData`, `registry.ts`) that `handleReviewing` writes at verdict dispatch and the merge/failing resets deliberately preserve (unlike the transient `lastReviewBody`/`preReviewSha`). Ambiguous or unknown names error with the candidates listed. `hold <worker>` (dashboard `⌥e` on the focused worker; the CLI form is for scripting) interrupts a working worker (sends Escape) and marks it `paused` — the operator-visible "I stopped this on purpose" state, since no Claude Code hook fires on a raw Escape. The next prompt clears it (`⌥e` also toggles it back to `idle`). Distinct from `pause`/`resume`, which toggle the post-merge auto-continue sentinel. Workers can self-identify via `$GARDEN_WORKER` / `$GARDEN_BRANCH` / `$GARDEN_BASE_BRANCH` / `$GARDEN_PROJECT`. `workers new <project> [--model <alias-or-id>]` pins any workflow's worker model (opaque string — an Anthropic alias resolved through the provider's modelMap on provider-backed projects, or a concrete model id; persisted to `WorkerEntry.model` for default/grow, `trellis.workerModel` for vines). `workers new <project> --base <branch>` (any workflow) overrides the merge base for that one worker, ahead of the project `baseBranch` and checkout (`resolveSpawnBase`); validated/published through the same origin-existence + auto-publish chain, pinned to `entry.baseBranch`. `workers new <project> --crew <name>` (default workflow only, mutually exclusive with `--harness`, rejects a provider-backed worker member) sets a per-worker crew: its build half folds into `entry.harness` at spawn, its review half is stamped on `entry.crew` and applied **live** by `resolveReviewRole` (which layers the crew's review harness ahead of `project.roles`) — so a worker's reviewer/resolver/ci-fix harness can be changed after spawn and takes effect on the next review. `workers new <project> --harness codex` (default workflow only) spawns a **Codex worker** instead of Claude Code: its own `workspace-write` sandbox (network on, writable roots incl. the shared git common dir — a linked worktree's git store), the lifecycle hook relay injected via `-c` on the launch (Codex loads project hooks from the repo root, not the worktree, so no `.codex/hooks.json` file), rules delivered as the worktree `AGENTS.md`, and directory-trust pre-seeded for the repo root in `CODEX_HOME/config.toml`. Persisted to `entry.harness`; the additive bootstrap keeps the claude path byte-identical (`_install-worker-runtime` runs the codex config after worktree setup). Spec + verified findings: `docs/future/CREWS.md`. Session-id capture, multi-phase auto-continue, and the `⌥h` history view now work for a Codex worker; remaining gaps: live-verifying `codex resume` and Codex-aware unsent-draft detection.
- **Trellis**: `trellis list|show|new|status|amend|resume|retire|revive`; plant via `workers new <project> --workflow trellis --trellis <name> [--model <alias-or-id>]` or the `⌥⇧N` workflow picker (`(t)` row). Spec: `WORKFLOWS.md` § "Trellis workflow".
- **Grow**: bounded hardening loop with no design doc; plant via `workers new <project> --workflow grow --seed <text>|--seed-file <path> [--max-iterations N]` or the `⌥⇧N` workflow picker (`(g)` row, prompts for a single-line seed; the CLI is required for multi-line / metacharacter-bearing seeds). Convert an active default worker into grow with `workers grow [<worker>] --seed/--seed-file/--goal-file <…>` (self-resolves via `$GARDEN_WORKER`). The durable goal lives at `<worktree>/.garden/grow-goal.md` and is operator-editable mid-loop — every iteration re-reads it at dispatch time. Default budget 5 (overridable per-project via `maxGrowIterations` config or per-plant via `--max-iterations`). Runs on the account-default model unless `--model` pins one.
- **Auto-continue gate**: `auto [on|off|status|threshold N|resume-on-reset on|off]` — global gate in `~/.garden/config.yml` under `autoContinue`. Usage-triggered closures are per-project: a project on a third-party `provider` or a non-default `claudeProfile` runs on a token pool the default account's meters don't describe, so `autoContinueGateReason(projectName)` exempts it (`projectUsageGateExempt`, `src/config.ts`); an explicit `garden auto off` still blocks every project.

## Workers (worktrees)

Every worker runs in its own git worktree at `~/.garden/worktrees/<project>/<worker>/`, on a branch named after the worker, branched from `origin/<base>` (fetched first). Each project has a dedicated **poller** in a hidden tmux window that drives review/merge using local git — no GitHub PRs. Reviewers and resolvers run headless in hidden `_<project>-review-<worker>` / `_<project>-resolve-<worker>` windows. Multiple reviews run in parallel within a project; the merge queue is serial. Full state machine: `docs/STATUS.md`.

Per-phase review sees only one delta against base, so when a multi-phase **default** worker reaches `done` having merged `>= 2` times, the poller can spawn one `holistic-review` worker to review the whole-task cumulative diff for cross-phase coherence defects. Gated per-project by `holisticReview: off|shadow|fix` (default `off`; `shadow` reports findings, `fix` fixes through the normal review/CI/merge gate with a deliberate-decision reviewer interlock). Spec: `WORKFLOWS.md` § "Holistic-review workflow"; `garden dashboard _holistic-backtest` replays it read-only against a past worker.

Worker prompt is `rules.md` (global) + `<project>/.garden/rules.md` (project) + per-worker preamble built by `buildWorktreeRules` in `src/rules.ts`. The preamble names the project's configured `checks` command (from `garden config <project> checks`) so the worker, the reviewer, and CI all gate on the same string — keep that command aligned with `.github/workflows/test.yml` or you reintroduce the asymmetry that caused workers to push broken state and CI to email "Run failed" on every commit. Workers and reviewers run it via `garden checks`, which executes exactly that string under the machine-wide checks semaphore (see DESIGN.md "Project Configuration" → checks) so overlapping suites queue instead of stampeding the workstation; CI runs the raw command ungated on its own runner. Worker panes start in `permissions.defaultMode: "auto"` inside an OS sandbox (Seatbelt/bubblewrap) configured by `sandbox.ts`. Workers commit and push autonomously — no operator confirmation; the poller handles review and merge.

## Dashboard internals

Permanent tmux layout — content is moved between visible slots and **hidden underscore-prefixed windows** (`_<project>-worker-N`, `_<project>-shell`, `_<project>-poller`, `_garden-{growhouse,root,logs,history,diary}`, `_garden-usage-poller`, `_garden-watchdog`) via `tmux swap-pane`. Pane slots are never destroyed.

- **Left column**: `garden` title pane (Claude quota meters), `status` pane (per-project worker list), and `growhouse` pane (cycles `⌥g` growhouse / `⌥r` root / `⌥l` logs / `⌥h` history / `⌥d` diary). Title and status panes refresh via SIGUSR1, replaying pre-baked files written atomically. Each project header row in the status pane carries a dimmed pencil `✎` when its diary holds non-whitespace content (`diaryHasContent` in `src/diary.ts`, stat-cached on mtime+size to stay off the refresh hot path; `formatDiaryGlyph` in `src/commands/status.ts`). Worker rows are ordered by attention/recency, not name — `compareWorkerFreshness` (`registry.ts`) sorts by tier (blocked-on-you → new/`ready` → active → in-flight → `done`; the bands descend a worker's life toward merge, so `reviewing`/`merging` sit below `working`, above `done`), then freshness (`workerSortFreshness` = `lastStateChangeAt ?? lastEventAt ?? createdAt`, 60s-bucketed to avoid jitter), then name; the same comparator drives the `⌥]`/`⌥[` cycle and `whoami` siblings. Ordering keys on `lastStateChangeAt` (the last real `agentStatus`/`prState` transition, stamped by `applyAndLog` on an `agentStatus` change and by `transitionState` on a `prState` change — never on the 10s heartbeat), NOT the raw `lastEventAt`: the 10s hook heartbeat bumps `lastEventAt` without repainting the status pane, so ordering by it let rows drift silently and snap on the next navigation-triggered repaint. `lastEventAt`/`workerFreshness` still drive the 24h stale-dim (`isWorkerStale`) — that wants heartbeat liveness. Active-band rows untouched >24h (`isWorkerStale`) render faint via `dimRow` — except the operator-held `paused`, which keeps its bold-cyan mark. In-flight/blocked rows (`reviewing`/`merge-pending`/`resolving`/`ci-fixing`/`asking`/`failing`) fold a dim time-in-state elapsed into the state cell (`reviewing 12m`, `asking 2h`) computed from `lastStateChangeAt` by `formatTimeInState` (`src/commands/status.ts`), yellow past a soft per-state expectation (the otherwise-uncolored pipeline states only; `asking`/`failing` stay dim since their row is already colored). It rides the same pre-baked-file path, so the watchdog's 60s tick re-bakes it via `refreshStatusElapsed` (`header.ts`) — the one recurring driver of the otherwise event-driven status pane — content-deduped so an idle fleet never repaints. The row grammar splits identity from status (`collectSegments`/`renderWorkerRow`, one path for CLI + baked): grey override-only identity badges (base `→ <base>`, member/harness, model, workflow via `workflowRowDecor` — grow shows `grow N/M`, a vine its `[trellis: …]` bracket) in a width-aligned column, status-class flags (CI bracket, `gate closed`) that never truncate, and a yellow per-project `⚠n` unread-alert count on each header (`unreadAlertCountsByProject`, cleared globally on `⌥l`). See DESIGN.md "Worker row grammar" + "Worker row ordering". The `⌥h` history view shows the focused worker's prompt history (operator prompts + brief verb-tagged assistant summaries), read from the worker's Claude transcript JSONL by `conversation.ts` and painted via the same pre-baked-file + SIGUSR1 path; `writeHistoryRendered` (`header.ts`) only parses the transcript when history is the active garden mode, keeping it off the hook firehose.
- **Right-pane clock**: the right pane (worker or project shell) shows a `%H:%M` clock in the right corner of its top border (mirroring the `garden` title in the top-left). The shared `pane-border-format` carries a right-aligned, bold-green segment (matching the `garden` title, capped with border dashes to the corner) gated on the `@garden_clock` pane var, set on worker panes and the right-pane shell (not the left-column garden shells); tmux strftime-expands it on each `status-interval` tick — no extra process or poll. Keep the style comma-free (`#[fg=green]#[bold]`) — a comma in the `#{?…}` conditional blanks the clock.
- **Project color dot**: the right pane's top border prefixes the worker/shell label with a `●` in the project's `logColor` (palette of 256-color indices in `src/log-palette.ts`; `logColorAnsi` / `logColorTmux` derive the ANSI and tmux renderings) — the border names the worker, never the project, so the dot is the pane's only project marker. Gated on the `@garden_color` pane var (`colour<N>`), set by `setPaneProjectColor` (`header.ts`) everywhere `@garden_clock` is applied; the format nests `#{@garden_color}` inside `#[fg=…]`, which tmux expands before parsing the style. Deliberately not echoed in the status pane or bottom bar — those already name the project in text.
- **Logs sticky filter**: `⌥/` opens `tmux command-prompt` (pre-filled with the current filter); `⌥.` clears it instantly. The typed expression persists in `~/.garden/sessions/logs.filter.json` and is honored by both the dashboard logs pane and bare `garden logs` until cleared. Syntax: `key:value` for `worker`/`src`/`level`/`project` plus bare fuzzy tokens. CLI escape hatch for metacharacter-bearing exprs: `garden logs filter <expr>` / `--clear`.
- **State of record**: registry (`dashboard.registry.json`) for workers, state file (`dashboard.state.json`) for UI runtime, alerts file for operator-visible issues. Tmux is the source of truth for pane existence; `validate.ts` reconciles on attach.
- **Status**: hooks write `agentStatus`, the poller writes `prState`, `pane-died` writes `agentStatus="exited"`, and the operator `hold` action (`⌥e` / `garden hold`) writes `agentStatus="paused"` (a raw Escape interrupt fires no hook). Event-driven; the only recurring tick is the liveness watchdog (`watchdog.ts`, `_garden-watchdog` window), which re-pokes projects whose workers sit in active states past a 5 min staleness threshold, keeps each project's poller window healthy (respawning a dead one, collapsing duplicates a spawn race left), and alerts on orphaned worker windows (a live tmux worker window with no registry entry) — it recovers lost event delivery or surfaces a casualty and never transitions state. Spec: `docs/STATUS.md`.
- **Auto-continue**: `continue.ts` re-prompts after interrupt (mid-turn dashboard kill / tmux crash / bounce-while-working) and after a clean merge (with the list of files changed during review). Worker opts out by writing `.garden-done` in its worktree root before ending its turn. `garden pause` / `resume` toggle the sentinel; `UserPromptSubmit` clears it. A worker whose continue prompt was blocked (global gate closed, or paste lost) parks in `merged`; the merged-state handler (`handleMerged`, `poller-merge.ts`) replays the auto-continue decision on every poke — the gate-reopen sweep — so the prompt lands on the first poke after the gate reopens. A gate-closed strand is surfaced three ways: the status pane appends a yellow `gate closed` suffix to the `merged` row (`formatGateSuffix`, `status.ts`), `garden whoami` prints the gate state (`auto-cont.` line, on/OFF + pause reason), and the sweep's gate-block logs at info once per worker per hour (an in-memory throttle in `maybeAutoContinue`, not per-poke debug). The gate's usage-triggered closures are per-project (see the auto-continue gate bullet under CLI surface): usage-exempt projects auto-continue through them, so their rows never show the suffix and their `whoami` line reads `on` with a separate-token-pool note — only an explicit `garden auto off` closes the gate for everyone. Before pasting, `continueWorker` also defers when the operator has an unsent draft in the worker's Claude input box (`capturePaneText` + `capturePaneCursor` + `extractOperatorDraft`) so an auto-continue can't be concatenated onto a half-typed message. The draft is the span between the `❯` prompt marker and the cursor column — Claude Code paints dimmed ghost/placeholder text into an *empty* box and `capture-pane` strips the dimming, so the marker-to-cursor bound (not the bare post-marker remainder) is what tells a real draft from a suggestion. The two primary dispatch legs re-arm a bounded 12s backoff (`rearmContinueIfDrafting`, `--attempt N`, capped at 15) until the box clears.
- **Post-merge**: advance the local base to the merged tip — `merge --ff-only` when it's the checked-out branch (also moves the working tree, so `postMerge` runs), else `git fetch origin <base>:<base>` to advance the ref alone (the many-base workflow: checkout parked elsewhere, ff-enforced + worktree-aware, postMerge skipped, silent). Then notify live siblings whose files overlap. A clean advance never alerts, and a redundant local commit whose clean tree already matches origin is auto-healed silently (`reset --hard origin/<base>`, reflog-preserved). Of the rest, `diverged`/`checked-out-elsewhere`/`dirty` warn (the operator's own checkout state, merge already on origin) and `stuck` — fetch failure or a wedged checkout — errors. The base checkout is the operator's shared working directory, not a pristine mirror, so all four are expected; each alert fires only on *entry* into the state, not every merge cycle (a diverged/dirty checkout would otherwise re-alert on every sibling merge). See `fastForwardBase` (`git.ts`) and `notifyPostMerge` (`poller-merge.ts`).
- **CI gate**: before each merge, `handleMergePending` queries `gh api repos/<owner>/<repo>/commits/<sha>/check-runs` (see `src/dashboard/poller-ci.ts`). Pending defers the merge (60 s recheck); failure dispatches a self-healing ci-fix agent (see `src/dashboard/poller-ci-fix.ts`, `_<project>-ci-fix-<worker>` hidden tmux window, budget 3 attempts per merge cycle). The agent reads `gh run view --log-failed` output, makes the minimum fix, and pushes — the gate then re-runs against the new SHA. Launch and success are routine lifecycle beats — logged (visible in `garden logs`) but not raised as operator alerts; only budget exhaustion alerts (error level), parking in `failing` with `failingReason: "ci"` for a genuinely red CI, or the kick-recoverable `failingReason: "transient-review"` when the agent only hit transient backend outages. The gate passes through on projects without a GitHub remote, without `gh` installed, with `requireCiSuccess: false`, or with zero check-runs on a project never observed to run CI; on a project already known to run CI, zero check-runs on a freshly force-pushed SHA are treated as not-yet-materialized and the merge defers within a bounded grace window (3 min) before passing through. This is defense-in-depth against GitHub's branch protection — the poller's force-push path bypasses the merge UI, so branch protection alone can't catch a red CI.

## Conventions

- **JSON when piped, pretty in TTY** — use `output()` / `outputLines()` from `src/output.ts` for all data output.
- **Project resolution** — use `resolveProject()` / `resolveProjectFromArgs()`. Never parse names manually. Auto-detected from cwd inside a registered project.
- **Bash escaping** — every value interpolated into a generated shell command goes through `shellEscape` (`src/dashboard/tmux.ts`). It returns a fully single-quoted bash literal — use the result without surrounding `'...'`. No inline `.replace(/'/g, "'\\''")`.
- **Atomic writes** — every persisted state file goes through `atomicWriteFile` (`src/dashboard/atomic-write.ts`). Readers pair this with an `is{ShapeName}` type guard before trusting parsed JSON. See `readDashState` / `readRegistry` / `readAlerts`.
- **Dashboard windows** — every window created in `DASHBOARD_SESSION` goes through `newDashboardWindow` (void) / `newDashboardWindowPaned` (returns the pane id) in `src/dashboard/tmux.ts`, which suppress the window name at creation. There is no global `window-status-format` default, so a raw `tmux("new-window", …)` leaks the window name into the status-bar center strip (`setupStatusBar` only blanks the `main` window).
- **Alert dedup** — `addAlert` (`src/dashboard/alerts.ts`) suppresses identical-key alerts within a 1-hour window. Default key is `${level}:${source}:${project}:${worker}:${message[:200]}`. When a message embeds time-varying detail (SHA, error string, file list), pass an explicit stable `dedupKey`.
- **Specs** — files containing the marker phrase **"the code is wrong"** in their opening paragraph are specs. The reviewer prompt-prepends a strong warning never to edit a spec to match the code. If the code disagrees, fix the code.
- **Tests** — `npm test` runs unit + integration (`test/integration/**`); the bundled-hook test catches module-init cycles vitest's source resolver misses. Don't move integration tests behind a flag.

## Adding a new command

1. `src/commands/<name>.ts` — export an async `(args: string[]) => Promise<void>`
2. Register in `src/commands/index.ts`
3. Add to the help text in `src/cli.ts`
4. Use `output()` and `resolveProject*()` per Conventions

## Adding a new workflow

See `WORKFLOWS.md`. Short version: define a `WorkflowDefinition` in `src/dashboard/workflows/<name>.ts`, register in `workflows/index.ts`, reuse `default.ts`'s state handlers and `defaultHookHandlers` wherever possible. Tests: `test/workflows.test.ts` + an integration test on real fs/git. Two concrete examples in the registry: `trellis.ts` (full-spec divergence — own reviewer prompt, verdict vocab, model pinning, post-merge dispatch) and `grow.ts` (minimal divergence — reuses default's reviewer/verdicts/hooks; only the iteration counter and post-merge dispatch differ). If your workflow shares the cold-respawn-per-iteration mechanics, supply a `LoopHooks` instance (see `src/dashboard/loop.ts`) instead of forking the dance.

**Per-workflow runtime data** (the trellis pattern). Anything the workflow accumulates per worker goes under an optional sub-object on `WorkerEntry`, not as flat fields — `entry.trellis?: TrellisData` and `entry.grow?: GrowData` are the two concrete examples (`registry.ts`). `updateWorkerFields({ <subObject>: { <field>: ... } })` deep-merges that sub-object so callers don't clobber sibling fields. Add a legacy-shape migration to `readRegistry` so on-disk entries from earlier shapes get rebuilt at next read. Don't add flat per-workflow fields to `WorkerEntry`; the flat-fields path was deliberately removed (the migration in `readRegistry` exists to scrub stragglers from old on-disk entries).

## Adding a new harness

See `docs/MULTI-MODEL.md` "Layer 3". Short version: implement `HarnessCore` in `src/dashboard/harness/<name>-core.ts` (command dialects, prompt delivery, transcript reader, transient-error shapes — keep its import closure light; it is reachable from `dist/hook.js`), add `installRuntimeConfig` in `harness/<name>.ts`, and register in both `harness/core.ts` and `harness/index.ts`. A harness without a turn-end signal cannot be registered — `capabilities.turnEnd` is typed `true` because STATUS.md's no-polling invariant is preserved by refusing such harnesses, not polling around them. The event side: translate the harness's native lifecycle onto the normalized `WorkflowHookHandlers` methods (`onTurnEnded` etc.) — for claude-code that translation is `hook-dispatcher.ts`'s wire-name switch.

## Keeping docs current

If your task changes commands, architecture, file layout, or conventions, update `DESIGN.md` and this file. Specs (`docs/STATUS.md`, WORKFLOWS.md § "Trellis workflow", WORKFLOWS.md § "Grow workflow", `docs/TRACKS.md`) are design targets — fix the code to match, not the spec.
