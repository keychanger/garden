# Garden

Garden is a CLI orchestrator for managing Claude Code sessions across multiple projects. Read DESIGN.md for the full architecture.

## Build and run

```bash
npm install
npm run build          # esbuild -> dist/cli.js
npm run dev -- help    # run via tsx during development
```

`npm link` makes `garden` available globally. The symlink points to `dist/cli.js`, so `npm run build` is all you need after changes.

## Source layout

- `src/cli.ts` — entry point, command dispatch, aliases, help text
- `src/commands/` — one file per command, registered in `index.ts`
- `src/worker.ts` — task loop running inside tmux (internal `_worker` command)
- `src/config.ts` — reads/writes `~/.garden/config.yml`, project resolution
- `src/tasks.ts` — CRUD for `.garden/tasks.json`
- `src/session.ts` — tmux operations, state files, SIGUSR1 signaling
- `src/events.ts` — append-only event log
- `src/output.ts` — TTY detection for JSON vs pretty output
- `src/notify.ts` — macOS notifications via osascript

## Adding a new command

1. Create `src/commands/<name>.ts` exporting an async function that takes `args: string[]`
2. Register it in `src/commands/index.ts`
3. Add it to the help text in `src/cli.ts`
4. Use `output()` / `outputLines()` from `src/output.ts` for data output
5. Use `resolveProject()` or `resolveProjectFromArgs()` for project resolution
6. Emit events via `emit()` from `src/events.ts` for any state changes

## Conventions

- All read commands: JSON when piped, pretty in TTY. Use `src/output.ts`.
- Task IDs are 4-char random hex. Generated by `tasks.ts`.
- Event log is append-only JSONL. Never delete or rewrite entries.
- Worker is an internal command (`garden _worker`), not user-facing.
- tmux sessions are named `garden-<project>` (workers) and `garden-dashboard` (dashboard).
- `garden stop --all` skips non-project sessions (dashboard is protected).
- `GARDEN_PROJECT` env var scopes commands inside sessions.
- Project name is auto-detected from cwd when inside a registered project.
- Top-level shortcuts (`add`, `done`, `block`, `backlog`) rewrite to `tasks` subcommands in `cli.ts`.

## Task lifecycle

`backlog` -> `pending` -> `in_progress` -> `done` | `blocked` | `failed`

The worker sets tasks to `in_progress`. Claude calls `garden tasks done <id>` or `garden tasks block <id>`. The worker checks status after Claude exits and emits the appropriate event.

On `garden stop`, `in_progress` tasks reset to `pending`. On `garden start`, `in_progress` tasks are picked up before `pending` ones.

## Rules system

The worker injects a system prompt built from:
1. Core garden instructions (task commands, agent behavior)
2. Global rules (`~/.garden/rules.md`)
3. Project rules (`<project>/.garden/rules.md`)
4. Task notes

Rules are plain markdown. They control commit behavior, testing requirements, PR workflow, and scope discipline.

## Git workflow

Feature branches, PRs, no direct commits to main. After opening a PR, create a review task so a separate session reviews the work. See `rules.md` for full details.

## Keeping docs current

If your task changes commands, architecture, file layout, or conventions, update DESIGN.md and CLAUDE.md as part of the task. Docs that disagree with code are worse than no docs.
