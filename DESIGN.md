# Garden

A minimal CLI orchestrator for managing Claude Code sessions across multiple projects.

Garden is a personal tool — opinionated toward a single developer managing many projects from one place. It is not a team tool, not a CI system, and not a framework. It's a thin, extensible layer over Claude Code.

## Core Concepts

### Project
A named reference to a directory on disk where Claude Code can operate. Projects are added with `garden add [path]` (name is derived from the directory basename).

### Dashboard
A tmux session (`garden-dashboard`) that serves as the primary interface. The dashboard is a left/right split: garden title and usage meters (top), project status (middle), and a growhouse pane (bottom) on the left; an active pane (worker or shell) on the right with a header bar. The growhouse pane cycles between six views: the growhouse (`⌥g`) with a bold green `garden>` prompt and auto-dispatch for garden commands, the root shell (`⌥r`) for general-purpose terminal use, a logs view (`⌥l`), a history view (`⌥h`) showing the focused worker's prompt history, a diary view (`⌥d`) editing the focused project's diary in `$EDITOR`, and an alerts view (`⌥a`). The same swap-pane mechanism as the right pane is used. You never interact with tmux directly — garden sets up the layout, keybindings, and pane management.

### Workers
Interactive Claude Code sessions running inside the dashboard. Each project can have multiple workers (e.g., one for a feature, one for a review). Workers persist when you switch between projects — they're parked in hidden tmux windows and swapped back in when you return.

### Workflows
A **workflow** is a `WorkflowDefinition` (state machine + state handlers + hook handlers) that drives a worker's lifecycle. Each worker has a `workflow` field on its registry entry; the poller dispatcher and the Claude Code hook dispatcher route through `getWorkflow(name)` rather than hard-coded switches. The `default` workflow reproduces the standard "review and merge" pipeline. Alternate workflows are introduced as data, not as forks of the dispatcher. Architectural rationale: `WORKFLOWS.md`. Author guide: `AGENTS.md` § "Adding a new workflow".

A `WorkflowDefinition` can also set `skipsReviewMerge: true` (the **botanist** design workflow): once its branch has commits ahead of base, the shared `handleWorking` routes it `working → merge-pending` directly, never launching a reviewer — its deliverable is a design document the operator already reviewed at the human gate, not code to critique. Before the transition it enforces that the committed diff touches only the publishable `docs/` boundary (`isPublishablePath`); a botanist that committed code parks in `failing` with `failingReason: "botanist-scope"` and an operator alert, and re-publishes automatically once the non-doc files are removed and re-pushed. The CI/merge gate still applies. See `src/dashboard/poller-review.ts` `handleSkipReviewMerge` and the `garden botanist publish` command.

### Rules System
Claude sessions are configured with layered rules files injected via `--append-system-prompt-file`:

1. **Global rules** (`<garden-repo>/rules.md`) — methodology, testing, git workflow. Lives in the garden repo itself (version-controlled). Resolved at runtime relative to `dist/cli.js` (or `src/rules.ts` in dev). Override via `GARDEN_RULES_PATH` env var.
2. **Project rules** (`<project>/.garden/rules.md`) — project-specific conventions

Rules are plain markdown. Edit them directly.

On the Codex path there is no `--append-system-prompt-file`, so the same composed
text is written into the worktree `AGENTS.md` instead (`installCodexAgentsMd`).
The format is owned by `src/dashboard/harness/agents-md.ts`, a string-only leaf:
garden's rules under `AGENTS_MARKER`, a `---`, then any `AGENTS.md` the repo
itself tracks. The file is git-excluded when untracked and marked
`skip-worktree` when tracked, so it never reaches a commit. `stripGardenRules`
is the inverse, and every reader of a worktree `AGENTS.md`-as-documentation must
apply it — `readDocSections` does, or a Codex worker's reviewer prompt would
carry the worker rules twice.

### Agent instruction files

A project's instructions live in **one** file. Claude Code reads `CLAUDE.md` and
never `AGENTS.md`; Codex reads `AGENTS.md` and never `CLAUDE.md`. A fleet that
runs both harnesses against the same repo — which this one does — therefore
needs `AGENTS.md` as the real file and `CLAUDE.md` as a pointer at it: a single
`@AGENTS.md` import line, or a symlink. Two independently-maintained files is
the failure mode, and it is silent — each harness works from a different set of
instructions and nothing reports the divergence.

Garden enforces this at two levels:

- **`rules.md`** carries the convention, so every worker maintains the pairing
  as part of ordinary doc upkeep.
- **`garden doctor`** reports it fleet-wide. `classifyAgentDocs`
  (`src/commands/doctor.ts`) classifies each registered project's checkout as
  `paired`, `unlinked` (both files exist independently), `claude-only`,
  `codex-only`, or `none`, and the check names the fix for each non-paired
  state. `none` is not reported — a repo with no agent instructions has nothing
  to unify, and doctor does not nag for docs a project never kept.

Prefer the import over the symlink: it leaves room for a Claude-only section
below it, it avoids interacting with garden's atomic rewrite of a Codex
worktree's `AGENTS.md`, and it needs no Administrator privileges on Windows.

### Panes

The title/usage and project-status panes are passive: keyboard input, mouse selection, and wheel scrolling are disabled. The growhouse slot and right pane retain normal interaction.

- **Garden title + Usage Meters** (top-left) — Dedicated pane with a bold green `garden` title label on the pane border and two or more Claude quota bars inside (5-hour rolling window, weekly total, and one bar per model-scoped weekly meter — `fable` on current plans). Height auto-sizes to the rendered content — the two flat bars plus one row per model-scoped weekly meter, plus one dim footer row each for an enabled extra-usage credit tally and a one-line health tag (stale snapshot or last-fetch error) when present, framed by a blank row above and below (`finalizePane`) so the meters sit clear of the pane's top border and the status bar beneath it. Every row, the blank ones included, carries a trailing `\x1b[K`: the pane's replay loop reads the baked file through a command substitution, which would otherwise strip the closing blank away as a trailing newline. Once any Codex process has reported usage — a worker or a headless reviewer/resolver/ci-fix agent, since capture is role-agnostic — a second Codex meter fills the empty space to the right of the Claude bars (see "Claude Usage Meter" below). Refreshed via SIGUSR1 from a pre-baked `usage.rendered` file.
- **Project Status** (mid-left) — Live-updating display of all projects and their workers. Shows which project is active (`◄`), each worker's lifecycle state via status icons (braille spinner for working, Unicode symbols for other states), a focus indicator (filled/empty circle) showing which worker is active, and aligned columns for name/status/activity. Auto-sizes to the number of projects. A project header row also carries a dimmed pencil `✎` after the name when that project's diary holds non-whitespace content — answering "did I leave notes here?", which nothing else on the row shows. Detection is `diaryHasContent` (`src/diary.ts`), which reads the diary directly (no mkdir) and stat-caches on mtime+size so the firehose of status re-bakes doesn't re-read every project's diary; `formatDiaryGlyph` (`src/commands/status.ts`) renders the glyph in both the baked dashboard path and `garden status`. An empty or whitespace-only diary counts as no content, so a never-written diary stays unmarked.
- **Growhouse Pane** (lower-left) — Cycles between six views: growhouse (bold green `garden>` prompt with auto-dispatch for garden commands), root (general-purpose shell), logs, history, diary, and alerts. `⌥g` jumps to growhouse, `⌥r` jumps to root, `⌥l` jumps to logs, `⌥a` jumps to alerts (the unread/read alert list — see "Alerts"), `⌥h` jumps to history (the focused worker's operator prompts + verb-tagged assistant summaries, read from the worker's Claude transcript JSONL by `conversation.ts`), `⌥d` jumps to the diary (the focused project's diary at `~/.garden/diary/<project>.md`, open in `$EDITOR`). The history pane renders via the same pre-baked-file + SIGUSR1 path as the usage meter; `writeHistoryRendered` parses the transcript only while history is the active mode. To keep the view a readable summary rather than a raw dump, `conversation.ts` (a) skips system-injected user-role messages — background-task completions (`<task-notification>`), slash-command echoes — identified by the transcript's `promptSource` field (genuine prompts are `typed`/`queued`) with a wrapper-tag denylist fallback for legacy transcripts, so a workflow launch and the edits it drove fold into one summary instead of being split by a multi-KB notification blob; and (b) collapses garden-injected user-role prompts to a compact dim `garden · <kind>` marker, keeping the response visible (a post-merge auto-continue is often a whole phase of real work): `[garden]`-fenced continuation prompts (post-merge auto-continue, handoff callback, trellis/grow iteration) via `gardenLabel`, and a spawned worker's `[handoff from <project>/<worker>]` seed briefing via `handoffSeedLabel` (labeled `garden · handoff from <project>/<worker>`). Operator prompts are shown in full (not capped). An assistant turn is summarized by what it DID (`summarizeTurn` — files edited, tests run, committed/pushed, files explored), never by the model's own prose, and one operator prompt yields exactly one assistant entry no matter how many messages the agent emitted answering it. **That shape is the harness-neutral contract, not a Claude detail**: the Codex reader (`harness/codex-core.ts` `readTurns`) accumulates rollout activity between operator prompts and feeds the same summarizer, mapping Codex's vocabulary onto the neutral tool names it reads (`apply_patch`/`patch_apply_end` → an edit, `exec_command`/`exec` → the shell command, `spawn_agent` → a subagent, `web_search_end` → research) and deriving the Read/Grep tools Claude has natively from the shell command text, since Codex reads and searches by shelling out. Without that mapping a Codex history is a reformatted copy of the agent pane: Codex emits a message per progress narration (`phase: "commentary"`), so a single prompt can produce dozens of full-prose entries. The garden/handoff marker collapsing is shared by both readers (`promptTurn`, `conversation.ts`) for the same reason — the operator types the same prompts and garden pastes the same continuations into either pane. The diary pane runs a wrapper loop (`diary-view.sh`) that re-resolves the focused project via `garden dashboard _diary-path` each time the editor exits, so quitting the editor reopens on the now-focused project's diary; switching views parks the editor with its state intact. Switching projects (`⌥1–9` / `⌥p`) makes the diary follow: `reloadDiaryEditor` (`navigate.ts`) drives the editor's save+exit so the loop reopens on the new project. The drive fires only when a nano/pico editor is actually live on the pane — `paneRunningEditor` (`tmux.ts`) probes the pane's tty for the editor process — so the keys never hit a shell (the diary-view loop between reopens, its editor exited, or a non-editor pane swapped into the slot) and ring the terminal bell (the macOS "chirp"). This fires whether the diary is the active garden pane or parked in the hidden `_garden-diary` window — re-entering the diary view reuses the parked editor rather than restarting it, so without the parked-case reload it would show whatever project was focused when it parked. A live modal editor can only be re-targeted by restarting it, which would discard unsaved notes, so this is nano/pico-only (the shipped default; on macOS `nano` is a symlink to pico): it sends `^C ^O Enter ^X` — a leading `^C` clears any write prompt a prior partial drive wedged, then `^O Enter` writes the buffer to its current file and `^X` exits cleanly. A custom `$EDITOR` is left untouched (`paneRunningEditor` matches only nano/pico, whose save keys alone can be driven blindly) and still reopens on the operator's own exit. When the editor is nano/pico it is launched with `-b` to enable word wrap, so long diary lines wrap to the pane width instead of scrolling off the right edge.
- **Bottom bar** (tmux status line) — Two-sided display. Left side shows the active project name (bold) and its current git branch. Right side shows the garden build version (git short SHA, or "dev" when running via tsx); when the running build trails its branch it is prefixed with `⚠ N behind` and the whole bar turns yellow (see "Build staleness" below), and when unread alerts exist it is prefixed with a red `⚠ N alerts — ⌥a to clear` badge.
- **Active Pane** (right) — The currently visible pane for the active project. Either a worker (Claude session) or the project shell. Only one is visible at a time; others are parked in hidden tmux windows.

### Right-side pane model

Each project has:
- **One shell** (always exists, created on first project switch, protected from kill)
- **Zero or more workers** (spawned on demand with `⌥n`)

Only one pane is visible at a time. `⌥]`/`⌥[` cycles through all of them. `⌥w` jumps to the first worker, `⌥s` jumps to the shell.

## Plots

A **plot** is a named, ordered subset of projects (max 9) that drives what the dashboard shows. `⌥1`–`⌥9` index into the *active* plot. `⌥p` / `⌥P` cycle through focused plots. Projects can appear in any number of plots.

Plots scale past the nine-project hotkey ceiling: you can register as many projects as you want in `~/.garden/config.yml`, group them into purpose-specific plots (`client`, `lab`, `imp`, …), and swap views with a single keystroke. Each plot has a `focused` flag controlling whether it appears in the `⌥p` cycle — unfocused plots are still reachable by name (`garden plot <name>`) but don't clutter the hot-cycle.

**Storage**:
- Plot definitions live in `~/.garden/config.yml` under `plots:`. Order is semantic: plot insertion order drives `⌥p` cycle position, project order inside a plot drives `⌥1`–`⌥9`.
- Active plot is runtime UI state in `~/.garden/sessions/dashboard.state.json` (`activePlot` field). A user who runs `garden plot imp` before the dashboard is open will still land on `imp` when it launches — `ensureDashboard` preserves the pre-existing `activePlot` across fresh-creation of the state file.

**Migration**: The first `loadConfig()` after upgrading synthesizes `plots.all = [currently-focused projects]` (preserving pre-plot visibility) and drops the deprecated per-project `focused` flag. Idempotent once migrated.

**Hotkey behavior**:
- `⌥1`–`⌥9` resolves against `getFocusedProjectNames(config, state.activePlot)` — the active plot's projects, filtered to those still registered. Indices beyond the plot's length show a "No project at index N" hint.
- `⌥p` / `⌥P` (`cyclePlot` in `src/dashboard/navigate.ts`) iterates only focused plots. `⌥o` is an alias for `⌥P` (cycle previous), for ergonomic left/right cycling with `⌥p`. If the active plot isn't focused, the next press lands on the first focused plot. When cycling, `activeProject` is clamped to the new plot's membership so the hotkey grid updates immediately. The leaving plot's `activeProject` is stashed in `state.lastActiveProjectByPlot`, so cycling back restores the prior selection instead of re-clamping to the first project.

**Header rendering**: `formatLeft` prefixes the active-project string with the plot name (e.g., `imp › garden • main`). The status pane's border renders a plot strip — one segment per focused plot, showing a filled circle on the active one and an empty circle on the others (mirroring the worker focus marker below it) — by writing the formatted string into `@garden_name` on the status pane (`buildPlotStrip` in `src/dashboard/header.ts`). Unfocused plots are omitted. `@garden_plot` is unused on that pane.

**Plot status indicators**: Each plot segment also carries a status icon derived from the aggregated state of all workers across the plot's projects (`resolvePlotStatus` in `src/dashboard/plot-status.ts`). Priority order: `failing-working` (red spinner) > `failing` (red ✖) > `asking` (yellow ⚑) > `working` (braille spinner) > `done` (green ✓) > `idle` (no icon). `failing-working` is a `failing` worker whose agent is mid-turn — the same red failure signal, animated, mirroring the worker row's crossover. It tracks the failing worker specifically: a plot whose failing worker is parked stays a static ✖ even while other workers in the plot are busy, so the strip's motion answers "is anyone fixing it" rather than "is anything happening". It is the only state that short-circuits the scan (a plain `failing` must keep looking for a failing worker that is working). Only `done` is green — `merged` (transient post-merge beat), `reviewing`, `merge-pending`, and `resolving` fall through to `working`, since none of those are operator-actionable. Colors override the active/inactive styling for non-working states; a working plot keeps the neutral bold/dim active/inactive distinction, spinner included — the spinner is not separately brightened, so a plot you aren't in is flat grey end to end. Every glyph in the strip carries an explicit `fg=`: the strip is drawn as the status pane's `pane-border-format`, where tmux resolves a colorless glyph against `pane-active-border-style` (whose stock value is `fg=green`, or `fg=yellow` in copy-mode) whenever that pane is active. A bare `#[default]` gap therefore turns green on focus and reads as a `done` plot — `formatPlotSegment` leaves none, and `test/header.test.ts` ("leaves no glyph colorless in any plot state") guards it. The spinner animates at the same 120ms cadence as worker rows by piggybacking on the status pane's existing SIGUSR1-driven tick: `buildPlotStrip` writes a template file (`~/.garden/sessions/plot-strip.template`) with a `__GSP__` sentinel where the spinner frame goes, and the status pane's bash loop substitutes the current frame and rewrites `@garden_name` each tick. The loop enters animation mode if either `$cur` has a braille char or the template file contains the sentinel.

**Right-pane clock**: The right pane — whether it holds a worker or the project shell — renders a `%H:%M` wall clock in the right corner of its top border, mirroring the `garden` title in the top-left. The shared `pane-border-format` (set in `setupStatusBar`) carries a right-aligned clock segment — bold green to match the `garden` title, wrapped in spaces and capped with two border dashes so the border runs to the right corner exactly as the left edge frames `garden` — gated on the `@garden_clock` pane variable. The clock's style is kept comma-free (`#[fg=green]#[bold]`, never `#[fg=green,bold]`): a comma inside the `#{?@garden_clock,…}` conditional is parsed as the true/false separator and silently blanks the clock. That variable is set on worker panes (`restoreWorkerPaneVars` in `navigate.ts` and the worker-pane creation sites in `workers.ts` / `create.ts`) and on the right-pane shell (`createShellWindow` in `create.ts` and `focusShell` in `navigate.ts`). The left-column garden shells (growhouse / root / logs) deliberately do not set it. The time is strftime-expanded by tmux on each `status-interval` tick (30s), so it advances on tmux's own timer with no extra process or poll.

**Project color in the right-pane border**: Every registered project carries a stable `logColor` (palette in `src/log-palette.ts`, auto-assigned by the `loadConfig()` migration), used to color project names in `garden logs`. The right pane's top border echoes that color as a small `●` before the worker/shell label — the one place project identity is otherwise absent (the border names the worker and task, never the project). The dot is gated on the `@garden_color` pane variable (a tmux color name like `colour208`), set by `setPaneProjectColor` (`src/dashboard/header.ts`) at the same sites that set `@garden_clock`; the shared `pane-border-format` renders `#[fg=#{@garden_color}]●#[default]` — tmux expands the nested variable before parsing the style, and the style must stay comma-free like the clock's. The color deliberately appears nowhere else in the dashboard (status pane and bottom bar already name the project in text), and the palette stores 256-color indices, deriving the ANSI form (`logColorAnsi`, log lines) and the tmux form (`logColorTmux`, border format) from the same index.

**Project removal** (`garden remove <project>`) also calls `purgeProjectFromPlots` to strip the project from every plot's project list. Empty plots are kept — delete explicitly with `garden plot delete`.

## Pane Management

### Swapping Mechanism
Each project's workers and shell live in hidden tmux windows when not active. When you switch projects:

1. A temporary hidden window is created, and the current active pane is swapped into it via `swap-pane`
2. The target project's pane is swapped from its hidden window into the right slot via `swap-pane`, then the hidden window is killed
3. The status pane and header update to reflect the new state

This preserves both the layout tree (the right pane slot is never destroyed) and all worker state across switches.

### Hidden Window Naming
Hidden windows follow the convention: `_<project>-worker-<N>`, `_<project>-shell`, `_<project>-poller`, `_<project>-review-<worker>`, `_garden-growhouse`, `_garden-root`, `_garden-logs`, `_garden-history`, `_garden-diary`, `_garden-alerts`, `_garden-usage-poller`, and `_garden-watchdog`. When switching projects, the visible pane is parked as `_<project>-active`. The underscore prefix marks them as managed by garden — not user-facing.

### Worker Lifecycle
1. `⌥n` creates a git worktree at `~/.garden/worktrees/<project>/<worker-name>/`, with a branch named after the worker that points at `origin/<base>` directly. Worker freshness does not depend on the main checkout being clean or fast-forwarded — a stale main checkout raises an alert but does not infect the worker
2. Claude launches in the worktree with project rules and worktree workflow instructions
3. The worker is interactive — you work with it directly
4. `⌥]`/`⌥[` cycles between workers and shell
5. `⌥x` kills the focused worker, removes its worktree and branch. Kills unconditionally — no confirmation, even on dirty worktrees — so a worker stuck in loading or otherwise unresponsive can always be torn down
6. Switching projects parks everything in hidden windows; switching back restores

### Poller and Auto-Merge
Each project gets its own background poller (`_<project>-poller`) running in a hidden tmux window. Pollers are independent — one project's reviews never block another. Each poller watches its project's worker branches for new commits and drives the review/merge lifecycle using local git operations (no GitHub PRs). Pollers start when a project's first worker is created and stop when the last worker is killed.

**State machine per worker:**
```
working -> reviewing -> merge-pending -> merged --(UserPromptSubmit)--> working
               |              |              \
               v              v               +-(.garden-done set)-> done
           failing        resolving (auto-resolver on rebase conflict)
                              |
                              +-> merge-pending (verified) or failing (budget exhausted)
```

1. **working**: Worker is active. When the worker's Claude Code Stop hook fires and the worktree has commits ahead of base, the hook marks the worker for review (`pendingReviewAt`) and pokes the poller, which transitions to reviewing. Multiple workers per project can transition independently.
2. **reviewing**: Poller launches a Claude reviewer (`claude -p`) asynchronously in a hidden tmux window (`_<project>-review-<worker>`). The reviewer runs inside the worker's worktree, so it inherits the worktree's `.claude/settings.json` sandbox config (auto-allow for bash within the configured filesystem/network allowlist). The reviewer rebases onto the base branch, resolves conflicts, runs optional checks, fixes check failures, and reviews code against project rules. The poller polls for review completion by checking if the review window still exists. On completion: if clean or fixed, force-pushes and transitions to merge-pending. If the reviewer cannot fix the issues, transitions to failing. If the review process fails for transient reasons (Anthropic API 5xx/429/`overloaded_error`/`rate_limit_error` and the reviewer didn't commit anything), the poller auto-retries with exponential backoff (30 s → 2 min → 5 min, budget 3) before escalating to `failing` with `failingReason: "transient-review"` — `garden kick` accepts that reason and re-queues without requiring new commits. A session/usage-**quota** cutoff is distinct: the reviewer hit a hard usage limit ("You've hit your session limit …" for Claude; "You've hit your usage limit … try again at …" for Codex) and emits no verdict, so a seconds-scale retry is useless. The response depends on the reviewer's harness. A **foreign** reviewer (e.g. a per-project Codex reviewer) runs on a separate subscription whose window resets on a multi-day scale — waiting it out would wedge the whole project's merge pipeline — so the poller falls back to the first-party Opus reviewer immediately (a deduped warn alert names the blocked harness and its reset time; the configured reviewer resumes automatically on the next cycle once its window clears). A **claude-code** reviewer runs on the operator's own account, so that limit *is* the operator's rolling window and there is no stronger fallback: the poller auto-retries on a flat 15-min cadence (budget 24, ~6 h ceiling) until the window resets and the review merges on its own with no operator action, escalating to `failingReason: "quota"` only if it never clears. Both `transient-review` and `quota` are `garden kick`-recoverable. A third case is an **unparseable verdict**: the reviewer produced genuine output (not an API error) that lacked a standalone `CLEAN`/`FIXED`/`FAILED` line — it trailed off in prose ("Final suite is green (2609 unit + 103 integration, lint clean)."), decorated the token (markdown, "Verdict: CLEAN"), or buried it above a long test dump past the 20-line scan window. The reviewer already reached a conclusion; it just failed to format the final line. Rather than re-run the whole (Opus) review, the poller first hands that output to a cheap, fast **Haiku classifier** (`extractReviewVerdict`, `verdict-extract.ts`) that reads the reviewer's own conclusion and returns the verdict. The call is synchronous with a hard 45 s timeout (the poll loop already blocks on git network I/O, so a bounded classification is architecturally consistent) and runs on the same first-party Anthropic account as the reviewer; an ambiguous answer, timeout, or spawn error yields no verdict and falls through. A recovered verdict dispatches through the normal path (force-push + merge-pending for CLEAN/FIXED, `failing` for FAILED). This fallback is **default-workflow only** — the trellis `DRIFT` verdict carries a structured drift list a one-word extraction can't reconstruct, so trellis skips straight to re-review. Only when the classifier also can't determine a verdict (or the reviewer produced no output at all) does the unparseable path re-review: when the reviewer ends its turn with prose instead of a standalone token and committed nothing (e.g. an adversarial multi-agent reviewer that kicked off async sub-work and stopped before folding in the verdict), the reviewed diff is unchanged and usually fine, so the poller re-runs the review on a short flat backoff (15 s, budget 2) before escalating to `failing` with `failingReason: "unparseable-verdict"` (also `garden kick`-recoverable). None of these retry relaunches — transient, quota, unparseable-verdict, or a foreign-reviewer Opus fallback — consumes a trellis/grow loop iteration: a retry re-reviews the same commits (the reviewer emitted no verdict, the worker did no new work), so `launchReview` advances the iteration counter only for a genuinely new worker turn, not a retry relaunch — otherwise a multi-hour quota wait would inflate `trellis.iteration`/`grow.iteration` toward the budget and falsely trip the iteration cap. An unparseable verdict where the reviewer *did* commit work takes the reviewer-committed-work recovery (force-push its commits, re-review once) instead; a review timeout still transitions to failing immediately. Unreviewed code is never auto-merged. An operator prompt landing mid-review does not by itself disturb the pass — but the moment the woken worker runs a mutating tool (Edit/Write; Bash is exempt so a read-only Q&A turn never cancels anything), its PostToolUse hook stamps `reviewInterruptedAt` and pokes the poller, which cancels the review outright: the reviewer shares the worker's worktree, so the tree under certification is being rewritten and any verdict — even one already written — is discarded rather than dispatched. The worker resets to `working` with `pendingReviewAt` re-armed; its next Stop re-reviews the complete branch at quiescence. The interposed holistic pass cancels the same way (its markers clear; the gate re-evaluates at the worker's next terminal state).
4. **merge-pending**: Review passed, waiting to merge. A serial merge queue processes one merge at a time per project (ordered by timestamp). The merge sequence: rebase onto current base branch, force-push, then ff-merge. If the rebase has conflicts (because the base branch advanced while waiting), the poller launches a dedicated resolver and transitions to `resolving`. If the rebase is clean, the merge proceeds.
5. **resolving**: A dedicated resolver Claude session is running in a hidden tmux window with a single narrow job: complete `git rebase origin/<base>` and commit any conflict resolutions. The resolver does not push and does not re-review code — the code was already approved. On Stop, the poller verifies the rebase actually landed (no `.git/rebase-merge` or `.git/rebase-apply` present; `origin/<base>` is an ancestor of HEAD; HEAD differs from `preResolveSha`). On pass, force-pushes and returns to `merge-pending`. On fail, retries up to `resolveAttempts = 2`; on budget exhaustion, transitions to `failing`. A genuine unresolvable conflict parks with `failingReason: "code"` and an operator alert that names the unmerged files; a transient backend outage (Anthropic/codex 5xx/429/`overloaded_error`/`rate_limit_error`) or a session/usage-quota cutoff parks with the kick-recoverable `failingReason: "transient-review"` instead — `garden kick` re-queues the merge once the outage or quota window clears, rather than telling the operator to push a fix they don't need. Unlike the reviewer, the resolver has no dedicated `quota` reason or Opus fallback: a quota block (a foreign harness's usage-limit surfaces only through `quotaLimitResetHint`, not `isTransientError`) folds into `transient-review`. Any worker push during `resolving` aborts and resets budget — the worker's new state is the new ground truth.
6. **failing**: Unfixable review issues, failed review process, exhausted resolver budget, or repeated merge failures (a diverged base or branch protection wedges the merge; once `failCount` hits the retry budget the poller stops re-reviewing and parks here instead of burning a review every cycle). Poller watches for new commits via SHA tracking. After 30s debounce with no new pushes, state transitions back to working for retry. Each failure increments a `failCount` on the worker entry; after 3 consecutive failures, an alert is surfaced. The count resets on successful merge.
7. **merged**: Transient post-merge beat — code just landed on the base branch. Renders neutral (not green) in the status pane; not an operator-actionable signal. Cleared the moment the auto-continue prompt's `UserPromptSubmit` fires, returning the worker to `working` for the next phase. If `agentStatus` is `working` at the moment `finalizeMerge` runs (a prompt landed mid-merge race), the poller clears `merged` immediately to `working`.
8. **done**: Worker self-declared finished via the `.garden-done` sentinel and the merge cycle has settled. Renders bold green ✓ in the status pane — the operator's "this work is complete, the worker can be cleaned up" signal. Two paths in: `finalizeMerge` sets `done` directly when the sentinel was set before the final push (skipping the transient `merged` beat); the Stop hook sets `done` when the worker writes the sentinel after auto-continue and ends with no commits ahead. Cleared on `UserPromptSubmit` (operator nudges the worker back to work).

### Project Configuration
Projects can define settings in `~/.garden/config.yml`, either by editing the file directly or via `garden config <project> <key> <value>`:

```yaml
projects:
  garden:
    path: /Users/joshua/code/keychange/garden
    checks: npx tsc --noEmit && npx vitest run
    postMerge: npm install && npm run build
```

**Base branch**: Each new worker branches from and merges into a base resolved at creation time by `resolveSpawnBase` (`src/dashboard/git.ts`), in precedence order: the per-worker `workers new --base <branch>` override, then the project's configured `baseBranch` key, then the current branch of the main checkout (the legacy default), falling through to the `origin/HEAD` symref and finally `"main"`. Setting `garden config <project> baseBranch <branch>` makes the base authoritative and independent of whatever the checkout happens to be parked on; leaving it unset preserves the checkout-follows behavior. `garden config` validates the name softly (a not-yet-on-origin base only warns; it is published at first spawn), so the network-free set stays snappy.

The resolved value is validated against the local `refs/remotes/origin/<base>` ref (no network call, so the ⌥n hotkey stays snappy on slow links) and pinned to the worker in the registry (`WorkerEntry.baseBranch`). If the base branch has no local origin ref — the natural case is the operator switching the main checkout to a brand-new local-only branch and pressing ⌥n — garden treats the ⌥n press as a publish gesture and runs `git push -u origin <base>` from the main checkout to create the ref, then proceeds with worker creation. Only when the publish itself fails (no remote, branch protection, non-fast-forward, network) is the worker rejected; the rejection message surfaces the actual git stderr so the operator can fix the real problem instead of guessing. The bootstrap script's fresh `git fetch origin <base>` is the backstop: if the branch has since been deleted from origin, the fetch fails and a `bootstrap` alert fires. Once pinned, all consumers (poller, Stop hook, kick, resume) use `getWorkerBaseBranch(entry, ...)` — they never re-resolve from the main checkout, so switching the main checkout's branch after a worker is spawned does not retarget that worker.

If the Stop hook still fails to count commits ahead of `origin/<pinned-base>` (e.g., the base branch was deleted from origin after creation), it raises a one-per-hour `base-drift` alert (`source: worker`, `level: warn`) rather than silently swallowing the error.

**checks**: Command the reviewer runs in the worker's worktree after rebasing onto the base branch, so checks validate the combined state of the branch plus latest base. If checks fail, the reviewer fixes the issues and re-runs. No checks configured means the reviewer only does the code review.

**holisticReview**: Controls the whole-task coherence review interposed after a multi-phase default worker reaches `done` with at least two merges. It is one headless reviewer pass on the worker's own branch (reusing the per-phase reviewer flow, so a configured Codex reviewer runs it too), not a spawned worker — the worker re-opens `done` → `reviewing` for the pass. `fix` is the default when the key is unset: the reviewer fixes genuine cross-phase defects directly and the fix rides the normal CI + merge gate. Set `shadow` for report-only findings (surfaced as an alert) or `off` to disable the review. See `WORKFLOWS.md` "Holistic-review workflow" for the dispatch gate and lifecycle.

Workers and reviewers are instructed to run the command via `garden checks [project]` (`src/commands/checks.ts`), which executes exactly the configured string under a **machine-wide checks semaphore** (`src/checks-semaphore.ts`): a hardware-derived number of concurrent suites (`max(1, floor(cores / 8))` — 1 on an 8-core laptop, 2 on a 16-core desktop) is admitted and the rest queue, so a merge wave stretches clock time instead of oversubscribing the operator's workstation. Slots are pid-stamped `checks-slot-<n>.lock` files in `~/.garden/sessions` claimed with `O_EXCL`; a slot whose owning pid is dead is stolen (a SIGKILLed run cannot leak its slot), and a 45-minute max wait fails open — a queued run eventually proceeds ungated rather than wedging the fleet on a semaphore bug. CI runs the raw command on its own isolated runner and is deliberately not gated. The slot count derives from the machine at each invocation, so the same config adapts when the hardware changes — unless the operator pins it with the garden-level `limits.checksSlots` override (see "Machine-wide limits").

**postMerge**: Command that runs on the main checkout after merging, but only when the *working tree itself* advanced — i.e. the base branch was the one checked out, so `merge --ff-only` moved the tree to the merged code. When the operator has parked the checkout on a different branch (the deliberate many-base workflow), the merged base ref is advanced on its own via `git fetch origin <base>:<base>` (fast-forward-enforced, worktree-aware) without touching the working tree, and postMerge is skipped — building a tree that's on another branch would build the wrong branch. That off-base ref advance is silent: a local base ref that merely trailed origin is normal here, not drift. The base checkout is the operator's shared working directory — they commit, pull, and edit in it — not a pristine mirror, so a failed fast-forward is expected and benign for merge correctness (the work already landed on origin; only the local rebuild lags). postMerge is not allowed to dirty it, though: after the hook runs (success or failure), `revertPostMergeChurn` restores tracked files that the hook modified but that were clean before it started, comparing `listModifiedTrackedFiles` snapshots taken either side. Operator edits already in flight are in the before-set and are left strictly alone, as are untracked and staged changes. This closes a self-sustaining trap: `npm install` rewrites package-lock.json, which sits harmless until a merged commit also touches that file (`merge --ff-only` tolerates a dirty file the merge does not touch and refuses only on a collision — a dependency bump supplies one soon enough), after which the refusal skips postMerge, so nothing ever cleans the file and the checkout freezes permanently along with any binary built from it. Observed in the field at 14 merges of drift with every merge still reporting success. The corollary is that postMerge cannot be used to leave generated files sitting in the checkout — never durable anyway, since garden does not commit them. One failure mode self-heals: when the on-base checkout has a redundant local commit whose *clean* tree already equals origin/<base> (e.g. an operator heal commit whose change also merged the normal way), the ref is reset onto origin (`reset --hard`, reflog-preserved, working tree unmoved) and postMerge runs — no alert. The remaining states alert, framed as "merge succeeded, local checkout needs a hand": it has *diverged* from origin with real local-only content (warn, the operator reconciles by hand), the base is checked out in *another worktree* (warn, that worktree needs a pull), the on-base checkout is *dirty* with uncommitted changes (warn, the operator cleans it — the alert names how many commits behind origin the checkout has fallen, and, when a `postMerge` hook builds from it, that anything built from it is that stale, so a long-running stall reads as one instead of as a routine blip; a checkout level with origin gets no drift clause at all), or it is *wedged*/unfetchable (`stuck`, error — infra trouble). Each alert fires only on *entry* into the state, not on every subsequent merge while it persists. This is essential for projects like garden itself, where the poller runs the compiled CLI. When the garden project itself rebuilds successfully, the poller spawns a detached `_post-rebuild-refresh` via the freshly-built binary; it respawns the status and logs panes, calls `restartLongLivedPollers()` so the usage-poller and per-project pollers reload the new bundle (they cache JS in memory at spawn time), and refreshes the dashboard.

**sandboxDomains**: Comma-separated list of extra network domains added to each worker/reviewer's sandbox allowlist. Use for private registries, internal services, or other hosts beyond the garden-wide defaults (Anthropic, GitHub, npm, the project's git remote host). Set via `garden config <project> sandboxDomains foo.com,bar.com`.

**sandboxDenyCredentials** (default `false`): When `true`, the worker sandbox additionally denies READ of the operator's credential paths (`~/.claude`, `~/.ssh`, `~/.aws/credentials`, cloud creds — `DENIED_CREDENTIAL_PATHS` in `src/dashboard/sandbox.ts`) via Claude Code's `sandbox.credentials` (mode `deny`) plus `filesystem.denyRead`. Both are OS-enforced (Seatbelt/bubblewrap) and, per Claude Code's docs, apply to sandboxed Bash **subprocesses only** — the parent `claude` and the headless `claude -p` reviewer authenticate before the sandbox boundary, so their own Anthropic auth is unaffected. This closes the credential-exfiltration path a prompt-injected worker would otherwise have (read `~/.claude/.credentials.json`, POST it out over an allowed host). It defaults **off** because that parent-auth timing is documented but not guaranteed for every release, and getting it wrong would break reviewer auth fleet-wide: enable it per project (`garden config <project> sandboxDenyCredentials true`) only after verifying a headless `claude -p` still authenticates in a sandboxed worktree carrying the config, and a sandboxed `cat ~/.claude/.credentials.json` is blocked. Requires Claude Code >= 2.1.187 (`sandbox.credentials` deny mode); `mask` mode is deliberately never emitted (it is ignored in a repo's `settings.json`). claude-code workers only — a Codex worker's `workspace-write` sandbox has no per-path read-deny.

**claudeProfile**: Name of an alternate Claude Code config dir to use for this project's workers and reviewers. Profiles are registered globally under `claudeProfiles:` in `~/.garden/config.yml` (each entry has a `configDir` and optional display `label`). When set, every `claude` invocation for the project — workers, reviewers, resolvers, the prefix-`C` ad-hoc launcher — runs with `CLAUDE_CONFIG_DIR=<configDir>`, so Claude reads its credentials, settings, and history from that dir instead of `~/.claude`. Projects without `claudeProfile` use the personal default. Manage profiles with `garden claude-profile {list,add,remove,login}`. The usage meter is not split per profile: `/api/oauth/usage` aggregates by user identity, so two workspace tokens tied to one email return identical data. Per-workspace quota for the alternate plan, if any, is only visible from the org owner's admin dashboard.

**provider**: Name of a model provider this project's WORKERS run on — an Anthropic-Messages-compatible backend (DeepSeek's `/anthropic` endpoint, a local Ollama, a gateway) the unchanged Claude Code harness reaches by env swap. Providers are registered globally under `providers:` in `~/.garden/config.yml` via `garden provider add <name> --base-url <url> --token-env <ENV_VAR> [--map opus=m1,sonnet=m2,haiku=m3] [--egress h1,h2]`. Worker launch commands get `ANTHROPIC_BASE_URL`, an `ANTHROPIC_AUTH_TOKEN="$<ENV_VAR>"` reference expanded at spawn time (the key never enters config or command lines), and `ANTHROPIC_DEFAULT_*_MODEL` from the model map; the sandbox allowlist gains the base-URL host plus any `--egress` extras. The key reaches panes through the tmux **session environment**: the server's own env is frozen at server start, so garden's operator-shell entry points (`provider add`, `config set provider`, dashboard create/attach, `workers new`, `auth status`) sync the key from the invoking shell via `tmux set-environment`, `workers new` refuses to spawn a provider worker whose key is in neither place, and `garden auth status` reports both locations (and syncs as it reads). Reviewer, resolver, and ci-fix agents deliberately ignore this key: `reviewerEnvPrefix` actively empties any inherited `ANTHROPIC_*` provider env so they stay on the first-party Anthropic path, and each of the three defaults to Opus on the claude-code path (not just for provider-backed projects) — the strong reviewer is the safety net that makes cheap or experimental worker models safe to try. Each default is overridable per role via `garden config <p> role <role> model <m>` (and the whole role is routable to another harness, e.g. Codex; see the per-role resolution in `docs/MULTI-MODEL.md` "Phase 4"). When *every* project has a provider, the Claude usage poller, the Stop-hook usage refresh, `garden usage`, and the meter pane switch off with an explanatory line. Applies to newly created or bounced workers; live panes keep their pinned env. See `docs/MULTI-MODEL.md`.

**harness**: Default agent CLI (harness) for this project's WORKERS — the axis-2 analog of `provider` (axis 1). Registered harnesses are `claude-code` (absent = this default) and `codex`; the operator-facing alias `claude` (the claude-code crew-member name) is accepted anywhere a harness name is entered — `--harness`, `config <p> harness`, `config <p> role <r> harness` — and canonicalizes to `claude-code` (`canonicalHarnessName`, `src/dashboard/harness/core.ts`). Set via `garden config <project> harness codex`; `garden workers new <project> --harness <name>` overrides it per worker. The project default applies to the **default workflow only** — trellis/grow workers stay on claude-code regardless (a foreign harness is not yet exercised against their per-iteration model resolution and cold-respawn identity). Only the worker default lives here; the review family (reviewer/resolver/ci-fix) selects its own harness under `garden config <p> role <role> harness <name>` — a provider never reaches review, the safety net. Applies to newly created or bounced workers. See `docs/MULTI-MODEL.md` "Layer 3".

**model / effort**: Default worker model and reasoning effort for this project's **default and grow** workers — the project-level analog of `garden workers new --model` / `--effort`. They layer beneath the per-spawn flags in `newWorker` in precedence order per-spawn flag > project key > account/provider default, exactly as `baseBranch` sits beneath `--base` via `resolveSpawnBase`. `model` is an opaque string (an Anthropic alias resolved through the provider `modelMap` on a provider-backed project, or a concrete model id), stamped onto `WorkerEntry.model`. `effort` is one of `low`/`medium`/`high`/`xhigh` (rendered as `--effort <level>`) or `ultra`, which resolves to the ultracode preset (max effort + dynamic workflows, Opus pin). Both are ignored by **trellis** (vines resolve their own model per iteration via `trellis.workerModel` and carry no effort). The **review family** ignores these project-level keys too, but is not effortless: reviewer/resolver/ci-fix take their own `model` and `effort` per role (`roles.<role>.effort`, or a crew's review half), resolved by `resolveReviewRole`. The model keeps its safety-net floor of Opus; effort has no floor, since unset simply means the account default. The ultracode preset's Opus pin still wins over `model` (an explicit per-spawn ultracode gesture is more specific than a project default), and a spawn that resolves to ultracode suppresses `effort`. Set via `garden config <project> model <alias-or-id>` / `garden config <project> effort <level>`, or the `⌥,` project menu's **model** / **effort** rows (curated alias/rung submenus; the CLI covers exotic model ids). A **stored crew** can pin these same two dimensions, in which case it resolves one layer *beneath* these flat keys (per-worker crew > flat project key > project's bound crew), so adopting a crew still leaves room to tweak one dimension per project. Builtin crews carry no model/effort and never interact with them. A codex worker renders `effort` through its own dial — `-c model_reasoning_effort=<level>` — rather than `--effort`; the four plain rungs are valid Codex reasoning levels, while `ultra` means the ultracode preset here and that preset has no Codex analog. (Codex's fuller ladder, which adds `max` and a genuine `ultra` reasoning level, is offered per-spawn by the `⌥⇧N` composer when codex is the build member — see "Spawn composer".) A provider-backed worker's model alias resolves through the provider `modelMap`. Applies to newly created workers.

**crew**: A named bundle of *who runs each role and how strong*, composing a project's whole fleet in one word: `garden config <project> crew <name>` / `garden crew apply <name> [project]` (or `⌥⇧C` in the dashboard). A crew pairs two **members** — a member being a registered harness (`claude`, `codex`) or one per configured provider (`deepseek` → claude-code against that backend). Any member may build, but only harness members review (a provider on review defeats the safety net), enforced structurally in `validateCrewDef`.

Crews come in two kinds. **Builtins** are generated (`builtinCrews`): the cross product of members × reviewer-members, named `<worker>-<reviewer>` with `all-X` sugar — `all-claude`, `codex-claude`, `deepseek-codex`, and so on, expanding for free as providers and harnesses are added. They carry a harness pairing only, because a *generated* namespace cannot express a model dim without exploding into names like `sonnet-xhigh-claude-opus-claude`. **Stored** crews (`crews` in `~/.garden/config.yml`, garden-level like `providers` — a shared resource projects reference by name) are operator-named, which puts the name in the operator's hands and so lets a crew also pin **model** and **effort**: `heavy`, `cheap`, `nightly`. Managed via `garden crew [list|show|add|edit|remove|apply]` (`src/commands/crew.ts`); `--from <crew>` clones any crew (builtin included) so "copy and tweak" is one call, and the literal `none` clears a pinned dimension. `listCrews` returns stored ∪ builtin, a stored name shadowing a builtin.

**Binding is by reference.** A project stores `crew: <name>` and the members resolve at spawn/review time, so `garden crew edit heavy --model opus` re-targets every project on `heavy` at its next spawn or review — the property that makes crew definitions worth editing at all. `applyCrew` therefore records the name and *clears* the flat keys the crew now owns; a stale flat key left behind would sit in the override layer and permanently shadow the crew. The flat project keys (`harness`/`model`/`effort`, `roles.*`) are that override layer, winning over the crew, so a project can adopt a crew and still tweak one dimension (`crewOverridden` reports this state). `config <p> crew none` unbinds, leaving the flat keys standing.

Resolution reads, per dimension: **per-worker crew → explicit project key → project's bound crew → default**. The worker half supplies harness (default workflow only, like `project.harness`) plus model and effort (default+grow, like `project.model`/`effort` — a crew effort of `ultra` promotes to the ultracode preset exactly as `--effort ultra` does); the review half supplies harness, model, and effort uniformly to reviewer/resolver/ci-fix via `resolveReviewRole` (`roles.ts`) — its effort ladder ends in `max` rather than `ultra`, since ultracode is a worker preset a headless run has nothing to enable, and unlike the model it has no safe-default floor (unset means the account default). **`provider` is the one write-through dimension** — its readers (`resolveProvider`/`projectUsageGateExempt` in `config.ts`, `reviewerEnvPrefix` in `claude-env.ts`) sit below `crew.ts` in the import graph and cannot consult a crew without a cycle, and `docs/future/CREWS.md` rules that PROJECT-level worker-provider stays the flat key to avoid split-brain; so the crew owns the value but writes it to `project.provider` where every reader already looks. (This governs the project binding only. A *per-worker* crew or build member resolves its provider at spawn onto `WorkerEntry.provider` instead — see "Spawn composer" — which is a distinct layer above the flat key and needs no write-through, since the launch env builders read the entry directly.) A dangling binding (crew deleted) is inert rather than broken: resolution skips the crew layer.

The **`⌥⇧C` picker** is also the crew editor. Selecting a crew binds it (the common act); below a separator sit `new crew…`, `edit crew…`, and `delete crew…`, shown unconditionally. Gating the latter two on a stored crew existing was tried and reverted: with none defined the menu showed a lone `new crew…` and read as a half-shipped feature, since an empty state is indistinguishable from a missing one. tmux `display-menu` has no disabled-row rendering to lean on, so the choice is show-with-a-message or hide; the chooser answers an empty list with "No crews defined yet — use 'new crew…' first." The **edit chooser lists builtins too**. A builtin has no storage to edit in place, but a stored crew SHADOWS a builtin of the same name, so editing one materializes an override you then tune, and deleting that override restores the generated pairing — lossless in both directions. `all-codex` is the natural starting point for "codex, but pinned to Opus", and requiring `crew add … --from` first was busywork. Rows are tagged with what selecting them does (`builtin — edit to override`, `reverts to builtin`), and the delete chooser stays stored-only since a pure builtin has nothing to remove. `garden crew edit <builtin>` does the same thing, so the CLI and the menu agree; `--from` remains the way to clone under a *different* name.

New/edit open a **composer**: one row per dimension (worker member, model, effort, reviewer member, review model, review effort), each opening a curated submenu, with the title reading the recipe back as composed (`New crew (claude opus/xhigh → codex)`). Composition state lives in a garden-level draft (`crew-draft.ts`, `SESSIONS_DIR/crew-draft.json`, 15-min TTL) — the same pattern as the ⌥⇧N spawn draft, and for the same reason: a tmux `display-menu` is fire-and-forget, so multi-field composition needs state that survives each re-open. It is garden-level rather than per-project because a crew is a garden-level resource. Save is withheld until both halves are named; creating prompts for the name via `command-prompt`, while editing saves straight to the name the draft was seeded with. The save path calls the same `saveCrew` the CLI does, so member validation and the review asymmetry are enforced once, not twice. Curated model/effort choices match the `⌥,` project menu's; exotic model ids stay on the CLI.

`garden config <p> crew` with no name lists the current crew, whether it is locally overridden, and the available set. A quiet grey crew badge rides the **focused** project's header in the status pane — shown for every crew including `all-claude` and `custom`; focused-only, so it reads as context for the project you're working in rather than standing grey across the whole list. A crew can also be set **per worker** (`workers new --crew`, persisted to `WorkerEntry.crew`), which badges that worker's own row with the crew name — superseding its build-member badge, since the crew name already encodes both build and reviewer. A per-worker crew's build half folds into `entry.harness` at spawn (its worker member is authoritative — a `claude-codex` crew builds with claude even on a project defaulting to codex, pinned explicitly so the project default can't override it), and its review half is applied live by `resolveReviewRole` — so a worker's reviewer/resolver/ci-fix can be re-targeted after it has started and takes effect on the next review (the poller resolves the role fresh each cycle). The **`⌥i` worker menu** (`src/dashboard/worker-menu.ts`) is the live surface for this — and for a running worker's base branch (rewrites `entry.baseBranch`, re-targeting the next merge) and model (set + bounce). See `src/dashboard/crew.ts` and `docs/future/CREWS.md`.

### Spawn composer

`⌥n` spawns a worker with no questions asked; `⌥⇧N` is the same act with the dials exposed. The picker's workflow rows sit above a separator, and below it one row per per-spawn dimension: **build** (`(w)`), **model** (`(m)`), **effort** (`(e)`), **crew** (`(c)`), **base branch** (`(b)`). Choosing a value stages it in a short-lived per-project draft (`spawn-draft.ts`, `SESSIONS_DIR/spawn-draft-<project>.json`, 5-min TTL, swept by the watchdog) and re-opens the picker, giving a fire-and-forget tmux menu the feel of a form; choosing a workflow consumes the draft (read + delete) into `newWorker`. The title reads the recipe back as composed — `New worker on garden (codex · gpt-5.6-sol · xhigh)`.

The re-open **keeps the cursor where the operator left it**: the composer re-opens with the dimension just staged still selected (`MenuSpec.startingChoice` → `display-menu -C`, an index over every item, separators included), and a dimension's submenu opens on the value already staged. Without it the form feel breaks down at exactly the point it matters — a menu that re-opens itself on every choice snapped back to the first workflow row each time, so composing three dimensions meant scrolling down to the same row three times. Nothing staged means no row describes the current state, so a first open (the `⌥⇧N` hotkey) and a submenu with nothing staged both keep tmux's default of the first row.

**Build** answers *who builds this worker*, in the same **member** vocabulary crews use (`listMembers`) — `claude`, `codex`, any registered harness, plus one row per configured provider (`deepseek` → claude-code against that backend). It is consumed as `newWorker`'s harness+provider **pair**, which is authoritative over a crew's worker half, so staging build *and* crew composes "this builder, that reviewer" without defining a crew for the pairing. This is the fast path the crew dimension alone could not give: spawning one Codex worker on an otherwise all-Claude project is `⌥⇧N w <n> d`, with no project reconfiguration to undo afterward.

A member is a **pair**, and naming one is a statement about both halves. `--harness claude` on a provider-backed project therefore means *first-party* claude, not "claude against the project's backend" — without that rule there is no way to spell first-party on such a project at all, and the composer would have to display `[claude]` for a worker that in fact launches against the provider. Precedence mirrors harness exactly: explicit member > per-worker crew's worker half > project key > project's bound crew. Only a genuine per-worker *override* is validated at creation (an operator who named a backend gets a loud failure for a name that resolves to nothing) and only an override is stamped on `WorkerEntry.provider` — a worker that named no member inherits the project key and writes nothing, so every pre-existing spawn path is unchanged. From there `entry.provider` threads through resume, bounce, and loop respawn alongside `entry.harness`, so the backend survives the worker's lifetime rather than silently reverting on the first respawn. Both halves of the worker's runtime read the same view (`workerProject` in `create.ts`, the one decoder of the empty-string marker): the launch env (`workerEnvPrefix`) and the sandbox egress allowlist (`buildSandboxConfig`, which admits the provider's inference host). Threading only the env would leave a worker pointed at one backend with another allowlisted, and a later bounce or loop refresh would rewrite the allowlist back to the project's — the half-threaded revert this design rules out. The review family never consults it: reviewer/resolver/ci-fix stay first-party by construction, since a provider on review defeats the safety net. The auto-continue usage gate does consult it — a worker on a provider spends a pool the Claude meters do not describe, so it is exempt on exactly the reasoning a provider-backed project is.

**Model and effort vocabularies belong to the build member, not to garden.** Codex names concrete slugs (`gpt-5.6-sol`) where Anthropic names aliases (`opus`), a provider serves only the aliases its `modelMap` defines (`providerModelAliases` — offering `fable` to a backend that never mapped it would send a name it cannot resolve, and an empty map falls back to the standard list rather than an empty submenu), and Codex's reasoning rungs are its own `model_reasoning_effort` values (adding `max`, and a genuine `ultra` level unrelated to garden's ultracode sentinel). Both submenus are therefore populated from the draft's **effective build member** — `effectiveBuildMember`: staged member > staged crew's worker half > project default (`projectWorkerMemberName`) — so a project bound to an all-claude crew offers Anthropic aliases, and staging `codex` re-populates both lists from Codex's catalog. Offering one harness's vocabulary while another builds was the defect this resolves: the lists looked like garden's opinion about available models when they were really just the Anthropic branch.

The Codex model list comes from **Codex's own on-disk catalog** (`$CODEX_HOME/models_cache.json`, read by `codexModels` in `harness/codex-models.ts`): visible slugs in Codex's own priority order, so a new OpenAI model appears with no garden edit. That file belongs to Codex, not garden — it may be absent (Codex never run, or no Codex in the fleet) and its shape may drift — so every read is best-effort behind `CODEX_FALLBACK_MODELS`. The Anthropic side stays a literal, its alias set being stable enough not to warrant discovery. Either way the CLI (`workers new --model <id>`) remains the escape hatch for a model neither list names.

Changing the build member to a **different `(harness, provider)` pair clears any staged model and effort**. The clear keys on the pair rather than the harness alone because two provider members share the claude-code harness without sharing a model vocabulary — keying on harness would carry a DeepSeek-only alias onto a different backend that never mapped it. Those values are named in the outgoing harness's vocabulary — `sonnet` and the ultracode `ultra` mean nothing to Codex, `gpt-5.6-sol` means nothing to Claude — so carrying them across would stage a recipe that cannot run. Clearing drops both to the account default, which is always valid, and the operator re-picks from the now-correct list.

At consume time `draftLaunchOpts(draft, harness)` renders the effort dim in the target harness's dialect: on claude-code the `ultra` rung becomes `ultracode: true` (the preset — max effort plus dynamic workflows — rather than an effort value), while on codex the whole ladder passes through untranslated as `entry.effort`, which the adapter renders as `-c model_reasoning_effort=<level>` and where ultracode stays a no-op. Build, model, and effort apply to **default and grow** workers only (trellis resolves its own model per iteration and carries no effort); build member and crew are default-workflow-only, like `--harness` itself.

### Machine-wide limits

Some resource budgets are properties of the **workstation**, not of any one project — the machine is a single shared resource, so a per-project knob would be the wrong shape (no project sensibly wants a different answer to "how much of my machine may the fleet use"). These live at the top level of `~/.garden/config.yml` under `limits` (`LimitsConfig` in `src/config.ts`), managed with `garden limits [status | checks-slots <N|unset> | max-reviews <N|unset>]` (`src/commands/limits.ts`) or the **`⌥;` garden settings menu** (`src/dashboard/garden-menu.ts`) — the garden-level sibling of the `⌥,` project menu (`⌥,` configures one project, `⌥;` the whole garden). The menu offers curated presets; arbitrary values stay on the CLI. Both keys are optional overrides of a safe default — an absent `limits` block is the shipped behavior.

- **`checksSlots`**: overrides the hardware-derived checks-semaphore slot count (`max(1, floor(cores / 8))`; see the checks-semaphore paragraph above). Use it to pin the concurrent-suite budget when the automatic value doesn't fit the machine (a heavier or lighter suite than the `~half-the-cores` assumption).
- **`maxConcurrentReviews`**: a fleet-wide cap on simultaneously running headless reviewers — counted live from tmux as the `_<project>-review-<worker>` windows across all projects (tmux is the source of truth for window existence, so the count is derived fresh with no acquire/release bookkeeping to leak across the fire-and-forget reviewer launches). The gate sits at the review-launch point in `handleWorking` (`src/dashboard/poller-review.ts`): when the cap is already met, the launch is **deferred** — `pendingReviewAt` stays set and a re-poke is scheduled, so the next poll (or any sibling FIFO event, such as a running review finishing and freeing a slot) re-drives the launch. Resolvers and ci-fix agents are deliberately **not** capped: they unblock already-in-flight merges, so throttling them could deadlock the pipeline; the cap governs only the pipeline's inflow. Default `0` = unlimited (the shipped behavior) — the count isn't even taken when the cap is off. This complements the checks semaphore: the semaphore bounds the heaviest thing a reviewer does (running the suite), while this bounds the number of concurrent reviewer inference processes.

### Merge Handling
After a review passes, workers enter the `merge-pending` state. The merge queue processes one worker at a time per project (ordered by `mergePendingAt` timestamp):

1. Fetch latest base branch (this also refreshes the local `origin/<base>` ref the resume check and CI gate read).
2. **Resume an interrupted merge** (`src/dashboard/poller-merge.ts`): if the worktree HEAD is already contained in `origin/<base>`, a prior finalization already fast-forward-pushed the merge but was torn down before the terminal-state transition (e.g. a garden rebuild restarted every project's poller mid-finalize). Skip the re-merge and run only the idempotent post-merge tail. Naively re-running rebase + force-push here would hit a `--force-with-lease` "stale info" rejection against the now-deleted remote branch; the force-push catch then re-arms a full re-review of the already-merged worker and fires a spurious push-failed alert (it no longer strands the worker, but the wasted cycle also masks a trellis ALIGNED convergence).
3. **Defer while the worker's Claude is mid-turn** (`src/dashboard/poller-merge.ts`): if the merge-pending worker's `agentStatus` is `working` — the operator prompted it and it may be editing tracked files not yet committed — defer the whole merge before touching the shared worktree. `cleanWorktree` (`git checkout -- .`) and the rebase below rewrite tracked files and HEAD; a plain rebase would refuse on a dirty tree, but `cleanWorktree` turns that refusal into a silent wipe of the uncommitted edits (there is no reflog for unstaged changes). This sits **after** the resume check — an already-pushed merge is safe to finalize regardless — and `launchResolver` guards the identical shared-worktree hazard. The deferral cannot strand the worker: its Stop hook re-pokes on turn end, and the watchdog backstops a lost poke since `merge-pending` is a watched state.
4. **CI gate** (`src/dashboard/poller-ci.ts`): query `gh api repos/<owner>/<repo>/commits/<sha>/check-runs` for the worker's HEAD. **Success** (every completed check-run conclusion is `success`/`skipped`/`neutral`) → proceed. **Pending** (any check-run not yet `completed`) → defer the merge with a 60 s re-poke; worker stays in `merge-pending`. **Failed** (any non-success conclusion) → dispatch a self-healing ci-fix agent (`src/dashboard/poller-ci-fix.ts`) in a hidden `_<project>-ci-fix-<worker>` tmux window and transition the worker to `ci-fixing`. The agent runs in the worker's own worktree, reads the failing logs via `gh run view --log-failed`, makes the minimum fix to turn the checks green, and pushes. The poller's verification path checks that the agent actually advanced HEAD (against the captured `preCiFixSha`) and that origin tracking matches the new local HEAD; on success it transitions back to `merge-pending` so the CI gate re-runs against the new SHA. Verdict `FIXED` without a verified push, verdict `FAILED`, or unparseable output: retry up to budget (3 attempts per merge cycle), then escalate to `failing` and an operator alert — `failingReason: "ci"` (push a fix) for a genuinely red CI the agent couldn't repair, or the kick-recoverable `failingReason: "transient-review"` when the agent only hit transient backend outages (Anthropic/codex 5xx/429/overloaded) or was cut off by a session/usage-quota limit (surfaced through `quotaLimitResetHint`, folded into `transient-review` like the resolver's). Launch and successful push are routine lifecycle beats — logged (visible in `garden logs`) but not raised as operator alerts; only budget exhaustion alerts, at error level, when the agent can't repair CI within the 3-attempt budget. The gate is a no-op for projects with `requireCiSuccess: false`, projects whose `origin` isn't a github.com remote, environments where `gh` isn't installed, and commits with zero check-runs on a project with no CI. "Has CI" is answered from the checkout on disk first (any `.github/workflows/*.yml`/`.yaml`), then from a check-run observed earlier in this poller's life. The disk read is load-bearing, not an optimization: the learned flag alone could never be set. The poller queries within seconds of the reviewer's force-push while GitHub takes ~5-12 s to create the runs, so every query returned zero check-runs — and only a non-zero observation set the flag. After any poller restart the gate silently passed everything through, which is how a red `main` merged on 2026-07-20. The learned flag remains as an OR for CI with no workflow file in the repo (CodeQL default setup, third-party check apps). On a project that has CI, zero check-runs on a freshly force-pushed SHA (a reviewer-fix or ci-fix commit whose runs haven't materialized yet — they appear ~30 s after a push) are treated as not-yet-materialized: the merge defers within a bounded grace window (3 min, re-poked every 60 s) before passing through, rather than merging the exact commit CI most needs to vet un-gated.

Both halves of that mechanism are **persisted, not in-memory**, and this is load-bearing for the same structural reason the disk read above is. The poller loop is `while true; do garden dashboard _poll <project>; read; done` — a fresh node process per poll, so any module-level `Map` is empty at the top of every poll. The grace stamp lived in one, which meant each poll re-stamped it as "now", the elapsed check measured ~0 ms, and the window could never expire: the merge deferred permanently. The 60 s recheck-poke dedup lived in another, so it never fired across the boundary and every external poke arriving during a pending-or-grace stall spawned an additional self-perpetuating sleeper. Together they stranded two `wolf` workers in `merge-pending` for 5.5 h behind 43 orphaned `sleep` processes on 2026-07-21. The grace stamp now lives on `WorkerEntry.ciNoRuns` (`{ sha, since }`, keyed by SHA so a force-push starts a fresh window on the new tip rather than inheriting an expired one); the poke dedup is the mtime of a `ci-recheck-<project>` marker file in `SESSIONS_DIR`, which needs no content or schema and fails open (arms the poke) when it can't be read or written — a duplicate poke is recoverable, a dropped one strands the merge. The general rule the incident establishes: **state that must survive from one poll to the next belongs on disk.** A module-level `Map` in poller code is per-poll scratch, never memory. The gate runs **before** the rebase/force-push so it reads CI for the SHA the worker actually published; the rebased commits that ultimately land on base are the same commits in rebased form, and the workers we guard push frequently enough during their turn that CI is usually already settled by the time the reviewer signs off. This is defense-in-depth against GitHub branch protection — the poller's force-push path bypasses the merge UI entirely, so branch protection alone can't block a red CI.
5. Clear any leftover rebase state from a prior crashed resolver (`ensureNoRebaseInProgress`)
6. Rebase onto current base branch
7. If rebase conflicts: abort rebase, launch a dedicated resolver in the worktree and transition to `resolving`. The resolver completes the rebase and commits the resolution; the poller verifies and pushes. Budget is 2 attempts per merge; exhaustion transitions to `failing` with an operator alert — `failingReason: "code"` naming the unmerged files for a genuine conflict, or the kick-recoverable `failingReason: "transient-review"` when the resolver only hit transient backend outages or a usage-quota cutoff.
8. If rebase is clean: force-push the rebased branch, fast-forward the remote base branch via direct refspec push (no local checkout needed). The refspec push runs `--no-verify`: it executes in the operator's checkout, and an operator `.git/hooks/pre-push` guard against direct human pushes to the base branch must not veto the merge queue's own authorized, already-reviewed push (such a guard was shadowed by the core.hooksPath leak until `scopeHooksPathToWorktree` fixed the leak, which re-armed it and blocked every merge)
9. Notify live sibling workers with overlapping files (see below)
10. Advance the local base branch to the merged tip — `merge --ff-only` if it is the checked-out branch (also moves the working tree, so postMerge can run), otherwise `git fetch origin <base>:<base>` to advance the ref alone (working tree untouched, postMerge skipped). A clean advance is silent, as is auto-healing a redundant local commit whose clean tree already matches origin (reset onto origin, then postMerge runs). The remaining states alert only on entry: the local base diverged from origin with real local-only content (warn), the base is checked out in another worktree (warn), the on-base checkout is dirty (warn), or it is wedged/unfetchable (`stuck`, error)
11. Mark the worker as `merged` (or `done` if `.garden-done` is present at the worktree) in the registry

The worker and its worktree are not automatically cleaned up on merge. Cleanup happens only when the user kills the worker with `opt-x` or runs `garden reset`. This allows inspecting merged work before disposal.

Projects don't block each other — each project has its own poller and merge queue.

### Auto-Continue Across the Merge Boundary
Multi-phase work (build → review → merge → keep building) used to require the operator to type "please proceed" after every merge. Garden eliminates that step: `finalizeMerge` ends with a call to `maybeAutoContinue`, which dispatches a delayed `_continue-worker-after-merge` subprocess that sends a "previous changes were merged, continue with the next phase" prompt to the worker pane.

The worker opts out by writing the sentinel file `<worktree>/.garden-done` before ending its turn. The worktree system prompt and the `done` skill instruct every worker, before writing the sentinel, to re-read the operator's original request and confirm each deliverable they asked for has landed in a merged commit and is verified working — explicitly distinguishing the operator's deliverables from the internal stages of any analysis or workflow the worker ran (research, design, implementation, a review or verification pass), which do not count, and treating "I feel finished" as insufficient evidence. This gate exists because the decision rests on the worker's own (and possibly context-compacted) memory of the request — garden keeps no durable copy of it for default workers — so deep or long-running workers were observed declaring done while a named deliverable was still unlanded or merely pushed-but-unverified. The bias remains toward stopping over inventing busywork: a worker must never fabricate "while we're here" scope to justify continuing. If the sentinel is missing on merge, garden assumes there is more to do and re-prompts.

Workers are nudged to invoke the sentinel-write via the `done` skill installed under `<worktree>/.claude/skills/done/SKILL.md` (see `src/dashboard/skills.ts`). Claude Code requires the directory + `SKILL.md` layout for project-skill discovery — a flat `done.md` at `.claude/skills/` is silently invisible to the planner. Skill descriptions act as Claude's trigger condition during planning — Claude evaluates "should I invoke this?" alongside its other tools when deciding the next action — which is more reliable than instructions buried in the system prompt. The skill body (when, when-not, mechanics, recovery) lives only in the skill file, not the main worktree-rules block, so the prompt stays scannable. The bootstrap script inlines the skill content at worker creation; the harness adapter's `installRuntimeConfig` rewrites it on every refresh/bounce so workers from rebuilds pick up content changes. Older workers created before the skill existed do not get it retroactively without a refresh — bouncing or recreating them is the only way to install it.

A second skill, `handoff`, lives alongside `done` and lets the operator pass a task to a fresh worker on another (or the same) project. Triggered when the operator instructs the worker to hand off; the skill body teaches the heredoc recipe `garden handoff <project> <<'EOF' ... EOF`. The CLI command writes the briefing to `~/.garden/sessions/seeds/seed-*.txt`, then submits a JSON request file under `~/.garden/sessions/handoff-requests/<id>.req.json` and pokes one or more project pollers. The pollers run in unsandboxed tmux windows; on wake they call `processPendingHandoffs` (`src/dashboard/handoff-dispatch.ts`), which atomically claims each request via `rename(*.req.json → *.req.json.processing)` and calls `newWorker({ projectName, seedMessageFile, background: true })`. The `--ultracode` flag threads a `ultracode: true` opt through the same request file into `newWorker`, which pins the child to Opus (`entry.model`) and stamps `entry.ultracode` so the harness `buildAgentCommand` renders `--effort max --settings '{"ultracodeKeywordTrigger":"on"}'` on every launch/resume/bounce — the operator's "hand this off to an ultracode worker" with no manual escape-edit-continue. The dispatcher writes a response file the CLI polls for (up to 15s) so the operator-facing line "Handed off to <project>/<worker>" still prints the real worker name. The request-file detour is load-bearing: the CLI runs inside the source worker's Claude Code OS sandbox, which blocks the tmux server socket (`/private/tmp/tmux-*/default` → "Operation not permitted"), so the CLI cannot create tmux windows itself. Routing through a poller — which lives outside the sandbox — gets the tmux ops done while keeping every disk write inside the sandbox-allowed `~/.garden/sessions` tree. The `background:true` flag remains load-bearing inside `newWorker`: handoff must not yank the operator out of whatever pane they're focused on, so the new worker is born hidden and `newWorker` skips the cross-project active-project/plot switch, the park-to-hidden of the visible pane, and the restore-from-hidden swap that the ⌥n hotkey path uses. The operator's `activePaneType`/`activeWindowName`/`activePaneId` stay exactly as they were; the dashboard refresh picks up the new worker in the status pane, and the operator reaches it via ⌥<n> on the target project + ⌥w to cycle. A delayed `_seed-worker` subprocess polls until the worker's `agentStatus` leaves `loading` and then sends the seed prompt prefixed with `[handoff from <source-project>/<source-worker>]`; pane resolution falls back to `windowExists` when the seed fires, so a hidden worker still receives its briefing. The source worker writes `.garden-done` itself (per the skill recipe) rather than having the CLI command do it implicitly, mirroring the `done` skill's recipe-style instructions and leaving room for a final commit before handoff.

Handoff callbacks (opt-in via `--expect-callback`) close the parent → child → parent communication loop. When the source worker passes `--expect-callback`, the CLI captures `$GARDEN_PROJECT`/`$GARDEN_WORKER` and threads `expectCallback`/`parentProject`/`parentWorker` through the request file into `processPendingHandoffs`, which stamps `parentProject` + `parentWorker` + `handoffCallbackExpected` onto the child's `WorkerEntry`. The dispatch chokepoint is `transitionState` (`src/dashboard/poller-state.ts`): every poller-driven PrState write flows through it, so terminal transitions to `merged`/`done`/`failing` are detected in one place regardless of which poller (review, merge, resolve) triggered them. One terminal write does NOT go through it — the Stop hook's trail-off `done` (`hooks/default.ts` writes `prState: "done"` via `updateWorkerFields` when a worker sets the sentinel with no commits ahead), so a callback-expecting child that finished without ever merging would leave its parent waiting forever. `handleDone` (the poller-context landing that same hook pokes) therefore calls `maybeFireHandoffCallback` on the quiescent-done leg as the poller-side sibling of the chokepoint. On the first terminal write for a callback-expecting child — from either site — `maybeFireHandoffCallback` sets `handoffCallbackFiredAt` under the registry lock (idempotency guard against replayed terminal events and against `handleDone` running on every poke of a quiescent worker) and lazy-imports `notifyHandoffCallback` from `continue.ts` to paste a one-shot `[garden] Handoff callback: …` prompt into the parent's pane. `notifyHandoffCallback` reuses `continueWorker`'s pane-resolution and claude-status gate (working/asking → silent no-op), so the callback can't stomp on a parent that has already moved on or is mid-turn. The child can stage a freeform note at any point before its terminal state via `garden reply -m "<text>"` (or stdin/heredoc); the note is stored on the child's own `WorkerEntry.handoffReplyNote` field and folded verbatim into the callback prompt. Multiple `garden reply` calls accumulate (blank-line-separated); `--replace` clobbers an earlier draft. Callbacks are opt-in by design — default handoff behavior is unchanged, so fan-out handoffs (where the parent doesn't care about results) and pass-the-baton handoffs (where the parent calls `done` immediately) both work exactly as before.

The sentinel lives at the worktree root because that is the only path satisfying all three constraints: (1) writable by Claude Code's harness sandbox, which blocks raw `/tmp` writes — only `$TMPDIR` works there; (2) writable by the OS-level Seatbelt sandbox (`src/dashboard/sandbox.ts` `DEFAULT_ALLOW_WRITE`), which permits the worktree, `~/.npm`, `~/.cache`, and `/tmp`; (3) reconstructible by the poller from the registry entry's `worktreePath`. `$TMPDIR` falls out on (3) because it is per-Claude-session. `~/.garden/sessions` falls out on (2). The worktree is the intersection. As a side effect, `killPane` no longer needs explicit sentinel cleanup — `git worktree remove --force` in `backgroundGitCleanup` removes the file along with the worktree. Workers are instructed not to commit the file (it is per-worker state, not project state).

Skip conditions (logged at `debug`):
- The `.garden-done` sentinel exists for this worker.
- The `.garden-awaiting-input` sentinel exists — a mid-task worker paused at a human gate (the botanist/plan workflows). Unlike `.garden-done` this does not mean "finished"; the resume is the operator's next prompt, which clears the sentinel via `UserPromptSubmit`.
- `agentStatus` is `working` or `asking` — the operator is already typing, same guard the interrupt-recovery path uses.
- `lastAutoContinueAt` is within the idempotency window — 10 seconds for the merge-time dispatch (guard against merge-event replay), 60 seconds for the gate-reopen sweep (guard against double-pasting a delivery still in flight).

The merge-continue prompt includes contextual preambles when applicable: a stale-files list when the reviewer modified files, a manual-sync nudge when the worktree could not auto-sync, and a postMerge acknowledgement when the project has a `postMerge` hook configured (so the worker does not redundantly suggest the operator run build/install steps that already ran).

Both autocontinue prompts (post-merge and interrupt recovery) lead with a branch-identity line naming the worker's own branch and base and forbidding any rebase/merge/reset/checkout onto another worker's branch. Every worker runs in a worktree of the *shared* project repo, so a sibling worker's branch — and its `origin/<branch>` tracking ref — is visible in `git branch -a` from this worktree. The prompt previously named no branch, and a worker on a multi-worker project rebased onto a sibling's branch when it tried to "continue on the merged base"; pinning the branch in the prompt (`branchIdentityLine` in `continue.ts`) removes that ambiguity. The base-sync operations the manual-sync nudge relies on (`git reset --hard origin/<base>`) stay allowed — only sibling worker branches are off-limits.

A successful dispatch logs at `info` (`auto-continued worker after merge`) so the operator sees the lifecycle transition in `⌥l` logs alongside the `merged` line. The post-merge dispatch fires a 5s primary plus a 16s retry (`_continue-worker-after-merge-if-stuck`): the 5s delay lets postMerge and the reviewer's force-push settle before keys land in the pane, and the retry recovers the case where the worker still read as `working`/`asking` at the 5s mark (e.g. mid-turn on a long response), under which the single-shot prompt would otherwise be lost with no recovery. The retry re-fires only when `prState` is still `merged` — a delivered prompt fires `UserPromptSubmit`, which clears `merged`, so any other state proves the prompt already landed and the retry no-ops rather than double-prompting. The interrupt-recovery dispatch uses the same shape (6s primary + 16s retry) to absorb the slower TUI bind under dashboard-rebuild load.

**Operator-draft deferral.** The `agentStatus` gate above catches a worker that is *already running*, but not one that is idle while the operator is mid-compose — text sitting unsent in the Claude input box. Pasting then would concatenate garden's prompt onto that draft and submit the mangled result. Every delivery path (interrupt recovery, post-merge, handoff callback) funnels through `continueWorker`, which therefore inspects the pane before pasting: `capturePaneText` reads the visible pane, `capturePaneCursor` reads the caret position, and `extractOperatorDraft` returns the operator's draft as the span between the prompt marker (`❯`, U+276F) on the bottom-most input line and the cursor column. A non-empty result means an unsent draft, and `continueWorker` skips the paste (leaving `interruptedWhileWorking` set, since the prompt is still owed). The cursor bound is load-bearing: an *empty* box is not blank — Claude Code paints dimmed ghost/placeholder/autosuggest text into it, and `capture-pane` strips the dimming, so the bare text after the marker can't distinguish a suggestion from a draft. The caret can: it sits at the end of typed text with any suggestion rendered to its right, so the marker-to-cursor span is empty for a ghost-only box and exactly the typed prefix when a partial draft is followed by a completion. A caret on a row below the marker means the draft wrapped (non-empty); a caret above it is not on the input line (no draft). The capture therefore drops `-J` so its row indices stay aligned with `cursor_y`. When the cursor is unreadable (pane unreachable), `extractOperatorDraft` falls back to the whole post-marker remainder — the conservative pre-cursor behavior — but in that state `capturePaneText` is also empty, so it resolves to "no draft" anyway. On a draft-deferred skip, the two primary dispatch legs (`_continue-worker`, `_continue-worker-after-merge`) re-arm via `rearmContinueIfDrafting`: a fresh detached child every 12s, threading an `--attempt N` counter, until the box clears or `MAX_DRAFT_RETRIES` (15, ≈3 min) is hit. Re-arm fires only while a draft is still present, so an `agentStatus`-caused skip (empty box) falls through to the existing `*-if-stuck` leg instead, and a delivered prompt — whose paste transiently fills the box — is not mistaken for a draft because the handler keys re-arm on the delivery result, not a re-capture. The merge path's gate-reopen sweep remains the long-tail backstop past the retry cap.

`garden pause <worker>` writes the sentinel; `garden resume <worker>` deletes it. Killing a worker (`opt-x`) removes the worktree entirely, so the sentinel goes with it.

A second, *global* opt-out lives alongside the per-worker sentinel: a gate in `~/.garden/config.yml` under `autoContinue` (`enabled`, `usageThreshold`, `resumeAfterReset`). Defaults are enabled, 95% threshold, no auto-resume. The gate is consulted on every `maybeAutoContinue` after the per-worker checks. The threshold check evaluates the `5h` and `weekly` meters from the latest usage snapshot; the model-scoped weekly meters are intentionally excluded since the workhorse is Opus. When any included meter is at or above `usageThreshold`, the gate flips `enabled=false`, persists `pausedUntil` (the latest `resetsAt` among tripped meters, so re-enabling does not immediately re-trip on the slower-resetting meter) and `pausedReason`, and fires a warn-level alert (source `usage`). With `resumeAfterReset: true`, the next call past `pausedUntil` flips `enabled` back on automatically; with it off (the default), the operator must run `garden auto on`. Manage with `garden auto [on|off|status|threshold <N>|resume-on-reset on|off]` (alias `auto-continue`).

The usage-triggered closures are per-project. The meters describe one token pool — the default Claude account (Keychain / `~/.claude`) — so a project whose workers draw from a different pool is exempt from them: a third-party `provider`, or a `claudeProfile` whose configDir resolves to something other than the default `~/.claude` (a separate Claude subscription). `autoContinueGateReason` takes the project name; for an exempt project it bypasses `usage-paused` and skips the meter evaluation entirely — no read, no trip side effect — so an exempt worker's merge never flips the global gate or fires the usage alert; the threshold trip fires from the next metered project's check, where it describes tokens that worker actually consumes. An explicit `garden auto off` (`enabled=false` with no `pausedUntil`) still blocks every project — that closure is operator intent, not a meter reading. The exemption falls out of facts already in config (`projectUsageGateExempt` in `src/config.ts`, mirroring `workerEnvPrefix`'s pool selection and failing closed on an unknown project, a configured-but-unresolvable `provider` (which, like the launch path, falls back to the first-party pool), or an unresolvable profile reference — the gate then applies); no new config keys. Deliberate trade-off: exempt projects run without usage protection, since garden does not meter non-default pools. The same project-scoped gate governs holistic-review dispatch (`poller-holistic-review.ts`) — the interposed review runs headless on the project's own profile/provider env, so the same pool reasoning applies.

A gate block does not lose the prompt. `maybeAutoContinue` is one-shot at merge time, so a worker whose continue was blocked parks in `merged`; the merged-state handler (`handleMerged` in `src/dashboard/poller-merge.ts`, shared by every workflow) replays the same auto-continue decision on each poller poke — the gate-reopen sweep. The first poke after the gate reopens (manual `garden auto on` or `resumeAfterReset` firing) delivers the stranded prompt; the sweep also fires the auto-resume check itself, so `resumeAfterReset` does not need a fresh merge to take effect. The poke is guaranteed even on a fully idle garden: `garden auto on` and `garden auto resume-on-reset on` wake every project poller directly, and the usage poller pokes all pollers when it observes that a paused window with auto-resume armed has passed (`pokeOnGateReset` in `usage-poller.ts`). Sweep-specific guards: a 60s idempotency window (wider than the 5s/16s delivery legs, so an in-flight merge-time dispatch is never double-pasted — this also recovers prompts whose paste was silently lost), gate blocks logged at info, and `claudeStatus: "exited"` workers skipped (no live Claude pane to paste into; reviving one is bounce territory). The intended one-hour `gateBlockLoggedAt` throttle is a module-level map and therefore resets with every one-shot poll process; the info line can currently appear once per poke. A gate-closed strand is surfaced three ways: that info log, a yellow `gate closed` suffix appended to the `merged` row in the status pane (`formatGateSuffix`, `src/commands/status.ts`), and the `auto-cont.` line in `garden whoami` (`formatAutoContinueLine`, `src/commands/whoami.ts`) reporting the gate state (on / OFF + pause reason). Both surfaces mirror the per-project exemption: on a usage-triggered closure, an exempt project's merged rows carry no `gate closed` suffix (`gateHoldsProject`, `status.ts` — they auto-continue and never strand) and its `whoami` line reads green `on` with a separate-token-pool note (JSON adds `usageGateExempt`); on an explicit `garden auto off`, both report closed for every project.

### Sibling Merge Notification
When code merges, the poller compares the changed files against every other active worker's branch in the same project. If files overlap and the sibling has a live Claude session, it is notified via `tmux send-keys` with the merged worker's commit summary and overlapping file list so it can review and avoid reverting the merged work. Dead workers are skipped — they will hit rebase conflicts naturally on their next review cycle.

### Claude Usage Meter
Two or more quota bars render in the top-left "garden" title pane sitting above the status pane: the 5-hour rolling window, the weekly total, and one bar per model-scoped weekly meter (labeled by the model — `fable` on current plans). Bars are colored by utilization — green <60%, yellow <85%, red at or above — with a bright `│` marker overlaid at the current time position in the window (so you can see whether usage is ahead of or behind the clock) and the reset countdown next to each. The model-scoped bars come from the response's `limits[]` array (the `weekly_scoped` entries, each tagged with `scope.model.display_name`), so the bar auto-tracks whatever model Anthropic scopes without a code change; the older flat `seven_day_sonnet`/`seven_day_opus` keys are now null. When the response carries no `weekly_scoped` entry, no model bar renders (the pane is just the two flat bars); a rolled-over window renders `—` for that entry. A scoped entry the account has not touched since the weekly reset is still served, as `is_active: false` / `percent: 0` / `resets_at: null` — the window has not opened, so there is no countdown to draw. That is a true 0% reading, so the bar renders at 0% with no reset text and no time marker rather than being dropped: the alternative made the `fable` bar vanish from the pane at every weekly reset and reappear only on first use, which reads as a broken meter.

When the account has pay-as-you-go extra usage enabled, the response's `extra_usage` bucket is surfaced as a dim credit footer under the meter bars (`extra  1234 / 5000 credits (25%)`) — an absolute credit tally, not a resetting time-window meter, so it renders as text rather than a fourth bar and is hidden entirely when extra usage is off. The same line appears in `garden usage`. A null/uncapped `monthly_limit` degrades to whatever fields the endpoint returns (`1234 credits used`).

Data comes from two sources split by cadence — the same design Claude Code itself uses — both authenticated with the OAuth token Claude Code writes to the macOS Keychain under service `Claude Code-credentials`. The **primary** source (every poll) is the `anthropic-ratelimit-unified-{5h,7d}-{utilization,reset}` headers that ride *every* `/v1/messages` response; garden reads them off a 1-token throwaway completion (`{model: haiku, max_tokens: 1, messages: [{role:"user", content:"quota"}]}` — `fetchUsageHeaders` → `parseUnifiedHeaders`). These carry the 5-hour and weekly bars, are documented/supported, and are governed by the generous messages limiter, so they essentially never throttle at garden's cadence. Utilization is a `0..1` fraction (scaled to percent) and the reset is unix epoch seconds. The **secondary** source (at most hourly) is `GET https://api.anthropic.com/api/oauth/usage`, the undocumented endpoint that is the *only* carrier of the model-scoped weekly bar (`fable`) and the extra-usage credit tally. That endpoint is strictly rate-limited — its limiter tightened server-side around 2026-07-10 to a fixed `Retry-After: 3600` with a sustained budget near 10-12 requests/hour. Both the scoped fetch and the primary header probe authenticate with the same OAuth token, so they draw on a shared per-token budget: a scoped call can burn budget that then collaterally 429s the next primary probe. To keep that pressure off, the scoped fetch is gated on *actual scoped-model use* — `fetchScopedIfDue` asks `scopedModelInUse` (which reads the registry) whether any live worker is running a scoped model, matching a worker's effective model against the last-seen scoped labels (default `fable`) with a fresh `lastEventAt`. The effective model is read from the worker's transcript (`readLatestTranscriptModel` — the newest assistant message's `model`), not from `WorkerEntry.model`: that field holds only an explicit pin (`workers new --model`, a project or crew default), and a worker spawned without one runs the account default, which the registry cannot name. Reading the pin alone made a fleet running entirely on the account-default Fable report as idle, holding the scoped bar on the 12h keepalive indefinitely; the pin is still preferred when present, and a worker whose model cannot be resolved counts as not-scoped. While a Fable worker is going the scoped bar refreshes hourly; when none is, it drops to a slow 12h keepalive (the 7-day scoped figure isn't moving anyway), removing ~22 of every 24 daily oauth calls on an idle fleet. A scoped 429 is silent for the *primary* bars — they're already live from headers, so the scoped bar just keeps its last value until the next refresh (`scopedFetchDue` gates on the last *attempt*, so a 429 waits a full interval rather than re-firing each poll). It is *surfaced* on the scoped row's health tag (`Fable meter rate-limited`) only when a Fable worker was active or the operator forced the refresh — i.e. when that bar is consequential; an idle-keepalive miss stays fully silent. The failure is tracked as `scopedError` on the snapshot and cleared on the next scoped success. Credential discovery probes the `GARDEN_CLAUDE_SESSION_KEY` env var first, then the macOS Keychain, then `~/.claude/.credentials.json`. When the stored access token has expired, the meter exchanges the refresh token against `https://platform.claude.com/v1/oauth/token` (the same endpoint Claude Code uses) and persists the rotated tokens back to the source so claude CLI's next read stays in sync — otherwise the meter would silently revoke claude CLI's cached refresh token and force the operator to re-login. A revoked refresh token (`invalid_grant`) is surfaced as `login expired` and held off the API for `AUTH_BACKOFF_MS` until `garden login` heals it. On any other failure the snapshot records a short error and the pane renders a single dim "claude usage: …" line instead of bars — the meter is a progressive enhancement, not a dependency. Fetched snapshots live in `~/.garden/sessions/claude-usage.json`; the snapshot tracks `dataAt` (primary-bar freshness, drives the stale tag) separately from `scopedAt`/`scopedAttemptedAt` (the scoped bar's own freshness and cadence), so the intentionally-slow scoped bar never trips the stale warning. Because that suppression also hides a genuinely rotting bar, the scoped row annotates itself with its own age (`· 11h old`) once `scopedAt` exceeds the hourly active cadence plus a 30-minute margin — an actively-metered row never shows it, an idle-keepalive one reads as throttled rather than broken.

Refresh is timer-driven with an event-driven backstop. A singleton poller (`_garden-usage-poller`) refreshes every 10 minutes and claims with its own cadence class, so a freshly respawned poller (dashboard restart) skips instead of firing an immediate fetch against a still-fresh snapshot. The per-poll cost is one tiny `/v1/messages` request (144/day, a rounding error against a Max plan); the throttled endpoint is touched only on the scoped refresh (hourly while a Fable worker runs, every 12h otherwise). Every Claude Code `Stop` hook calls `maybeRefreshUsage()` — a fire-and-forget detached fetch gated by a cooldown slightly *above* the poller cadence, so it only fires when the poller has missed its window (window killed, machine slept) rather than adding traffic alongside a healthy poller. The header call rarely 429s (only when the account itself is at its cap, or when the shared OAuth-token budget is exhausted by scoped calls), but if it does the stored backoff is the server's `Retry-After` plus a 15-minute margin, doubling on consecutive 429s (capped at 4 hours), and both paths honor it; the pane's health tag shows the countdown labeled as the account meter so it isn't mistaken for a scoped miss (`account meter rate-limited, retrying in 1h 10m`).

**Build staleness (bottom bar).** `garden 0038f10` reads equally authoritative whether the build is current or three weeks stale, which is exactly how a frozen install goes unnoticed. The bar now qualifies it: when the running build trails its branch, `⚠ N behind` appears left of the version and the whole status bar turns yellow instead of the default green (`statusBarStyle`, `alerts.ts`). Color is the at-a-glance signal — the bar changes without being read — and the count is the detail.

The number is `<build-sha>..origin/<branch>` counted in `gardenInstallRepo()`: the repo the running binary was compiled from, resolved from `argv[1]` via `realpathSync` (which follows the npm-link symlink `bin/garden -> <repo>/dist/cli.js`). Deliberately the *install* rather than the registered `garden` project — the install is what goes stale, and it is reachable whether or not the operator registered it. There is no fetch; it reads the local `origin/<branch>` ref, which `fastForwardBase` advances on every merge, i.e. the same cadence the answer can change on.

It is computed on the watchdog's 5-minute throttle and cached in `DashboardState.buildBehind`, never at render time: `formatRightBar` runs on the hook firehose, so a `git rev-list` per call would mean a subprocess per tool use. State is already read on every refresh, so carrying the number there is free. A build that cannot be measured — a `dev` build, or an install outside a checkout — leaves `buildBehind` null and the bar green; garden does not warn about drift it never established.

The compared-against branch is garden-level (`build.branch` in `~/.garden/config.yml`, `getBuildBranch`, default `main`), since the install is machine-wide rather than per-project. It is set from the `⌥;` garden settings menu's *build branch* row; the submenu enumerates the install repo's own branches via `listBranches` rather than offering a hardcoded main/dev pair, falling back to those two only when the install is not in a checkout.

**Codex meter (second column).** When Codex is in the fleet in any role, a second meter renders in the empty space to the right of the Claude bars — Claude keeps its full-width fit, Codex fills the remainder (`renderCodexColumn` in `usage.ts`, sourced from `codex-usage.ts`). Codex writes a `rate_limits` object into its rollout JSONL (an `event_msg` payload carrying `primary`/`secondary` rolling windows plus a credits balance — the same shape as Anthropic's quota response), so garden needs no new auth or endpoint: the data is already on disk.

The two-column meter block is bounded by matching full-width grey rules: the labelled header rule above and an unlabelled closing rule below. A blank row clears the meters from the header underline; the closing rule's otherwise-empty row supplies the bottom clearance.

Capture is **role-agnostic**, and deliberately so. Every Codex process spends the same quota, but only an interactive Codex *worker* fires garden's lifecycle hooks — the headless reviewer, resolver, and ci-fix agents (`launchHeadlessAgent`) do not. The original implementation captured at `Stop`-hook time from the worker's `transcript_path`, which meant a project on the `claude-codex` crew (Claude builds, Codex reviews) burned Codex quota on every review and showed no meter at all. `captureCodexUsageLatest` instead reads whichever rollout under `$CODEX_HOME/sessions/YYYY/MM/DD` is newest by **mtime** (not by name — a long-running worker's rollout keeps being appended, so it can hold a fresher reading than a newer-named short run), which covers every role and any role added later from one call site. The descent takes the lexicographically largest entry at each level and backtracks when a branch holds no rollout files, so an empty day dir just after midnight falls through without walking the year-deep tree.

Codex emits `rate_limits` on every turn but populates it only periodically: the common on-disk shape is `{ primary: null, secondary: null, credits: { balance: null, unlimited: false } }`. That is **not a reading** — counting the truthy-but-empty `credits` object as one produced a `windows: []` snapshot that renders as nothing *and* overwrote a good prior one. Both the backward line scan within a rollout and the choice of rollout skip such entries, falling through up to `MAX_ROLLOUTS_TRIED` (5) rollouts back before giving up; a short reviewer run routinely ends without ever getting a populated reading while a sibling from the same day holds dozens.

Reading the rollout is **passive**: it can only ever be as fresh as the last time Codex actually ran. A fleet that runs Codex occasionally therefore sits on a reading captured days ago — and if the operator changes plan in between, that reading is not merely stale but a percentage of a quota that no longer exists (observed on a real upgrade: `limit_id` moved `premium` -> `codex`, `plan_type` appeared as `plus`, and the window moved from 43200 to 10080 minutes, so the displayed 91% was arithmetic against a different denominator). `probeCodexUsage` is the active half — a minimal `codex exec` run purely to make Codex report its quota, the direct analog of the Claude meter's 1-token `/v1/messages` completion. It uses a read-only sandbox and a temp cwd so it can never touch a worktree, `--skip-git-repo-check` because that cwd is not a repo, and closed stdin because `codex exec` reads instructions from stdin when the prompt argument is absent and would otherwise block forever. A failure (offline, codex absent, out of quota) is non-fatal and still captures: the out-of-quota case writes a rollout on its way down.

Because the probe spends real quota, every caller gates on `codexInFleet()` — true when any project sets `harness: codex` or any `roles.{reviewer,resolver,ciFix}.harness: codex`, or any registered worker carries a codex harness or a crew name containing `codex`. Call sites split by who initiated them. The **ambient** ones fire on a cadence garden does not control and must go through `probeCodexUsageIfStale`, which adds a `CODEX_PROBE_INTERVAL_MS` (6h) snapshot-age gate on top of the fleet gate: the watchdog tick (which also keeps an outer 6h throttle so the two gate reads stay off the 60s tick, advanced unconditionally once it opens so a probe that captured nothing is not retried a minute later), and `garden dashboard _usage-refresh` — which is not an operator command but the Claude Code Stop hook's usage backstop (`maybeRefreshUsage`), re-firing on every hook while the usage poller is down, so an ungated probe there would spend quota per hook rather than per plan change. The **explicit** call site is `garden usage refresh`, which probes outright: the operator asking is itself the reason, exactly as that command already forces past the auth/error backoff. It probes before the `anyAnthropicMeteredProject` gate, since Codex is a separate pool and a provider-only fleet still has a Codex meter to refresh. A fleet actively running Codex is fed for free by the passive capture and never probes; the watchdog's throttle timestamp is seeded to process start so a respawn cannot be used to trigger one. `PROBE_TIMEOUT_MS` (30s) is deliberately kept under the watchdog's `SLEEP_SLACK_MS` (60s): the probe runs synchronously in the watchdog loop body, and that loop reads its own iteration overrun as machine-suspend time, so a probe allowed to block for a full slack window would be misread as a suspend and discount a minute from every live review's timeout.

The capture is driven from the **watchdog** tick (`watchdog.ts`), not the usage poller: the watchdog is the fleet's one unconditional recurring tick, whereas `startUsagePoller` is gated on `anyAnthropicMeteredProject()` — hanging it there would leave an all-Codex fleet with no meter. It writes only when the reading actually moves (so an idle fleet never churns the file) and repaints the title pane via `refreshDashboard()` only on that change. The snapshot is cached to `~/.garden/sessions/codex-usage.json`. Each rolling window renders as a bar labelled by duration (`5h` / `week` / `30d`, from `window_minutes`); windows sort smaller-first to mirror the Claude meter's 5h-over-week ordering; a subscription account typically reports only the 30d (`window_minutes=43200`) window. A pay-as-you-go credit balance renders as a dim `credits $NN.NN` (or `unlimited`) footnote below the bars — only when there is a balance to watch: a zero balance is the steady state for a subscription account with no credits, so a permanent `$0.00` row would carry no information and is omitted. Like the Claude bars, a window whose reset time has already passed renders `—` rather than a stale percentage. The whole second column is gated on a captured Codex snapshot with at least one window existing, so a fleet that has never run Codex leaves the pane byte-for-byte unchanged. The gate is the rollout on disk, not garden's own registry: reading `$CODEX_HOME/sessions` is what makes the capture role-agnostic, and the same breadth means an operator who runs Codex *outside* garden will see the column on an all-Claude fleet. That is the intended trade — the meter reports the operator's Codex quota, which is one pool no matter who spent it. The two-column layout also downgrades to single-column Claude when the pane is too narrow to fit a second column (data stays captured and reappears once the terminal is wide enough). Spacing is computed, not fixed: the Codex column is rendered first at the minimum `COLUMN_GAP` (measuring it with the most room it could have), then pushed right by whatever slack remains, holding back a `RIGHT_MARGIN` equal to the left `INDENT` so the content sits inside symmetric margins instead of bunching left with a ragged empty right. Because the widening only ever consumes measured leftover, it cannot overflow the pane. `MAX_COLUMN_GAP` caps it — past that the columns stop reading as a pair and start reading as two unrelated things at opposite edges, so on a very wide pane the extra slack is left on the right. The two-column path also keeps the leading blank line rather than spending it on the column-header row, which had put the headers hard against the pane border; the pane auto-sizes to its content, so that row costs only the space it exists to provide (the single-column all-Claude render is untouched). Each `claude`/`codex` label is underlined across the full width of the column it heads (`columnHeader` in `usage.ts` — the name bold, the rule plain, emitted as two SGR runs that pin the SAME explicit grey, since a bold run leaving the color unset inherits the default foreground and renders bright white against the grey rule it continues into; weight is the only difference between the two runs). A blank row separates that rule from the meters because terminal underlines sit at the bottom of their cell and otherwise butt directly against the first bar; whole rows are the terminal's smallest spacing unit. Unlike the Claude meter there is no network poller — the snapshot advances on the watchdog's tick by re-reading the newest rollout on disk, so between Codex turns it shows the last-captured value.

### Alerts
The dashboard surfaces important events as alerts — persistent messages that require operator attention. Alerts are stored atomically in `~/.garden/sessions/dashboard.alerts.json` (same write-tmp-then-rename pattern as other state files), capped at 100 entries.

**Events that generate alerts:**
- Worker bootstrap could not fast-forward main checkout (stale main, dirty worktree)
- Review process failure (Claude unavailable, timeout, unparseable output)
- Reviewer or resolver exceeded the 60-minute wall-clock cap and was killed (typically a hung subprocess — e.g. tests with no timeout blocked by the sandbox — wedging the state machine)
- Reviewer could not fix issues (FAILED verdict)
- Merge failure
- Force-push failed after a passing review, in the merge queue, or after conflict resolution (source: `poller`, level: `warn`; deduped per worker via `push-failed:<project>:<worker>`). The worker is re-armed for a fresh review (`pendingReviewAt` + a 30 s delayed poke) rather than stranded, so a transient failure self-heals and a persistent one stays visible
- Local base ref could not be advanced after merge — only when it diverged from origin with real local-only content (warn), is checked out in another worktree (warn), the on-base checkout is dirty (warn), or it is wedged/unfetchable (`stuck`, error); a clean off-base ref advance and an auto-healed redundant local commit are both silent. Each alert fires only on entry into the state, not every merge cycle
- Repeated failures (3+ consecutive failures on the same worker)
- Base-branch drift after worker creation (Stop hook cannot count commits against `origin/<pinned-base>`; deduped to one firing per worker per hour)
- Auto-continue auto-disabled by usage threshold (source: `usage`, level: `warn`)
- `.garden-done` tracked in HEAD of the project main at worker spawn (source: `create`, level: `warn`; deduped per project per hour).
- Orphaned worker window: a live tmux worker window with no registry entry (the create/sweep race casualty; source: `watchdog`, level: `warn`; deduped per orphan per hour).

Worker "needs operator input" events (AskUserQuestion, ExitPlanMode, auto-mode permission prompts) do **not** fire alerts — they flip the worker to `asking` (yellow row in the status pane), which is the visual signal. The alert channel is reserved for failures and errors.

**Visibility:**
- Bottom bar shows a red `⚠ N alerts — ⌥a to clear` badge on the right when unread alerts exist. The badge appears instantly on `addAlert()` via `tmux set-option @garden_right` + `refresh-client -S`.
- Every alert is also streamed to `dashboard.log` at its declared level (`warn` or `error`), so it appears live in the `garden logs --follow` pane (the `_garden-logs` window) with the `[!]` prefix.
- Pressing `⌥a` focuses the alerts view **and** acknowledges all current alerts, clearing the badge (the bar badge and every project header's `⚠n`). Acknowledgement is explicit — an alert that fires while the alerts pane is already focused still lights the badge, so autonomous failures aren't silently missed when the user is away.
- The alerts view is a passive SIGUSR1 repaint pane (`_garden-alerts`), the same pre-baked-file shape as the history and usage panes: `writeAlertsRendered` (`header.ts`) bakes `alerts.rendered` from `renderAlertsPane` (`commands/alerts.ts`), which shares the store, split, and glyph vocabulary with the `garden alerts` CLI but lays each alert out for the narrow pane — a `glyph age location` header line with the message wrapped beneath. Alert messages are not authored for display — they splice in raw git stderr (multi-line) and raw agent markdown (the reviewer alert embeds 300 characters of a model's reply verbatim) — so both surfaces run the message through `condenseMessage` first: fenced blocks dropped, headings/emphasis markers stripped, and every embedded newline collapsed to a space. Without it those newlines escaped the gutter and rendered at column 0, visually running one alert into the next. The pane then caps the message at three wrapped lines; the store and `garden logs` keep it verbatim. Read alerts dim only their gutter, not the message — the message is what the operator opened the view to read, and the section header plus dim gutter already say "seen". Both surfaces run chronologically top-to-bottom (read section then unread, oldest first within each): the render prints from the top, so an overflowing list scrolls its oldest alerts into tmux scrollback and leaves the newest on screen — the operator reads down to the latest instead of scrolling up for it.
- Acking on entry would erase the unread/read split at exactly the moment the operator looks at it, so the split is driven by `state.alertsSeenMark` — the seen-time snapshotted *before* the ack — and holds for as long as the view is open. Pressing `⌥a` again re-snapshots (now the entry ack), folding those alerts into read: the second press means "I'm done with these", which is why an already-focused view still does this work instead of early-returning. Leaving the view clears the mark, so the next visit shows them read.
- The bake is deliberately NOT wired into `refreshDashboard`, unlike its `writeHistoryRendered` sibling: `refreshDashboard` is in `dist/hook.js`'s import closure, so calling it there pulls `renderAlertsPane` (and `commands/logs.ts`, for `wrapDetail`) into the lean hook bundle on every hook fire's cold start — measured at +2.8KB, versus +260 bytes when esbuild can tree-shake it out. Its CLI-bundle callers are `focusAlerts` (entry), `refreshStatusElapsed` (the watchdog's 60s tick, which advances row ages and picks up poller-raised alerts), and `rebakePanesOnResize` (which re-wraps the view to the resized pane width). Ambient alerts are therefore up to one tick late *in the pane* — the same latency the status pane's per-project `⚠n` counts already have, and the bar badge is instant regardless.
- `garden alerts` lists full history split into unread (added since the last `⌥a` acknowledgement — `lastSeenAt`) and read, with per-level glyphs (`✖` error / `⚠` warn) and relative age; `garden alerts clear` wipes the store.

### Worker Isolation Model
- Every worker operates in its own git worktree — no shared working directory
- The project shell (`⌥s`) stays on the main checkout for manual work
- Branch name equals the worker name (e.g., `swift-oak`)
- Worktrees persist until the worker is killed, enabling the review cycle and manual inspection
- Every agent-CLI-specific decision (the launch command dialect, the `.claude/settings.json` runtime config below, headless invocation, transcript reading, prompt delivery, transient-error shapes, session identity) lives on the harness adapter registry in `src/dashboard/harness/` — `claude-code` is the default adapter; a second adapter (`codex`) is reachable as a **reviewer/resolver/ci-fix** via per-role resolution (`garden config <p> role reviewer harness codex`; see `resolveReviewRole` in `src/dashboard/roles.ts`) and as a **worker** via `garden workers new <p> --harness codex` (default workflow only). Session-id capture, history/continue routing, and status-pane activity summaries for a Codex worker are wired — the hook captures Codex's self-assigned session id onto `WorkerEntry.sessionId` (feeding `codex resume <id>`), while the `⌥h` history view and status detail read the transcript through the entry's adapter (`readTurns`/`resolveTranscriptPath`/`readActivity`); live-verifying `codex resume` and Codex-aware unsent-draft detection remain (Phase 4). `WorkerEntry.harness` names a worker's adapter and the launch/resume/bounce/loop paths thread it. The adapter splits into a light core (`harness/core.ts`, importable from the hook bundle) and the full adapter (`harness/index.ts`, adds the heavyweight `installRuntimeConfig`; CLI bundle only) so `dist/hook.js` stays lean; `package.json` sets `"sideEffects": false` to keep that split effective, which means modules must stay free of import-time side effects (only entry points execute at top level). See `docs/MULTI-MODEL.md` "Layer 3".
- Each worktree's `.claude/settings.json` configures Claude's OS-level sandbox (Seatbelt on macOS, bubblewrap on Linux) — auto-allow mode approves sandboxed bash without prompts while blocking out-of-allowlist filesystem writes and network calls at the kernel. Workers and reviewers run without `--dangerously-skip-permissions` but remain autonomous inside the sandbox. Allowlist defaults (Anthropic, GitHub, npm, the project's git remote host, plus worktree + standard subprocess caches) are built in `src/dashboard/sandbox.ts` and extended per-project via the `sandboxDomains` config key. The config lives in `settings.json` (not `settings.local.json`) because Claude Code writes permission approvals to `settings.local.json` and can clobber our keys; keeping hooks/sandbox in `settings.json` isolates them from that churn.
- The same `settings.json` sets `permissions.defaultMode: "auto"`, so every Claude process in the worktree (worker, reviewer, resolver, resume) starts in Anthropic's built-in auto mode. The classifier auto-approves low-risk tool calls and only prompts the operator for the rest. `permissions.allow` also pre-approves `Bash(tmux:*)` plus read-only tail utilities (`echo`, `head`, `tail`, `cat`, `grep`, `wc`) since workers routinely query pane/window state and pipe or chain the output — Claude Code checks each subcommand of a compound bash call against the allow list independently, so without the tails a command like `tmux list-keys -T root | head -40` still escalates. Garden wires a `PermissionRequest` hook (no matcher — all tools) that fires **only** when a prompt is actually being shown; it flips `agentStatus` to `asking`, which renders the worker row bold-yellow in the status pane. A catch-all `PostToolUse` hook (no matcher — all tools) flips `asking` back to `working` once the operator approves, regardless of which tool the classifier escalated

### Telemetry ledger

An append-only JSONL event ledger (`src/dashboard/telemetry.ts`) records worker lifecycle facts for cross-model / provider / harness / workflow / prompt-version analysis. It is the durable history garden otherwise lacks: `removeWorker` hard-deletes the registry entry and `dashboard.log` tail-trims at 10MB, so nothing else survives a worker's cleanup. One line per fact (never an aggregate), sharded monthly at `~/.garden/telemetry/events-YYYY-MM.jsonl` and **never truncated** — aggregation happens at read time, which keeps future questions answerable against past data.

- **Design constraints.** Best-effort throughout (every write is wrapped and swallows — a telemetry failure must never break the poller or a launch, exactly like `log.ts`). The module is kept THIN (`fs`/`path`/`crypto`/`config` only) and its directory is resolved lazily inside the write, so it is safe to pull into any import graph — including the `dist/hook.js` closure that `registry.ts` reaches — without an import-time dependency. Callers construct the already-primitive payloads (harness/model/crew/`rulesHash` are resolved caller-side in CLI-only modules); the module only stamps `v`+`ts` and serializes. Every line carries a schema version `v` for read-time migration.
- **Join key.** Worker names are randomly generated slugs that collide over months, so the durable identity is `workerId = project/name/createdAt`. Every event carries it; the lean lifecycle events join back to `worker.created` on it.
- **Lifecycle events (Phase 1).**
  - `worker.created` — emitted from `newWorker` (`workers.ts`) with the full configuration snapshot frozen onto the event (config is mutable, so "what was configured when this ran" cannot be reconstructed later): `workflow`, `harness`, `provider`, `model`, `ultracode`, `crew` (the per-worker `entry.crew` when set, else the project's `deriveCrew`), per-role `{harness, model}` for reviewer/resolver/ci-fix (`resolveReviewRole`, resolved with `entry.crew` so a per-worker crew's review harness is recorded, not the project's), `baseBranch`, `rulesHash` (a short hash of the composed global+project rules — the prompt-version axis), and `gardenVersion` (the build axis).
  - `state` — emitted from `transitionState` (`poller-state.ts`) on every genuine prState move (`from`/`to`/`workflow`). The lifecycle backbone: time-in-state (review/resolve/cycle durations) falls out of consecutive events' timestamps at read time.
  - `merge` — emitted from `transitionToTerminal` (`poller-merge.ts`) with the counts the pure `state` event can't carry: `terminalState` (`done`/`merged`), the cumulative `mergeCount` ordinal, and this cycle's `changedFiles`. The terminal move thus appears as both a `state` line (machine trace) and a `merge` line (enrichment), distinguished by event type.
- **Review-cycle quality events (Phase 2).** The review family emits its outcome with magnitude and effort — the signal the `state` stream can't carry.
  - `review.verdict` — emitted from `handleReviewing` (`poller-review.ts`) at the single point a parseable verdict is known (both workflows, every clean/fixed/failed and trellis ALIGNED/DRIFT/FLAGGED outcome): the verdict, the review `durationMs` (from `reviewStartedAt`), and the reviewer's **fix magnitude** — `getDiffNumstat` over `preReviewSha..tipSha` (`git.ts`), zero on CLEAN and the edit size on FIXED. The headline quality metric: a worker a reviewer must rewrite N lines per merge to land is not the cheap worker it appears.
  - `resolve.outcome` / `cifix.outcome` — emitted from `poller-resolve.ts` / `poller-ci-fix.ts` at the point the outcome is known: the agent's advisory `verdict`, the ground-truth `verificationPassed` (only a verified push counts), the `attempts` against the per-cycle budget, and `durationMs`. Success/failure is already inferable from the following `state` transition; these add the effort + duration it can't encode.
- **Autonomy events (Phase 3).** How much the operator has to hand-hold a config — the dimension no review score captures.
  - `continue.dispatched` — emitted from `continueWorker` (`continue.ts`) at the single paste-success point, so it covers every garden-*initiated* prompt (`kind`: `post-merge` / `interrupt` / `handoff-callback` / `seed`). Operator-typed prompts arrive via UserPromptSubmit and are deliberately NOT recorded, so operator-initiated work = all prompts − these: marking garden's own here is what makes that subtraction possible.
  - `operator.action` — emitted from `holdWorker` / `bounceWorker` (`workers.ts`, shared by the CLI and the `⌥e`/`⌥b` hotkeys) and the `kick` command (`commands/kick.ts`), with the `action` name. The direct "this config needed manual intervention" signal.
- **Cost events (Phase 4).** The worker's token spend — the axis a model/provider cost comparison turns on (the review family is always strong Opus, so its cost isn't the variable under study).
  - `worker.tokens` — emitted from `transitionToTerminal` (`poller-merge.ts`) at each merge: the worker's CUMULATIVE token usage (`input`/`output`/`cacheRead`/`cacheCreation`) summed over its Claude transcript by `sumTranscriptUsage` (`conversation.ts`), plus the turn count, the transcript's ground-truth `model`, and the `mergeCount`. Cumulative because a default worker's phases share one growing session, so per-cycle cost is a read-time diff of consecutive samples for the same workerId. The sum **dedupes by `message.id`** — Claude Code re-emits each assistant message on every streaming update carrying the message's cumulative usage, so a naive per-line sum overcounts ~2.7x (measured). Best-effort: absent when the transcript can't be read, so it never blocks the merge event.
  - Deliberately deferred (documented, not built): reviewer/resolver/ci-fix token cost (their headless throwaway-session transcripts are a separate discovery problem), Codex stderr token-trailer parsing (its numeric format isn't modeled — building a parser blind would be guessing), and a usage-meter utilization time-series (`snapshotMeters` gives only fleet-level percentages, not per-config tokens).
- **Read surface (Phase 5): `garden stats`** (`src/commands/stats.ts`) aggregates the ledger into a per-config comparison — quality (clean-review rate, reviewer fix magnitude, fail rate, review duration), cost (output tokens per merge), and autonomy (operator interventions per merge). `readTelemetryEvents` (`telemetry.ts`) is the sole read path (scans every shard, tolerant of torn lines). The unit of comparison is the config group; `--by` re-keys it (`config` default → `model`/`provider`/`harness`/`workflow`/`crew`/`rules`/`version`), `--since Nd|Nh|Nm` windows it, `-p` scopes to one project. The workerId→config join is built from the FULL `worker.created` history (never time-windowed) so a worker created before a `--since` window still resolves its config; only metric events are windowed. Events whose workerId has no `worker.created` (workers predating the ledger) bucket to `(unknown)` rather than vanishing, and age out as those workers are cleaned up. JSON when piped (complete data), a table in a TTY. Deferred cost refinements (reviewer token cost, Codex trailer, usage-meter time-series) remain as noted above; the four event families plus this read surface deliver the model/provider/workflow/config comparison the ledger was built for.

## Worker Status Detection

Each worker has two independent status axes:

**Process status** — what Claude is doing, written by Claude Code hooks (except `paused`, written by the operator `hold` action — a raw Escape fires no hook):
- ⏳ **loading** — worker pane started, bootstrap script running, Claude not yet launched
- ◇ **ready** — Claude launched but not yet tasked
- ⠋ **working** — Claude is processing a submitted prompt (braille spinner animation)
- ⚑ **asking** — Claude is blocked mid-turn on operator input (plan approval, question, permission escalation); row is highlighted bold-yellow in the status pane
- ◆ **idle** — turn has ended, Claude is at the prompt waiting for the next message
- ‖ **paused** — operator deliberately halted the worker mid-turn via the hold action (`⌥e` / `garden hold`); held awaiting a redirect, cleared by the next prompt; row is highlighted bold-cyan in the status pane
- ○ **exited** — process has terminated

**Lifecycle status** — where the worker's code is in the review pipeline, written by the poller:
- ◎ **reviewing** — automated reviewer is checking the worker's commits
- ◷ **merge-pending** — review passed, in the merge queue
- ◔ **resolving** — automated resolver is fixing a merge-queue rebase conflict
- ✖ **failing** — review failed, waiting for worker to fix; row is highlighted bold-red in the status pane. When the operator has prompted the failed worker and it is mid-turn (`agentStatus` = working), the icon becomes the braille spinner while the state cell and red row are unchanged — "still broken, being worked on" versus "broken and parked" (`isFailingBusy` / `iconFor`, `src/commands/status.ts`)
- ✓ **merged** — transient post-merge beat; row is uncolored (not actionable; cleared by the next auto-continue prompt)
- ✓ **done** — worker self-declared finished via `.garden-done`; row is highlighted bold-green in the status pane (operator cleanup signal)

The display combines both axes: lifecycle state takes priority when present, otherwise the process state is shown. A worker that is "reviewing" shows the reviewing bullseye regardless of what Claude is doing. The animated braille spinner belongs to the "working" display state and to one crossover: a `failing` worker whose agent is working (see above), which spins in red.

**Base-branch divergence indicator**: how a worker's row flags its base depends on whether the project has an explicit `baseBranch` configured.

*Configured projects* (`baseBranch` set): the project header carries a grey `⋅<base>` token (what workers merge into, at a glance), and each worker row is judged against that configured base independently — no project-wide toggle. A worker whose pinned base matches shows nothing; one that differs shows a grey `→ <base>` (a deliberate per-worker override, e.g. `workers new --base`); one whose base has vanished from origin shows a yellow `→ <base>` — the only genuine fault, since the merge will fail. The missing-from-origin check (`branchExistsOnOrigin`) is TTL-cached per project like the checkout-branch lookup, and only configured projects pay it (`formatConfiguredBaseHint` / `collectMissingBases` in `src/commands/status.ts`).

*Unset projects* (legacy checkout-follows default): a worker whose pinned `baseBranch` differs from the branch currently checked out in the project's main directory gets a grey `→ <baseBranch>`, and when *any* worker diverges the matching siblings show their base in grey too (`projectHasBranchDivergence` / `formatBranchHint`). This keeps a mixed project unambiguous but toggles every row on one worker's divergence — the jitter the explicit `baseBranch` key retires. The pin/checkout mismatch is informational, not a warning — merging into a non-checked-out base is a fully supported workflow (the post-merge step advances that base's ref on its own) — so it wears the quiet grey of the identity cluster rather than a yellow alert color; the yellow `→ <base>` is reserved for the one genuine fault (a base gone from origin, where the merge will fail), which only the configured-base path can detect. The project's current branch itself isn't repeated next to the project name — the bottom status bar (`formatLeft` in `header.ts`) already shows it for the active project. The post-merge alert is correspondingly narrow — `notifyPostMerge` stays silent when an off-base base ref advances cleanly or a redundant local commit auto-heals, and otherwise alerts only on entry into the state: `diverged` (real local-only commits, warn), `checked-out-elsewhere` (base live in another worktree, warn), `dirty` (uncommitted changes on the on-base checkout, warn), or `stuck` (fetch failure or a wedged checkout, error).

**Worker row ordering**: rows are ordered by attention and recency rather than by name (the name is just an address handle). `compareWorkerFreshness` (`src/dashboard/registry.ts`) sorts by attention tier first — (0) blocked on the operator (`failing`/`asking`), (1) new and awaiting its first prompt (`loading`/`ready`), (2) active/recent (`working`/`idle`/`paused`/`exited`), (3) in flight under the poller (`reviewing`/`resolving`/`ci-fixing`/`merge-pending`/`merged`), (4) `done` (sinks to the bottom as a cleanup candidate) — then within a tier by freshness descending, then by name as a stable tiebreak. The bands follow a worker's life top-to-bottom: needs-you at the top, then the work descends through active → in-flight → done as it heads toward merge. The in-flight prState is classified before the new (`loading`/`ready`) agentStatus, so a worker whose turn ended and was picked up for review lands in the in-flight band even if its agentStatus is a stale `ready`/`loading` (a STATUS.md invariant). The active band's tier number is the exported `ACTIVE_SORT_TIER`, shared with `isWorkerStale` so the stale-dim follows the active band if the bands are ever renumbered. Ordering freshness (`workerSortFreshness`) is the most recent of `lastStateChangeAt` — the worker's last *meaningful* transition (an `agentStatus` change, stamped by `applyAndLog`, or a `prState` change, stamped by `transitionState`; never the 10s heartbeat) — then `lastEventAt`, then `createdAt` (stamped at `addWorker` so a brand-new worker sorts fresh before its first hook; both timestamps are backfilled on read for pre-existing entries by `migrateCreatedAt` / `migrateLastStateChangeAt`). Keying on the state-change time, not the raw `lastEventAt`, is deliberate: the 10s hook heartbeat bumps `lastEventAt` for a working agent without repainting the status pane (the refresh is gated on a real state change), so ordering by `lastEventAt` let the registry order drift silently and then snap on the next unrelated repaint — e.g. the operator navigating to another worker. Tying ordering to the transition keeps every reorder coincident with the repaint that the same transition already triggers, so the list stays fixed while you navigate and only moves when a worker genuinely changes state. Freshness is compared at 60-second granularity so a burst of state changes among co-active workers doesn't reshuffle the list. The same comparator orders the ⌥]/⌥[ cycle (`cyclePane`) and the `whoami` sibling list, so navigation matches the visible order; the default focus target on project switch is deliberately left in tmux insertion order. An active-band worker untouched for over `WORKER_STALE_MS` (24 h — far coarser than the 15-min health staleness, since this only drives a dim) is rendered faint via `dimRow`, which re-arms the faint attribute after each inner ANSI reset so embedded colored segments (the base-divergence hint, the trellis counter) don't half-brighten the row. Blocked, new, in-flight, and `done` rows are never dimmed; nor is the one colored active-band state, `paused` (an explicit operator hold rendered bold cyan — a dim would fight that color and hide a deliberate state), which `isWorkerStale` excludes so `dimRow` only ever wraps an uncolored row.

**Time-in-state suffix**: in-flight and blocked rows (`reviewing`/`merge-pending`/`resolving`/`ci-fixing`/`asking`/`failing`) carry a dim elapsed suffix showing how long the worker has sat in its current state — `reviewing 12m`, `merging 47m`, `asking 2h` — computed by `formatTimeInState` (`src/commands/status.ts`) from `lastStateChangeAt`. It reads grey by default and turns yellow once elapsed passes a soft per-state expectation (10 min for `reviewing`/`merge-pending`/`resolving`, 15 min for `ci-fixing`), well under the hard `REVIEW_TIMEOUT_MS` (60 min) kill, so "slow" is visible long before "killed". Only the otherwise-uncolored pipeline states escalate to yellow; `asking`/`failing` rows are already whole-row colored, so their elapsed stays dim rather than fight the row color. The suffix is suppressed under a minute (no `0m`) and is folded into the state column — `reviewing 12m` is one cell, one fact — so how long a worker has been reviewing sits next to *what* it is doing, not adrift at the end of the row. Because it rides the same pre-baked-file + SIGUSR1 path as the rest of the status pane, the elapsed value would otherwise freeze between state transitions; the liveness watchdog's 60 s tick re-bakes it (`refreshStatusElapsed`, `header.ts`), the one recurring driver of the otherwise event-driven pane, content-deduped so a fully idle fleet (static icons) never repaints. The `working` spinner frame is baked FIXED (`iconFor`) and animated locally by the pane at 0.12 s, so a busy fleet's baked bytes stay stable too — the dedup (in-process cache plus an on-disk byte-compare, so it holds even in the one-shot hook/hotkey processes) suppresses the write and SIGUSR1 on a tick where no row's suffix actually advanced.

**Worker row grammar (identity vs. status)**: a worker row is `<focus> <icon> <name>  <state+elapsed>  <detail>  <badges>  <model>  <flags>`, built once by `collectSegments`/`renderWorkerRow` (`src/commands/status.ts`) for both the `garden status` CLI and the baked dashboard pane. Two info classes, two treatments. *Identity* facts — a worker's base (`→ <base>` when it overrides the project base), per-worker crew (the crew name, when `entry.crew` differs from the project default — it supersedes the member badge, since the crew name already encodes the build harness), member (its build harness, when it differs from the project default — `codex` on a Claude project), model (`sonnet`/`opus`, when pinned), and workflow — render as quiet **grey** badges, and only when they differ from the project default: **default is invisible, override is grey**. The whole identity cluster — base, crew, member, workflow, and the model — trails the detail column as ragged tags (no shared leading column), so nothing sits between the state and the description: the description is the row's primary content and reads first (operator call, 2026-07-16). Ragged-right means each badge costs width only on the row that carries it, rather than a width-aligned leading column that would push every plain row's description to the right — the same reason the model tag already trailed. The **state column** itself is sized to the widest state cell actually on screen (`computeStatusWidth`, across every project's workers, floored at `STATUS_MIN_WIDTH`), the same way the name column sizes to the longest name — so a fleet of short `done`/`idle` rows isn't padded out to the 13 columns only the longest transient state (`reviewing 12m`) needs, which was the dead space between the state and the description. When a worker enters an elapsed-bearing state the column widens on that bake and the detail column shifts right in step (and tightens again once it clears); it is recomputed each bake off the same `now` the elapsed suffix uses, so measured and rendered widths never drift. *Status* facts — the state word, the folded-in elapsed, the CI bracket, and the `gate closed` flag — own the color-escalation vocabulary (grey/yellow/red). Workflow decoration is a pure `workflowRowDecor` switch on `entry.workflow` (a vine's `[trellis: …]` bracket and a grow loop's `grow N/M` counter fill the detail slot; a botanist gets a grey `botanist` badge in the identity cluster instead, so the live activity keeps the detail slot), deliberately kept off the `src/dashboard/workflows/` import graph so `status.ts` (and thus `dist/hook.js`) never pulls in the poller graph. Truncation follows the grammar: the core (through the state cell) and the flags never drop, the identity cells (the badge cluster and the trailing model) drop as a unit next, and the detail column truncates first and absorbs the width — a narrow pane shows *what* and *where it stands* before it shows prose. A truncated detail is marked with a trailing `…` (`truncateToVisibleWidth`'s `ellipsis` flag, which reserves the marker's column so the row still fits the cap): a summary is prose, and prose stopped mid-word with no marker reads as a broken render rather than a long line (operator call, 2026-07-27). The whole-line backstop applied after the rows are built is deliberately unmarked — it only trims what the grammar already fit, so a marker there would claim a truncation that did not happen. Each project header also carries a yellow `⚠n` unread-alert count (`unreadAlertCountsByProject`, `alerts.ts`) beside the diary pencil — the count clears globally on `⌥a` (there is one `lastSeenAt`), so it answers "did anything happen here while I was away?" without switching to the alerts view.

**Where the detail text comes from (per harness)**: the detail column renders `entry.task`, the worker's own "what am I doing" summary, refreshed by the hook path (`applyAndLog`) and both status render paths (`refreshWorkerTasks` in `header.ts` and `status.ts`). The source is the harness's, not garden's — `resolveWorkerActivity` (`harness/core.ts`) asks the harness core for a `readActivity` and only reads the tmux pane title when it has none. Claude Code rewrites its terminal title as it works, so it defines no `readActivity` and the pane title IS the summary. Codex does not: its title is configurable (`[tui].terminal_title`) but every item is metadata or a counter — verified against codex 0.144.6, `activity` is a bare spinner glyph, `task-progress` renders `Tasks 3/5`, `thread-title` renders the thread UUID even once a title exists on disk, and the default `["activity", "project-name"]` resolves `project-name` to the cwd basename, which for a garden worktree is the worker's own name (the row read `weak-brave-snow  weak-brave-snow`). So the Codex core derives the summary from its rollout instead (`codex-core.ts` `readActivity`): the step the newest `update_plan` call is on — a short model-written phrase, the closest analog to Claude's title — falling back, until a plan exists, to the opening prompt's first line, which is what Codex itself extracts as the thread title. A harness that defines `readActivity` is authoritative over the field: a null return means "keep the previous summary", never "fall back to the pane title", since for such a harness the title is known-useless. Both reads are bounded tails/heads of the transcript, because this runs on the hook path; the head bound clears the rollout's instruction preamble, measured at 70-90KB for a real garden worker.

### Bead intake (board→garden delegation)

The intake loop (`src/dashboard/poller-intake.ts` + the bd client in `src/dashboard/beads.ts`) converts ready, dispatch-labeled beads in a project's `.beads` store into garden workers. It is garden's half of the board→garden delegation design (board's `docs/DELEGATION.md` is the authority): bd owns the work graph and computes the ready frontier (`bd swarm status <epic> --json` — never the `--parent` family, which is empty for dependency-edge epics on bd 1.0.3); board steers dispatch via labels on the epic; garden subscribes to the frontier and executes. Opt-in per project via `beadIntake: true` (+ optional `beadIntakeCap`, default 3). Projects without the flag never shell out to bd.

**Where it runs.** A step at the end of each poller cycle (`poll()` in `poller.ts`), throttled to one pass per 60 s via an on-disk mtime stamp (`intake-last-<project>` in `SESSIONS_DIR` — poller processes are exec-per-wake, so any remembered state lives on disk). `garden poke [project]` bypasses the throttle: it writes an `intake-poke-<project>` marker, ensures the project's poller exists, and pokes its FIFO (`<project>-poll-signal`), so the very next cycle runs intake now — this is the fire-and-forget wake board's dispatch gate keys use. The liveness watchdog adds the one recurring beat the design needs (`INTAKE_BEAT_MS`, 5 min): it keeps a poller alive for each opted-in project even when the project has no workers, then sends a plain FIFO poke, so a gated epic can dispatch the project's first worker when no lifecycle event is arriving.

**The label contract** (all on the epic, except `retry` on the bead):

- `dispatch:manual` — operator-armed authorization for ONE dispatch pass (the trust ramp; board's `g`). After a pass that spawns at least one worker, intake consumes it by rewriting to `dispatch:dispatched`; board re-arms by restoring `dispatch:manual`. An armed epic whose frontier is empty stays armed.
- `dispatch:auto` — the wavefront marches unattended (board's `G`).
- `dispatch:off` — gate closed; wins over manual/auto if both are present.
- `budget:N` — operator-set cap on total dispatched sessions for the epic; retries count. Intake tracks spend in a garden-written `dispatch:spent:N` label (bd labels are the sanctioned durable channel — registry entries hard-delete on worker removal — and board can render "N sessions spent" from the same label). At the cap intake halts, labels `dispatch:budget-exhausted`, and raises an error alert; in-flight workers are never killed (operator decision). Clearing the exhausted label and raising `budget:N` resumes.
- `dispatch:retry:N` — written on a bead each time the reaper recovers it.

**Dispatch pass.** For each open epic carrying any `dispatch:*` label: read the frontier, filter `ready[]` to unassigned beads (assigned-but-open beads stay in `ready[]` on 1.0.3 and carry an `assignee` field), and dispatch up to `min(cap slack, budget remaining, wave size)` — highest priority first (`bd show` supplies priorities; board's reordering steers which beads win scarce slots). Each dispatch: write the seed file, `newWorker({background: true, seedMessageFile})`, then claim the bead AS the worker (`BEADS_ACTOR=<worker-name> bd update <id> --claim`) — one atomic bd write that sets assignee + in_progress, removes the bead from the frontier, and establishes the join. The concurrency governor counts live intake workers via that same join (bd assignees with a live registry entry — no invented registry state), and same-pass spawns count immediately.

**The join contract.** Workers of a `beadIntake` project get `BEADS_ACTOR=<worker-name>` and `BEADS_DIR=<project-checkout>/.beads` exported alongside the `GARDEN_*` vars (bootstrap + resume paths, `beadsEnvExports` in `create.ts`), and the sandbox allows writes to the canonical `.beads` dir. `BEADS_ACTOR` makes the bd assignee the garden registry key — board joins bd assignee ↔ registry entry with zero invented state. `BEADS_DIR` is load-bearing: a worktree carries the tracked `.beads` files but not the gitignored Dolt database, so bd run bare in a worktree would bootstrap a divergent local store and the worker's `bd close` would never reach board or intake.

**bd 1.0.3 route-arounds** (each verified against the installed binary): `--claim` never overwrites a foreign assignee and a same-actor claim on a pre-assigned open bead is a no-op that does NOT set in_progress — so the design doc's `garden-pending` pre-assign stack is replaced by the claim-as-worker flow above, and the worker's own seeded `bd update <id> --claim` lands on the verified idempotent same-actor path. `bd human <id>` only prints a help menu — the seed's stuck path is `bd update <id> -s blocked` + `bd label add <id> human` + `bd comment <id> "<why>"` (surfaced by `bd human list`).

**Reaper.** Runs each pass over every gated epic's `active[]` (in_progress) beads, before dispatch. A bead is recovered — `bd reopen` + unassign + `dispatch:retry:N` bump, with a warn alert — only when its assignee provably maps to a dead garden worker: a registry entry with `agentStatus === "exited"` still in `working` prState, past a 10-min grace (`REAPER_GRACE_MS`, spanning bounce gaps), or the legacy `garden-pending` marker. No registry entry at all means a foreign/operator actor — never touched. Entries in pipeline states keep their beads (review/merge continues headless), and `done`-but-open beads are board's amber "missed `bd close`" divergence, not a crash. Because intake claims pre-spawn are made only after `newWorker` returns a name (a registered entry), every intake-claimed bead's assignee has an entry, so the missed-spawn and crashed-worker cases share this one recovery.

The full specification for status tracking and display lives in `docs/STATUS.md`. The registry is the single source of truth: Claude Code hooks (`SessionStart`, `UserPromptSubmit`, `Stop`) write `agentStatus`; the poller writes `prState`; the tmux `pane-died` hook writes `agentStatus="exited"`; the operator `hold` action (`⌥e` / `garden hold`) writes `agentStatus="paused"` (the one operator-initiated writer — a raw Escape interrupt fires no hook, so a deliberate halt is otherwise invisible). There is no pgrep, no marker file, no fallback poll. Every transition is event-triggered. The single recurring tick in the system is the liveness watchdog (`watchdog.ts`, `_garden-watchdog` window): every 60 s it (1) re-pokes any project holding a worker stranded in an active state past a 5 min staleness threshold, recovering dropped one-shot pokes (poller respawn gap, reboot-killed detached wake-ups), and (2) keeps each project's poller window healthy — respawning it if it died uncleanly (a poke is useless with no poller reading the FIFO) and collapsing duplicates to one if a spawn race left several (resolving windows by index, since a tmux name target is ambiguous across duplicates). The spawn race itself is prevented at the source: `startProjectPoller` runs its check-and-spawn under a per-project file lock (`<project>-poller.spawn.lock`), so two concurrent starters serialize and the second no-ops instead of opening a second window — the watchdog collapse is now a backstop, not the primary defense. It also (3) alerts on orphaned worker windows — a live tmux worker window with no registry entry, the casualty of the create/sweep race fixed in `dropGhostEntries` — making the detached worker visible (detection only; it never reconstructs the entry) so the operator can recover it. Finally, it (4) discounts machine-sleep/clock-jump time from live review/resolve/ci-fix timeouts (`absorbSleep`): the watchdog is the fleet's one fixed-cadence process, so a loop iteration that overran a full extra tick of slack measures the suspend, and it shifts each live-windowed worker's `reviewStartedAt` forward by that slippage so a laptop that slept mid-review doesn't wake to a spurious `REVIEW_TIMEOUT_MS` kill (`isReviewTimedOut`/`isCiFixTimedOut` read that wall-clock anchor). On a separate hourly throttle it (5) runs disk housekeeping (`housekeeping`): `truncateLog` enforces the 10MB `dashboard.log` cap on a recurring cadence (previously only called on fresh dashboard creation, so a long-lived session's log grew unbounded between restarts), `sweepBootstrapScripts` deletes spent `bootstrap-<project>-<branch>.sh` scripts older than 6h (each worker launch writes one, consumed by its pane within seconds and never touched again, but nothing removed them — one orphan per worker ever created), and `sweepSpawnDrafts` deletes stale `spawn-draft-<project>.json` composer overrides past their 5-min TTL. These actions only restore lost event delivery, surface a casualty, discount suspend time from a timeout anchor, or bound an accumulating on-disk artifact — the watchdog never transitions state itself.

                             [--model <alias-or-id>] [--effort low|medium|high|xhigh|ultra]

                                   # .garden/botanist/artifact.md to the tracked --to path (must be

## Technology

- TypeScript, compiled via esbuild to `dist/cli.js` (plus `dist/hook.js`, a minimal entrypoint for the per-tool-call Claude hook so its node cold-start parses only the hook dispatcher's closure; worker hook commands prefix it with a fleet-shared `NODE_COMPILE_CACHE` dir under `~/.cache` so each cold start reuses the bundle's cached V8 bytecode)
- tmux for session persistence and pane management
- `js-yaml` for config parsing
- No CLI framework — lightweight `process.argv` dispatch with aliases

## Principles

1. **Human-first.** The dashboard is for a human operator. Everything is driven by keyboard shortcuts and CLI commands.
2. **Files over databases.** YAML, JSON. All human-inspectable.
3. **Shell out, don't abstract.** Call `claude` directly. Don't wrap the API.
4. **Hotkeys over commands.** Inside the dashboard, keyboard shortcuts are the primary interface. CLI commands are for setup and scripting.
5. **Grow by adding, not changing.** New commands, new pane types, new hotkeys — avoid breaking what works.
