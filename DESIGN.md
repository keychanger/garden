# Garden

A minimal CLI orchestrator for managing Claude Code sessions across multiple projects.

Garden is a personal tool — opinionated toward a single developer managing many projects from one place. It is not a team tool, not a CI system, and not a framework. It's a thin, extensible layer over Claude Code.

## Installation

Fresh-machine installation is documented in `README.md`: clone, install locked
build dependencies with `npm ci --include=dev`, build, link, and run `garden init`.
The supported Node range is `^22.12.0 || >=24.0.0`, matching the locked tooling.
`garden doctor` runs before initialization and checks Git (2.30 or later) as well as
the dashboard and agent tools. Of the tools it checks, only `gh` is optional (`garden create` and the CI merge gate use it), so a missing `gh`, or one whose `gh auth status` fails, is a warning rather than a failure. Its diagnostics do not establish Claude login or
remote push permissions. Installing Garden needs only repository read access;
managed projects require push access to worker branches and the chosen base.

## Core Concepts

### Project
A named reference to a directory on disk where Claude Code can operate. Projects are added with `garden add [path]` (name is derived from the directory basename). `garden register` and `garden unregister` are aliases for `add` and `remove`.

### Dashboard
A tmux session (`garden-dashboard`) that serves as the primary interface. The dashboard is a left/right split: garden title and usage meters (top), project status (middle), and a growhouse pane (bottom) on the left; an active pane (worker or shell) on the right with a header bar. The growhouse pane cycles between six views: the growhouse (`⌥g`) with a bold green `garden>` prompt and auto-dispatch for garden commands, the root shell (`⌥r`) for general-purpose terminal use, a logs view (`⌥l`), a history view (`⌥h`) showing the focused worker's prompt history, a diary view (`⌥d`) editing the focused project's diary in `$EDITOR`, and an alerts view (`⌥a`). The same swap-pane mechanism as the right pane is used. You never interact with tmux directly — garden sets up the layout, keybindings, and pane management.

### Workers
Interactive Claude Code sessions running inside the dashboard. Each project can have multiple workers (e.g., one for a feature, one for a review). Workers persist when you switch between projects — they're parked in hidden tmux windows and swapped back in when you return.

### Workflows
A **workflow** is a `WorkflowDefinition` (state machine + poller state handlers) that drives a worker's review/merge lifecycle. Each worker has a `workflow` field on its registry entry, and the poller dispatcher routes through `getWorkflow(name)` rather than a hard-coded switch. Agent activity hooks are shared lifecycle plumbing: `hook-dispatcher.ts` binds directly to `workerHookHandlers` and never imports the workflow registry, whose static definitions retain every review/merge/resolve handler. This keeps the per-tool-call hook graph independent from the poller graph. The `default` workflow reproduces the standard "review and merge" pipeline. Alternate workflows are introduced as data, not as forks of the poller dispatcher. The holistic whole-task review (`poller-holistic-review.ts`) is not a `WorkflowDefinition`: it is one reviewer pass the poller interposes on a finished default worker (see `holisticReview` under "Project Configuration"). Architectural rationale: `WORKFLOWS.md`. Author guide: `AGENTS.md` § "Adding a new workflow".

A `WorkflowDefinition` can also set `skipsReviewMerge: true`; designer and planner both do. For the **designer** design workflow, once its branch has commits ahead of base, the shared `handleWorking` pushes the branch and routes it `working → merge-pending` directly, never launching a reviewer — its deliverable is a design document the operator already reviewed at the human gate, not code to critique. The push comes first because the CI gate reads the SHA on GitHub before the merge queue's own push, and an unpublished publish commit read as missing there; a failed push leaves the worker `working` with its review still armed, and a 30s re-poke, one outstanding per project, retries it. Before the transition it enforces that the committed diff touches only the publishable `docs/` boundary (`isPublishablePath`); a designer that committed code parks in `failing` with `failingReason: "designer-scope"` and an operator alert, and re-publishes automatically once the non-doc files are removed and re-pushed. The check lists that diff with rename detection off (`getChangedFilesNoRenames`, `git.ts`): with it on, `git mv src/x.ts docs/x.md` lists only the `docs/` destination, so the source deletion merged with no reviewer. A diff git cannot produce does not pass the check; the worker stays `working` and the same 30s re-poke retries. The route also waits on the clean-tree gate a review launch does (without taking a review slot), since the merge queue's `cleanWorktree` would otherwise discard an uncommitted edit, keeping it only as a saved patch. That `docs/` prefix is `DESIGNER_PUBLISH_ROOT`, defined beside `isPublishablePath` in `designer-paths.ts`. The CI/merge gate still applies. At the approval gate the designer states the downstream plan; a bare approval publishes first, then has the designer spawn a default-workflow builder through `garden handoff` from a self-contained `.garden/designer/handoff-brief.md` that inlines the design. The operator can instead approve no builder. The designer's four-phase method (frame, options, converge, publish) is carried by the bundled `designer` skill (`skills.ts`), which the `rules.ts` designer branch points the worker at. A planner normally has no tracked commit at all; its bead DAG is reviewed through board's promotion gate, and any accidental commit follows the same docs-only skip-review boundary. See `WORKFLOWS.md` §§ "Designer workflow" and "Planner workflow", `src/dashboard/poller-review.ts` `handleSkipReviewMerge`, and the `garden designer publish` command.

### Rules System
Claude sessions are configured with layered rules files injected via `--append-system-prompt-file`:

1. **Global rules** (`<garden-repo>/rules.md`) — methodology, testing, git workflow. Lives in the garden repo itself (version-controlled). Resolved at runtime relative to `dist/cli.js` (or `src/rules.ts` in dev). Override via `GARDEN_RULES_PATH` env var.
2. **Project rules** (`<project>/.garden/rules.md`) — project-specific conventions

Rules are plain markdown. Edit them directly.

On the Codex path there is no `--append-system-prompt-file`, so the same composed
text is written into the worktree's `AGENTS.override.md` instead
(`installCodexAgentsMd`). Codex reads at most one instruction file per directory
and prefers that name to `AGENTS.md` (verified against 0.163.0), so the override
carries the repo's `AGENTS.md`, as it stands in the worktree, below garden's
rules. The format is owned by `src/dashboard/harness/agents-md.ts`, a
string-only leaf: garden's rules under `AGENTS_MARKER`, a `---`, then the repo's
own `AGENTS.md`. `composeAgentsMd` builds that composition. The override is untracked and excluded by a root-anchored
pattern (`/AGENTS.override.md`; the shared `info/exclude` governs every checkout
of the repo), so it reaches neither a commit nor the clean-tree review gate,
while the repo's `AGENTS.md` stays an ordinary tracked file that rebases, resets
and a worker's edits all reach. An override garden did not write, or one the
repo tracks, is left alone with a warning.

Older builds wrote the composition into `AGENTS.md` itself, marked
`skip-worktree` when tracked. Git refuses to rebase, reset or merge over such a
file once the base changes `AGENTS.md`, so the merge queue parked those workers
in `failing` as a rebase error, and a worker's edit to the file could be neither
seen nor committed. They also excluded a bare `AGENTS.md`, which hid every new
nested `AGENTS.md` repo-wide. The next refresh retires both
(`retireAgentsMdComposition`): the composition is restored from the index and
unhidden when tracked, or deleted when untracked, after anything besides
garden's rules and the repo's text is saved as an excluded
`AGENTS.md.garden-legacy-<ms>` (`composedOver` matches from the end, so a `---`
inside the rules cannot pass for a worker's edit). An edit inside garden's own
block, or appended to an untracked composition with no `---`, cannot be told
from garden's text and is not saved; the old refresh discarded both too. The
bare exclude lines go last: the file is shared, and in a checkout whose
untracked composition is still in place the bare `AGENTS.md` line is all that
keeps it out of `git status` and a commit, so the composition in every checkout
`git worktree list` reports is retired first, and that line stays while one
remains. The root-anchored lines go in before the bare ones come out, so a
worktree-root `.codex/` an older build wrote stays excluded. The bare lines
outlast a project's Codex workers, so the claude-code installer and a Claude
worker's spawn run the same retirement as the Codex installer
(`retireUnanchoredCodexExcludes`). `stripGardenRules` is the inverse of the
composition, and every reader
of `AGENTS.md`-as-documentation must apply it. `readDocSections` reads the
committed file, which never holds the composition unless one was committed by
mistake, and strips it anyway.

The worker is not the file's only reader: a headless resolver or CI-fix run
that Codex runs in the same worktree loads the override as project
instructions too (a reviewer loads none; see below). So `installCodexAgentsMd`
opens garden's block with a note scoping it to the worker session: a headless
run follows its prompt, pushes only if the prompt says to, and leaves
`.garden-done`, `.garden-awaiting-input` and `garden blocked` to the worker.
Claude reviewers that read the worker rules unscoped, through a repo's
`CLAUDE.md` `@AGENTS.md` import while older builds composed into `AGENTS.md`,
pushed their review commits "so the poller sees" them; the review prompts now
also say not to push.

Codex reads its instruction file only up to `project_doc_max_bytes`, 32 KiB by
default, and garden's rules alone fill about 20KB of that. The worker launch
therefore passes `-c project_doc_max_bytes=1048576`, so a Codex worker reads the
composed file whole, as a Claude worker reads `AGENTS.md` through its
`CLAUDE.md` import. A headless Codex reviewer passes
`-c project_doc_max_bytes=0` instead, at which Codex loads no project
instruction file and leaves the rest of its prompt input as it was (verified
against 0.163.0 with `codex debug prompt-input`; the operator's
`$CODEX_HOME/AGENTS.md` still loads). In a Codex worker's worktree that file
would hand the reviewer the worker's rules (commit and push, touch
`.garden-done` once the request is done), and the review prompt carries the
repo's docs itself, inline or named for the reviewer to read. Resolver and
CI-fix prompts carry no repo docs, so those runs keep the 32 KiB default and
read the repo's `AGENTS.md` through the override; the scope note sits at its
top, where a capped read keeps it.
The rollout records the composed file twice ahead of the opening prompt (the
instructions message and the `world_state` snapshot), so the head read that
finds that prompt for the status row and thread titles (`ACTIVITY_HEAD_BYTES`,
`codex-core.ts`) is derived from the worker's cap.

### Agent instruction files

A project's instructions live in **one** file. Claude Code reads `CLAUDE.md` and
never `AGENTS.md`; Codex reads `AGENTS.md` and never `CLAUDE.md`. A fleet that
runs both harnesses against the same repo — which this one does — therefore
needs `AGENTS.md` as the real file and `CLAUDE.md` as a pointer at it: a single
`@AGENTS.md` import line, or a symlink. Two independently-maintained files is
the failure mode, and it is silent — each harness works from a different set of
instructions and nothing reports the divergence.

Garden enforces this at two levels:

- **`rules.md`** carries the convention, so every worker maintains the pairing
  as part of ordinary doc upkeep.
- **`garden doctor`** reports it fleet-wide. `classifyAgentDocs`
  (`src/commands/doctor.ts`) classifies each registered project's checkout as
  `paired`, `unlinked` (both files exist independently), `claude-only`,
  `codex-only`, or `none`, and the check names the fix for each non-paired
  state. `none` is not reported — a repo with no agent instructions has nothing
  to unify, and doctor does not nag for docs a project never kept.

Prefer the import over the symlink: it leaves room for a Claude-only section
below it, and it needs no Administrator privileges on Windows. The import line is the pattern Claude Code documents for this (`https://code.claude.com/docs/en/memory#agents-md`).

### Panes

The title/usage and project-status panes are passive: keyboard input, mouse selection, and wheel scrolling are disabled. The growhouse slot and right pane retain normal interaction.

Every baked pane file (`status.rendered`, `usage.rendered`, `history.rendered`, `alerts.rendered`) is written through `atomicWriteFile`, so a pane's SIGUSR1 replay reads either the previous bake or the new one. On 2026-08-14 a signal that landed in the fork window of one of the status pane loop's command substitutions left a full duplicate of the loop running: the duplicate repainted a stale snapshot over the fresh content while the real loop blocked waiting on it, and the pane froze mid-garble. The loop therefore compares the pid it runs as with the one it recorded at start on every outer iteration (`buildStatusCommand`, `header.ts`), so a duplicate exits at its next iteration. `garden redraw` (`src/commands/redraw.ts`) remains the manual recovery: its `respawn-pane -k` kills each pane's whole process group, so no duplicate survives it.

- **Garden title + Usage Meters** (top-left) — Dedicated pane with a bold green `garden` title label on the pane border and two or more Claude quota bars inside (5-hour rolling window, weekly total, and one bar per model-scoped weekly meter — `fable` on current plans). Height auto-sizes to the rendered content — the two flat bars plus one row per model-scoped weekly meter, plus one dim footer row each for an enabled extra-usage credit tally and a one-line health tag (stale snapshot or last-fetch error) when present, framed by a blank row above and below (`finalizePane`) so the meters sit clear of the pane's top border and the status bar beneath it. Every row, the blank ones included, carries a trailing `\x1b[K`: the pane's replay loop reads the baked file through a command substitution, which would otherwise strip the closing blank away as a trailing newline. Once any Codex process has reported usage — a worker or a headless reviewer/resolver/ci-fix agent, since capture is role-agnostic — Claude and Codex meters share equally sized columns (see "Claude Usage Meter" below). Refreshed via SIGUSR1 from a pre-baked `usage.rendered` file.
- **Project Status** (mid-left) — Live-updating display of all projects and their workers. Shows which project is active (`◄`), each worker's lifecycle state via status icons (braille spinner for working, Unicode symbols for other states), a focus indicator (filled/empty circle) showing which worker is active, and aligned columns for name/status/activity. Auto-sizes to the number of projects. A project header row also carries a dimmed pencil `✎` after the name when that project's diary holds non-whitespace content — answering "did I leave notes here?", which nothing else on the row shows. Detection is `diaryHasContent` (`src/diary.ts`), which reads the diary directly (no mkdir) and stat-caches on mtime+size so the firehose of status re-bakes doesn't re-read every project's diary; `formatDiaryGlyph` (`src/commands/status.ts`) renders the glyph in both the baked dashboard path and `garden status`. An empty or whitespace-only diary counts as no content, so a never-written diary stays unmarked.
- **Growhouse Pane** (lower-left) — Cycles between six views: growhouse (bold green `garden>` prompt with auto-dispatch for garden commands), root (general-purpose shell), logs, history, diary, and alerts. `⌥g` jumps to growhouse, `⌥r` jumps to root, `⌥l` jumps to logs, `⌥a` jumps to alerts (the unread/read alert list — see "Alerts"), `⌥h` jumps to history (the focused worker's operator prompts + verb-tagged assistant summaries, read from the worker's harness transcript JSONL by `conversation.ts`), `⌥d` jumps to the diary (the focused project's diary at `~/.garden/diary/<project>.md`, open in `$EDITOR`). The history pane renders via the same pre-baked-file + SIGUSR1 path as the usage meter; `writeHistoryRendered` parses the transcript only while history is the active mode, and then only when a bake could differ: it stores the bake's inputs besides the transcript's content (transcript path, size and mtime, pane width, the worker's working/asking status, the build) in `history.rendered.key` together with the text that bake produced, and a refresh whose inputs match while `history.rendered` still holds that text skips the tail read. That covers every refresh the fleet makes while the view shows a worker that is not working; a working worker's transcript grows, so each refresh still re-reads it. Binding the text means a bake by another process, or a placeholder written while focus was elsewhere, invalidates the key without any ordering between the two files. To keep the view a readable summary rather than a raw dump, `conversation.ts` (a) skips system-injected user-role messages — background-task completions (`<task-notification>`), slash-command echoes — identified by the transcript's `promptSource` field (genuine prompts are `typed`/`queued`) with a wrapper-tag denylist fallback for legacy transcripts, so a workflow launch and the edits it drove fold into one summary instead of being split by a multi-KB notification blob; and (b) collapses garden-injected user-role prompts to a compact dim `garden · <kind>` marker, keeping the response visible (a post-merge auto-continue is often a whole phase of real work): `[garden]`-fenced continuation prompts (post-merge auto-continue, handoff callback, grow iteration) via `gardenLabel`, and a spawned worker's `[handoff from <project>/<worker>]` seed briefing via `handoffSeedLabel` (labeled `garden · handoff from <project>/<worker>`). Both prefixes are matched after stripping the `<pasted_content id="…">` tags Claude Code records around pasted text (garden pastes every prompt, so without the strip no continuation collapses). Claude Code's context-compaction summary (`isCompactSummary`) is also a user-role record, but it continues the prompt in flight rather than starting a new one, so it folds into that turn as a `· compacted` tag on its summary. Operator prompts are shown in full (not capped). Each exchange's divider rule carries its local time, and the first divider of each local day also carries the date in the logs pane's day-rule format (`─ Thu 10-15 · 12:08pm ─`). An assistant turn is summarized by what it DID (`summarizeTurn` — files edited, tests run, committed/pushed, files explored), never by the model's own prose, and one operator prompt yields exactly one assistant entry no matter how many messages the agent emitted answering it. **That shape is the harness-neutral contract, not a Claude detail**: the Codex reader (`harness/codex-core.ts` `readTurns`) accumulates rollout activity between operator prompts and feeds the same summarizer, mapping Codex's vocabulary onto the neutral tool names it reads (`apply_patch`/`patch_apply_end`/an `item_completed` `FileChange` → an edit, `exec_command`/`exec` → the shell command, `spawn_agent` → a subagent, `web_search_end` → research) and deriving the Read/Grep tools Claude has natively from the shell command text, since Codex reads and searches by shelling out. Without that mapping a Codex history is a reformatted copy of the agent pane: Codex emits a message per progress narration (`phase: "commentary"`), so a single prompt can produce dozens of full-prose entries. The garden/handoff marker collapsing is shared by both readers (`promptTurn`, `conversation.ts`) for the same reason — the operator types the same prompts and garden pastes the same continuations into either pane. **How far back the view reaches is bounded by bytes, not by turns, so the tail escalates.** A transcript's bytes-per-exchange varies by orders of magnitude — a Codex rollout inlines every command's stdout, and a four-day worker measured 178MB with 78% of it shell output — so the fixed 16MB tail the reader started with held 4 of that worker's 32 prompts, and the history view silently showed the last few hours of a four-day run while reporting nothing wrong. `readTurnsFromTail` (`conversation.ts`, shared by every harness reader) instead re-reads with a 4x wider window until the parse recovers `TAIL_TARGET_PROMPTS` (8) exchanges, up to a 128MB ceiling past which it accepts the clipped head. Escalation is driven by what the parse recovered rather than by a byte estimate, so an ordinary transcript still costs one read capped at 16MB and only a fat one pays for the width it needs (the 178MB rollout resolves in one widening, 120ms). Lines are decoded from the read buffer one at a time rather than materializing the window as a single string, which keeps a wide window's peak memory at roughly the buffer. The leading line of a clipped window is dropped: it is a fragment and may start mid-UTF-8 sequence. The diary pane runs a wrapper loop (`diary-view.sh`) that re-resolves the focused project via `garden dashboard _diary-path` each time the editor exits, so quitting the editor reopens on the now-focused project's diary; switching views parks the editor with its state intact. Switching projects (`⌥1–9` / `⌥p`) makes the diary follow: `reloadDiaryEditor` (`navigate.ts`) drives the editor's save+exit so the loop reopens on the new project. The drive fires only when a nano/pico editor is actually live on the pane — `paneRunningEditor` (`tmux.ts`) probes the pane's tty for the editor process — so the keys never hit a shell (the diary-view loop between reopens, its editor exited, or a non-editor pane swapped into the slot) and ring the terminal bell (the macOS "chirp"). This fires whether the diary is the active garden pane or parked in the hidden `_garden-diary` window — re-entering the diary view reuses the parked editor rather than restarting it, so without the parked-case reload it would show whatever project was focused when it parked. A live modal editor can only be re-targeted by restarting it, which would discard unsaved notes, so this is nano/pico-only (the shipped default; on macOS `nano` is a symlink to pico): it sends `^C ^O Enter ^X` — a leading `^C` clears any write prompt a prior partial drive wedged, then `^O Enter` writes the buffer to its current file and `^X` exits cleanly. A custom `$EDITOR` is left untouched (`paneRunningEditor` matches only nano/pico, whose save keys alone can be driven blindly) and still reopens on the operator's own exit. When the editor is nano/pico it is launched with `-b` to enable word wrap, so long diary lines wrap to the pane width instead of scrolling off the right edge. `editorIsNano` (`src/diary.ts`) recognizes nano/pico from the `$EDITOR` command's binary name.
- **Bottom bar** (tmux status line) — Two-sided display. Left side shows the active project name (bold) and its current git branch. Right side shows the garden build version (git short SHA, or "dev" when running via tsx); when the running build trails its branch it is prefixed with `⚠ N behind` and the whole bar turns yellow (see "Build staleness" below), and when unread alerts exist it is prefixed with a red `⚠ N alerts — ⌥a to clear` badge. The bar's color also answers "is this the window I'm typing into": a tmux client whose terminal window has lost focus draws the bar background dim grey (the alert badge stays red), and it returns to green (or yellow) the moment focus comes back. tmux resolves this per client by matching `focused` in `client_flags` inside the status-style (`statusBarStyle`, `alerts.ts`). Native `client-focus-in` / `client-focus-out` hooks run `refresh-client -S` for the event client so an idle dashboard repaints immediately without an external process; it depends on the server-wide `focus-events on` that `setupStatusBar` sets, and tmux applies that option only to clients that attach after it is set, so an already-attached terminal needs one detach/reattach.
- **Active Pane** (right) — The currently visible pane for the active project. Either a worker (Claude session) or the project shell. Only one is visible at a time; others are parked in hidden tmux windows.

The left status column and the right active pane divide the terminal at a configured ratio — `layout.leftPercent` in `~/.garden/config.yml` (`LayoutConfig` in `src/config.ts`), default **45%** left / 55% right, bounded to 30–70. Every tmux site sizes the *right* pane from the complement of the configured left percentage: creation and right-slot repair split there, and attaching to an existing dashboard, the `client-resized` handler, and the ⌥; menu's own apply restore that ratio before repainting the width-shaped panes. Pane contents continue to move only through swaps.

The default is not an even split because the two columns don't have equal floors. The left column carries `garden logs`, whose pretty mode spends a fixed gutter on the timestamp and identity columns before any message text (see "Logs gutter"), so an even split gives the agent pane width the left column can't use and the message column width it can't spare. 45/55 leaves the log message column where a 50/50 split left it — after the gutter reclaim — and hands the difference to the pane showing code. Set it from the **`⌥;` garden settings menu**'s *column split* row, which applies the new ratio to the live dashboard immediately by running the same path a terminal resize does (`rebakePanesOnResize` + `presizeHiddenWindows`): changing the ratio moves exactly the widths a resize moves, so it must repair exactly the same things.

Applying it is **reconciled, not only event-driven** (`src/dashboard/column-split.ts`). The four tmux sites that size the right slot each fire on an event — creation, attach, right-slot repair, `client-resized` — which leaves a gap with no event in it: a value that changes while a session simply stays attached never reaches the panes. That is not hypothetical, it is how this shipped: the merged 45/55 default sat on a live 50/50 dashboard, because the post-rebuild refresh respawns the status and logs panes but never touches widths. So the watchdog reconciles it each tick like every other drift it owns, comparing the configured value against `DashboardState.appliedLeftPercent` — the last value actually applied. Keyed on the configured value rather than on measured pane widths deliberately: an operator dragging a pane border leaves config untouched and is never fought, while a changed setting (or a dashboard predating one) is applied within a tick. Creation and attach size the slot themselves and record the applied value so their work doesn't read as drift; the marker is written only after the panes take the change, so a failure retries on the next tick. The tick's entry point is `reconcileColumnSplit`, which, like attach, resizes the right pane and records the value under the dashboard state lock. An explicit `⌥;` selection forces the apply, so reselecting the configured split after a manual drag still restores it. Every sizing site lands within one cell of the configured split, the slack being the divider and rounding.

### Logs gutter

`garden logs` pretty mode renders each entry as `timestamp · project · worker · glyph · message`, and everything before the message is a fixed gutter paid on every row. The logs pane lives in the left column — the narrower half — so that gutter is the left column's floor, and it is what sets the column split's default (see "Dashboard Layout").

Two rules keep it honest:

- **The identity columns are measured, not assumed.** The project column is the widest registered `displayName` that fits under the 16-char cap; the worker column is the widest name in the registry, floored at 12 and capped at 20 (the true ceiling for an adj-adj-noun name over a 6-char-max vocabulary — `names.ts`). A display name *over* the cap gets no vote: it is truncated at whatever the column turns out to be either way, so letting it pin the column to the cap would spend ten columns of every other project's rows on one project's long label. Widths are measured once per process and memoized, because `--follow` is a long-lived tail that appends rows — a width recomputed as names arrive would misalign every row already on screen. `prettyLayout` (`commands/logs.ts`) does that measuring. A name longer than its column behaves as it always has: the project column truncates, the worker column pushes its own row right (never truncates — a clipped worker name is unusable as the argument `garden logs -w` and `garden kick` take).
- **The date is a property of a run of entries, not of each one.** Pretty mode's clock is `HH:MM:SS`, and the date rides a dim full-width rule (`── Thu 09-17 ─────`) emitted on its own line when the calendar day changes. Repeating `MM-DD` on every row spent six columns on a value that changes once a day. In the `--follow` loop a day boundary also ends the current dedup block, because the in-place `(×N)` rewrite walks the cursor up through the previous render and must never reach across the rule. Raw mode is unchanged: its timestamps carry the date, so it emits no rules.

Nothing may exceed the pane. Details were wrapped from the start, but **headlines were emitted raw** — any message wider than the message column ran off and the terminal re-wrapped its tail to column 0, out of alignment with every other row (measured: 83 of 4000 real entries on a 97-column pane, the worst an alert at 412 columns). Headline whitespace is collapsed before wrapping so embedded newlines cannot escape the message column; an empty headline still retains its timestamp and identity row. Headlines now wrap to the same bound, capped at `HEADLINE_MAX_LINES` so one multi-KB alert cannot take the pane, with continuations at the message column and no `↳` — that glyph means "detail of the message above", and a wrapped headline is still the message. Two things also come off a row's budget: the shift an over-long worker name causes (never truncated, so it pushes its own row right) and `dedupReserve` — the columns a `(×N)` suffix will need, reserved *before* wrapping, since appending to a line already wrapped to the full width is exactly what would push it over. On a pane too narrow for even that reserve the count takes its own line. The fixed gutter and minimum wrap widths still impose a lower bound: headlines require ten message columns after any worker overflow, and details require twelve. Narrower panes may still overflow. Everything is fitted to the width at print time, so a pane that later narrows (terminal resize, column split change) would hold rows and date rules wider than itself; the `--follow` loop therefore redraws its backlog on resize, debounced so a border drag redraws once, clearing the screen and scrollback first so the stale copies do not remain above the redraw. Raw mode does not redraw: its rows are never fitted to a width, so clearing would only cost the scrollback. The file can also shrink under the loop: the watchdog's hourly `truncateLog` rewrites `dashboard.log` down to its newest ~8MB. The loop can then only re-read it from the top, so it skips every line no newer than the newest timestamp it has read, in both modes and when piped; treating the shrink as a fresh file replayed every retained line (34,380 rows after an 11MB trim, measured).

Net: a 59-column gutter became 47 on the reference fleet, which is what makes 45/55 cost nothing.

### Right-side pane model

Each project has:
- **One shell** (always exists, created on first project switch, protected from kill)
- **Zero or more workers** (spawned on demand with `⌥n`)

Only one pane is visible at a time. `⌥]`/`⌥[` cycles through all of them. `⌥w` jumps to the first worker, `⌥s` jumps to the shell.

## Plots

A **plot** is a named, ordered subset of projects (max 9) that drives what the dashboard shows. `⌥1`–`⌥9` index into the *active* plot. `⌥p` / `⌥P` cycle through focused plots. Projects can appear in any number of plots.

Plots scale past the nine-project hotkey ceiling: you can register as many projects as you want in `~/.garden/config.yml`, group them into purpose-specific plots (`client`, `lab`, `imp`, …), and swap views with a single keystroke. Each plot has a `focused` flag controlling whether it appears in the `⌥p` cycle — unfocused plots are still reachable by name (`garden plot <name>`) but don't clutter the hot-cycle.

**Storage**:
- Plot definitions live in `~/.garden/config.yml` under `plots:`. Order is semantic: plot insertion order drives `⌥p` cycle position, project order inside a plot drives `⌥1`–`⌥9`.
- Active plot is runtime UI state in `~/.garden/sessions/dashboard.state.json` (`activePlot` field). A user who runs `garden plot imp` before the dashboard is open will still land on `imp` when it launches — `ensureDashboard` preserves the pre-existing `activePlot` across fresh-creation of the state file.

**Migration**: `loadConfig()` synthesizes `plots.all = [currently-focused projects]` for a config with no `plots` (preserving pre-plot visibility) and drops the deprecated per-project `focused` flag. It migrates in memory only; the next config mutation persists the result (see "Shared-State Transactions"). Idempotent once persisted.

**Hotkey behavior**:
- `⌥1`–`⌥9` resolves against `getFocusedProjectNames(config, state.activePlot)` — the active plot's projects, filtered to those still registered. Indices beyond the plot's length show a "No project at index N" hint.
- `⌥p` / `⌥P` (`cyclePlot` in `src/dashboard/navigate.ts`) iterates only focused plots. `⌥o` is an alias for `⌥P` (cycle previous), for ergonomic left/right cycling with `⌥p`. If the active plot isn't focused, the next press lands on the first focused plot. When cycling, `activeProject` is clamped to the new plot's membership so the hotkey grid updates immediately. The leaving plot's `activeProject` is stashed in `state.lastActiveProjectByPlot`, so cycling back restores the prior selection instead of re-clamping to the first project.

**Header rendering**: `formatLeft` prefixes the active-project string with the plot name (e.g., `imp › garden • main`). The status pane's border renders a plot strip — one segment per focused plot, showing a filled circle on the active one and an empty circle on the others (mirroring the worker focus marker below it) — by writing the formatted string into `@garden_name` on the status pane (`buildPlotStrip` in `src/dashboard/header.ts`). Unfocused plots are omitted. `@garden_plot` is unused on that pane.

**Plot status indicators**: Each plot segment also carries a status icon derived from the aggregated state of all workers across the plot's projects (`resolvePlotStatus` in `src/dashboard/plot-status.ts`). Priority order: `failing-working` (red spinner) > `failing` (red ✖) > `asking-working` (yellow ⚑ plus a yellow spinner) > `asking` (yellow ⚑) > `working` (braille spinner) > `done` (green ✓) > `idle` (no icon). `failing-working` is a `failing` worker whose agent is mid-turn — the same red failure signal, animated, mirroring the worker row's crossover. It tracks the failing worker specifically: a plot whose failing worker is parked stays a static ✖ even while other workers in the plot are busy, so the strip's motion answers "is anyone fixing it" rather than "is anything happening". `asking` is the opposite call: a question parks one worker, not the plot, so when any other worker in the plot is in a `working`-class state the flag gains a spinner beside it (`asking-working`, derived after the scan since no single worker holds it) — the flag still says someone is waiting on you, the spinner says the rest of the plot is still moving. `failing-working` is the only state that short-circuits the scan (a plain `failing` must keep looking for a failing worker that is working). Only `done` is green — `merged` (transient post-merge beat), `reviewing`, `merge-pending`, and `resolving` fall through to `working`, since none of those are operator-actionable. Colors override the active/inactive styling for non-working states; a working plot keeps the neutral bold/dim active/inactive distinction, spinner included — the spinner is not separately brightened, so a plot you aren't in is flat grey end to end. Every glyph in the strip carries an explicit `fg=`: the strip is drawn as the status pane's `pane-border-format`, where tmux resolves a colorless glyph against `pane-active-border-style` (whose stock value is `fg=green`, or `fg=yellow` in copy-mode) whenever that pane is active. A bare `#[default]` gap therefore turns green on focus and reads as a `done` plot — `formatPlotSegment` leaves none, and `test/header.test.ts` ("leaves no glyph colorless in any plot state") guards it. The spinner animates at the same 120ms cadence as worker rows by piggybacking on the status pane's existing SIGUSR1-driven tick: `buildPlotStrip` writes a template file (`~/.garden/sessions/plot-strip.template`) with a `__GSP__` sentinel where the spinner frame goes, and the status pane's bash loop substitutes the current frame and rewrites `@garden_name` each tick. The loop enters animation mode if either `$cur` has a braille char or the template file contains the sentinel. A frame forks only its `sleep` and, while the strip spins, that one `tmux set-option`: the spinner rows are found once per outer iteration (a SIGUSR1 wake or ~60s of animation) by one awk that stores each row behind its cursor-position escape, and a frame repaints them with a single builtin `${var//frame/next}` substitution; the template is re-read with the `read` builtin, since `$(<file)` still forks a subshell in bash 3.2. Each fork in the frame recurs ~8 times a second for as long as anything on screen is working. `test/integration/status-loop.real.test.ts` runs the generated loop and counts the children each frame forks, so a fork added to the frame fails the suite.

**Right-pane clock**: The right pane — whether it holds a worker or the project shell — renders a `%H:%M` wall clock in the right corner of its top border, mirroring the `garden` title in the top-left. The shared `pane-border-format` (set in `setupStatusBar`) carries a right-aligned clock segment — bold green to match the `garden` title, wrapped in spaces and capped with two border dashes so the border runs to the right corner exactly as the left edge frames `garden` — gated on the `@garden_clock` pane variable. The clock's style is kept comma-free (`#[fg=green]#[bold]`, never `#[fg=green,bold]`): a comma inside the `#{?@garden_clock,…}` conditional is parsed as the true/false separator and silently blanks the clock. That variable is set on worker panes (`restoreWorkerPaneVars` in `navigate.ts` and the worker-pane creation sites in `workers.ts` / `create.ts`) and on the right-pane shell (`createShellWindow` in `create.ts` and `focusShell` in `navigate.ts`). The left-column garden shells (growhouse / root / logs) deliberately do not set it. The time is strftime-expanded by tmux on each `status-interval` tick (30s), so it advances on tmux's own timer with no extra process or poll.

**Project color in the right-pane border**: Every registered project carries a stable `logColor` (palette in `src/log-palette.ts`, auto-assigned by the `loadConfig()` migration), used to color project names in `garden logs`. The right pane's top border echoes that color as a small `●` before the worker/shell label — the one place project identity is otherwise absent (the border names the worker and task, never the project). The dot is gated on the `@garden_color` pane variable (a tmux color name like `colour208`), set by `setPaneProjectColor` (`src/dashboard/header.ts`) at the same sites that set `@garden_clock`; the shared `pane-border-format` renders `#[fg=#{@garden_color}]●#[default]` — tmux expands the nested variable before parsing the style, and the style must stay comma-free like the clock's. The color deliberately appears nowhere else in the dashboard (status pane and bottom bar already name the project in text), and the palette stores 256-color indices, deriving the ANSI form (`logColorAnsi`, log lines) and the tmux form (`logColorTmux`, border format) from the same index.

**Project removal** (`garden remove <project>`) also calls `purgeProjectFromPlots` to strip the project from every plot's project list. Empty plots are kept — delete explicitly with `garden plot delete`. It refuses, naming them, while the registry holds any worker for the project: the status pane and the pollers resolve projects through the config, so those workers would keep running with no row, no review and no merge, and removing them is the operator's act (`garden workers stop <worker>`). An unreadable registry refuses too, since it cannot show there are none.

## Pane Management

### Swapping Mechanism
Each project's workers and shell live in hidden tmux windows when not active. When you switch projects:

1. A temporary hidden window is created, and the current active pane is swapped into it via `swap-pane`
2. The target project's pane is swapped from its hidden window into the right slot via `swap-pane`, then the hidden window is killed
3. The status pane and header update to reflect the new state

This preserves both the layout tree (normal navigation never destroys the right pane slot) and all worker state across switches. If the slot's pane dies independently, `healActivePaneInState` is the single repair exception: it adopts an untracked surviving occupant or recreates the missing full-height slot, and the watchdog retries the repair each tick until it succeeds. A foreground worker spawn runs the same repair before it parks the visible pane, so a stale id cannot fail the spawn or strand the new worker hidden until the next tick; if the slot cannot be repaired the spawn is refused and rolled back, and a failure after parking puts the parked pane back and persists what tmux holds. The spawn also checks that the park and the restore actually moved panes, since either helper can return without swapping, and its rollback gives the parked pane back its recorded identity only once that pane is confirmed in the slot again, including when the final state write fails after the new worker is already visible. From `⌥n` a failed spawn is reported in the tmux status line until a key is pressed (`newWorkerFromHotkey`), because that key binding discards the route's output. Beside the watchdog and the spawn, `validateAndHeal` runs the repair on attach and for `garden health --fix`. The repair asks tmux whether the pane is still there, so it first asks whether tmux answers at all (`dashboardExists`): a garden run inside an agent sandbox is denied the server socket, and every probe — `paneExists`, the occupant scan, the split — then fails exactly as a destroyed slot does. Reading that as damage nulls `activePaneType`/`activeWindowName` on a perfectly healthy dashboard, after which the park fallback files a live worker's pane under the nameless `_<project>-active` window and the status pane loses that worker entirely (observed 2026-09-17). An unreachable session is left strictly alone. `validateAndHeal` (`validate.ts`) and the passive-pane healer (`healStatusPane`, run from every poll) make the same check before acting on a missing pane and change nothing while tmux does not answer: tmux, not dashboard state, is the source of truth for whether a pane exists. Adoption takes the pane id but not, on faith, the identity recorded beside it: `activeWindowName` is only a claim, and carried onto a pane that is not running that worker (a fresh shell in `$HOME`, observed 2026-09-21) the next park files that pane under the worker's window name and quarantines the real agent parked there. `paneHoldsWorker` (`window-heal.ts`) checks the occupant — cwd inside the worker's worktree and more than a bare shell on its tty — and on a mismatch the identity is dropped; when the occupant is a bare shell, the claimed worker's own parked window is swapped back in over it. Nothing else is: the restore kills the window the occupant is swapped into, so the repair never pulls a fallback in over the occupant, and never replaces a shell in another worker's worktree, which may be the only pane that worker has. A shell in the claimed worker's own worktree with no window parked under that name keeps the identity. A visible worker has no hidden window, and its pane becomes exactly that shell when the agent exits (the launch command ends in `exec $SHELL`); dropping the identity would take the worker off the status pane and get it reported as having no pane. A name that parses to no registered worker, or a worker with no recorded worktree path, gives `paneHoldsWorker` nothing to check the pane against, so the claim is kept as it is.

The common case skips the temp window: `swapDirect` (layout.ts) swaps the visible pane with the hidden target's pane, then renames the hidden window (now holding the parked content) to the park name. In the direct and right-pane restore paths, mutations on an already-resolved hidden window — rename, resize, kill — target the **window id** (`@N`), never the name: window names can be duplicated (a respawn race), and a tmux name target then fails outright (`rename-window`) or resolves to an arbitrary duplicate. A silently failed post-swap rename files the parked pane under the wrong window name, and because the status pane derives worker rows from window names, that worker vanishes from the dashboard while another project shows its phantom row — and each subsequent navigation renames yet another worker's window into the same name (the 2026-08-22 duplicate-window cascade: six windows named for one worker, holding live panes of five different projects). `swapDirect` rolls the pane exchange back before asking its caller to use the temp-window fallback if that ID-targeted rename fails; if the rollback also fails, it keeps dashboard state aligned with the completed exchange and leaves the watchdog to repair the hidden name. `swapDirect` also declines when a hidden window already holds the park name, so that case always takes the guarded `parkToHidden` path below; when that path finds the incoming pane to be the misfile, it still clears the name's other stale windows before it creates its temporary window. Two safety nets back the id-based targeting: `parkToHidden` clears a stale window already holding its park name by killing it only when its pane is a bare shell, quarantining a live pane under a `_stray-<id>` name instead (the old kill-all-by-name would have destroyed live agents misfiled under that name) — unless that pane is the one actually running the worker (`paneHoldsWorker`) and the pane being parked is not, in which case the parked pane is the misfile: it goes under a `_stray-p<pane>` name, or is discarded outright when it is a bare shell, and the live worker keeps its window; and the watchdog runs a **window heal** each tick (`window-heal.ts`) that joins each worker-named or `_stray-` window's pane cwd against the registry's worktree paths and renames misfiled windows back to the worker they actually hold. The heal renames on cwd evidence only when the window's name is provably wrong — a stray, a name parsing to no live worker, or a duplicated name (worker names are unique, so duplicates prove at most one holder is right); a unique correctly-parsing name is never touched, since pane cwd tracks the foreground process and a worker's shell may transiently sit in a sibling worktree. Two live panes claiming one worker (a duplicate agent launch) are surfaced as a warn alert, never resolved automatically.

### Hidden Window Naming
Hidden windows follow the convention: `_<project>-worker-<N>`, `_<project>-shell`, `_<project>-poller`, `_<project>-review-<worker>`, `_garden-growhouse`, `_garden-root`, `_garden-logs`, `_garden-history`, `_garden-diary`, `_garden-alerts`, `_garden-usage-poller`, and `_garden-watchdog`. When switching projects, the visible pane is parked under the name it already carries; `_<project>-active` is the fallback for when dashboard state has lost that name. It is a last resort, not a normal park target: the name encodes no worker, so `parseWorkerSuffix` cannot parse it and `listHiddenWorkerWindows` does not match it, and a worker parked under it disappears from the status pane while `validateAndHeal` marks its live registry entry `exited`. `parkNameFor` (navigate.ts) therefore recovers the real name from the pane's own `@garden_name` label first; the watchdog's window heal (`window-heal.ts`) re-files a pane already stranded under the parking name by joining its cwd to the registry's worktree paths, the same way it recovers a `_stray-` window — the parking name is definitionally not a worker's, so cwd is strictly better evidence and no duplicate-name proof is required, though a worker that already owns a correctly-named window still yields a reported conflict rather than a rename; and the restore side (`swapVisibleToProject`, `pickRefillTarget`) types a pane restored from the parking window as **unknown** rather than as a worker — worker-targeted keys report no focused worker until a navigation lands on a real window, instead of acting on an identity nothing can resolve. Navigation and a foreground spawn both park through `parkNameFor`, which accepts a pane's label only when it names the project's shell or a worker in the project's registry. `⌥x` is among the keys that refuse an unknown pane: with `activePaneType` null it reports no focused worker to kill. The underscore prefix marks them as managed by garden — not user-facing.

### Worker Lifecycle
1. `⌥n` creates a git worktree at `~/.garden/worktrees/<project>/<worker-name>/`, with a branch named after the worker that points at `origin/<base>` directly. Worker freshness does not depend on the main checkout being clean or fast-forwarded — a stale main checkout raises an alert but does not infect the worker
2. Claude launches in the worktree with project rules and worktree workflow instructions
3. The worker is interactive — you work with it directly
4. `⌥]`/`⌥[` cycles between workers and shell
5. `⌥x` kills the focused worker, removes its worktree and branch. Kills unconditionally — no confirmation, even on dirty worktrees — so a worker stuck in loading or otherwise unresponsive can always be torn down
6. Switching projects parks everything in hidden windows; switching back restores

### Poller and Auto-Merge
Each project gets its own background poller (`_<project>-poller`) running in a hidden tmux window. Pollers are independent — one project's reviews never block another. Each poller watches its project's worker branches for new commits and drives the review/merge lifecycle using local git operations (no GitHub PRs). Pollers start when a project's first worker is created and stop when the last worker is killed. A stop unlinks the poll FIFO only once tmux answers that no poller window is left, or that no dashboard is running (`stopProjectPoller`): the poller holds the FIFO open, so unlinking it under a poller that survived the kill (any kill from an agent sandbox, which is denied the tmux socket) leaves that poller deaf to every poke, and nothing recreates the path while its window exists.

**State machine per worker:**
```
working -> reviewing -> merge-pending -> merged --(UserPromptSubmit)--> working
               |              |              \
               v              v               +-(.garden-done set)-> done
           failing        resolving (auto-resolver on rebase conflict)
                              |
                              +-> merge-pending (verified) or failing (budget exhausted)
```

1. **working**: Worker is active. When the worker's Claude Code Stop hook fires and the worktree has commits ahead of base AND no uncommitted changes (`git status --porcelain` empty), the hook marks the worker for review (`pendingReviewAt`) and pokes the poller, which transitions to reviewing. A dirty tree — tracked or untracked changes, or an indeterminate check — skips the queue entirely: the agent stopped mid-work (e.g. paused to answer an operator question with WIP on disk), and the reviewer certifies the committed snapshot of that same worktree, so reviewing now would certify a stale tree and force-push under live edits. The next clean-tree Stop re-arms. Because `pendingReviewAt` can outlive the clean tree it was set on, `handleWorking` re-checks cleanliness at the launch point and defers (flag left set) until the tree is provably clean. Multiple workers per project can transition independently. Every one of those refusals records **why** on the entry (`reviewBlockedReason`, `"dirty"` or `"indeterminate"`, written through `setReviewBlockedReason` and cleared the moment a review is armed or launched — or when the branch has nothing left to review). The poller writes it at both points in `handleWorking` that defer a launch on a tree that is not provably clean: that launch-point recheck, and the stale-`working` escape hatch, which launches a review for a worker whose `working` status has gone hook-silent past `STALE_AGENT_STATUS_MS`. Without it the stall is invisible: no `prState` is ever set, so the row renders a plain `idle` indistinguishable from a worker that finished with nothing to review, and the only evidence anywhere is one info line in the log. A single untracked build artifact — a generated `poetry.lock` — silently held two pushed workers out of the merge queue this way. The status pane renders the recorded reason as a yellow `dirty tree` / `tree unknown` flag on the idle row. Two cases never raise that flag. A `Stop` while the worker still has background tasks pending (`backgroundTasks`, see `docs/STATUS.md`) ended on a wait rather than on finished work: models that run their checks in the background end the turn with edits uncommitted and commit when the result wakes them, so the Stop hook skips the queue without setting a reason. And the bootstrap restores `package-lock.json` after its own `npm install` when it was clean beforehand, since a base whose lockfile disagrees with its `package.json` would otherwise start every worker with a modified lockfile.
2. **reviewing**: The prompt carries the whole branch diff inline, and a prompt past the reviewer's context window is rejected by the agent CLI before the reviewer starts. Every review-prompt builder therefore composes through `composeWithinCeiling` (`prompt-compose.ts`): it measures the assembled prompt against `MAX_REVIEW_PROMPT_BYTES` (1 MB) and, when it busts, recomposes with parts of it replaced by pointers. The reviewer runs inside the worktree with a shell, so a branch too large to inline is still reviewable — it reads what was left out itself instead of receiving it. Reference material is paged before the subject under review: first the test files inlined for the changed sources, then the documentation, each reduced to a list of paths. The test files lead because they scale with a branch's breadth rather than its size — one whole test file per changed source — so a broad branch can bust the ceiling on reference material alone: a 95-file branch inlined 977 KB of test files beside a 460 KB DESIGN.md + AGENTS.md, and with only its diff paged still assembled to 1.4 MB. Only when the prompt cannot fit with the diff inline is the diff replaced by its `git diff --stat` summary plus the exact command to page the delta file by file; the references then come back as far as they fit, so a merely huge diff degrades exactly as it did before the references were pageable. The substituted diff block instructs the reviewer to state which files it did *not* read so a partial pass cannot read as full coverage. A test file that two same-named sources map to (`src/commands/workers.ts` and `src/dashboard/workers.ts` both map to `test/workers.test.ts`) is inlined once. An agent doc the reviewer's harness loads on its own is named rather than inlined: a claude-code reviewer runs `claude -p` in the worktree, and Claude Code loads CLAUDE.md there, following an `@AGENTS.md` pointer, so inlining it too put AGENTS.md (179 KB in this repo at the time) in the reviewer's context twice (`claudeLoadedDocs`, `prompt-compose.ts`; the launch resolves the reviewer before building the prompt). A Codex reviewer gets it inline: it runs with `project_doc_max_bytes=0` and loads no instruction file of its own ("Rules System"). A degraded review beats the alternative of parking a worker and reviewing nothing; a branch that fits takes the byte-identical original path. The ceiling is deliberately set well below the reviewer's context window rather than at it: the reviewer works in that same window — rebasing, resolving conflicts, running the checks suite (whose failure output alone runs to tens of KB), reading and editing files — and a prompt sized to fill the window compacts mid-review, leaving the reviewer certifying a summary of the diff rather than the diff. It is sized from measurement: across the last 80 commits of two active repos the median review delta was 3-14 KB, p95 88-155 KB, and the largest single delta 336 KB, while the failure that motivated the guard was a 2.88 MB single-commit diff assembling to ~1.16M tokens against a 1M limit. At 1 MB a borderline-large branch still reaches the reviewer with its diff intact. `launchReview` re-checks the ceiling as a **backstop**: reaching it means degradation could not help — with the diff, docs and test files all paged, what remains (rules, commit log, file summary) still exceeds the ceiling — and no reviewer can be launched at all. Then — and only then — the worker goes to `failing` with `failingReason: "oversized-diff"` and an alert naming the size, the ceiling, and the remedy (split the work across smaller branches). This is *not* an operator-action reason — shrinking the branch changes the SHA, and the new SHA re-enters review through the normal failing debounce, so the fix retries itself; `garden kick` deliberately does not accept it, since kicking an unchanged branch re-fails. The interposed holistic pass degrades identically and applies the same backstop with a different disposition: it is best-effort over work that already merged and already passed per-phase review, so an unreviewable whole-task range leaves the worker `done` with a warn alert rather than failing it. Past the ceiling check, the poller launches a Claude reviewer (`claude -p`) asynchronously in a hidden tmux window (`_<project>-review-<worker>`). Before launching a Claude reviewer, resolver, CI-fix agent, or holistic reviewer, `launchHeadlessAgent` builds fresh settings from the caller's current project config into a protected `<promptFile>.settings.json` sidecar under `~/.garden/control/headless` (`installHeadlessSettings`). `installHeadlessSettings` lives in the claude-code adapter (`harness/claude-code.ts`). The sidecar carries the sandbox and none of garden's hooks: every headless launch sets `GARDEN_REVIEWER=1`, which made each hook a node start that returned before reading its input, on every tool call of the run. This covers resurrected Codex worktrees, whose resume path installs only the Codex runtime, and means a retry after a sandbox repair (`sandboxWriteRoots`, `sandboxAllowLocalBinding`) runs under the repaired permissions. The worker's own settings file (`claudeSettingsPath(cwd)`) is never rewritten — it carries the worker's own sandbox, which may name a per-worker backend the project's config does not — and a failed write aborts launch. The reviewer is launched with `--settings` pointing at that sidecar, so it runs under the project's sandbox config (auto-allow for bash within the configured filesystem/network allowlist), and with `--permission-mode acceptEdits`: auto mode never engages under `-p` (verified on 2.1.251 — no headless transcript ever carries the `auto_mode` attachment), so without the flag every Edit/Write falls to a permission prompt a headless session has nobody to answer and is rejected; reviewers survived that only by editing through Bash heredocs, and an Opus reviewer that declined the workaround reported FAILED on a sound branch. The reviewer rebases onto the base branch, resolves conflicts, runs optional checks, fixes check failures, and reviews code against project rules. The poller polls for review completion by checking if the review window still exists. On completion: if clean or fixed, force-pushes and transitions to merge-pending. If the reviewer cannot fix the issues, transitions to failing. If the review process fails for transient reasons (Anthropic API 5xx/429/`overloaded_error`/`rate_limit_error` and the reviewer didn't commit anything), the poller auto-retries with exponential backoff (30 s → 2 min → 5 min, budget 3) before escalating to `failing` with `failingReason: "transient-review"` — `garden kick` accepts that reason and re-queues without requiring new commits. A session/usage-**quota** cutoff is distinct: the reviewer hit a hard usage limit ("You've hit your session limit …" for Claude; "You've hit your usage limit … try again at …" for Codex) and emits no verdict, so a seconds-scale retry is useless. The response depends on the reviewer's harness. A **foreign** reviewer (e.g. a per-project Codex reviewer) runs on a separate subscription whose window resets on a multi-day scale — waiting it out would wedge the whole project's merge pipeline — so the poller falls back to the first-party Opus reviewer immediately (a deduped warn alert names the blocked harness and its reset time; the configured reviewer resumes automatically on the next cycle once its window clears). A **claude-code** reviewer runs on the operator's own account, so that limit *is* the operator's rolling window and there is no stronger fallback: the poller auto-retries on a flat 15-min cadence (budget 24, ~6 h ceiling) until the window resets and the review merges on its own with no operator action, escalating to `failingReason: "quota"` only if it never clears. Both `transient-review` and `quota` are `garden kick`-recoverable. Until a retry's `reviewRetryAt` passes, the launch defers on every poke, and its re-poke is deduped to one per project by `control/review-backoff-recheck-<project>`, whose mtime is the deadline the armed poke is due at: a worker due sooner arms its own, and one due later is re-checked when that poke fires. Armed on every poll instead, a backoff (15 min on a quota wait) collected one sleeper per poll, all firing together when it ran out. A third case is an **unparseable verdict**: the reviewer produced genuine output (not an API error) that lacked a standalone `CLEAN`/`FIXED`/`FAILED` line — it trailed off in prose ("Final suite is green (2609 unit + 103 integration, lint clean)."), decorated the token (markdown, "Verdict: CLEAN"), or buried it above a long test dump past the 20-line scan window. The reviewer already reached a conclusion; it just failed to format the final line. Rather than re-run the whole (Opus) review, the poller first hands that output to a cheap, fast **Haiku classifier** (`extractReviewVerdict`, `verdict-extract.ts`) that reads the reviewer's own conclusion and returns the verdict. The call is synchronous with a hard 45 s timeout (the poll loop already blocks on git network I/O, so a bounded classification is architecturally consistent) and runs on the same first-party Anthropic account as the reviewer; an ambiguous answer, timeout, or spawn error yields no verdict and falls through. It runs with no tools (`--tools ""`), because the output it reads derives from worker-written content and the process runs unsandboxed. A run that exits non-zero also yields no verdict: the `claude` CLI prints its own failures, such as an expired login, to stdout, and `Failed to authenticate` used to read as FAILED. So does an `UNKNOWN` answer, which the classifier is told to give when the reviewer never reached a conclusion (its output is an error message, such as an API or auth error, or it stopped before finishing). Each of these takes the unparseable re-review (`handleUnparseableReview`) rather than failing the worker as code. A recovered verdict dispatches through the normal path (force-push + merge-pending for CLEAN/FIXED, `failing` for FAILED). Only when the classifier also can't determine a verdict (or the reviewer produced no output at all) does the unparseable path re-review: when the reviewer ends its turn with prose instead of a standalone token and committed nothing, the reviewed diff is unchanged and usually fine, so the poller re-runs the review on a short flat backoff (15 s, budget 2) before escalating to `failing` with `failingReason: "unparseable-verdict"` (also `garden kick`-recoverable). The dominant source of that prose tail is a reviewer that **backgrounded** its long command — overwhelmingly `garden checks` — and ended its turn waiting to be re-invoked: a headless process exits when its turn ends, so the background task is orphaned and the promised completion notification never arrives. Six consecutive reviews of one wolf worker died that way over two days, each on a variant of "I'll wait for the completion notification," and each re-review repeated the mistake because it was made the same way. The prompt-side guard is `headlessSingleTurnNote` (`prompts.ts`), carried by all four headless roles' output-format sections and reinforced in the checks step: stating the rule alone was not enough — reviewers rationalized around it ("the background checks job already notifies on completion, so no monitor is needed") — so the note names the *mechanism* (this process exits when the turn ends) and gives the escape hatch for a suite too long for one tool call, which is foreground chunks, never a background launch. The note also tells the agent to emit its verdict in that same response, never deferred to a background task, an async workflow or a later message. None of these retry relaunches — transient, quota, unparseable-verdict, or a foreign-reviewer Opus fallback — consumes a grow loop iteration: a retry re-reviews the same commits (the reviewer emitted no verdict, the worker did no new work), so `launchReview` advances the iteration counter only for a genuinely new worker turn, not a retry relaunch, and only once that review's reviewer window has opened (a launch that stopped short of `reviewing` is no iteration) — otherwise a multi-hour quota wait would inflate `grow.iteration` toward the budget and end the loop early. An unparseable verdict where the reviewer *did* commit work takes the reviewer-committed-work recovery (force-push its commits, re-review once) instead; a review timeout still transitions to failing immediately. Unreviewed code is never auto-merged. An operator prompt landing mid-review does not by itself disturb the pass — but the moment the woken worker runs a mutating tool (an Edit/Write from any thread naming a file inside the worktree, or a main-thread Bash command that changed the worktree: the review launches on Stop, so main-thread activity during it means a prompt landed, and a prompted worker edits through the shell as readily as through Edit. A `PreToolUse` hook on Bash records a worktree fingerprint while a review runs and `PostToolUse` compares, so a read-only answer leaves the review running; an unrecorded start counts as a change, and a subagent's Bash never counts. Outside the review-to-merge states that hook records nothing, so its shell command drains its input and exits before starting node while a per-worktree marker beside the settings file exists (`editsUnwatchedMarkerPath`): the poller creates the marker under the registry lock only after reading an unwatched state and removes it in the locked write that enters a watched one, so a missing marker only costs the node start, and a marker is never present while edits are watched. The fingerprints are kept in `entry.reviewBashBaselines`, keyed by `tool_use_id`, and `syncEditsUnwatchedMarker` (`poller-state.ts`) creates and removes the marker. An edit tool counts unless the file it names lies outside the worktree both as written and through symlinks: the path (`file_path`, or `notebook_path` for NotebookEdit; a relative one resolved against the hook input's `cwd`) is compared with the worktree directly and as the real path of its nearest existing ancestor, since a Write can create directories, so a link outside the tree that points into it still counts, and a missing or unresolvable path counts as well. An edit outside the tree, such as a subagent's scratch copy, the memory directory or a temp file, cannot change what the reviewer certifies; before this rule, a background workflow agent's edits to its own scratch copy cancelled one worker's review twice in twenty minutes on 2026-10-24), its PostToolUse hook stamps `reviewInterruptedAt` and pokes the poller, which cancels the review outright: the reviewer shares the worker's worktree, so the tree under certification is being rewritten and any verdict — even one already written — is discarded rather than dispatched. The worker resets to `working` with `pendingReviewAt` re-armed; its next Stop re-reviews the complete branch at quiescence. The interposed holistic pass cancels the same way (its markers clear; the gate re-evaluates at the worker's next terminal state).

**Unfinished reviewer rebase.** The reviewer rebases before it reviews, so a rebase still in progress once its window is gone means it stopped partway, with HEAD a partial replay. That HEAD can be the base tip itself, which the merge queue's resume check reads as a merge that already landed. `handleReviewing` aborts the rebase before anything reads or pushes HEAD, and only a FAILED from that pass stands; a CLEAN or FIXED, parsed or recovered by the Haiku classifier, goes to the unparseable re-review. This is the reviewer-side counterpart of `docs/STATUS.md` invariant 7, which accepts a resolver's `DONE` only after verifying the worktree, including that no rebase is in progress. A review cancelled because the worker edited mid-review leaves the rebase alone, since aborting it would reset the tree the worker is editing, and raises a warn alert naming it instead.

Reviewer, resolver, and CI-fix prompt/result exchanges live under `~/.garden/control/headless`, outside the worker-writable `~/.garden/sessions` IPC tree. This makes the verdict channel a control-plane boundary: a worker cannot replace a result after the headless agent exits. `headless-paths.ts` preserves valid project and worker names but maps unsafe, malformed, or oversized identities to bounded SHA-256 components, so even a forged registry name cannot traverse outside the control directory or exceed filesystem filename limits. Transient exchanges are swept after their window exits; durable holistic shadow reports live separately under `~/.garden/control/reports`.

**Non-blocking notes.** A reviewer has one outcome between fixing a finding and failing the review: a finding the project's own rules classify as non-blocking (for example, a rule that a new guard, latch, or implementation-pinning test must cite a real incident, and this one cites none) is listed under a `Non-blocking notes:` heading directly above the verdict line and is not implemented. Such notes never change the verdict — a review whose only findings are notes is `CLEAN`. The convention is `nonBlockingNotesConvention` (`prompts.ts`), carried by the per-phase review prompt and the holistic fix-mode prompt, and only for a project whose rules or agent docs (`DESIGN.md`/`AGENTS.md`/`CLAUDE.md`) mention non-blocking findings at all. `nonBlockingNotesFor` makes that check, a case-insensitive `non[- ]?blocking` match over the rules and the committed text of those docs. It also tells the reviewer that a pre-existing or unrelated problem, a coverage nit, or a passing observation is not a note. Offered to every project, the heading became a catch-all for observations in projects with no rule to classify anything. Because the review body is scrubbed at merge, the poller lifts the section out of every parsed verdict (`recordReviewNotes`, `review-notes.ts`; any verdict, including Haiku-recovered ones and the holistic pass) and appends it with its timestamp, worker, branch, and verdict to `~/.garden/control/reports/review-notes-<project>.jsonl` — the trusted control tree, beside the holistic shadow reports, so a worker cannot forge one. It raises no alert: a note is by definition nothing to act on now, and one alert per review turned the alerts pane into a feed of them. `garden notes <project>` prints them (`--clear` removes them). Extraction is tolerant: a missing or `none` section records nothing, the last such heading wins, the section ends at the next markdown heading, and every failure is logged and swallowed rather than touching the verdict.

4. **merge-pending**: Review passed, waiting to merge. A serial merge queue processes one merge at a time per project (ordered by timestamp). The merge sequence: rebase onto the base tip origin reports (skipped outright when the branch already contains the base tip, and merge-preserving when it carries merge commits — see "Merge Handling" step 6), force-push, then ff-merge. If the rebase has conflicts (because the base branch advanced while waiting), the poller launches a dedicated resolver and transitions to `resolving`. If the rebase is clean, the merge proceeds.
5. **resolving**: A dedicated resolver Claude session is running in a hidden tmux window with a single narrow job: complete the rebase onto origin's base branch and commit any conflict resolutions. That window is the worker's `_<project>-review-<worker>`: `launchResolver` (`poller-resolve.ts`) reuses the review window name and the review prompt and result paths, so no resolver-specific window exists. The resolver does not push and does not re-review code — the code was already approved. When the project configures a `checks` command, it runs `garden checks` in the foreground on the rebased result and fixes only what the two sides broke in combination, reporting `FAILED` when it cannot make them pass: the review ran the checks before the base moved, and the poller verifies only that the rebase landed, so a project without a CI gate would otherwise merge the resolution untested. On Stop, the poller verifies the rebase actually landed (no `.git/rebase-merge` or `.git/rebase-apply` present; `origin/<base>` is an ancestor of HEAD; HEAD differs from `preResolveSha`). On pass, force-pushes and returns to `merge-pending`. On fail, retries up to `resolveAttempts = 2`; on budget exhaustion, transitions to `failing`. A resolver that times out parks in the kick-recoverable `review-timeout` with the budget reset, as the budget-exhausted park resets it: the attempt was counted at launch, so a budget carried through the recovery would escalate the next conflict without launching a resolver. A `FAILED` resolver that did complete the rebase leaves HEAD off the cleared `mergeReadySha`, so its retry goes back through a full review instead of merging it. A genuine unresolvable conflict parks with `failingReason: "code"` and an operator alert that names the unmerged files; a transient backend outage (Anthropic/codex 5xx/429/`overloaded_error`/`rate_limit_error`) or a session/usage-quota cutoff parks with the kick-recoverable `failingReason: "transient-review"` instead — `garden kick` re-queues the merge once the outage or quota window clears, rather than telling the operator to push a fix they don't need. Unlike the reviewer, the resolver has no dedicated `quota` reason or Opus fallback: a quota block (a foreign harness's usage-limit surfaces only through `quotaLimitResetHint`, not `isTransientError`) folds into `transient-review`. Any worker push during `resolving` aborts and resets budget — the worker's new state is the new ground truth.
6. **failing**: Unfixable review issues, failed review process, exhausted resolver budget, or repeated merge failures (a diverged base or branch protection wedges the merge; once `failCount` hits the retry budget the poller stops re-reviewing and parks here instead of burning a review every cycle). Poller watches for new commits via SHA tracking. After 30s debounce with no new pushes, state transitions back to working for retry. Each failure increments a `failCount` on the worker entry; after 3 consecutive failures, an alert is surfaced. The count resets on successful merge.
7. **merged**: Transient post-merge beat — code just landed on the base branch. Renders neutral (not green) in the status pane; not an operator-actionable signal. Cleared the moment the auto-continue prompt's `UserPromptSubmit` fires, returning the worker to `working` for the next phase. If `agentStatus` is `working` or `asking` when `finalizeMerge` writes either terminal state (a prompt landed mid-merge and may now be blocked on a question), the poller clears `merged`/`done` immediately to `working`; rendering then falls back to the live process status, preserving the yellow `asking` signal when applicable.
8. **done**: Worker self-declared finished via the `.garden-done` sentinel and the merge cycle has settled. Renders bold green ✓ in the status pane — the operator's "this work is complete, the worker can be cleaned up" signal. Two paths in: `finalizeMerge` sets `done` directly when the sentinel was set before the final push (skipping the transient `merged` beat); the Stop hook sets `done` when the worker writes the sentinel after auto-continue and ends with no commits ahead, but only from no `prState`, `working`, `merged` or `done` (a compare-and-set under the registry lock). The pipeline states are the poller's, and two of them also read as no commits ahead with the sentinel on disk: a holistic pass reviews a branch fast-forwarded to base, and a merge has pushed before its terminal write. Nor does it set `done` over uncommitted changes: `git status --porcelain` must come back empty (the bootstrap's `info/exclude` keeps the sentinel itself out of it), and a check that cannot run counts as dirty, as for the review gate. `done` invites the operator to remove the worker, and removal deletes the worktree with `--force`, so a turn that wrote the sentinel over an uncommitted edit is not marked `done`, and the hook logs the skip. So that a sentinel written by a turn that ran while a merge finalized is not lost, `finalizeMerge` reads it again at the terminal write, after `postMerge`. Cleared on `UserPromptSubmit` (operator nudges the worker back to work).

### Shared-State Transactions

Config, registry, and dashboard state are shared by short-lived hooks, pollers, and operator commands, so atomic rename alone is not enough: an unlocked read-modify-write can still replace a newer complete file with an older complete snapshot. `mutateConfig` serializes every config mutation, and is the only config writer besides `garden init`: `loadConfig` migrates in memory (plots, project log colors) and leaves persisting that to the next `mutateConfig`, which loads under the lock, because a reader that saved wrote back a snapshot taken outside it — reverting a mutation committed after its read, or persisting a file an editor had truncated mid-rewrite; `mutateRegistry`, `updateWorkerFields`, and `updateWorkerFieldsIf` do the same for worker records; `addWorkerWithUniqueName` generates and inserts a globally unique worker identity from one locked registry snapshot; `withStateLock` protects visible dashboard pane/state changes. The common `file-lock.ts` lock record contains the holder PID plus a unique acquisition token. Dead holders and old unparseable partial records are reclaimable, as is a lock whose live PID belongs to a process `ps` reports starting more than 30s after the lock was written (the holder died and its PID was handed out again); a demonstrably live PID is never evicted because of age, and release removes the pathname only while its token still owns it.

Poller lifecycle moves use `transitionState`, which reads the worker's current `prState`, validates the workflow edge, applies the fields, and claims any one-shot handoff callback in one registry transaction. A stale caller therefore cannot validate one snapshot and overwrite a newer state; invalid moves return `false` without writing. `forceTransitionState` is the explicit recovery escape hatch rather than an implicit warn-and-write path.

The fields that live for one review, resolve or ci-fix cycle (the review retry counters and markers, the resolver and ci-fix budgets with their last attempt, the holistic pass markers) are cleared through named reset sets in `cycle-resets.ts` that every cycle-ending transition spreads, not through per-site lists. The lists had drifted: three of the eleven sites that cleared the review retry counters also cleared the one-shot unparseable-verdict marker, so a cycle ended by a worker push, an edit, a timeout or a failing park handed the marker to the next cycle, whose first unparseable verdict then went straight to `failing` without its retry.

Worker creation keeps slow and failure-prone preparation outside the dashboard state lock: provider preflight, base-branch publication, registry setup, model resolution, and bootstrap construction all finish first. A foreground spawn then re-reads dashboard state under `withStateLock` for only the project/pane swap and final state write. A background handoff never acquires that lock because it creates a detached window and does not mutate the operator's visible state.

### Project Configuration
Projects can define settings in `~/.garden/config.yml`, either by editing the file directly or via `garden config <project> <key> <value>`. The CLI and the `⌥,` project menu set a scalar key through the same `setProjectConfigKey` (`src/dashboard/project-config-mutate.ts`), so both share one writer and its validation; the per-role review dims go through `setProjectRoleDim`, which only the CLI calls. Both return a `MutateResult` (a message plus notes) for each surface to present. In the `⌥,` project menu, the base-branch row shows the effective base (the branch new workers would resolve to), tagged `(default)` while `baseBranch` is unset; the crew row opens the `⌥⇧C` picker; and there is no `config.yml` editor row. A file that exists but does not load (a YAML syntax error from a hand edit) is reported as itself: `loadConfig` names the file and the fault, and `tryGetProject` / `detectProjectFromPath` pass that error on instead of reading it as an unknown project. They answer "no project" only for a project that is not configured or a garden that is not initialized. The watchdog raises the failure as an error alert (see "Alerts"):

```yaml
projects:
  garden:
    path: /Users/joshua/code/keychange/garden
    checks: npx tsc --noEmit && npx vitest run
    postMerge: npm install && npm run build
```

**Base branch**: Each new worker branches from and merges into a base resolved at creation time by `resolveSpawnBase` (`src/dashboard/git.ts`), in precedence order: the per-worker `workers new --base <branch>` override, then the project's configured `baseBranch` key, then the current branch of the main checkout (the legacy default), falling through to the `origin/HEAD` symref and finally `"main"`. Setting `garden config <project> baseBranch <branch>` makes the base authoritative and independent of whatever the checkout happens to be parked on; leaving it unset preserves the checkout-follows behavior. `garden config` validates the name softly (a not-yet-on-origin base only warns; it is published at first spawn), so the network-free set stays snappy.

The resolved value is validated against the local `refs/remotes/origin/<base>` ref (no network call, so the ⌥n hotkey stays snappy on slow links) and pinned to the worker in the registry (`WorkerEntry.baseBranch`). If the base branch has no local origin ref — the natural case is the operator switching the main checkout to a brand-new local-only branch and pressing ⌥n — garden treats the ⌥n press as a publish gesture and runs `git push -u origin <base>` from the main checkout to create the ref, then proceeds with worker creation. Only when the publish itself fails (no remote, branch protection, non-fast-forward, network) is the worker rejected; the rejection message surfaces the actual git stderr so the operator can fix the real problem instead of guessing. The bootstrap script's fresh `git fetch origin <base>` is the backstop: when the fetch fails, `ls-remote --exit-code` disambiguates why. Once the base is settled, the bootstrap asks origin for that branch's commit (`baseShaStep`) and uses the SHA it reports for both the main-checkout fast-forward and the `worktree add`, rather than the `refs/remotes/origin/<base>` ref its own fetch just wrote: that ref is in the shared git dir every worker sandbox can write, and the new worktree's dependencies are then installed with their package scripts, unsandboxed, as the operator — so a worker that rewrote it would be choosing the code that install runs. A reading origin cannot supply aborts the spawn like the unreachable-origin case above rather than falling back to the local ref, which is the value being distrusted. Because a SHA start point leaves the new branch with no upstream, the bootstrap sets it explicitly; garden's own worker rules have every worker check `git log @{u}..HEAD` before ending a turn. Exit 2 (origin answered, ref absent — the branch was deleted from origin) triggers the fallback to origin's default branch; any other failure (auth, outage, DNS — GitHub returns "Permission denied (publickey)" when its git auth path is degraded, so this class hits every project at once) means origin was unreachable, and the bootstrap aborts with a "could not reach origin — retry the spawn" alert instead of second-guessing a base that may be healthy. Once pinned, all consumers (poller, Stop hook, kick, resume) use `getWorkerBaseBranch(entry, ...)` — they never re-resolve from the main checkout, so switching the main checkout's branch after a worker is spawned does not retarget that worker.

If the Stop hook still fails to count commits ahead of `origin/<pinned-base>` (e.g., the base branch was deleted from origin after creation), it raises a one-per-hour `base-drift` alert (`source: worker`, `level: warn`) rather than silently swallowing the error.

**checks**: Command the reviewer runs in the worker's worktree after rebasing onto the base branch, so checks validate the combined state of the branch plus latest base. If checks fail, the reviewer fixes the issues and re-runs. No checks configured means the reviewer only does the code review. The worker's preamble (`buildWorktreeRules`, `src/rules.ts`) names the same command, so the worker, the reviewer and CI gate on one string, and the command has to stay aligned with what the project's CI workflow runs (`.github/workflows/test.yml` for garden). Before 2026-05-06 the worker prompt did not name it and the configured string left out suites CI ran, so workers pushed state that only CI caught.

**holisticReview**: Controls the whole-task coherence review interposed after a multi-phase default worker reaches `done` with at least two merges. It is one headless reviewer pass on the worker's own branch (reusing the per-phase reviewer flow, so a configured Codex reviewer runs it too), not a spawned worker — the worker re-opens `done` → `reviewing` for the pass. `fix` is the default when the key is unset: the reviewer fixes genuine cross-phase defects directly and the fix rides the normal CI + merge gate. Set `shadow` for report-only findings (surfaced as an alert) or `off` to disable the review. See `WORKFLOWS.md` "Holistic-review workflow" for the dispatch gate and lifecycle.

Workers and reviewers are instructed to run the command via `garden checks [project]` (`src/commands/checks.ts`), which executes exactly the configured string under a **machine-wide checks semaphore** (`src/checks-semaphore.ts`): a hardware-derived number of concurrent suites (`max(1, floor(cores / 8))` — 1 on an 8-core laptop, 2 on a 16-core desktop) is admitted and the rest queue, so a merge wave stretches clock time instead of oversubscribing the operator's workstation. Slots are pid-stamped `checks-slot-<n>.lock` files in `~/.garden/sessions` claimed with `O_EXCL`; a slot whose owning pid is dead, or belongs to a process `ps` reports starting after the claim, is stolen (a SIGKILLed run cannot leak its slot), while an empty slot is a claim in progress for its first 30s, and a 45-minute max wait fails open — a queued run eventually proceeds ungated rather than wedging the fleet on a semaphore bug. CI runs the raw command on its own isolated runner and is deliberately not gated. The slot count derives from the machine at each invocation, so the same config adapts when the hardware changes — unless the operator pins it with the garden-level `limits.checksSlots` override (see "Machine-wide limits").

**postMerge**: Command that runs on the main checkout after merging, but only when the *working tree itself* advanced — i.e. the base branch was the one checked out, so `merge --ff-only` moved the tree to the merged code. When the operator has parked the checkout on a different branch (the deliberate many-base workflow), the merged base ref is advanced on its own via `git fetch origin <base>:<base>` (fast-forward-enforced, worktree-aware) without touching the working tree, and postMerge is skipped — building a tree that's on another branch would build the wrong branch. That off-base ref advance is silent: a local base ref that merely trailed origin is normal here, not drift. The base checkout is the operator's shared working directory — they commit, pull, and edit in it — not a pristine mirror, so a failed fast-forward is expected and benign for merge correctness (the work already landed on origin; only the local rebuild lags). postMerge is not allowed to dirty it, though: after the hook runs (success or failure), `revertPostMergeChurn` restores tracked files that the hook modified but that were clean before it started, comparing `listModifiedTrackedFiles` snapshots taken either side. Operator edits already in flight are in the before-set and are left strictly alone, as are untracked and staged changes. A file the operator saves while the hook runs cannot be told from its churn, so what is reverted is first saved as a patch under `~/.garden/control/reports` (`discarded-<project>-<time>.patch`, restorable with `git apply`, named in the revert's log line), and nothing is reverted when the patch cannot be written. This closes a self-sustaining trap: `npm install` rewrites package-lock.json, which sits harmless until a merged commit also touches that file (`merge --ff-only` tolerates a dirty file the merge does not touch and refuses only on a collision — a dependency bump supplies one soon enough), after which the refusal skips postMerge, so nothing ever cleans the file and the checkout freezes permanently along with any binary built from it. Observed in the field at 14 merges of drift with every merge still reporting success. The corollary is that postMerge cannot be used to leave generated files sitting in the checkout — never durable anyway, since garden does not commit them. One failure mode self-heals: when the on-base checkout has a redundant local commit whose *clean* tree already equals origin/<base> (e.g. an operator heal commit whose change also merged the normal way), the ref is reset onto origin (`reset --keep`, reflog-preserved, working tree unmoved; `--keep` refuses rather than overwrite a file saved after the clean-tree check, and refuses outright mid-merge) and postMerge runs — no alert. The remaining states alert, framed as "merge succeeded, local checkout needs a hand": it has *diverged* from origin with real local-only content (warn, the operator reconciles by hand), the base is checked out in *another worktree* (warn, that worktree needs a pull), the on-base checkout is *dirty* with uncommitted changes (warn, the operator cleans it — the alert names how many commits behind origin the checkout has fallen, and, when a `postMerge` hook builds from it, that anything built from it is that stale, so a long-running stall reads as one instead of as a routine blip; a checkout level with origin gets no drift clause at all), or it is *wedged*/unfetchable (`stuck`, error — infra trouble). Each alert fires only on *entry* into the state, not on every subsequent merge while it persists: the last outcome per project and base is kept on disk (`control/ff-state-<hash>`), since each poll is a fresh process and an in-memory record read every merge as an entry. This is essential for projects like garden itself, where the poller runs the compiled CLI. When the garden project itself rebuilds successfully, the poller spawns a detached `_post-rebuild-refresh` via the freshly-built binary; it reinstalls the status bar and key bindings (the poller's own pre-spawn calls run pre-rebuild code, so a binding change would otherwise wait for the next merge), respawns the status and logs panes, calls `restartLongLivedPollers()`, and refreshes the dashboard. That restarts the two processes that hold their build in memory, the usage poller and the watchdog. Per-project pollers are not restarted: each pass of their bash loop execs a fresh `dashboard _poll`, so the next poll already runs the new bundle, and killing one mid-poll cuts a rebase, push, or merge finalization short (the merge that triggered the rebuild is itself still finishing in the garden poller). What a running loop does pin is its own command line, the runner path included, so `startProjectPoller` stamps each poller pane with a hash of that command (`@garden_poller_loop`) and `restartDriftedPollers` restarts a poller whose stamp differs from the one the current build would start, only while it waits between polls; the watchdog runs the same check every tick, so a poller that was busy is caught on a later one. The bundles themselves are swapped atomically: `scripts/build.mjs` writes each to a temp file (mode 0755, since `garden` on PATH is a symlink to `dist/cli.js`) and renames it into place, because esbuild rewrites an existing outfile in place and a hook or poll starting mid-build could load a truncated file.

**sandboxDomains**: Comma-separated list of extra network domains added to each worker/reviewer's sandbox allowlist. Use for private registries, internal services, or other hosts beyond the garden-wide defaults (Anthropic, GitHub, npm, the project's git remote host). Set via `garden config <project> sandboxDomains foo.com,bar.com`.

**sandboxDenyCredentials** (default `false`): When `true`, the worker sandbox additionally denies READ of the operator's credential paths (`~/.claude`, `~/.ssh`, `~/.aws/credentials`, cloud creds — `DENIED_CREDENTIAL_PATHS` in `src/dashboard/sandbox.ts`) via Claude Code's `sandbox.credentials` (mode `deny`) plus `filesystem.denyRead`. Both are OS-enforced (Seatbelt/bubblewrap) and, per Claude Code's docs, apply to sandboxed Bash **subprocesses only** — the parent `claude` and the headless `claude -p` reviewer authenticate before the sandbox boundary, so their own Anthropic auth is unaffected. This closes the credential-exfiltration path a prompt-injected worker would otherwise have (read `~/.claude/.credentials.json`, POST it out over an allowed host). It defaults **off** because that parent-auth timing is documented but not guaranteed for every release, and getting it wrong would break reviewer auth fleet-wide: enable it per project (`garden config <project> sandboxDenyCredentials true`) only after verifying a headless `claude -p` still authenticates in a sandboxed worktree carrying the config, and a sandboxed `cat ~/.claude/.credentials.json` is blocked. Requires Claude Code >= 2.1.187 (`sandbox.credentials` deny mode); `mask` mode is deliberately never emitted (it is ignored in a repo's `settings.json`). claude-code workers only — a Codex worker's `workspace-write` sandbox has no per-path read-deny.

**sandboxAllowLocalBinding** (default: false): Opts a project's Claude Code sandbox into `network.allowLocalBinding` for HTTP-serving tests and paired engine/server checks on macOS. It permits listening and direct localhost connections; it also reaches other services on the host's localhost and permits non-loopback listeners, so it is project-specific rather than a fleet default. Domain filtering, credential denies, and filesystem restrictions remain in force. Linux's sandbox network namespace is unchanged. Set with `garden config <project> sandboxAllowLocalBinding true`; new/bounced workers and each new headless launch use the value.

Claude sandbox temporary write roots include `/tmp`, its canonical target (`/private/tmp` on macOS), and the canonical `os.tmpdir()` inherited by the trusted launcher (the per-user macOS temporary directory). Application test data stays project-specific: use `sandboxWriteRoots` for the exact application directory, such as `~/Library/Application Support/Godot/app_userdata/<project name>`, rather than granting all of Application Support or all Godot data.

**sandboxWriteRoots** (default: none): Extra directories every worker sandbox may write, beyond the built-in roots (worktree, `~/.npm`, `~/.cache`, `~/.garden/sessions`, `/tmp`) and the per-project git/beads roots, which are all preserved. Applied to both harnesses — Claude Code `sandbox.filesystem.allowWrite` and Codex `sandbox_workspace_write.writable_roots` — on newly created or bounced workers and every headless Claude launch. The motivating case is `~/.config/gcloud`, so `gcloud` can refresh credentials and complete Google Prompt MFA inside the sandbox instead of each session needing a one-off grant. Managed as a list: `garden config <project> sandboxWriteRoots [list | add <path> | remove <path>]`. `add` expands `~` against HOME, normalizes to an absolute path (no trailing slash or `..`), dedupes against existing entries, and refuses a root that is relative or too broad — the filesystem root, a top-level directory, the home directory or any ancestor of it, or anything overlapping garden's control plane (`~/.garden/control`) — checking a symlink's resolved target as well. Every entry is re-validated at launch (`resolveSandboxWriteRoots`, `src/config.ts`), so a hand-edited `config.yml` entry that `add` would refuse fails the launch instead of being granted. Only paths are stored or printed; garden never reads the directories, and grants no credential path by default.

Existing `sandboxWriteRoots` targets must be directories. Validation canonicalizes symlinks, including a missing leaf below an existing symlinked ancestor, stores the resolved target rather than a mutable alias, and refuses a symlink whose target cannot be resolved. This also preserves the threat-model invariant that `~/.garden/config.yml` is not grantable as a write root. A configured `beadsDir` is the other route into the same grant (a bead-intake project's workers may write the store), so it is held to the same refusals and canonical form (`resolveBeadsWriteRoot`).

Worker launch-plan resolution validates and canonicalizes the roots before adapter rendering. The Codex command renderer consumes that validated runtime project, keeping filesystem validation out of the hook bundle.

**displayName** (default: none): Operator-facing label for the project. When set, the status pane's project header, the bottom bar's left segment, the pretty `garden logs` project column (including the dashboard logs pane), and the pretty `garden list` / `garden plot list` / `garden plot show` views show it in place of the project key (`projectDisplayName` in `src/config.ts` resolves the fallback). It is cosmetic only: the key stays the project's identity in CLI arguments, JSON output (`garden list` adds a `displayName` field beside `name`), log filtering, `$GARDEN_PROJECT`, worktree paths, branch names, hidden window names, and `project:<name>` bead labels, and commands do not accept the display name as a project argument. Set with `garden config <project> displayName <label>`; blank and multi-line values are refused, and `unset` clears it.

**claudeProfile**: Name of an alternate Claude Code config dir to use for this project's workers and reviewers. Profiles are registered globally under `claudeProfiles:` in `~/.garden/config.yml` (each entry has a `configDir` and optional display `label`). When set, every `claude` invocation for the project — workers, reviewers, resolvers, the prefix-`C` ad-hoc launcher — runs with `CLAUDE_CONFIG_DIR=<configDir>`, so Claude reads its credentials, settings, and history from that dir instead of `~/.claude`. On macOS the credentials live in a Keychain entry keyed by that dir (`Claude Code-credentials-<first 8 hex of sha256(configDir)>`), not in the shared default entry. `keychainServiceFor` (`credentials.ts`) derives that service name, and Claude Code reads the entry ahead of `<configDir>/.credentials.json`. Which plan a profile spends is decided by the account approved at `/login`, so `garden auth status` names each profile's account and flags one that shares the personal organization. `/login` approves whatever account the browser is signed into, so a profile can silently land on the personal account and spend the personal plan; the fix is `garden login <profile>` with the browser signed into the intended account. `auth status` reads each account from the `oauthAccount` record Claude Code writes at `/login` (`<configDir>/.claude.json` for a profile, `~/.claude.json` for the default), and identifies each credential by a short SHA-256 digest of its access token rather than the token's first characters: the column exists to tell credentials apart, which a digest does without putting secret material in a terminal, a scrollback or a piped log. Projects without `claudeProfile` use the personal default. Manage profiles with `garden claude-profile {list,add,remove,login}`. The usage meter is not split per profile: `/api/oauth/usage` aggregates by user identity, so two workspace tokens tied to one email return identical data. Per-workspace quota for the alternate plan, if any, is only visible from the org owner's admin dashboard.

**provider**: Name of a model provider this project's WORKERS run on — an Anthropic-Messages-compatible backend (DeepSeek's `/anthropic` endpoint, a local Ollama, a gateway) the unchanged Claude Code harness reaches by env swap. Providers are registered globally under `providers:` in `~/.garden/config.yml` via `garden provider add <name> --base-url <url> --token-env <ENV_VAR> [--map opus=m1,sonnet=m2,haiku=m3] [--egress h1,h2]`. Worker launch commands get `ANTHROPIC_BASE_URL`, `ANTHROPIC_AUTH_TOKEN`, and `ANTHROPIC_DEFAULT_*_MODEL` from the model map; the sandbox allowlist gains the base-URL host plus any `--egress` extras. The key never enters config or a generated shell command. Garden's operator-shell entry points (`provider add`, `config set provider`, dashboard create/attach, `workers new`, `auth status`) copy it into a provider-specific **hidden** tmux environment variable, which persists for bounce/resume but is not inherited by ordinary panes. Every provider-worker create/resume/bounce/loop path funnels through `tmuxWorkerCommand`: one atomic tmux command queue temporarily makes only that provider's vault variable inheritable, starts the selected pane, and re-hides it; `providerEnvPrefix` maps the variable to `ANTHROPIC_AUTH_TOKEN` and removes the internal vault name before the agent process starts. The failure path independently re-hides it if tmux aborts the queue. `workers new` refuses to spawn a provider worker whose key is in neither the invoking shell nor the vault, and `garden auth status` reports both locations (and syncs as it reads). Provider profiles are an Anthropic env-swap contract, so `workerLaunchCompatibilityError` rejects any harness with `providerProfiles: false`; it also enforces `sandbox` and the harness's explicit `workerWorkflows` allowlist before launch. Reviewer, resolver, and ci-fix agents deliberately ignore provider keys: `reviewerEnvPrefix` actively empties any inherited `ANTHROPIC_*` env so they stay on the first-party Anthropic path, and each of the three defaults to Opus on the claude-code path (not just for provider-backed projects) — the strong reviewer is the safety net that makes cheap or experimental worker models safe to try. Each default is overridable per role via `garden config <p> role <role> model <m>` (and the whole role is routable to another harness, e.g. Codex; see the per-role resolution in `docs/MULTI-MODEL.md` "Phase 4"). When *every* project has a provider, the Claude usage poller, the Stop-hook usage refresh, `garden usage`, and the meter pane switch off with an explanatory line. Applies to newly created or bounced workers; live panes keep their pinned env. See `docs/MULTI-MODEL.md`.

**harness**: Default agent CLI (harness) for this project's WORKERS — the axis-2 analog of `provider` (axis 1). Registered harnesses are `claude-code` (absent = this default) and `codex`; the operator-facing alias `claude` (the claude-code crew-member name) is accepted anywhere a harness name is entered — `--harness`, `config <p> harness`, `config <p> role <r> harness` — and canonicalizes to `claude-code` (`canonicalHarnessName`, `src/dashboard/harness/core.ts`). Set via `garden config <project> harness codex`; `garden workers new <project> --harness <name>` overrides it per worker. The project default applies to the **default workflow only** — grow workers stay on claude-code regardless (a foreign harness is not yet exercised against their cold-respawn identity). Only the worker default lives here; the review family (reviewer/resolver/ci-fix) selects its own harness under `garden config <p> role <role> harness <name>` — a provider never reaches review, the safety net. Applies to newly created or bounced workers. See `docs/MULTI-MODEL.md` "Layer 3".

**model / effort**: Default worker model and reasoning effort for this project's **default and grow** workers — the project-level analog of `garden workers new --model` / `--effort`. They layer beneath the per-spawn flags in `newWorker` in precedence order per-spawn flag > project key > account/provider default, exactly as `baseBranch` sits beneath `--base` via `resolveSpawnBase`. `model` is an opaque string (an Anthropic alias resolved through the provider `modelMap` on a provider-backed project, or a concrete model id), stamped onto `WorkerEntry.model`. A model name belongs to one harness's vocabulary, though the key serves workers on more than one: an Anthropic name (a family alias such as `opus`, bare or context-tagged like `opus[1m]`, or a `claude-` id) is claude-code's, and any other name is taken to belong to the project's builder, the harness its default workers build with (the flat `harness` key, else the bound crew's builder). A worker launching on another harness skips the key, as a codex builder skips a project `ultra` (`projectModelFor`, `crew.ts`): a codex default worker under an Anthropic alias launches on the bound crew's seat model or Codex's launch default rather than `codex -m opus`, and a codex project's own model does not reach its claude-code grow workers. The status row's baseline (`projectWorkerModel`) applies the same rule, and setting an Anthropic name on a codex-building project says that its default workers skip it. `effort` is checked against the builder's ladder: one of `low`/`medium`/`high`/`xhigh` (rendered as `--effort <level>`) or `ultra`, which resolves to the ultracode preset (max effort + dynamic workflows, Opus pin), and for a codex builder also Codex's `max`. The resolved effort, other than the ultracode preset, is stamped onto `WorkerEntry.effort` and, like `WorkerEntry.model`, passed again on every resume, bounce and loop respawn. The **review family** ignores these project-level keys, but is not effortless: reviewer/resolver/ci-fix take their own `model` and `effort` per role (`roles.<role>.effort`, or a crew's review half), resolved by `resolveReviewRole`. The model keeps its safety-net floor of Opus; effort has no floor of its own, since unset simply falls through to the harness default (the account default on claude-code; on codex the pinned pair below). The ultracode preset's Opus pin still wins over `model` (an explicit per-spawn ultracode gesture is more specific than a project default), and a spawn that resolves to ultracode suppresses `effort`. Set via `garden config <project> model <alias-or-id>` / `garden config <project> effort <level>`, or the `⌥,` project menu's **model** / **effort** rows, whose submenus offer the builder's vocabulary (`projectBuilderChoices`, `project-menu.ts`, reading the composer's `composerModels`/`composerEfforts`): Codex's catalog and levels for a codex builder, a provider's `modelMap` aliases, else the Anthropic aliases and the claude-code rungs. `ultra` is offered only to a claude-code builder, since another builder's workers skip it; the CLI covers exotic model ids. A **stored crew** can pin these same two dimensions, in which case it resolves one layer *beneath* these flat keys (per-worker crew > flat project key > project's bound crew), so adopting a crew still leaves room to tweak one dimension per project. A seat's model and effort are in its own member's vocabulary, so they apply only while that seat's member (harness + provider) is the one building: naming a different builder over the crew — the `⌥⇧N` build dim, or `--harness` on a designer — leaves those dims to fall through rather than launching claude-code on a Codex model. Builtin crews pin each seat's model from their harness's seat ladder — plus `high` effort on the Claude builder seat — and interact with these keys exactly as a stored crew does. A codex worker renders `effort` through its own dial — `-c model_reasoning_effort=<level>` — rather than `--effort`; the four plain rungs are valid Codex reasoning levels, while `ultra` means the ultracode preset here and that preset has no Codex analog: a project or crew `ultra` is skipped for a codex builder, leaving the next layer or Codex's launch default to supply the effort (the preset's Opus pin would otherwise reach `codex -m`), and an explicit per-spawn ultracode request for a codex worker is refused. (Codex's genuine `ultra` reasoning level is offered per-spawn only, by the `⌥⇧N` composer when codex is the build member — see "Spawn composer"; at project level `ultra` names the preset.) A provider-backed worker's model alias resolves through the provider `modelMap`. Applies to newly created workers.

**crew**: A named bundle of *who runs each role and how strong*, composing a project's whole fleet in one word: `garden config <project> crew <name>` / `garden crew apply <name> [project]` (or `⌥⇧C` in the dashboard). A crew names three **seats** — who *designs* (read by a designer-workflow spawn), who *builds*, and who *reviews* — over **members**, a member being a registered harness (`claude`, `codex`) or one per configured provider (`deepseek` → claude-code against that backend). Any member may design or build, but only harness members review (a provider on review defeats the safety net), enforced structurally in `validateCrewDef`. The design seat is optional: a crew naming none derives it from its review half (`designerSeat`, minus the review effort), on the reasoning that the model strong enough to be the safety net is the one to choose the approach.

Crews come in two kinds. **Builtins** are generated (`builtinCrews`): the cross product of members × reviewer-members, named `<worker>-<reviewer>` with `all-X` sugar — `all-claude`, `codex-claude`, `deepseek-codex`, and so on, expanding for free as providers and harnesses are added. They carry each harness's **seat ladder** (`SEAT_MODELS` in `crew.ts`): the strong model fills the designer and reviewer seats, the middle one the builder — so `claude-codex` designs on Fable, builds on Opus, and reviews on Codex's Astra, and `codex-claude` is its mirror (Astra designs and builds, Fable reviews — Codex's ladder is Astra on every seat, the same `DEFAULT_CODEX_MODEL` an unpinned Codex launch takes). The Claude builder seat also pins `high` effort, so a builtin-crew Opus builder never rides the account default rung (the Codex builder already gets `DEFAULT_CODEX_EFFORT` from launch tuning). Provider members carry no ladder (their vocabulary is the provider's `modelMap`). That is the most a *generated* namespace can express — one ladder per harness, not a rung per crew, which would explode into names like `sonnet-xhigh-claude-opus-claude`. **Stored** crews (`crews` in `~/.garden/config.yml`, garden-level like `providers` — a shared resource projects reference by name) are operator-named, which puts the name in the operator's hands and so lets a crew also pin **model** and **effort**: `heavy`, `cheap`, `nightly`. Managed via `garden crew [list|show|add|edit|remove|apply]` (`src/commands/crew.ts`); `--from <crew>` clones any crew (builtin included) so "copy and tweak" is one call, and the literal `none` clears a pinned dimension. `--designer <member>`, `--designer-model` and `--designer-effort` set the design seat (`--designer none` drops it), and `--review-effort` pins the review seat's rung. `listCrews` returns stored ∪ builtin, a stored name shadowing a builtin.

**Binding is by reference.** A project stores `crew: <name>` and the members resolve at spawn/review time, so `garden crew edit heavy --model opus` re-targets every project on `heavy` at its next spawn or review — the property that makes crew definitions worth editing at all. `applyCrew` therefore records the name and *clears* the flat keys the crew now owns; a stale flat key left behind would sit in the override layer and permanently shadow the crew. The flat project keys (`harness`/`model`/`effort`, `roles.*`) are that override layer, winning over the crew, so a project can adopt a crew and still tweak one dimension (`crewOverridden` reports this state). `config <p> crew none` unbinds, leaving the flat keys standing.

Resolution reads, per dimension: **per-worker crew → explicit project key → project's bound crew → default**. The worker half supplies harness (default workflow only, like `project.harness`) plus model and effort (default+grow, like `project.model`/`effort` — a crew effort of `ultra` promotes to the ultracode preset exactly as `--effort ultra` does, for a claude-code builder only); the **design seat** supplies harness, provider, model, and effort together to a **designer** spawn (per-worker crew, else the project's bound crew), ahead of the workflow's Opus/xhigh default (its Opus half on claude-code only: a Codex designer with no seat model keeps Codex's launch default) and beneath a per-spawn flag — the flat project keys stay out of it, since they describe the project's builders; the review half supplies harness, model, and effort uniformly to reviewer/resolver/ci-fix via `resolveReviewRole` (`roles.ts`) — its effort ladder ends in `max` rather than `ultra`, since ultracode is a worker preset a headless run has nothing to enable, and unlike the model it has no safe-default floor (unset falls through to the harness default — see the Codex launch defaults below). Every rung on that ladder is one both registered harnesses accept, so a Codex review seat's effort reaches its reviewer verbatim (`-c model_reasoning_effort=<level>`) rather than being dropped. A claude-code reviewer gets its effort as `--effort` on the headless `claude -p`, a top-level flag valid there just as on the interactive launch; with none set the flag is omitted, leaving the account default every review ran on before the review half had an effort dial. Like a builder seat, though, a review layer's model and effort apply only while that layer's harness (explicit, or inherited from the layers beneath it) is the one reviewing: an explicit `role <r> harness codex` over a Claude crew launches Codex on its own defaults rather than on the crew's Claude model and effort, and a per-worker crew's reviewer never inherits a role model set for another harness. Layer harnesses are compared by registry name, so a hand-edited `harness: claude` (the member name) keeps its Opus floor and profile env. **`provider` is the one write-through dimension** — its readers (`resolveProvider`/`projectUsageGateExempt` in `config.ts`, `reviewerEnvPrefix` in `claude-env.ts`) sit below `crew.ts` in the import graph and cannot consult a crew without a cycle, and `docs/future/CREWS.md` rules that PROJECT-level worker-provider stays the flat key to avoid split-brain; so the crew owns the value but writes it to `project.provider` where every reader already looks. Spawning still falls back to the bound crew's builder when that key is absent (see "Spawn composer"), so `garden config <p> provider unset` refuses while the bound crew's builder is provider-backed: clearing the key would leave new workers on the provider while every flat-key reader, the reviewer's env neutralization included, treated the project as first-party. The operator changes or unbinds the crew instead. (This governs the project binding only. A *per-worker* crew or build member resolves its provider at spawn onto `WorkerEntry.provider` instead — see "Spawn composer" — which is a distinct layer above the flat key and needs no write-through, since the launch env builders read the entry directly.) A dangling binding (crew deleted) is inert rather than broken: resolution skips the crew layer.

The **`⌥⇧C` picker** is also the crew editor. Selecting a crew binds it (the common act); below a separator sit `new crew…`, `edit crew…`, and `delete crew…`, shown unconditionally. Gating the latter two on a stored crew existing was tried and reverted: with none defined the menu showed a lone `new crew…` and read as a half-shipped feature, since an empty state is indistinguishable from a missing one. tmux `display-menu` has no disabled-row rendering to lean on, so the choice is show-with-a-message or hide; the chooser answers an empty list with "No crews defined yet — use 'new crew…' first." The **edit chooser lists builtins too**. A builtin has no storage to edit in place, but a stored crew SHADOWS a builtin of the same name, so editing one materializes an override you then tune, and deleting that override restores the generated pairing — lossless in both directions. `all-codex` is the natural starting point for "codex, but pinned to Opus", and requiring `crew add … --from` first was busywork. Rows are tagged with what selecting them does (`builtin — edit to override`, `reverts to builtin`), and the delete chooser stays stored-only since a pure builtin has nothing to remove. `garden crew edit <builtin>` does the same thing, so the CLI and the menu agree; `--from` remains the way to clone under a *different* name.

New/edit open a **composer**: one row per dimension (designer member, designer model, designer effort, worker member, model, effort, reviewer member, review model, review effort), each opening a curated submenu, with the title reading the recipe back as composed (`New crew (claude opus/xhigh → codex)`). Composition state lives in a garden-level draft (`crew-draft.ts`, `SESSIONS_DIR/crew-draft.json`, 15-min TTL) — the same pattern as the ⌥⇧N spawn draft, and for the same reason: a tmux `display-menu` is fire-and-forget, so multi-field composition needs state that survives each re-open. It is garden-level rather than per-project because a crew is a garden-level resource. Save is withheld until both halves are named; creating prompts for the name via `command-prompt`, while editing saves straight to the name the draft was seeded with. The save path calls the same `saveCrew` the CLI does, so member validation and the review asymmetry are enforced once, not twice. Curated model/effort choices match the `⌥,` project menu's; exotic model ids stay on the CLI.

`garden config <p> crew` with no name lists the current crew, whether it is locally overridden, and the available set. The name shown there, on the `⌥,` menu's crew row and on the status-pane badge below, comes from `deriveCrew`: the binding when there is one (`custom` if it no longer resolves); otherwise the crew the flat harness, provider and review-role keys spell, so a config written before crews were stored still reports a name; and `custom` when they spell none. The reverse mapping is display-only: resolution reads the binding `applyCrew` records. A quiet grey crew badge rides the **focused** project's header in the status pane — shown for every crew including `all-claude` and `custom`; focused-only, so it reads as context for the project you're working in rather than standing grey across the whole list. A crew can also be set **per worker** (`workers new --crew`, default and designer workflows, persisted to `WorkerEntry.crew`), which badges that worker's own row with the crew name — superseding its build-member badge, since the crew name already encodes both build and reviewer. `garden handoff` forwards that per-worker crew to the child it spawns unless `--crew` names another, which is how a designer's builder lands on the crew that designed. A per-worker crew's build half folds into `entry.harness` at spawn (its worker member is authoritative — a `claude-codex` crew builds with claude even on a project defaulting to codex, pinned explicitly so the project default can't override it), and its review half is applied live by `resolveReviewRole` — so a worker's reviewer/resolver/ci-fix can be re-targeted after it has started and takes effect on the next review (the poller resolves the role fresh each cycle). On the default workflow `workers new` refuses `--crew` together with `--harness`, since the crew already selects the build member. The **`⌥i` worker menu** (`src/dashboard/worker-menu.ts`) is the live surface for this — and for a running worker's base branch (rewrites `entry.baseBranch`, re-targeting the next merge) and model (set + bounce). See `src/dashboard/crew.ts` and `docs/future/CREWS.md`.

**Codex launch defaults.** An otherwise unpinned Codex launch takes `DEFAULT_CODEX_MODEL` (`gpt-6-astra`) at `DEFAULT_CODEX_EFFORT` (`high`) reasoning. The pin is applied by `harnessTuning` in `resolveWorkerLaunchPlan`/`resolveHeadlessLaunchPlan` (`launch-plan.ts`) rather than in the adapter, so the interactive worker launch and all three headless roles cannot drift to different strengths — the same reason every other execution-identity dimension is bound there. It sits at the bottom of the precedence chain: explicit worker, project, crew, or role tuning still wins, and claude-code is untouched (its unpinned launches keep inheriting the account default, with the review family's own Opus floor on top).

### Spawn composer

`⌥n` spawns a worker with no questions asked; `⌥⇧N` is the same act with the dials exposed. The picker's workflow rows sit above a separator, and below it one row per per-spawn dimension: **provider** (`(p)`), **model** (`(m)`), **effort** (`(e)`), **crew** (`(c)`), **base branch** (`(b)`). Choosing a value stages it in a short-lived per-project draft (`spawn-draft.ts`, `SESSIONS_DIR/spawn-draft-<project>.json`, 5-min TTL, swept by the watchdog) and re-opens the picker, giving a fire-and-forget tmux menu the feel of a form; choosing a workflow consumes the draft (read + delete) into `newWorker`. The title reads the recipe back as composed — `New worker on garden (codex · gpt-6-astra · xhigh)`. The build member, model and effort read bare; crew and base carry a label (`crew all-codex`, `base dev`). The `(d)` default row dispatches `_compose-default`, which consumes the draft, rather than `⌥n`'s `_new-worker`, which never reads one.

The re-open **keeps the cursor where the operator left it**: the composer re-opens with the dimension just staged still selected (`MenuSpec.startingChoice` → `display-menu -C`, an index over every item, separators included), and a dimension's submenu opens on the value already staged. Without it the form feel breaks down at exactly the point it matters — a menu that re-opens itself on every choice snapped back to the first workflow row each time, so composing three dimensions meant scrolling down to the same row three times. Nothing staged means no row describes the current state, so a first open (the `⌥⇧N` hotkey) and a submenu with nothing staged both keep tmux's default of the first row. `stageSpawnDraft` re-opens the composer through `runWorkflowPicker` with the staged dimension as `focus`, which `buildWorkflowPickerPlan` turns into that row's index; a value submenu takes its index from `currentIndex`.

**Provider** answers *who builds this worker*, in the same **member** vocabulary crews use (`listMembers`) — `claude`, `codex`, any registered harness, plus one row per configured provider (`deepseek` → claude-code against that backend). It is consumed as `newWorker`'s harness+provider **pair**, which is authoritative over a crew's worker half, so staging provider *and* crew composes "this builder, that reviewer" without defining a crew for the pairing. This is the fast path the crew dimension alone could not give: spawning one Codex worker on an otherwise all-Claude project is `⌥⇧N p <n> d`, with no project reconfiguration to undo afterward.

A member is a **pair**, and naming one is a statement about both halves. `--harness claude` on a provider-backed project therefore means *first-party* claude, not "claude against the project's backend" — without that rule there is no way to spell first-party on such a project at all, and the composer would have to display `[claude]` for a worker that in fact launches against the provider. Precedence mirrors harness exactly: explicit member > per-worker crew's worker half > project key > project's bound crew. Every effective provider is validated by `resolveWorkerLaunchPlan` before execution; an unknown or malformed profile is a launch error, never permission to change accounts. A named member is stamped on `WorkerEntry.provider` (the empty string records explicit first-party), and a provider inherited from a project-bound crew is also pinned when no flat project key exists, so resume cannot silently lose a crew-only backend. A worker that inherits the flat project provider leaves the field absent and resolves that current project value at its next launch boundary. The plan's `runtimeProject` drives both the launch env and sandbox egress allowlist, while the same plan's resolved provider drives scoped tmux credential injection. Threading only one of those would leave a worker pointed at one backend with another allowlisted, or unveil the wrong credential on a later bounce/loop refresh — the half-threaded revert the plan rules out. The review family never consults the worker provider: reviewer/resolver/ci-fix stay first-party by construction, since a provider on review defeats the safety net. The auto-continue usage gate does consult the per-worker provider — a worker on a provider spends a pool the Claude meters do not describe, so it is exempt on exactly the reasoning a provider-backed project is.

**Model and effort vocabularies belong to the build member, not to garden.** Codex names concrete slugs (`gpt-5.6-sol`) where Anthropic names aliases (`opus`), a provider serves only the aliases its `modelMap` defines (`providerModelAliases` — offering `fable` to a backend that never mapped it would send a name it cannot resolve, and an empty map falls back to the standard list rather than an empty submenu), and Codex's reasoning rungs are its own `model_reasoning_effort` values (adding `max`, and a genuine `ultra` level unrelated to garden's ultracode sentinel). Both submenus are therefore populated from the draft's **effective build member** — `effectiveBuildMember`: staged member > staged crew's worker half > project default (`projectWorkerMemberName`) — so a project bound to an all-claude crew offers Anthropic aliases, and staging `codex` re-populates both lists from Codex's catalog. Offering one harness's vocabulary while another builds was the defect this resolves: the lists looked like garden's opinion about available models when they were really just the Anthropic branch. The lists come from `composerModels` and `composerEfforts` (`harness/vocabulary.ts`), which the `⌥,` project menu also reads for the project's builder. On claude-code the effort list is `WORKER_EFFORT_LEVELS` (`worker-effort.ts`) plus `ultra`, so "fable ultracode" is model `fable` with effort `ultra` and "extra-high sonnet" is model `sonnet` with effort `xhigh`; on codex it is `CODEX_EFFORT_LEVELS` (`harness/codex-models.ts`).

The Codex model list comes from **Codex's own on-disk catalog** (`$CODEX_HOME/models_cache.json`, read by `codexModels` in `harness/codex-models.ts`): visible slugs in Codex's own priority order, so a new OpenAI model appears with no garden edit. That file belongs to Codex, not garden — it may be absent (Codex never run, or no Codex in the fleet) and its shape may drift — so every read is best-effort behind `CODEX_FALLBACK_MODELS`. The Anthropic side stays a literal, its alias set being stable enough not to warrant discovery. Either way the CLI (`workers new --model <id>`) remains the escape hatch for a model neither list names.

Changing the build member to a **different `(harness, provider)` pair clears any staged model and effort**. The clear keys on the pair rather than the harness alone because two provider members share the claude-code harness without sharing a model vocabulary — keying on harness would carry a DeepSeek-only alias onto a different backend that never mapped it. Those values are named in the outgoing harness's vocabulary — `sonnet` and the ultracode `ultra` mean nothing to Codex, `gpt-5.6-sol` means nothing to Claude — so carrying them across would stage a recipe that cannot run. Clearing drops both to the account default, which is always valid, and the operator re-picks from the now-correct list.

At consume time `draftLaunchOpts(draft, harness)` renders the effort dim in the target harness's dialect: on claude-code the `ultra` rung becomes `ultracode: true` (the preset — max effort plus dynamic workflows — rather than an effort value), while on codex the whole ladder passes through untranslated as `entry.effort`, which the adapter renders as `-c model_reasoning_effort=<level>` and where ultracode stays a no-op. Model and effort apply to **default and grow** workers only; provider is default-workflow-only, like `--harness` itself, and crew applies to default and designer spawns.

### Machine-wide limits

Some resource budgets are properties of the **workstation**, not of any one project — the machine is a single shared resource, so a per-project knob would be the wrong shape (no project sensibly wants a different answer to "how much of my machine may the fleet use"). These live at the top level of `~/.garden/config.yml` under `limits` (`LimitsConfig` in `src/config.ts`), managed with `garden limits [status | checks-slots <N|unset> | max-reviews <N|unset>]` (`src/commands/limits.ts`) or the **`⌥;` garden settings menu** (`src/dashboard/garden-menu.ts`) — the garden-level sibling of the `⌥,` project menu (`⌥,` configures one project, `⌥;` the whole garden). The menu offers curated presets; arbitrary values stay on the CLI. Both keys are optional overrides of a safe default — an absent `limits` block is the shipped behavior.

- **`checksSlots`**: overrides the hardware-derived checks-semaphore slot count (`max(1, floor(cores / 8))`; see the checks-semaphore paragraph above). Use it to pin the concurrent-suite budget when the automatic value doesn't fit the machine (a heavier or lighter suite than the `~half-the-cores` assumption).
- **`maxConcurrentReviews`**: a fleet-wide cap on simultaneously running headless reviewers — counted live from tmux as the `_<project>-review-<worker>` windows across all projects (tmux is the source of truth for window existence, so the count is derived fresh with no acquire/release bookkeeping to leak across the fire-and-forget reviewer launches). The gate (`deferForReviewCap`, `src/dashboard/poller-review.ts`) sits at both points where a new review launches: the per-phase launch in `handleWorking`, and the holistic whole-task pass (`maybeDispatchHolisticReview`, `poller-holistic-review.ts`), whose window counts against the cap like any other. When the cap is already met, the launch is **deferred** — `pendingReviewAt` stays set (a holistic deferral leaves its high-water guard unset) and a re-poke is scheduled, so the next poll (or any sibling FIFO event, such as a running review finishing and freeing a slot) re-drives the launch. The re-poke is the only wake a quiet `done` worker gets, since a slot freed in another project wakes only that project's poller. It is deduped to one outstanding poke per project by an mtime marker in the control tree (`review-cap-recheck-<project>`): every poke re-runs every deferred launch, so a poke armed per deferral multiplied, the amplification the CI recheck marker was added for. A marker that cannot be written still arms the poke. Resolvers and ci-fix agents are deliberately **not** capped: they unblock already-in-flight merges, so throttling them could deadlock the pipeline; the cap governs only the pipeline's inflow. Default `0` = unlimited (the shipped behavior) — the count isn't even taken when the cap is off. This complements the checks semaphore: the semaphore bounds the heaviest thing a reviewer does (running the suite), while this bounds the number of concurrent reviewer inference processes.

The `⌥;` menu is no longer limits-only: it also carries the garden-level settings that are not resource budgets — the build-staleness branch (`build.branch`) and the terminal column split (`layout.leftPercent`, see "Dashboard Layout"). Those two rows write through `setBuildBranch` and `setLeftColumnPercent` (`src/config.ts`), as the limit rows write through `setLimit`.

### Lid-closed awake

`garden awake on [--for <duration>]` (`src/commands/awake.ts`, mechanism in `src/dashboard/awake.ts`) keeps a MacBook running with its lid closed so the fleet keeps working in a dark room. macOS has one switch that overrides lid-close (clamshell) sleep, the undocumented root-only `pmset -a disablesleep 1`: `pmset sleep 0` governs only the idle timer, clamshell mode needs an external display, and `caffeinate` cannot hold a closed lid.

A Mac that never sleeps is dangerous to forget (a laptop in a bag overheats and drains), so awake is **held only while plugged in** and always has a way back off:

- `on` refuses on battery, refuses when the `_garden-watchdog` window is not running (nothing would release it), and refuses until the sudoers entry exists. It flips the switch, then records `{since, until?}` in `~/.garden/control/awake.json`. That directory is outside every worker sandbox, and the file's presence is what marks the switch as garden's: a `disablesleep` the operator set by hand is never touched.
- The watchdog calls `enforceAwake` every 60s tick. With no state file it reads nothing and forks nothing. Otherwise it releases on the first tick where the machine is on battery or `until` has passed, and a closed-lid machine is then put to sleep with `pmset sleepnow`, which is what closing the lid would have done. If sleep was re-enabled outside garden, it only forgets the state. A failed release raises an error alert naming the manual `sudo pmset -a disablesleep 0` and keeps the state so the next tick retries.
- `garden dashboard exit` releases it, since the watchdog is gone after that.
- `off` releases immediately without `sleepnow` (the operator is at an open laptop).

The watchdog has no terminal, so the toggle needs passwordless root. `garden awake setup` installs `/etc/sudoers.d/garden-awake` (`visudo -cf` validated, `0440 root:wheel`) allowing exactly `/usr/bin/pmset -a disablesleep 0` and `... 1` for the operator's user and nothing else. Every unattended sudo call passes `-k -n`; setup's interactive validation and install calls may ask for a password. Readiness inspects the matching rule from `sudo -ll` for `!authenticate` on both toggles: successful listing alone does not prove passwordless execution.

Activation, explicit off, watchdog enforcement, and dashboard shutdown serialize through `control/awake.json.lock`. Activation validates the timer before changing power settings, proves the release command works, verifies each toggle through `pmset -g`, and restores sleep if recording ownership fails. The watchdog releases a managed hold when power inspection fails as well, since it can no longer establish AC power. Shutdown releases before stopping the watchdog and refuses to close if release fails, preserving the retry path. Power subprocesses have a five-second timeout so a failed probe cannot stall enforcement indefinitely.

### Merge Handling
After a review passes, workers enter the `merge-pending` state. The merge queue processes one worker at a time per project (ordered by `mergePendingAt` timestamp, passing over a worker whose agent is mid-turn: it keeps its place and goes first once idle, so its step-3 deferral holds only itself). A head that defers anywhere else, as at its CI gate in step 4 (checks pending, the no-runs or `gh` grace window, a commit missing on GitHub), still holds every younger merge, and those merges logged nothing, so a stalled queue showed only the head's CI lines. Each merge held behind an older one logs that at info, once per hold, naming the head (`behind`); since every poll re-runs the gate, `control/merge-held-<project>` records the holds already logged, keeping only those behind the current head. Each merge then runs:

1. Ask origin for the base tip (`remoteTipSha`, over `git ls-remote`), then fetch the base branch, which brings that commit in and refreshes the local `origin/<base>` ref the resume check and CI gate read.
2. **Resume an interrupted merge** (`src/dashboard/poller-merge.ts`): if the worktree HEAD is already contained in `origin/<base>`, a prior finalization already fast-forward-pushed the merge but was torn down before the terminal-state transition (e.g. a garden rebuild restarted every project's poller mid-finalize). Skip the re-merge and run only the idempotent post-merge tail. Naively re-running rebase + force-push here would hit a `--force-with-lease` "stale info" rejection against the now-deleted remote branch; the force-push catch then re-arms a full re-review of the already-merged worker and fires a spurious push-failed alert (it no longer strands the worker, but the cycle is wasted).
3. **Defer while the worker's Claude is mid-turn** (`src/dashboard/poller-merge.ts`): if the merge-pending worker's `agentStatus` is `working` — the operator prompted it and it may be editing tracked files not yet committed — defer the whole merge before touching the shared worktree. `cleanWorktree` (`git checkout -- .`) and the rebase below rewrite tracked files and HEAD; a plain rebase would refuse on a dirty tree, but `cleanWorktree` turns that refusal into a silent wipe of the uncommitted edits (there is no reflog for unstaged changes). This sits **after** the resume check — an already-pushed merge is safe to finalize regardless — and `launchResolver` guards the identical shared-worktree hazard. The deferral cannot strand the worker: its Stop hook re-pokes on turn end, and the watchdog backstops a lost poke since `merge-pending` is a watched state. It is logged at info, and it holds no other worker: the serial gate used to wait on the earliest merge-pending worker whatever it was doing, so one worker the operator prompted held every younger merge in its project for its whole turn (43 minutes on wolf, 2026-09-23). Past that deferral the queue merges only the SHA cleared for it: every move into `merge-pending` — a review verdict, a verified resolver or ci-fix push, the queue's own rebase below — stamps `WorkerEntry.mergeReadySha`, and a HEAD that has moved since (a worker prompted while it waited on CI commits work no reviewer saw, and before this check it merged anyway) goes back to `working` with its review re-armed (`resetToWorkingOnWorkerPush`). Entries written before the stamp existed carry none and merge as before. So does a `reviewInterruptedAt` mark, which the hook sets for a mutating tool call from the review's launch until the merge, not only while `reviewing`: through `resolving` and `ci-fixing` too. A resolver or ci-fix agent the worker edits under is left to finish rather than killed, since killing a resolver nearly always strands its rebase half-replayed in the worker's tree; its verified result reaches `merge-pending` still carrying the mark, and goes back through review here, edits included. That covers two cases the stamp cannot see. An edit the worker has not committed moves no HEAD: the deferral above covers only `working`, so a worker that asked a question, was held, or ended its turn before committing reached `cleanWorktree` with its edit in the tree. And an edit landing while the verdict poll was still dispatching, after it read the entry (the Haiku fallback alone can hold it for 45 s), makes the stamp that dispatch writes name the worker's own commit. Unlike a check on the tree, the mark is not set by what the reviewer left behind, which the queue still cleans. Edits made from a `!` shell command fire no hook, so the mark does not cover them; `cleanWorktree` therefore saves whatever it discards as a patch under `~/.garden/control/reports` (`discarded-<project>-<worker>-<time>.patch`, restorable with `git apply`, pruned after two weeks) and logs the paths at warn, keeps the changes when the patch cannot be written, and says nothing when there is nothing to discard. An edit the operator makes in the worktree from their own editor fires no hook either, and reaches `cleanWorktree` the same way. Pending background tasks (`backgroundTasks`: a `run_in_background` command or async Agent a turn left running) do not count as mid-turn, as `docs/STATUS.md` "Delegated background work" specifies for the merge gate: a dev server or watcher can run for the worker's whole life, so deferring on them could hold this merge, and every younger one queued behind it, indefinitely. The cost is a background process's write to a tracked file during the merge, which no hook reports; `cleanWorktree` discards it with the patch saved.
4. **CI gate** (`src/dashboard/poller-ci.ts`): query `gh api repos/<owner>/<repo>/commits/<sha>/check-runs` for the worker's HEAD. **Success** (every completed check-run conclusion is `success`/`skipped`/`neutral`) → proceed. **Missing commit** (`gh` reports `No commit found for SHA`) → defer with a 60 s re-poke and a per-worker/SHA alert asking for publication. This is distinct from unavailable CI infrastructure and from an existing commit with zero check-runs; neither an API-error fallback nor expiration of the no-runs grace window permits merging a missing commit. **Pending** (any check-run not yet `completed`) → defer the merge with a 60 s re-poke; worker stays in `merge-pending`. **Failed** (any non-success conclusion) → dispatch a self-healing ci-fix agent (`src/dashboard/poller-ci-fix.ts`) in a hidden `_<project>-ci-fix-<worker>` tmux window and transition the worker to `ci-fixing`. The agent runs in the worker's own worktree, reads the failing logs via `gh run view --log-failed`, makes the minimum fix to turn the checks green, and pushes. The poller's verification path checks that the agent actually advanced HEAD (against the captured `preCiFixSha`) and that origin tracking matches the new local HEAD; on success it transitions back to `merge-pending` so the CI gate re-runs against the new SHA. Verdict `FIXED` without a verified push, verdict `FAILED`, or unparseable output: retry directly within `ci-fixing` up to budget (3 attempts per merge cycle), then escalate to `failing` and an operator alert — `failingReason: "ci"` (push a fix) for a genuinely red CI the agent couldn't repair, or the kick-recoverable `failingReason: "transient-review"` when the agent only hit transient backend outages (Anthropic/codex 5xx/429/overloaded) or was cut off by a session/usage-quota limit (surfaced through `quotaLimitResetHint`, folded into `transient-review` like the resolver's). Retries retain the original `preCiFixSha` and failing-check summary, so an agent can publish an existing local repair without manufacturing another commit. An unverified repair never returns to `merge-pending`; local commits remain intact if the budget expires. Launch and successful push are routine lifecycle beats — logged (visible in `garden logs`) but not raised as operator alerts; only budget exhaustion alerts, at error level, when the agent can't repair CI within the 3-attempt budget. The ci-fix prompt inlines the branch diff exactly as a review prompt does, so `buildCiFixPrompt` composes through the same `composeWithinCeiling` — an oversized delta degrades to a `git diff --stat` summary the agent pages itself in the worktree — and `launchCiFix` applies the same backstop as `launchReview`: a prompt still over `MAX_REVIEW_PROMPT_BYTES` means the non-diff context (for this prompt, the commit summary and prior-review body — it carries no rules/docs/tests sections) does not fit, the agent CLI would reject the request before the fix agent starts, and every attempt would fail identically. The worker parks in `failing` with `failingReason: "ci"` and an error alert naming the size and pointing at a hand fix, with `ciFixAttempts` **reset rather than incremented** — nothing ran, and a worker that later recovers must not carry a silently-reduced budget into the next merge cycle. The gate is a no-op for projects with `requireCiSuccess: false`, projects whose `origin` isn't a github.com remote, environments where `gh` isn't installed, and commits with zero check-runs on a project with no CI. "Has CI" is answered from the checkout on disk first (a `.github/workflows/*.yml`/`.yaml` whose `push` trigger would run for the worker's branch), then from a check-run seen on one of the project's SHAs within the last week. The disk read is `projectDefinesCi` (`poller-ci.ts`), which parses each workflow's `on:` block and GitHub's branch filters with `workflowRunsOnPush`. A workflow that runs only on pull requests (garden opens none), a schedule, a manual dispatch, tags, or pushes to other branches never puts check-runs on a worker SHA, so counting it held every merge in that project for the full grace window while gating nothing; one whose triggers cannot be read still counts, because a wrong yes costs a grace window and a wrong no lets an ungated SHA through. The disk read is load-bearing, not an optimization: the check-run sighting alone could never be recorded. The poller queries within seconds of the reviewer's force-push while GitHub takes ~5-12 s to create the runs, so every query returned zero check-runs — and only a non-zero observation recorded a sighting. After any poller restart the gate silently passed everything through, which is how a red `main` merged on 2026-07-20. The sighting remains as an OR for CI with no workflow file in the repo (CodeQL default setup, third-party check apps). It is the mtime of `control/ci-seen-<project>`, rewritten on every observed check-run: until 2026-10 it was a module-level flag, empty in every fresh poll process, so it never gated that CI. It sits in the control tree because a worker that deleted it from `sessions` would open the gate, and it lapses a week after the last sighting so a removed check app stops holding every merge for the grace window. On a project that has CI, zero check-runs on a freshly force-pushed SHA (a reviewer-fix or ci-fix commit whose runs haven't materialized yet — they appear ~30 s after a push) are treated as not-yet-materialized: the merge defers within a bounded grace window (3 min, re-poked every 60 s) before passing through, rather than merging the exact commit CI most needs to vet un-gated. A `gh` call that times out (30 s) or gets a 5xx, a rate limit, or no connection leaves the result just as unknown, so on a project that has CI the merge defers the same way, for up to 10 min on the same per-SHA stamp, then passes through with the warn alert; a failure that waiting cannot fix (bad credentials, a 404) still passes through at once.

Both halves of that mechanism are **persisted, not in-memory**, and this is load-bearing for the same structural reason the disk read above is. The poller loop is `while true; do garden dashboard _poll <project>; read; done` — a fresh node process per poll, so any module-level `Map` is empty at the top of every poll. The grace stamp lived in one, which meant each poll re-stamped it as "now", the elapsed check measured ~0 ms, and the window could never expire: the merge deferred permanently. The 60 s recheck-poke dedup lived in another, so it never fired across the boundary and every external poke arriving during a pending-or-grace stall spawned an additional self-perpetuating sleeper. Together they stranded two `wolf` workers in `merge-pending` for 5.5 h behind 43 orphaned `sleep` processes on 2026-07-21. The grace stamp now lives on `WorkerEntry.ciNoRuns` (`{ sha, since }`, keyed by SHA so a force-push starts a fresh window on the new tip rather than inheriting an expired one); the poke dedup is the mtime of a `ci-recheck-<project>` marker file in `SESSIONS_DIR`, which needs no content or schema and fails open (arms the poke) when it can't be read or written — a duplicate poke is recoverable, a dropped one strands the merge. The general rule the incident establishes: **state that must survive from one poll to the next belongs on disk.** A module-level `Map` in poller code is per-poll scratch, never memory. The gate runs **before** the rebase/force-push so it reads CI for the SHA the worker actually published; the rebased commits that ultimately land on base are the same commits in rebased form, and the workers we guard push frequently enough during their turn that CI is usually already settled by the time the reviewer signs off. This is defense-in-depth against GitHub branch protection — the poller's force-push path bypasses the merge UI entirely, so branch protection alone can't block a red CI.
5. Clear any leftover rebase state from a prior crashed resolver (`ensureNoRebaseInProgress`)
6. Rebase onto the base tip origin reported in step 1 (`rebaseBranch`, `git.ts`, given that SHA), never onto the `origin/<base>` ref. The ref is in the shared git dir every worker sandbox can write, and step 8's fast-forward check passes a forged base committed on top of origin's real tip, so a rebase onto the ref put the forged commits beneath the reviewed ones and the queue pushed them to the base. When origin did not answer in step 1, or the fetch did not bring that commit in, the queue skips the rebase rather than the merge: step 8 asks origin again and refuses anything but a fast-forward, which sends a branch the base has moved past back through review. The rebase runs in one of three modes, because a plain `git rebase` **drops merge commits** and linearizes. **(a) Fast-forward short-circuit**: if the base tip is already an ancestor of HEAD the branch sits strictly on top of the base and merging it is a pure fast-forward, so no rebase runs at all (`up-to-date`). Git does not make this decision itself when the branch carries a merge commit — its own fast-forward check requires linear history — so it would flatten the merge and replay the merged-in side's commits against a tree that already contains their content. That is an unwinnable conflict: it burns the resolver's whole budget and parks a mergeable branch in `failing` (observed on `lex/lost-light-pulse`, 2026-08-12, where a worker had legitimately merged 103 base-side commits into its branch). **(b) Merge-preserving rebase**: the base genuinely advanced *and* the commits from the base tip to HEAD include merge commits → `git rebase --rebase-merges`, which recreates the merge topology rather than flattening it. **(c) Plain rebase** for the ordinary linear branch. The reviewer prompt carries both mode-selection conditions. The resolver is launched only after the poller's own rebase has conflicted, so its prompt carries the merge-preserving condition but does not need the already-on-base short-circuit.
7. If rebase conflicts: abort rebase, launch a dedicated resolver in the worktree and transition to `resolving`. The resolver completes the rebase, commits the resolution, and runs the project's checks on the result; the poller verifies and pushes. Budget is 2 attempts per merge; exhaustion transitions to `failing` with an operator alert — `failingReason: "code"` naming the unmerged files for a genuine conflict, or the kick-recoverable `failingReason: "transient-review"` when the resolver only hit transient backend outages or a usage-quota cutoff.
8. If rebase is clean: force-push the rebased branch, fast-forward the remote base branch via direct refspec push (no local checkout needed). The commit that push names, and the commit the operator's checkout is later advanced to, are both read from **origin itself** (`remoteTipSha`, over `git ls-remote`) rather than from the `refs/remotes/origin/*` refs the queue's own fetch just wrote: those refs live in the shared git dir, which is inside every worker sandbox's write grant, so a worker could rewrite one in the window between the fetch and the read and choose what landed on the base branch — then have it installed and built as the operator by the next bootstrap and by `postMerge`. Reading them from origin does not by itself keep unreviewed commits off the base: the fast-forward check proves only that the branch descends from origin's base tip, which a forged base built on that tip also does, so step 6 takes its target from origin too. Both functions already contact origin for their own fetch, so this is an extra round-trip, not a new dependency on the network. The refspec push runs `--no-verify`: it executes in the operator's checkout, and an operator `.git/hooks/pre-push` guard against direct human pushes to the base branch must not veto the merge queue's own authorized, already-reviewed push (such a guard was shadowed by the core.hooksPath leak until `scopeHooksPathToWorktree` fixed the leak, which re-armed it and blocked every merge)
9. Notify live sibling workers with overlapping files (see below)
10. Advance the local base branch to the merged tip — `merge --ff-only` if it is the checked-out branch (also moves the working tree, so postMerge can run), otherwise `git fetch origin <base>:<base>` to advance the ref alone (working tree untouched, postMerge skipped). A clean advance is silent, as is auto-healing a redundant local commit whose clean tree already matches origin (reset onto origin, then postMerge runs). The remaining states alert only on entry: the local base diverged from origin with real local-only content (warn), the base is checked out in another worktree (warn), the on-base checkout is dirty (warn), or it is wedged/unfetchable (`stuck`, error)
11. Mark the worker as `merged` (or `done` if `.garden-done` is present at the worktree) in the registry

The worker and its worktree are not automatically cleaned up on merge. Cleanup happens only when the user kills the worker with `opt-x`, runs `garden workers stop <worker>`, or runs `garden reset`. This allows inspecting merged work before disposal.

Projects don't block each other — each project has its own poller and merge queue.

`garden queue [project]` (`src/commands/queue.ts`) shows this queue from the persisted registry fields alone. Among its numbered `merge-pending` rows it marks the earliest whose agent is not mid-turn `← next`, since that is the worker the queue takes. A `ci-fixing` row carries `CI fix N/3` (its `ciFixAttempts` against the 3-attempt budget), and a worker parked in `failing` with `failingReason: "ci"` carries `CI ✗ <sha>`, its shortened `failingSha`.

### Auto-Continue Across the Merge Boundary
Multi-phase work (build → review → merge → keep building) used to require the operator to type "please proceed" after every merge. Garden eliminates that step: `finalizeMerge` ends with a call to `maybeAutoContinue`, which dispatches a delayed `_continue-worker-after-merge` subprocess that sends a "previous changes were merged, continue with the next phase" prompt to the worker pane.

The worker opts out by writing the sentinel file `<worktree>/.garden-done` before ending its turn. The worktree system prompt and the `done` skill instruct every worker, before writing the sentinel, to re-read the operator's original request and confirm each deliverable they asked for has landed in a merged commit and is verified working — explicitly distinguishing the operator's deliverables from the internal stages of any analysis or workflow the worker ran (research, design, implementation, a review or verification pass), which do not count, and treating "I feel finished" as insufficient evidence. This gate exists because the decision rests on the worker's own (and possibly context-compacted) memory of the request — garden keeps no durable copy of it for default workers — so deep or long-running workers were observed declaring done while a named deliverable was still unlanded or merely pushed-but-unverified. The bias remains toward stopping over inventing busywork: a worker must never fabricate "while we're here" scope to justify continuing. If the sentinel is missing on merge, garden assumes there is more to do and re-prompts.

Workers are nudged to invoke the sentinel-write via the `done` skill installed under `<worktree>/.claude/skills/done/SKILL.md` (see `src/dashboard/skills.ts`). Claude Code requires the directory + `SKILL.md` layout for project-skill discovery — a flat `done.md` at `.claude/skills/` is silently invisible to the planner. Skill descriptions act as Claude's trigger condition during planning — Claude evaluates "should I invoke this?" alongside its other tools when deciding the next action — which is more reliable than instructions buried in the system prompt. The skill body (when, when-not, mechanics, recovery) lives only in the skill file, not the main worktree-rules block, so the prompt stays scannable. The bootstrap script inlines the skill content at worker creation; the harness adapter's `installRuntimeConfig` rewrites it on every refresh/bounce so workers from rebuilds pick up content changes. Older workers created before the skill existed do not get it retroactively without a refresh — bouncing or recreating them is the only way to install it.

A second skill, `handoff`, lives alongside `done` and lets the operator pass a task to a fresh worker on another (or the same) project. Triggered when the operator instructs the worker to hand off; the skill body teaches the heredoc recipe `garden handoff <project> <<'EOF' ... EOF`. The CLI command writes the briefing to `~/.garden/sessions/seeds/seed-*.txt`, then submits a UUID-named JSON request under the sandbox-writable `~/.garden/sessions/handoff-requests/` inbox and pokes one or more project pollers. On wake an unsandboxed poller calls `processPendingHandoffs` (`src/dashboard/handoff-dispatch.ts`) and atomically renames the request into `~/.garden/control/handoff/claims` before parsing it. The filename UUID is authoritative and all body fields are shape/bounds checked, so a forged body cannot select a response path. The seed is read once through a no-follow regular-file descriptor with before/after containment, inode, link-count, size, and timestamp checks, then copied to `~/.garden/control/handoff/seeds`; delayed `_seed-worker` delivery never re-opens the worker-writable pathname. Claims carry the dispatcher PID plus a unique owner token. A later poller leaves a live owner alone but takes over a demonstrably dead owner; `WorkerEntry.handoffRequestId` reconciles a recovered claim to a worker already registered before the crash, and a control-tree receipt makes result delivery replayable without repeating the spawn. `newWorker` registers the entry before it opens the worker's window, so the reconciliation reports success only when that worker's pane exists (`workerPaneLive`): an entry with no window (its dispatcher died or threw in between) gets an error receipt telling the requester to submit again (the ghost sweep removes the entry), and a tmux that does not answer leaves the claim for a later poll instead of deciding. A live pane does not prove the worker was seeded: `newWorker` dispatches the seed after the pane opens, so a dispatcher killed in between left a running worker with no task under a success receipt. Recovery therefore dispatches the seed again whenever its protected copy is still on disk (a delivery that lands intact removes it), before writing the receipt; the seeder claim below keeps that from doubling a seeder the dead dispatcher had already started. A claim whose processing throws is settled where it failed, by delivering its receipt if one was persisted and otherwise writing an error receipt: a claim left in place is replayed ahead of the inbox on every later poll, so one that always throws would block every handoff behind it. Receipts double as the client-readable response and expire after 24h. The client keeps the fast 15s no-poller failure but, once it observes the inbox request was claimed, extends the completion window to 75s so the synchronous 60s base-branch publication path cannot produce a false timeout and delete the seed under a successful spawn. A timeout atomically withdraws and cleans up only an inbox request it can still unlink; if the dispatcher already won the rename, the CLI preserves the seed for recovery and tells the operator the spawn may still complete. `--model <alias-or-id>` and `--effort low|medium|high|xhigh|ultra` ride the same request fields into `newWorker`, where a per-spawn model/effort outranks the crew's builder seat and the project default; they are the sandboxed caller's only way to pick the child's rung, since minting a pinned crew needs a config write the worker sandbox denies. Those fields are `HandoffRequest.model` and `.effort`, mapped onto `NewWorkerOptions`, and `garden handoff` and `garden workers new` parse both flags through one module (`commands/launch-flags.ts`, over the `dashboard/worker-effort.ts` vocabulary leaf). A model override keeps the harness the child would build with anyway (the inherited or selected crew's builder, else the target project's default), so a Codex model needs a Codex-building crew as well (`--crew codex-claude --model gpt-6-astra`). The crew travels as `HandoffRequest.crew`, a name only, resolved against garden config at spawn: a request whose crew resolves to nothing is refused, since `newWorker` would read the unknown name as no crew and spawn on the project default. `--effort ultra` names the ultracode preset rather than a rung, so it and `--ultracode` are mutually exclusive, and both the CLI and the dispatcher's shape guard refuse an out-of-vocabulary rung, a flag-shaped model id, and a request setting both effort and ultracode, rather than launching on a configuration the caller did not ask for. The CLI also refuses an unrecognized flag outright: unknown tokens used to fall through to the briefing scan and be silently ignored, which is how an unsupported `--model` spawned a child on the wrong model with nothing said about it. `workers new` and `workers grow` refuse an unknown flag as well: a misspelled `--modle opus` was once stored there and never read, so the worker launched on the default the flag was meant to override. Options are parsed in order, each value consumed once, so the `-m` argument is opaque briefing text even when it equals a supported flag. The `--ultracode` flag threads a `ultracode: true` opt through the request into `newWorker`, which pins the child to Opus (`entry.model`) and stamps `entry.ultracode` so the harness `buildAgentCommand` renders `--effort max --settings '{"ultracodeKeywordTrigger":"on"}'` on every launch/resume/bounce — the operator's "hand this off to an ultracode worker" with no manual escape-edit-continue. The preset is claude-code's, so `newWorker` refuses the request when the child would build with another harness (the target's default or the forwarded crew), and the handoff reports that failed spawn rather than launching a Codex worker on an Opus pin. The request-file detour is load-bearing: the CLI runs inside the source worker's Claude Code OS sandbox, which blocks the tmux server socket (`/private/tmp/tmux-*/default` → "Operation not permitted"), so the CLI cannot create tmux windows itself. Worker-authored writes stay inside `~/.garden/sessions`; only the unsandboxed poller writes the protected control artifacts. The `background:true` flag remains load-bearing inside `newWorker`: handoff must not yank the operator out of whatever pane they're focused on, so the new worker is born hidden and `newWorker` skips the cross-project active-project/plot switch, the park-to-hidden of the visible pane, the restore-from-hidden swap, and the dashboard state lock that only protects those visible mutations. The operator's `activePaneType`/`activeWindowName`/`activePaneId` stay exactly as they were; the dashboard refresh picks up the new worker in the status pane, and the operator reaches it via ⌥<n> on the target project + ⌥w to cycle. A delayed `_seed-worker` subprocess polls until the harness reports the worker ready for a prompt — through `agentStatus` for Claude Code or the adapter's pane probe for Codex — and then sends the seed prefixed with `[handoff from <source-project>/<source-worker>]`; pane resolution falls back to `windowExists` when the seed fires, so a hidden worker still receives its briefing. The source worker writes `.garden-done` itself (per the skill recipe) rather than having the CLI command do it implicitly, mirroring the `done` skill's recipe-style instructions and leaving room for a final commit before handoff.

Handoff callbacks (opt-in via `--expect-callback`) close the parent → child → parent communication loop. When the source worker passes `--expect-callback`, the CLI captures `$GARDEN_PROJECT`/`$GARDEN_WORKER` and threads `expectCallback`/`parentProject`/`parentWorker` through the request file into `processPendingHandoffs`, which stamps `parentProject` + `parentWorker` + `handoffCallbackExpected` onto the child's `WorkerEntry`. The dispatch chokepoint is `transitionState` (`src/dashboard/poller-state.ts`): every poller-driven PrState write flows through it, so terminal transitions to `merged`/`done`/`failing` are detected in one place regardless of which poller (review, merge, resolve) triggered them. One terminal write does NOT go through it — the Stop hook's trail-off `done` (`hooks/default.ts` writes `prState: "done"` via `updateWorkerFields` when a worker sets the sentinel with no commits ahead), so a callback-expecting child that finished without ever merging would leave its parent waiting forever. `handleDone` (the poller-context landing that same hook pokes) therefore calls `maybeFireHandoffCallback` on the quiescent-done leg as the poller-side sibling of the chokepoint. On the first poller-driven terminal write, `transitionState` persists the terminal state, `handoffCallbackFiredAt`, and the rendered `[garden] Handoff callback: …` message (`handoff-callback-text.ts`) on the PARENT's `WorkerEntry.pendingHandoffCallbacks` in one conditional registry update; the `handleDone` sibling claims and records the callback the same way on its own quiescent path. The claim and the record share one write because the claim is permanent: recorded in a later write at the end of the poll, the callback was lost for good to a poller killed or crashed in between, or to that write failing on the registry lock or on an unreadable registry. Both then lazy-import `notifyHandoffCallback` from `continue.ts`, which only tries to paste it through `continueWorker` (same pane resolution and gates: a parent that is mid-turn, asking, held, drafting, or at a bare shell is not pasted into). The callback stays owed until a paste lands — before this, the one-shot claim was spent before delivery was attempted, so a callback that met a busy parent (the common fan-out shape) vanished. `dispatchOwedHandoffCallbacks` re-attempts it at the parent's next turn end: the Stop hook (`onTurnEnded`) calls it, and so does the Codex missed-turn-end heal (`codex-input.ts`), since Codex does not reliably fire Stop last. It spawns a delayed `garden dashboard _deliver-handoff-callbacks` (5s, like the post-merge continue, so the pane is idle), which re-arms on an operator draft through the shared `rearmContinueIfDrafting` backoff. Every owed callback is pasted as ONE prompt, so children that settled during one turn arrive together, and only the callbacks actually pasted are cleared. Recording happens before the first attempt, so a turn end racing the child's settle always finds it — either that turn end sees the owed entry, or it came first and the parent is idle for the inline attempt. The child can stage a freeform note at any point before its terminal state via `garden reply -m "<text>"` (or stdin/heredoc); the note is stored on the child's own `WorkerEntry.handoffReplyNote` field and folded verbatim into the callback prompt. Multiple `garden reply` calls accumulate (blank-line-separated); `--replace` clobbers an earlier draft. Callbacks are opt-in by design — default handoff behavior is unchanged, so fan-out handoffs (where the parent doesn't care about results) and pass-the-baton handoffs (where the parent calls `done` immediately) both work exactly as before.

The sentinel lives at the worktree root because that is the only path satisfying all three constraints: (1) writable by Claude Code's harness sandbox, which blocks raw `/tmp` writes — only `$TMPDIR` works there; (2) writable by the OS-level Seatbelt sandbox (`src/dashboard/sandbox.ts` `DEFAULT_ALLOW_WRITE`), which permits the worktree, `~/.npm`, `~/.cache`, and `/tmp`; (3) reconstructible by the poller from the registry entry's `worktreePath`. `$TMPDIR` falls out on (3) because it is per-Claude-session. `~/.garden/sessions` falls out on (2). The worktree is the intersection. As a side effect, `killPane` no longer needs explicit sentinel cleanup — `git worktree remove --force` in `backgroundGitCleanup` removes the file along with the worktree. Workers are instructed not to commit the file (it is per-worker state, not project state).

#### Blocked on the operator

A worker has three ways to end a turn, and until `garden blocked` existed only two of them were expressible — which meant the third case was routinely reported as one of the other two, wrongly.

- **Keep going.** Push, end the turn, and let the post-merge auto-continue above prompt the next phase. The default.
- **Done.** `.garden-done`, per everything above: every named deliverable landed and verified.
- **Blocked.** Work remains, the worker has pushed what it could, and the next step needs a decision only the operator can make — a product-shape question, a spend or credentials approval, a choice the request gives no basis to make.

The third had no surface. A worker in that position had to pick one of the other two, and both misreport it: `.garden-done` puts a bold green check on the row *and* arms the whole-task holistic review over a task that is not whole, while ending the turn silently leaves an ordinary `idle`. Neither says "the operator's answer is the blocker", so the fact reached exactly one surface — a message in a pane nobody away from the dashboard is reading. On 2026-09-09 a worker stopped two phases short this way: it named both remaining phases in its final message, wrote the sentinel because the remaining work needed operator decisions, and sat `done` behind a spent holistic pass while the operator was away expecting it to finish.

`garden blocked "<question>"` (`src/commands/blocked.ts` → `blockWorker` in `src/dashboard/workers.ts`) is that third exit. Deliberately **not** a new `PrState`: blocked-on-the-operator is orthogonal to the PR lifecycle — a worker can be blocked while `merged`, or with no `prState` at all — so a state would have needed edges from and to nearly every other one plus entries in `PR_STATE_KIND`, the transition validator, `queue`, `plot-status`, and STATUS.md's machine. It instead generalizes the `.garden-awaiting-input` human gate the designer workflow already used, adding the following behavior:

- **`WorkerEntry.blockedQuestion`**, whose presence lifts the row to the top blocked-on-you band (`workerSortTier`). A registry field rather than a sentinel read because the sort comparator is pure over the entry and runs on hot paths, and because a blocked worker whose branch merged sits at `merged` — the in-flight band, which descends toward `done` and sinks below every active worker. The row most needing attention was the hardest to find.
- **The `asking` display state.** `resolveWorkerStatus` reports a worker carrying a question as `asking` — the state garden already uses for "the agent needs you" — so the whole existing treatment applies at once: the bold yellow row, the `⚑` icon, the plot strip's yellow flag, and `whoami`. One derivation rather than three parallel special cases that could drift. It outranks the lifecycle states because those describe where the worker's *code* is (`merged` is explicitly a transient beat, not an operator signal) while this describes what it needs from a person; `failing` is the exception, since red means something is broken and that is more urgent than a question. Display derivation only, exactly like the `isDelegating` → `working` branch beside it: `agentStatus` and `prState` are untouched in the registry, so review/merge gating and the poller keep seeing the real state. The two remain distinguishable where it matters — a true `asking` is an agent blocked *mid-turn* (hook-detected), this is a worker that ended its turn cleanly and recorded that it cannot start the next one.
- **No alert.** An early version raised a warn-level alert. That was wrong: the alerts pane is where faults go, its rows wear `✖`/`⚠`, and a worker asking a question is the system working rather than failing (operator call, 2026-09-09). The away case the alert was reaching for is covered better by the **plot strip**, which aggregates across every project in a plot — one glance at the top bar shows a question waiting anywhere in the fleet, with no pane to open and no read/unread state to manage.
- **`.garden-done` removed** when a block is written, making the two exits mutually exclusive by construction. A worker can never be simultaneously finished and blocked, and therefore can never arm the holistic review from a blocked stop.
- **The question on the row**, trailing the topic in the elastic detail column as `<topic> · <question>` (`composeDetail`, `status.ts`). The topic leads in every lifecycle state because it is what a glance must always recover — which worker this is about — and the question follows it, so a narrow pane truncates the question before the topic. The holistic pass's `holistic review` tag trails the topic the same way. Capped at `MAX_BLOCKED_QUESTION_LEN` (280); reasoning belongs in the pane message. The derived `asking` state also supplies the `⚑` icon, which means the same thing to the operator — you are the blocker — and replaces the misleading `✓` a worker blocked after a merge would otherwise wear. The icon sits in the never-truncating row core, so a narrow pane still says "blocked" once the question is squeezed away, and it comes off the registry field, so a worker whose worktree has gone missing still reads as blocked. The trailing yellow `?` (`formatAwaitingInputGlyph`) is consequently now a *fallback*, shown only for a worker holding the sentinel with no recorded question — a worktree written by the old bare `touch` and not yet refreshed — since repeating a fact the icon, the placement and the text all already carry would spend a column saying nothing new.

The worker's branch is still reviewed and merged normally — being blocked concerns what comes *next*, not the commits already pushed. The operator's next prompt to the pane clears the question, the sentinel, and the row flag together (`onPromptSubmitted`), because that prompt is the answer. Not every answer is a prompt: a `!` shell command typed into the pane (`! gcloud auth login`, the most common thing a blocked worker asks for) starts a new turn without firing `UserPromptSubmit`. So on claude-code the Stop hook stamps `blockedTurnEndedAt` when the turn that asked ends, and the next main-thread `PostToolUse` after it clears the block the same way (`onToolActivity`) — the worker is running again, so it has its answer; a worker that still needs one re-blocks. Subagent tool calls never clear it, and Codex is excluded because its `Stop` fires mid-turn with `PostToolUse` still following. Nor does a turn Claude Code starts itself: when a background command, Monitor or async agent reports, or another session sends a message (how a subagent's final report arrives), it submits a prompt framed as `<task-notification>` or "Another Claude session sent a message", and `UserPromptSubmit` fires for it exactly as for a typed one (observed in the fleet's logs for such turns across 2.1.282–2.1.309, while no `!` command fired it). `onPromptSubmitted` recognizes those frames (`isHarnessPrompt`), keeps the question and the sentinel, and un-stamps `blockedTurnEndedAt` so that turn's own tool calls cannot read as the answer; its Stop stamps it again, so a `!` answer after it still clears the block. An answer sent from another Claude session arrives in the same frame, so it leaves the question up as well; `garden resume <worker>` clears it. `garden resume <worker>` clears a block without prompting, alongside its existing `.garden-done` clear.

One invariant holds that clear together: **the registry flag is cleared on the same predicate the auto-continue gate reads** — `isAwaitingInput`, not whether the unlink succeeded. The two differ, and the difference is a trap in both directions. A refused unlink leaves the sentinel in place, so the gate still skips and the flag must stay. But a worker with no `worktreePath` — which `validate.ts` clears whenever a worktree goes missing, and a blocked worker can outlive its worktree — holds no sentinel at all, so nothing is being skipped; keying on the unlink there would pin the flag on permanently, and since `garden resume` refuses a pathless worker the operator would have no way to clear a row still asking them for an answer they already gave. Sharing one predicate with the consumer makes that class of disagreement unrepresentable rather than merely fixed. A clear bypasses the hook heartbeat throttle and repaints the dashboard even when `agentStatus` is already `working`, since the row changes either way. A failed unlink is retried on a later tool event, and once it succeeds the registry fields and the row flag clear together.

Reachability is the other half, and is why the exit is named in four prompt surfaces rather than one: the bundled `blocked` skill (`src/dashboard/skills.ts`, installed like `done`), the worker preamble in `src/rules.ts`, the post-merge continue prompt (`MERGE_CONTINUE_BASE`), and the `done` skill's "when NOT to use". The last is load-bearing — this is the case that most resembles being finished and is not, so `done` has to route it away explicitly. The designer workflow's own human gate now runs the same command instead of a bare `touch`, so both gates share one mechanism and a designer parked mid-phase also sorts up and flags its plot.

Skip conditions (logged at `debug`):
- The `.garden-done` sentinel exists for this worker.
- The `.garden-awaiting-input` sentinel exists — a worker paused at a human gate, either a designer between its phases or any worker that ran `garden blocked` (see "Blocked on the operator" above). Unlike `.garden-done` this does not mean "finished"; the resume is the operator's next prompt, which clears the sentinel via `UserPromptSubmit` (or, for a `garden blocked` worker answered by a `!` shell command, the first main-thread tool call after the blocking turn ended). The planner's review gate is board-side promotion, so it does not use this sentinel.
- `agentStatus` is `working` or `asking` — the operator is already typing, same guard the interrupt-recovery path uses.
- `lastAutoContinueAt` is within the idempotency window — 10 seconds for the merge-time dispatch (guard against merge-event replay), 60 seconds for the gate-reopen sweep (guard against double-pasting a delivery still in flight).

The merge-continue prompt includes contextual preambles when applicable: a stale-files list when the reviewer modified files, a manual-sync nudge when the worktree could not auto-sync, and a postMerge acknowledgement when the project has a `postMerge` hook configured (so the worker does not redundantly suggest the operator run build/install steps that already ran). That auto-sync (`syncWorktreeToRemote`, `git.ts`) moves the worker's worktree onto its merged branch with `reset --keep`, not `--hard`, as the base-checkout heal does: its fetch runs after the clean-tree check, and a worker prompted in that window may already be writing, which `--keep` refuses to overwrite.

Both autocontinue prompts (post-merge and interrupt recovery) lead with a branch-identity line naming the worker's own branch and base and forbidding any rebase/merge/reset/checkout onto another worker's branch. Every worker runs in a worktree of the *shared* project repo, so a sibling worker's branch — and its `origin/<branch>` tracking ref — is visible in `git branch -a` from this worktree. The prompt previously named no branch, and a worker on a multi-worker project rebased onto a sibling's branch when it tried to "continue on the merged base"; pinning the branch in the prompt (`branchIdentityLine` in `continue.ts`) removes that ambiguity. The base-sync operations the manual-sync nudge relies on (`git reset --hard refs/remotes/origin/<base>`) stay allowed — only sibling worker branches are off-limits. Both prompts name origin's base in full, as the review prompts do: any worker can create a tag or branch named `origin/<base>`, which the short form resolves to first.

A successful dispatch logs at `info` (`auto-continued worker after merge`) so the operator sees the lifecycle transition in `⌥l` logs alongside the `merged` line. The post-merge dispatch fires a 5s primary plus a 16s retry (`_continue-worker-after-merge-if-stuck`): the 5s delay lets postMerge and the reviewer's force-push settle before keys land in the pane, and the retry recovers the case where the worker still read as `working`/`asking` at the 5s mark (e.g. mid-turn on a long response), under which the single-shot prompt would otherwise be lost with no recovery. The retry re-fires only when `prState` is still `merged` — a delivered prompt fires `UserPromptSubmit`, which clears `merged`, so any other state proves the prompt already landed and the retry no-ops rather than double-prompting. The interrupt-recovery dispatch uses the same shape (6s primary + 16s retry) to absorb the slower TUI bind under dashboard-rebuild load.

**Paste delivery.** Every garden-initiated prompt reaches a worker the same way: `pasteAndSubmit` (`tmux.ts`) loads the message into a tmux buffer over stdin, pastes it into the pane, and taps Enter. Two properties of that sequence are load-bearing, and both were learned from delivery failures.

*Bracketed paste.* The paste goes out as `paste-buffer -p`, which wraps the payload in the terminal's paste control codes (`ESC[200~` / `ESC[201~`) when the TUI has requested bracketed-paste mode. Without `-p` two failure modes compound. `paste-buffer` replaces every LF with CR, so each blank line between prompt paragraphs arrived as a bare Enter keystroke; and with no bracket markers the TUI had only an arrival-timing heuristic to tell a paste from fast typing. Prompts consequently landed **truncated** — the head dropped and an arbitrary mid-sentence suffix submitted as the entire message. Across retained worker transcripts on 2026-08-29, 7 of 11 post-merge auto-continue prompts had arrived truncated, one down to its trailing 20 characters, spanning four workers in three projects; the surviving tail was typically the prompt's closing *"do not invent additional work"* clause with its subject stripped, which a freshly merged worker then acted on as a standalone instruction. Inside paste brackets every byte is content, so no embedded newline can submit early and no heuristic has to guess. If the TUI has not requested bracketed-paste mode, tmux omits the control codes and inserts the payload normally.

*Settle wait.* The Enter waits for the composer to actually hold the paste instead of guessing with a fixed delay. The caret is the harness-agnostic signal — it sits at the end of composed text — so `pasteAndSubmit` snapshots `capturePaneCursor` before the paste and then polls every 100ms until the caret has moved off that position *and* held still for one poll, which means the burst was ingested and rendered (including the collapsed `[Pasted text #N +L lines]` placeholder a large paste renders as). The fixed 300ms Enter this replaces fired mid-burst: in the wan-smooth-mead case the prompt registered 312ms after the paste carrying 20 of its ~2000 characters. Polling costs one `display-message` fork per 100ms for at most 3s and only on prompt delivery — never on the hook firehose. Every exit path submits: an unreadable caret (sandbox, dead pane) skips the wait for the old fixed delay, and a blown deadline submits anyway, so the worst case is the previous behavior rather than a prompt that never lands. The confirming Enter 1.2s later is retained as the cold-respawn safety net (see *Stuck-paste recovery*).

*Delivery verification.* Neither guard above proves the worker received what garden sent — a mangled paste still submits, and `continueSentAt` is cleared by any `UserPromptSubmit`, so a prompt that arrived as a fragment of itself read as delivered, fired no retry, and left no trace. That is how the truncation above ran for days while every log line said `continue sent`. Bracketed paste removed the known cause; this is the check that would have caught it. After a successful paste `continueWorker` watches the transcript — the ground truth of what the model actually received — polling every 1.5s (20s ceiling) for the prompt to land, and classifies it with `classifyPromptDelivery` (`prompt-verify.ts`): `intact` when the landed text is ours, `truncated` when it is a substantial proper prefix or suffix *of* ours, `pending` otherwise. The length and end-fragment bounds keep a short phrase shared with an unrelated operator message from triggering an automatic paste. On `truncated` the full prompt is re-pasted once, behind a preamble telling the worker the previous message was a fragment and to disregard what it read into it — the worker is at that moment acting on that fragment, which is what makes the resend corrective rather than merely noisy. The resend deliberately bypasses `continueWorker`: a truncated prompt has already submitted, so the worker reads as `working` and `continueWorker` would refuse it — the very state our own mangled prompt caused. Its verifier carries the original fragment as the baseline until the corrective prompt appears, so transcript lag does not look like a second truncation. A genuine second truncation stops and raises an error alert rather than pasting a third copy. If the worker has exited, the pane disappeared, an operator draft blocks the resend, the corrective paste fails, or its transcript confirmation never arrives, garden does not paste unsafely and raises the same actionable error alert. For a seed, the `UserPromptSubmit` acknowledgement may belong to the known fragment, so `seedWorker` retains the briefing file until the corrective prompt is observed intact; a failed or unverified correction therefore leaves the full recovery copy named by the alert. `pending` is deliberately the catch-all: only the observed failure shape is actionable, and re-delivering on anything else would risk double-prompting over a comparison quirk. The whole path is best-effort before a truncation is known — an unreadable transcript or a harness with no reader yields "cannot verify" and leaves delivery on its pre-existing terms; after a truncation is known, an unverified correction is surfaced rather than silently abandoning the worker on the fragment.

The pre-paste prompt text remains an active baseline only while the worker's `continueSentAt` still equals the stamp written for this delivery. `UserPromptSubmit` clears that stamp when a new user turn registers. Pairing the content baseline with that existing acknowledgment is what makes two byte-identical post-merge or interrupt prompts distinguishable: the old identical tail remains `pending`; after the hook clears the stamp, the newly appended identical prompt is `intact`. The corrective resend writes and watches its own stamp for the same reason.

Reading the landed prompt is per-harness and lives in a **table** in `prompt-verify.ts` rather than a `HarnessCore` method, for a bundle reason: `continue.ts` is reachable from the lean `dist/hook.js`, which now sits under a hard 144KB ceiling (the 128KB ceiling of the time had under 1KB of headroom), and the core objects are literals held live by the `CORES` registry, so their method bodies cannot be tree-shaken — hanging the reader there cost the hook bundle 1251 bytes it never uses and busted the ceiling. As a leaf reached only from `continueWorker`, the module shakes out entirely (+15 bytes measured). The cost is that the type checker no longer enforces coverage, so `prompt-verify.test.ts` asserts the table has a reader for every registered harness. `readLandedPrompt` is the lookup through that table.

**Operator-draft deferral.** The `agentStatus` gate above catches a worker that is *already running*, but not one that is idle while the operator is mid-compose — text sitting unsent in the agent's input box. Pasting then would concatenate garden's prompt onto that draft and submit the mangled result. Every delivery path (interrupt recovery, post-merge, handoff callback) funnels through `continueWorker`, which therefore inspects the pane before pasting: `capturePaneText(paneId, { styles: true })` reads the visible pane with its SGR attributes (`capture-pane -e`), `capturePaneCursor` reads the caret position, and `extractDraftInfo` returns the operator's draft as the non-dimmed span between the prompt marker (Claude Code's `❯` U+276F, or Codex's `›` U+203A) on the bottom-most input line and the cursor column. A non-empty result means an unsent draft, and `continueWorker` skips the paste (leaving `interruptedWhileWorking` set, since the prompt is still owed). An *empty* box is not blank — Claude Code paints dimmed ghost/autosuggest text into it (Codex: a dimmed `Ask Codex to do anything`) — so dimmed text is dropped before anything else: typed text and both harnesses' paste placeholders render at normal intensity (verified on Claude Code 2.1.274 and Codex 0.154), so this never hides a draft or a stuck paste. The dimming filter is primary because the caret is not reliably on the input line: an idle Claude Code pane was observed (2026-09-17) with its caret hidden and parked at the pane's bottom-left, which the caret bound alone read as a wrapped draft and deferred the post-merge continue indefinitely. The caret still bounds what remains: it sits at the end of typed text, so the span is exactly the typed prefix when a partial draft is followed by a completion. Both TUIs also reuse their glyph as the selection cursor of numbered menus (`› 2. Keep current model`, `❯ 1. Yes, try it`), whose rows are not dimmed; a marker row reading as a numbered option beside another numbered row is reported as a **menu** (`DraftInfo.menu`) rather than a draft. It blocks the paste all the same — a paste into a menu picks options and Enter confirms one — and is re-armed by the same backoff, but the skip, re-arm, and truncated-resend alert name the menu instead of blaming an operator draft. A caret on a row below the marker means the draft wrapped (non-empty); a caret above it is not on the input line (no draft). The capture therefore drops `-J` so its row indices stay aligned with `cursor_y`. When the cursor is unreadable (pane unreachable), `extractDraftInfo` falls back to the whole post-marker remainder — the conservative pre-cursor behavior — but in that state `capturePaneText` is also empty, so it resolves to "no draft" anyway. On a draft-deferred skip, the two primary dispatch legs (`_continue-worker`, `_continue-worker-after-merge`) re-arm via `rearmContinueIfDrafting`: a fresh detached child every 12s, threading an `--attempt N` counter, until the box clears or `MAX_DRAFT_RETRIES` (15, ≈3 min) is hit. Re-arm fires only while a draft (or menu) is still present, so an `agentStatus`-caused skip (empty box) falls through to the existing `*-if-stuck` leg instead, and a delivered prompt — whose paste transiently fills the box — is not mistaken for a draft because the handler keys re-arm on the delivery result, not a re-capture. The merge path's gate-reopen sweep remains the long-tail backstop past the retry cap. The sweep itself does not dispatch while a draft or menu holds the box (`workerInputBlocker`, given the entry so garden's own stuck paste still counts as deliverable): a dispatch would find the same draft and start another chain, so every poke past the sweep's window started one, for as long as the draft sat there (`garden/round-brisk-mead`, 2026-09-17: six chains in 18 minutes, three of them running at once). A standing draft now costs one pane read per poke, and the first poke after it clears delivers.

**Stuck-paste recovery.** The guard above has one systematic false positive: garden's *own* paste. `pasteAndSubmit` pastes the message and taps Enter once the composer has settled, then again 1.2s later; when both taps are eaten (TUI mid-redraw), the message sits unsent in the box, and every retry then re-captured that same text, read it as an operator draft, and deferred — a starvation loop, since a stuck paste never clears itself (this is how bead-intake workers missed their seeded `bd close` in board's delegation-loop acceptance run, 2026-08-14). `continueWorker` therefore classifies a detected draft before deferring, on two joint conditions (`isOwnStuckPaste`): `entry.continueSentAt` — stamped at `continueWorker`'s success exit and cleared by the `UserPromptSubmit` hook, so while set, garden pasted and no prompt of any kind has landed since — and a garden-paste signature on the draft's visible head (`[garden]` / `[handoff` verbatim, or the collapsed-paste placeholder — Claude Code's `[Pasted text #N +L lines]` or Codex's `[Pasted Content N chars]`, the common rendering for these multi-line prompts). A draft matching both is garden's own paste whose submit was eaten: the recovery is `pressEnter` (the message is already in the box; re-pasting would double it), with no extra `continue.dispatched` telemetry record for the Enter. Ordinary continues retain the original paste-success record; verified seeds record exactly once when the prompt hook confirms the eventual user turn. `continueSentAt` stays set until the prompt hook confirms a landed prompt, so a replay retries the Enter if it is eaten again. A signature draft with no outstanding `continueSentAt` (the operator pasted content of their own) still defers as before.

The signatures cover every prompt garden composes itself, but not an operator-authored **single-line** seed, which carries no such head (a multi-line one renders as the `[Pasted text …]` placeholder). `isOwnStuckPaste` therefore takes a second, signature-free route when the caller knows what it is about to paste — `continueWorker` always does, since a retry re-sends the same text. Under an outstanding `continueSentAt`, a whitespace-normalized draft that **equals** the pending message in full is our own stuck paste: a partial operator compose cannot equal the whole text, so the arm carries no false-positive risk. When the draft **wrapped** (the caret sits below the marker, so the visible marker row is only its first row and equality is unavailable), an exact *prefix* match is accepted instead — safe without an arbitrary length floor precisely because it wrapped, which requires the operator to have retyped a full visual row of our message character-for-character. `extractDraftInfo` carries that wrap bit, which the older `extractOperatorDraft` string return discarded; wrap is reported false whenever the cursor is unknown, since it cannot then be established. A plain draft under an outstanding stamp that matches neither arm (the operator cleared our text and is composing their own) still defers. The loop workflows' mirrored gate uses `paneHasBlockingOperatorDraft`, which applies the same carve-out — a stuck garden paste never blocks the cold respawn, which discards it and re-seeds.

**Verified seed delivery.** A *seed* — the first prompt a freshly spawned worker receives (handoff briefings, `workers new --seed`, and each loop workflow's per-iteration cold-respawn prompt) — is the one continuation a worker cannot recover from losing. An interrupt or post-merge continue has a retry leg and, failing that, an operator looking at a worker that is visibly mid-task; a lost seed leaves a live worker parked at an empty prompt with no task at all, which reads as "the workers didn't start" (observed three times on 2026-08-19). `pasteAndSubmit` cannot detect this: `tmux load-buffer` succeeds whether or not the TUI was accepting input, so the old fire-and-forget `seedWorker` logged "continue sent" for a briefing that never existed.

`seedWorker` therefore runs three phases — wait, paste, **confirm** — and the confirmation signal is the one the registry already carries: `continueSentAt` is stamped by `continueWorker`'s paste and cleared *only* by the `UserPromptSubmit` hook, so a stamp that changes after our send is proof a prompt registered as a real user turn (`classifySeedDelivery`, with `agentStatus` reaching `working`/`asking` as the corroborating arm — not a stale-status false positive, since `continueWorker` refuses to send to a worker already mid-turn). An unconfirmed send is re-pasted after a 45s window, up to 3 attempts; retries are safe by construction, because `continueWorker` skips an active worker and routes a paste still sitting unsent through the `isOwnStuckPaste` → `pressEnter` recovery above rather than pasting twice. A decline (no pane, bare shell, worker mid-turn, operator drafting) is transient and re-polls *without* consuming an attempt, bounded instead by a 5-minute overall delivery deadline. The cold-boot wait rose from 90s to 180s: the old cap expired routinely on a slow bootstrap, and expiry meant pasting into a still-`loading` TUI — the exact swallow. It still sends on expiry (the `loading` status may itself be the lost signal) but that send is now verified.

The wait's readiness signal is **harness-specific**, because `agentStatus` only answers the question for a harness that reports its own boot. Claude Code does — its `SessionStart` hook fires when the TUI comes up, clearing `loading` within seconds. Codex does not: it fires `SessionStart` at the first *turn*, so a Codex worker stays `loading` until something prompts it, and this wait is what withholds the prompt. That is a deadlock, broken only by the 180s expiry, and every handoff into a Codex worker paid it as a flat three-minute dead pane (`lean-stout-quartz`, 2026-08-25: launch 18:28:32, `SessionStart` 18:31:39 — 0.6s *after* the seed paste that caused it). A harness in that position implements the optional `HarnessCore.promptReady`, which reads boot off its own pane; the seed wait consults it whenever `agentStatus` still says `loading`, and sends as soon as either signal says ready. The wait reaches it through `harnessSignalsPromptReady` (`harness/core.ts`). Codex's probe is its composer — the `›` glyph paired with the placeholder it paints into an empty input box, measured live at under a second from launch. The glyph alone is not enough: Codex reuses it as the selection cursor in startup dialogs (`› 1. Yes, continue` on the directory-trust prompt), and the two failure directions are not symmetric — a false negative costs the 180s backstop that predates the probe, while a false positive pastes the briefing into a menu where Enter picks an item and the seed is lost to a retry. So the probe is precise rather than permissive, and a future Codex whose placeholder differs degrades to the backstop — the rollout file is not usable, since it is born at the first turn with its `session_meta` timestamp back-stamped to session start, and so says the same thing `SessionStart` does, only later. A harness that omits `promptReady` keeps the pure-`agentStatus` wait and never pays a `capture-pane` fork. The probe runs only while a worker is still `loading` and has therefore never been prompted, so the pane it reads holds the harness's own boot output and nothing a conversation could forge.

Exhaustion is **loud and recoverable**: an error-level log plus an operator alert naming the worker, and the seed file is deliberately *retained* — it holds the only copy of the briefing — with its re-delivery command (`garden dashboard _seed-worker <project> <worker> <file>`) in the alert text. The file is unlinked only on confirmed delivery or on a worker that no longer exists.

`newWorker` dispatches the seed the moment the worker's pane is live. Everything after that point (the telemetry record, ensuring the project poller, the dashboard refresh) is best-effort and logs a warn instead of throwing: a throw there used to skip the seed and report a spawn failure for a worker that was running, so a handoff child sat idle with no task and `⌥n` said "New worker failed" over the new pane. The watchdog starts a missing poller on its next tick.

Starting a second seeder for the same seed file is harmless, which handoff recovery relies on. Each seeder claims its file before it pastes anything (`<seed>.seeder`, naming the seeding process) and stands down while another seeder holds the claim; a claim whose pid no longer answers, or answers for a process started after the claim was written, is taken over, so a seeder that exited or died leaves it to the next. Without the claim, two seeders waiting out the same boot paste together. And no paste goes out for a seed the transcript already shows landed whole (`readLandedPrompt`, the corrective resend included): a seeder taking over from one that died after delivering, or one whose confirmation missed its own landed paste, would otherwise send the briefing twice.

`garden pause <worker>` writes `.garden-done`; `garden resume <worker>` deletes it and also clears `.garden-awaiting-input` plus its recorded blocked question when present. The worker's next `UserPromptSubmit` deletes `.garden-done` too when it clears a `merged` or `done` state, so a later Stop with no commits ahead cannot re-trip `done` from an earlier phase's declaration. Removing a worker (`opt-x` or `garden workers stop`) removes the worktree entirely, so either sentinel goes with it.

A second, *global* opt-out lives alongside the per-worker sentinel: a gate in `~/.garden/config.yml` under `autoContinue` (`enabled`, `usageAutoClose`, `usageThreshold`, `resumeAfterReset`). Defaults are enabled, usage close off (95% threshold once it is on), no auto-resume. The usage close is off by default because usage is capped on the Anthropic side (extra usage on or off), so a garden-side closure duplicates that cap and only strands merged workers; `garden auto usage-close on` arms it, and `usage-close off` also lifts a usage pause it had already set (a manual `garden auto off` carries no `pausedUntil` and is left alone). The gate is consulted on every `maybeAutoContinue` after the per-worker checks. With usage close on, the threshold check evaluates the `5h` and `weekly` meters from the latest usage snapshot; the model-scoped weekly meters are intentionally excluded since the workhorse is Opus. When any included meter is at or above `usageThreshold`, the gate flips `enabled=false`, persists `pausedUntil` (the latest `resetsAt` among tripped meters, so re-enabling does not immediately re-trip on the slower-resetting meter) and `pausedReason`, and fires a warn-level alert (source `usage`). With `resumeAfterReset: true`, the next call past `pausedUntil` flips `enabled` back on automatically; with it off (the default), the operator must run `garden auto on`. Manage with `garden auto [on|off|status|usage-close on|off|threshold <N>|resume-on-reset on|off]` (alias `auto-continue`).

The usage-triggered closures are per worker. The meters describe one token pool — the default Claude account (Keychain / `~/.claude`) — so a worker that draws from a different pool is exempt from them: a harness other than claude-code (a Codex worker spends OpenAI quota), a third-party `provider` (the worker's own, or its project's), or a project `claudeProfile` whose configDir resolves to something other than the default `~/.claude` (a separate Claude subscription). A project can host both kinds at once (`entry.harness`, per-worker crews and build members), so the answer belongs to the worker: `workerUsageGateExempt` in `src/config.ts` is the one rule, and the gate, the status pane's `gate closed` suffix, and `whoami` all apply it. `autoContinueGateReason` takes the project name and the worker's provider and harness; for an exempt worker it bypasses `usage-paused` and skips the meter evaluation entirely — no read, no trip side effect — so an exempt worker's merge never flips the global gate or fires the usage alert; the threshold trip fires from the next metered worker's check, where it describes tokens that worker actually consumes. An explicit `garden auto off` (`enabled=false` with no `pausedUntil`) still blocks every worker — that closure is operator intent, not a meter reading. The exemption falls out of facts already in config and the registry, and fails closed on an unknown project: an unresolvable provider or profile is not itself evidence of a separate token pool, though another independently valid dimension may still prove one. Only the exempting direction is per worker: a claude-code worker on an exempt project stays exempt. Worker execution separately rejects an invalid provider identity instead of falling back to another account. No new config keys are required. Deliberate trade-off: exempt workers run without usage protection, since garden does not meter non-default pools. Holistic-review dispatch (`poller-holistic-review.ts`) consults the same gate with the worker's provider but not its harness: the pass spends its reviewer's pool, and the reviewer is resolved apart from the worker's harness (a Codex worker on a `codex-claude` crew is reviewed by first-party Claude).

A gate block does not lose the prompt. `maybeAutoContinue` is one-shot at merge time, so a worker whose continue was blocked parks in `merged`; the merged-state handler (`handleMerged` in `src/dashboard/poller-merge.ts`, shared by every workflow) replays the same auto-continue decision on each poller poke — the gate-reopen sweep. The first poke after the gate reopens (manual `garden auto on` or `resumeAfterReset` firing) delivers the stranded prompt; the sweep also fires the auto-resume check itself, so `resumeAfterReset` does not need a fresh merge to take effect. The poke is guaranteed even on a fully idle garden: `garden auto on` and `garden auto resume-on-reset on` wake every project poller directly, and the usage poller pokes all pollers when it observes that a paused window with auto-resume armed has passed (`pokeOnGateReset` in `usage-poller.ts`). Sweep-specific guards: a 60s idempotency window (wider than the 5s/16s delivery legs, so an in-flight merge-time dispatch is never double-pasted — this also recovers prompts whose paste was silently lost), gate blocks logged at info, `agentStatus: "exited"` workers skipped (no live agent pane to paste into; reviving one is bounce territory), and a worker whose input box holds an operator draft or menu skipped until it clears. The gate-block info line is logged at most once per worker per hour rather than on every poke, and a worker whose gate opens again is dropped from that throttle, so its next strand logs at once. The throttle is `control/gate-blocked-<project>`, one line per worker logged within the hour: it was a module-level map, which every one-shot poll process started empty, so the line logged once per poke. A gate-closed strand is surfaced three ways: that info log, a yellow `gate closed` suffix appended to the `merged` row in the status pane (`formatGateSuffix`, `src/commands/status.ts`), and the `auto-cont.` line in `garden whoami` (`formatAutoContinueLine`, `src/commands/whoami.ts`) reporting the gate state (on / OFF + pause reason). Both surfaces mirror the per-worker exemption (`workerUsageGateExempt`): on a usage-triggered closure, an exempt worker's merged row carries no `gate closed` suffix (`gateHoldsWorker`, `status.ts` — it auto-continues and never strands) and its `whoami` line reads green `on` with a separate-token-pool note (JSON adds `usageGateExempt`); on an explicit `garden auto off`, both report closed for every worker.

### Sibling Merge Notification
When code merges, the poller compares the changed files against every other active worker's branch in the same project that merges into the same base (for a sibling on another base, that base's own divergence would read as overlap, and the notice's "rebase onto <base>" would carry it into the wrong branch). If files overlap and the sibling has a live Claude session, it is notified via a pasted prompt with the merged worker's newest commit and the overlapping file list so it can review and avoid reverting the merged work. Dead workers are skipped — marked `exited`, or with the agent exited back to the pane's shell under a launch wrapper that recorded no exit (one older than the exit record, or whose record failed), which can still read `idle` (the pasted notice would run there as shell commands, and it quotes a worker-written commit subject) — they will hit rebase conflicts naturally on their next review cycle. So is any pane waiting on the operator: `asking`, held (`paused`), blocked on a `garden blocked` question, or holding an unsent draft or menu. The notice is pasted with Enter, which would pick a menu option, resume a hold, clear the question as if it were answered, or submit the half-typed draft; the skip is logged, and the merge queue's own rebase still catches any conflict.

### Claude Usage Meter
Two or more quota bars render in the top-left "garden" title pane sitting above the status pane: the 5-hour rolling window, the weekly total, and one bar per model-scoped weekly meter (labeled by the model — `fable` on current plans). Bars are colored by utilization — green <60%, yellow <85%, red at or above — with a bright `│` marker overlaid at the current time position in the window (so you can see whether usage is ahead of or behind the clock) and the reset countdown next to each. The model-scoped bars come from the response's `limits[]` array (the `weekly_scoped` entries, each tagged with `scope.model.display_name`), so the bar auto-tracks whatever model Anthropic scopes without a code change; the older flat `seven_day_sonnet`/`seven_day_opus` keys are now null. When the response carries no `weekly_scoped` entry, no model bar renders (the pane is just the two flat bars); a rolled-over window renders `—` for that entry. A scoped entry the account has not touched since the weekly reset is still served, as `is_active: false` / `percent: 0` / `resets_at: null` — the window has not opened, so there is no countdown to draw. That is a true 0% reading, so the bar renders at 0% with no reset text and no time marker rather than being dropped: the alternative made the `fable` bar vanish from the pane at every weekly reset and reappear only on first use, which reads as a broken meter.

When the account has pay-as-you-go extra usage enabled, the response's `extra_usage` bucket is surfaced as a dim credit footer under the meter bars (`extra  1234 / 5000 credits (25%)`) — an absolute credit tally, not a resetting time-window meter, so it renders as text rather than a fourth bar and is hidden entirely when extra usage is off. The same line appears in `garden usage`. A null/uncapped `monthly_limit` degrades to whatever fields the endpoint returns (`1234 credits used`).

Data comes from two sources split by cadence — the same design Claude Code itself uses — both authenticated with the OAuth token Claude Code writes to the macOS Keychain under service `Claude Code-credentials`. The **primary** source (every poll) is the `anthropic-ratelimit-unified-{5h,7d}-{utilization,reset}` headers that ride *every* `/v1/messages` response; garden reads them off a 1-token throwaway completion (`{model: haiku, max_tokens: 1, messages: [{role:"user", content:"quota"}]}` — `fetchUsageHeaders` → `parseUnifiedHeaders`). These carry the 5-hour and weekly bars, are documented/supported, and are governed by the generous messages limiter, so they essentially never throttle at garden's cadence. Utilization is a `0..1` fraction (scaled to percent) and the reset is unix epoch seconds. The **secondary** source (movement-triggered with an hourly backstop) is `GET https://api.anthropic.com/api/oauth/usage`, the undocumented endpoint that is the *only* carrier of the model-scoped weekly bar (`fable`) and the extra-usage credit tally. `fetchUsageRaw` requests it and `normalizeUsage` parses the response into the scoped meters and the credit tally. That endpoint is strictly rate-limited — its limiter tightened server-side around 2026-07-10 to a fixed `Retry-After: 3600` with a sustained budget near 10-12 requests/hour. Both the scoped fetch and the primary header probe authenticate with the same OAuth token, so they draw on a shared per-token budget: a scoped call can burn budget that then collaterally 429s the next primary probe. To keep that pressure off, the scoped fetch is gated on *actual scoped-model use* — `fetchScopedIfDue` asks `scopedModelInUse` (which reads the registry) whether any live worker is running a scoped model, matching a worker's effective model against the last-seen scoped labels (default `fable`) with a fresh `lastEventAt`. The effective model is read from the worker's transcript (`readLatestTranscriptModel` — the newest assistant message's `model`), not from `WorkerEntry.model`: that field holds only an explicit pin (`workers new --model`, a project or crew default), and a worker spawned without one runs the account default, which the registry cannot name. Reading the pin alone made a fleet running entirely on the account-default Fable report as idle, holding the scoped bar on the 12h keepalive indefinitely. Nor does a pin settle it: a harness can move a pinned session off its pin, so the watchdog's reading (`WorkerEntry.runningModel`, see "Model drift") comes first, then the pin, and the gate reads the transcript itself only for a worker neither names; a worker whose model cannot be resolved counts as not-scoped. A worker's headless reviewer, resolver or ci-fix agent spends too, while the worker itself fires no hook, and builtin crews put Fable on the review seat: a worker in `reviewing`, `resolving` or `ci-fixing` whose agent launched within `REVIEW_TIMEOUT_MS` counts when that role resolves (`resolveReviewRole`) to a scoped model. The transcript read (`readLatestTranscriptModel`, `conversation.ts`) is a bounded tail read, unlike `sumTranscriptUsage`'s whole-file parse, which is too heavy to run per live worker every cycle, and it skips a worker on any harness other than claude-code, since such a worker spends no Anthropic quota. `usage.ts` loads `resolveReviewRole` with a dynamic import, and only while some worker is in one of those states, because `roles.ts` reaches the workflow registry, whose poller handlers import `usage.ts`. When no scoped worker is live the bar drops to a slow 12h keepalive (the 7-day scoped figure isn't moving anyway), removing ~22 of every 24 daily oauth calls on an idle fleet.

While one *is* live, the cadence is **movement-triggered rather than a timer**. A flat hourly poll spent a request whether or not anything had happened and withheld one when a lot had, so the bar sat up to an hour behind a burning fleet while its neighbours refreshed every 90 seconds. The trigger exploits the fact that Fable consumption necessarily consumes *account* weekly quota too: the account weekly bar rides the primary headers, so it is free and live, and an unmoved weekly bar is proof the scoped bar cannot have moved either. `scopedFetchDue` therefore spends a scoped request when the live weekly utilization has advanced by at least `SCOPED_MOVEMENT_PCT` since the last scoped attempt — the baseline is `weeklyPctAtScoped`, re-stamped on every attempt from that cycle's primary reading — spaced by a `SCOPED_MIN_INTERVAL_MS` (10 min) floor, with `SCOPED_POLL_MS` (1h) retained as the backstop for movement the trigger cannot see. A weekly bar that *dropped* arms the next floor-eligible attempt: the window rolled over, so the scoped bar reset with it and the held value is wrong rather than merely stale. The interval floor doubles as the rate bound and is the reason no separate request governor exists — every healthy attempt gates on elapsed-since-the-last-attempt, so the ceiling is 6 requests/hour against the endpoint's ~10-12/hour budget, and only during an actively-burning Fable session. The result is strictly better on both axes: fresher during a burst, and still zero spend on an idle fleet. Movement is ignored on the idle branch, because non-Fable traffic advances the weekly bar without touching the scoped one. Degradation is toward the old behavior: a snapshot written before `weeklyPctAtScoped` existed, or a cycle with no live weekly reading, falls back to the backstop alone — the safe direction for a throttled endpoint. A scoped 429 is silent for the *primary* bars — they're already live from headers, so the scoped bar just keeps its last value until the next refresh; `scopedError: "rate-limited"` holds every scoped retry to the hourly backstop, honoring the endpoint's observed `Retry-After: 3600` instead of retrying at the 10-minute healthy-path floor; a forced refresh (`garden usage refresh`, `garden login`) skips the scoped cadence but not that hold. Nor does it fetch beside another refresh. Each refresh first writes a claim, which keeps the prior snapshot's error, backoff and both endpoints' 429 state, so a refresh that reads it mid-fetch still sees both holds; a forced refresh skips the cadence check that keeps every other caller off a claim, so it waits for a claim in flight (`claimedAt`, counted as in flight for `CLAIM_IN_FLIGHT_MS`, 60s, longer than the three 15s-bounded calls a refresh makes) to land, then decides on what landed. Fetching beside it sent the scoped endpoint a second request before the first one's 429 was recorded, and whichever final write came last discarded the other's outcome. It is *surfaced* on the scoped row's health tag (`Fable meter rate-limited`) only when a Fable worker was active or the operator forced the refresh — i.e. when that bar is consequential; an idle-keepalive miss stays fully silent. The failure is tracked as `scopedError` on the snapshot and cleared on the next scoped success. Credential discovery probes the `GARDEN_CLAUDE_SESSION_KEY` env var first, then the macOS Keychain, then `~/.claude/.credentials.json`. When the stored access token has expired, the meter exchanges the refresh token against `https://platform.claude.com/v1/oauth/token` (the same endpoint Claude Code uses) and persists the rotated tokens back to the source so claude CLI's next read stays in sync — otherwise the meter would silently revoke claude CLI's cached refresh token and force the operator to re-login. Both Keychain calls, discovery's read and that writeback, carry a timeout (`KEYCHAIN_TIMEOUT_MS`, `credentials.ts`), because a locked keychain makes `security` wait for an unlock nobody is there to supply: the usage poller and the Stop hook's detached `_usage-refresh` run unattended. The writeback passes the credential as the `-w` argument: `security`'s prompted form (`-w` with no value) reads through libc `getpass()`, which uses `/dev/tty` whenever a controlling terminal exists and truncates input to 128 characters, so it would store a truncated, unparseable credential in the entry the claude CLI reads. A revoked refresh token (`invalid_grant`) is surfaced as `login expired` and held off the API for `AUTH_BACKOFF_MS` until `garden login` heals it. On any other failure the snapshot records a short error and the pane renders a single dim "claude usage: …" line instead of bars — the meter is a progressive enhancement, not a dependency. Fetched snapshots live in `~/.garden/control/claude-usage.json`; the snapshot tracks `dataAt` (primary-bar freshness, drives the stale tag) separately from `scopedAt`/`scopedAttemptedAt` (the scoped bar's own freshness and cadence), so the intentionally-slow scoped bar never trips the stale warning. Because that suppression also hides a genuinely rotting bar, the scoped row annotates itself with its own age (`· 11h old`) once `scopedAt` exceeds the hourly backstop plus a 30-minute margin — an actively-metered row never shows it, an idle-keepalive one reads as throttled rather than broken. `assembleSnapshot` folds the primary outcome, the scoped outcome and the prior snapshot into each new snapshot and stamps `dataAt`, `scopedAt` and `scopedAttemptedAt`; the age threshold is `SCOPED_AGE_TAG_AFTER_MS`, and `formatScopedAge` renders the tag.

Refresh is **demand-driven with a timer floor**. The bars only move when workers spend tokens, so the fetch that keeps them fresh is the one triggered by work: every Claude Code `Stop` hook calls `maybeRefreshUsage()`, a fire-and-forget detached fetch gated by `HOOK_REFRESH_COOLDOWN_MS` (90s) — *below* the poller cadence, making turn-end the primary lane. That poller cadence is `POLL_OK_MS`. Its cost is bounded by the cooldown rather than by fleet size, because the gate reads the shared on-disk snapshot's `fetchedAt`: twelve workers ending turns at once produce one fetch, not twelve. An idle fleet ends no turns and so triggers none — correctly, since an idle meter isn't moving and its last reading is still true. Underneath sits the singleton poller (`_garden-usage-poller`) at 10 minutes, now serving as the idle floor and the liveness backstop rather than the main lane; it claims with its own cadence class, so a freshly respawned poller (dashboard restart) skips instead of firing an immediate fetch against a still-fresh snapshot, and during active work it mostly finds a young snapshot and sleeps. Worst case is one tiny `/v1/messages` request per 90s (~40/hour against the generously-limited messages endpoint, versus the throttled endpoint's ~10-12/hour budget, which is touched only on the scoped refresh — at most every 10 min while a Fable worker actively burns quota, every 12h otherwise). The faster cadence is a *healthy-path* rule only: `decideRefresh` applies the error backoffs to both lanes identically and they outrank the cooldown, so the demand lane cannot become a way around a 429. The header call rarely 429s (only when the account itself is at its cap, or when the shared OAuth-token budget is exhausted by scoped calls), but if it does the stored backoff is the server's `Retry-After` plus a 15-minute margin, doubling on consecutive 429s (capped at 4 hours), and both paths honor it; the pane's health tag shows the countdown labeled as the account meter so it isn't mistaken for a scoped miss (`account meter rate-limited, retrying in 1h 10m`). The log line names it the same way (`account meter probe rate-limited`).

**Build staleness (bottom bar).** `garden 0038f10` reads equally authoritative whether the build is current or three weeks stale, which is exactly how a frozen install goes unnoticed. The bar now qualifies it: when the running build trails its branch, `⚠ N behind` appears left of the version and the whole status bar turns yellow instead of the default green (`statusBarStyle`, `alerts.ts`). Color is the at-a-glance signal — the bar changes without being read — and the count is the detail. The yellow is the focused client's color; an unfocused client's bar background is grey regardless of staleness, and the `⚠ N behind` text stays visible either way.

The number is `<build-sha>..origin/<branch>` counted in `gardenInstallRepo()`, from the full SHA the build stamps (`GARDEN_COMMIT`), since git resolves the short `GARDEN_VERSION` through refs first and a tag of that name would stand in for the build: the repo the running binary was compiled from, resolved from `argv[1]` via `realpathSync` (which follows the npm-link symlink `bin/garden -> <repo>/dist/cli.js`). Deliberately the *install* rather than the registered `garden` project — the install is what goes stale, and it is reachable whether or not the operator registered it. There is no fetch; it reads the local `origin/<branch>` ref, which `fastForwardBase` advances on every merge, i.e. the same cadence the answer can change on.

It is computed on the watchdog's 5-minute throttle and cached in `DashboardState.buildBehind`, never at render time: `formatRightBar` runs on the hook firehose, so a `git rev-list` per call would mean a subprocess per tool use. `refreshBuildStaleness` (`watchdog.ts`) is that watchdog step. State is already read on every refresh, so carrying the number there is free. A build that cannot be measured — a `dev` build, or an install outside a checkout — leaves `buildBehind` null and the bar green; garden does not warn about drift it never established.

The compared-against branch is garden-level (`build.branch` in `~/.garden/config.yml`, `getBuildBranch`, default `main`), since the install is machine-wide rather than per-project. It is set from the `⌥;` garden settings menu's *build branch* row; the submenu enumerates the install repo's own branches via `listBranches` rather than offering a hardcoded main/dev pair, falling back to those two only when the install is not in a checkout. `listBranches` (feeding this submenu and every base-branch picker) excludes worker branches — names matching the generated adjective-adjective-noun shape (`isGeneratedWorkerName`, `names.ts`) — since a sibling worker's branch is never a sensible base or build target and an active fleet's recent-first ordering would otherwise fill the list with them.

**Codex meter (second column).** When Codex is in the fleet in any role, a second meter renders beside Claude in an equally sized column, with both providers using the same bar width (`renderCodexColumn` in `usage.ts`, sourced from `codex-usage.ts`). `renderUsagePane` builds the whole pane and chooses between the single-column and two-column layouts. Codex writes a `rate_limits` object into its rollout JSONL (an `event_msg` payload carrying `primary`/`secondary` rolling windows plus a credits balance — the same shape as Anthropic's quota response), so garden needs no new auth or endpoint: the data is already on disk.

The two-column meter block is bounded by matching full-width grey rules: the labelled header rule above and an unlabelled closing rule below. A blank row clears the meters from the header underline; the closing rule's otherwise-empty row supplies the bottom clearance.

Capture is **role-agnostic**, and deliberately so. Every Codex process spends the same quota, but only an interactive Codex *worker* fires garden's lifecycle hooks — the headless reviewer, resolver, and ci-fix agents (`launchHeadlessAgent`) do not. The original implementation captured at `Stop`-hook time from the worker's `transcript_path`, which meant a project on the `claude-codex` crew (Claude builds, Codex reviews) burned Codex quota on every review and showed no meter at all. `captureCodexUsageLatest` instead reads whichever rollout under `$CODEX_HOME/sessions/YYYY/MM/DD` is newest by **mtime** (not by name — a long-running worker's rollout keeps being appended, so it can hold a fresher reading than a newer-named short run), which covers every role and any role added later from one call site. The descent takes the lexicographically largest entry at each level and backtracks when a branch holds no rollout files, so an empty day dir just after midnight falls through without walking the year-deep tree.

Codex emits `rate_limits` on every turn but populates it only periodically: the common on-disk shape is `{ primary: null, secondary: null, credits: { balance: null, unlimited: false } }`. That is **not a reading** — counting the truthy-but-empty `credits` object as one produced a `windows: []` snapshot that renders as nothing *and* overwrote a good prior one. Both the backward line scan within a rollout and the choice of rollout skip such entries, falling through up to `MAX_ROLLOUTS_TRIED` (5) rollouts back before giving up; a short reviewer run routinely ends without ever getting a populated reading while a sibling from the same day holds dozens.

Reading the rollout is **passive**: it can only ever be as fresh as the last time Codex actually ran. A fleet that runs Codex occasionally therefore sits on a reading captured days ago — and if the operator changes plan in between, that reading is not merely stale but a percentage of a quota that no longer exists (observed on a real upgrade: `limit_id` moved `premium` -> `codex`, `plan_type` appeared as `plus`, and the window moved from 43200 to 10080 minutes, so the displayed 91% was arithmetic against a different denominator). `probeCodexUsage` is the active half — a minimal `codex exec` run purely to make Codex report its quota, the direct analog of the Claude meter's 1-token `/v1/messages` completion. It uses a read-only sandbox and a temp cwd so it can never touch a worktree, `--skip-git-repo-check` because that cwd is not a repo, and closed stdin because `codex exec` reads instructions from stdin when the prompt argument is absent and would otherwise block forever. A failure (offline, codex absent, out of quota) is non-fatal and still captures: the out-of-quota case writes a rollout on its way down.

Because the probe spends real quota, every caller gates on `codexInFleet()` — true when any project sets `harness: codex` or any `roles.{reviewer,resolver,ciFix}.harness: codex`, or any registered worker carries a codex harness or a crew name containing `codex`. Call sites split by who initiated them. The **ambient** ones fire on a cadence garden does not control and must go through `probeCodexUsageIfStale`, which adds a `CODEX_PROBE_INTERVAL_MS` (6h) snapshot-age gate on top of the fleet gate, then claims the attempt on disk (`control/codex-probe-attempt`, under a lock): a probe that confirmed nothing leaves the snapshot stale, and every `_usage-refresh` is a fresh process, so only a persisted attempt keeps one unconfirmed probe from being repeated on the next refresh, or by several refreshes at once. The callers are the watchdog tick (which also keeps an outer 6h throttle so the two gate reads stay off the 60s tick, advanced unconditionally once it opens so a probe that captured nothing is not retried a minute later), and `garden dashboard _usage-refresh` — which is not an operator command but the Claude Code Stop hook's usage lane (`maybeRefreshUsage`), firing on that lane's 90s demand cooldown throughout active work, so an ungated probe there would spend Codex quota every 90 seconds rather than per plan change. That gate is what lets the Claude meter run on a demand cadence without dragging the Codex probe along with it: the two meters share this entry point but not their costs. The **explicit** call site is `garden usage refresh`, which probes outright: the operator asking is itself the reason, exactly as that command already forces past the auth/error backoff. `garden usage` and `garden usage refresh` print the Codex reading as a `codex` section under the Claude one (and as an additive `codex` key when piped), with its own reset countdown and a `fetched` age (or the same `no window reading yet` placeholder the pane shows for a windowless snapshot); a probe that captures a populated quota event timestamped after it started re-stamps `capturedAt` even when the reading is unchanged (`probeCodexUsage` passes its start time to `captureCodexUsageLatest`), so that age means "last confirmed" rather than "last changed"; a failed probe, or a clean exit that produced no new quota report (capture can still be reading an older rollout), leaves it alone. It probes before the `anyAnthropicMeteredProject` gate, since Codex is a separate pool and a provider-only fleet still has a Codex meter to refresh. A fleet actively running Codex is fed for free by the passive capture and never probes; the watchdog's throttle timestamp is seeded to process start so a respawn cannot be used to trigger one. `PROBE_TIMEOUT_MS` (30s) is deliberately kept under the watchdog's `SLEEP_SLACK_MS` (60s): the probe runs synchronously in the watchdog loop body, and that loop reads its own iteration overrun as machine-suspend time, so a probe allowed to block for a full slack window would be misread as a suspend and discount a minute from every live review's timeout. The timeout kills with SIGKILL rather than the default SIGTERM: the npm `codex` wrapper traps SIGTERM, forwards it to the native binary and waits for that to exit, and `execFileSync` waits with it, so a SIGTERM bound was no bound (a probe sent SIGTERM at 30s ran to 107s).

The capture is driven from the **watchdog** tick (`watchdog.ts`), not the usage poller: the watchdog is the fleet's one unconditional recurring tick, whereas `startUsagePoller` is gated on `anyAnthropicMeteredProject()` — hanging it there would leave a provider-only fleet, for which `anyAnthropicMeteredProject()` is false, with no Codex meter. It writes only when the reading actually moves (so an idle fleet never churns the file) and repaints the title pane via `refreshDashboard()` only on that change. The snapshot is cached to `~/.garden/control/codex-usage.json`. Each rolling window renders as a bar labelled by duration (`5h` / `week` / `30d`, from `window_minutes`); windows sort smaller-first to mirror the Claude meter's 5h-over-week ordering; a subscription account typically reports only the 30d (`window_minutes=43200`) window. A pay-as-you-go credit balance renders as a dim `credits N` (or `unlimited`) footnote below the bars (the whole-number credit count — Codex reports credits, not a currency amount), and only when there is a balance to watch: a zero balance is the steady state for a subscription account with no credits, so a permanent `0` row would carry no information and is omitted. Codex writes `credits.balance` as a string (`"0"`), so capture coerces it to a number rather than type-testing it, which would drop a genuine balance. Like the Claude bars, a window whose reset time has already passed renders `—` rather than a stale percentage. A run cut off at the quota limit reports credits with `primary`/`secondary` null; that reading says nothing about the windows, so capture keeps the prior snapshot's windows under it — the at-limit bar and its reset countdown stay visible exactly when they matter. A snapshot that has never held a window still renders its labeled column with a dim `no window reading yet`, so the pane never collapses to an unlabeled Claude-only layout once Codex has reported. The whole second column is gated on a captured Codex snapshot existing, so a fleet that has never run Codex leaves the pane byte-for-byte unchanged. The gate is the rollout on disk, not garden's own registry: reading `$CODEX_HOME/sessions` is what makes the capture role-agnostic, and the same breadth means an operator who runs Codex *outside* garden will see the column on an all-Claude fleet. That is the intended trade — the meter reports the operator's Codex quota, which is one pool no matter who spent it. The two-column layout also downgrades to single-column Claude when the pane is too narrow to fit a second column (data stays captured and reappears once the terminal is wide enough). The available width is divided into equal columns after reserving four-cell outer margins and a three-cell gap; an odd leftover cell goes into the gap. Both providers use the same meter fit, shrinking their bars together from 24 to six cells and dropping reset text together when needed. Scoped age text is omitted when it cannot fit beside the shared bar, and status/credit footers stay within their column. Below 51 cells the pane falls back to Claude alone. Headers and closing rules fill the equal column widths even on very wide panes; longer annotations never shift Codex or shorten its bar. The two-column path also keeps the leading blank line rather than spending it on the column-header row, which had put the headers hard against the pane border; the pane auto-sizes to its content, so that row costs only the space it exists to provide (the single-column all-Claude render is untouched). Each `claude`/`codex` label is underlined across the full width of the column it heads (`columnHeader` in `usage.ts` — the name bold, the rule plain, emitted as two SGR runs that pin the SAME explicit grey, since a bold run leaving the color unset inherits the default foreground and renders bright white against the grey rule it continues into; weight is the only difference between the two runs). A blank row separates that rule from the meters because terminal underlines sit at the bottom of their cell and otherwise butt directly against the first bar; whole rows are the terminal's smallest spacing unit. Unlike the Claude meter there is no network poller — the snapshot advances on the watchdog's tick by re-reading the newest rollout on disk, so between Codex turns it shows the last-captured value.

### Alerts
The dashboard surfaces important events as alerts — persistent messages that require operator attention. Alerts are stored atomically in `~/.garden/sessions/dashboard.alerts.json` (same write-tmp-then-rename pattern as other state files), capped at 100 entries.

**Events that generate alerts:**
- Worker bootstrap could not fast-forward the main checkout (stale main, dirty worktree), or aborted because the requested base was missing with no usable origin default or origin could not be reached
- Review process failure (Claude unavailable, timeout, unparseable output)
- Reviewer or resolver exceeded the 120-minute wall-clock cap and was killed (`failingReason: "review-timeout"`, `garden kick`-recoverable — typically a hung subprocess, e.g. tests with no timeout blocked by the sandbox, wedging the state machine; a slow-but-live reviewer is bounded by the same cap)
- Reviewer could not fix issues (FAILED verdict)
- Merge failure
- Force-push failed after a passing review, in the merge queue, or after conflict resolution (source: `poller`, level: `warn`; deduped per worker via `push-failed:<project>:<worker>`). The worker is re-armed for a fresh review (`pendingReviewAt` + a 30 s delayed poke) rather than stranded, so a transient failure self-heals and a persistent one stays visible
- Local base ref could not be advanced after merge — only when it diverged from origin with real local-only content (warn), is checked out in another worktree (warn), the on-base checkout is dirty (warn), or it is wedged/unfetchable (`stuck`, error); a clean off-base ref advance and an auto-healed redundant local commit are both silent. Each alert fires only on entry into the state, not every merge cycle
- Repeated failures (3+ consecutive failures on the same worker)
- Base-branch drift after worker creation (Stop hook cannot count commits against `origin/<pinned-base>`; deduped to one firing per worker per hour)
- Auto-continue auto-disabled by usage threshold (source: `usage`, level: `warn`)
- `.garden-done` tracked in HEAD of the project main at worker spawn (source: `create`, level: `warn`; deduped per project per hour).
- Orphaned worker window: a live tmux worker window with no registry entry (the create/sweep race casualty; source: `watchdog`, level: `warn`; deduped per orphan per hour). Not raised from a registry read that failed, which returns an empty registry.
- Duplicate live panes for one worker discovered by the window heal (source: `watchdog`, level: `warn`; deduped by expected worker window + surplus window id). Detection only: the alert identifies the candidate surplus window for operator inspection and never kills it automatically.
- Orphaned worktrees: one or more directories under `~/.garden/worktrees/<project>/` that no registry entry claims (source: `watchdog`, level: `warn`; one alert per affected project, fired on change only). The worktree analogue of the line above — there the entry is missing while a *window* lives, here while a *directory* does. `validate.ts` reconciles registry → disk (clearing a dangling `entry.worktreePath`, dropping ghost `loading` entries) but never walks the directories asking which are unclaimed, so these were invisible by omission rather than by policy: 12 accumulated over roughly four months, 6.3GB, before a sweep found them. Detection only, never deletion — an unclaimed tree can hold the only copy of uncommitted work (one of those 12 held 978 uncommitted lines), so the disposition is the operator's. Committed work is never at stake, since a branch outlives its worktree, and the alert says so because that is what makes removal safe. A directory counts as claimed only by a registry entry with the (project, name) pair its path encodes, never by `entry.worktreePath`, which `validate.ts` clears once the path goes missing. The alert names up to five orphans with their size and days idle, counts the rest, and gives the `git worktree remove --force` + `prune` remedy; sizing visits at most `ORPHAN_WORKTREE_WALK_CAP` (50k) entries per tree and reports a floor past that, so a `node_modules` cannot stall the watchdog tick. Guarded against two races by a 1h mtime idle floor (a spawn mid-`npm install`, a kill's detached cleanup) and by skipping any worktree whose `workerCleanupMarkerPath` marker exists. A sweep whose registry read failed (an intact file that could not be read comes back empty) is skipped without touching the signature. Fires on change only against `DashboardState.orphanWorktreeSignature` — the sweep re-derives a months-old set every hour, and the watchdog's in-loop throttle resets to 0 on respawn, so a signature-free alert would nag roughly hourly forever. Deliberate simplification: the signature is fleet-wide, so a new orphan in one project re-alerts every other affected project once; that is bounded by genuine set changes rather than the clock, and a per-project signature map was judged not worth the state.
- Pseudo-terminal pressure: allocated ptys at or above 70% of the machine limit (`kern.tty.ptmx_max`, 511 by default on macOS; source: `watchdog`, level: `warn`; deduped hourly on a fixed key). Every pane needs a pty, so at the limit tmux cannot fork a pane and every worker spawn fails with `fork failed: Device not configured`. That errno is not proof of the limit: during the 2026-10-04 failures 79 of 511 were allocated. The watchdog takes a census on a 5-minute throttle (`pty-census.ts`): the count from `/dev/ttysNNN` nodes, the holders from `lsof /dev/ptmx`, each holder attributed to the garden pane it descends from, else to the worker worktree it runs in (a process reparented away from its dead pane), else "outside garden"; the tmux server is compared against its live pane count, since it holds one pty per pane by design. It logs a `pty census` line whenever the holdings a live pane does not explain change (tmux's own per-pane ptys churn with every review and are excluded), and the alert names the top holders. A spawn that fails with that errno takes a census at that moment and reports it: `out of pseudo-terminals (N/limit in use; top holders: …)` when the count has reached the limit, otherwise that tmux could not open a pseudo-terminal below the machine limit, with the same count and holders. Each command the census runs is bounded at 5s and SIGKILLed past it, since it runs synchronously in the watchdog loop and lsof can block on an unresponsive mount; a holder listing that did not finish skips that census rather than logging every holder as gone. macOS only; elsewhere the census is skipped.

- `~/.garden/config.yml` exists but does not load (source: `watchdog`, level: `error`; dedup key `config-unloadable`, so at most once per dedup window). Raised at the watchdog tick's first config read (`loadConfigOrAlert`); the message is the first line of the load error, which names the file and the YAML fault with its line:column, because every project's poll stops at its own first config read until the file loads. The failure no longer ends the tick, so the duties after it (awake release, cleanup retries, pane heals) still run.
- Worker removal stopped because its `worker.removed` tombstone could not be written (source: `workers`, level: `warn`; deduped per project/worker). The registry entry, worktree, branch, and bead claim are kept; the alert names the telemetry directory and says to rerun `garden workers stop <worker>` from a shell that can write there.
- Worker with no worktree path in the registry, while it has pipeline work waiting: a review armed, or any state but `working`, `merged` and `done` (source: `poller`, level: `warn`; deduped per worker via `worktree-missing:<project>:<worker>`). `validate.ts` clears the path once the directory is gone, and every lifecycle handler, the attach-time resume, and bounce used to fall back to the project checkout: the operator's own working directory, where the merge queue runs `git checkout -- .`, rebases, and force-pushes. The poller now skips such a worker and attach and bounce leave it unresumed; the alert names the stop-and-resurrect recovery.
- Worker git cleanup deferred past `CLEANUP_DEFER_ALERT_AFTER_MS` (30 min) because a pane is still running in the worktree or the dashboard session could not be enumerated (source: `cleanup`, level: `warn`; deduped per project/worker, raised once per request). The alert names the pane and window, notes that the standing request hides the worktree from the orphan sweep and blocks resurrection, and gives the manual remedy.
- Worker git cleanup exhausted its retry budget (source: `cleanup`, level: `warn`; deduped per project/worker). The alert names the canonical worktree/branch, the last git error, and the manual worktree-remove/prune remedy. The request marker is retired first so the hourly orphan sweep can independently surface any worktree that remains.

"Needs operator input" events do **not** fire alerts. Mid-turn AskUserQuestion, ExitPlanMode, and auto-mode permission prompts set `agentStatus` to `asking`; a completed turn that runs `garden blocked` derives the same display state from `blockedQuestion`. In both cases the bold-yellow worker row and plot-strip flag are the visual signal.

**Visibility:**
- Bottom bar shows a red `⚠ N alerts — ⌥a to clear` badge on the right when unread alerts exist. The badge appears instantly on `addAlert()` via `tmux set-option @garden_right` + `refresh-client -S`.
- Every alert is also streamed to `dashboard.log` at its declared level (`info`, `warn`, or `error`), so it appears live in the `garden logs --follow` pane (the `_garden-logs` window) with the `[!]` prefix.
- Pressing `⌥a` focuses the alerts view **and** acknowledges all current alerts, clearing the badge (the bar badge and every project header's `⚠n`). Acknowledgement is explicit — an alert that fires while the alerts pane is already focused still lights the badge, so autonomous failures aren't silently missed when the user is away.
- The alerts view is a passive SIGUSR1 repaint pane (`_garden-alerts`), the same pre-baked-file shape as the history and usage panes: `writeAlertsRendered` (`header.ts`) bakes `alerts.rendered` from `renderAlertsPane` (`commands/alerts.ts`), which shares the store, split, and glyph vocabulary with the `garden alerts` CLI but lays each alert out for the narrow pane — a `glyph age location` header line with the message wrapped beneath. Alert messages are not authored for display — they splice in raw git stderr (multi-line) and raw agent markdown (the reviewer alert embeds 300 characters of a model's reply verbatim) — so both surfaces run the message through `condenseMessage` first: terminal control sequences removed, fenced blocks dropped, headings/emphasis markers stripped, and every embedded newline collapsed to a space. Without it those newlines escaped the gutter and rendered at column 0, visually running one alert into the next. Control sequences are removed (`stripControlSequences`, `tmux.ts`) because a message can carry text a worker controls: the intake budget alert names an epic by its title from the sandbox-writable `.beads` store, and the reviewer alert's reply was written while reading worker-authored code, so a CSI or OSC sequence in either would clear or restyle the pane, or reach the outer terminal when `garden alerts` runs outside tmux. Every new alert is also logged, so `garden logs` removes them from each message and data value it prints, in both modes. The pane then caps the message at three wrapped lines; the store, `garden logs --raw` (less control sequences), and JSON output retain the full message. Read alerts dim only their gutter, not the message — the message is what the operator opened the view to read, and the section header plus dim gutter already say "seen". Both surfaces run chronologically top-to-bottom (read section then unread, oldest first within each): the render prints from the top, so an overflowing list scrolls its oldest alerts into tmux scrollback and leaves the newest on screen — the operator reads down to the latest instead of scrolling up for it.
- Acking on entry would erase the unread/read split at exactly the moment the operator looks at it, so the split is driven by `state.alertsSeenMark` — the seen-time snapshotted *before* the ack — and holds for as long as the view is open. Pressing `⌥a` again re-snapshots (now the entry ack), folding those alerts into read: the second press means "I'm done with these", which is why an already-focused view still does this work instead of early-returning. Leaving the view clears the mark, so the next visit shows them read.
- The bake is deliberately NOT wired into `refreshDashboard`, unlike its `writeHistoryRendered` sibling: `refreshDashboard` is in `dist/hook.js`'s import closure, so calling it there pulls `renderAlertsPane` (and `commands/logs.ts`, for `wrapDetail`) into the lean hook bundle on every hook fire's cold start — measured at +2.8KB, versus +260 bytes when esbuild can tree-shake it out. Its CLI-bundle callers are `focusAlerts` (entry), `refreshStatusElapsed` (the watchdog's 60s tick, which advances row ages), and `rebakePanesOnResize` (which re-wraps the view to the resized pane width).
- A newly written alert re-bakes the view immediately, so one raised while the operator is watching appears at once instead of on the watchdog's next tick (the pane was otherwise baked only on entry: a worker failing under an open alerts view showed nothing until `⌥a` was pressed again). `addAlert`'s side-effect block calls `refreshAlertsPane` (`alerts.ts`), which spawns `garden dashboard _refresh-alerts` — out of process for the same two reasons the bake is not in `refreshDashboard`: `header.ts` imports `alerts.ts`, so importing back is a cycle, and `addAlert` is itself reachable from the hook bundle. It is gated on `gardenPaneType === "alerts"`, so an alert raised while any other garden view is up spawns nothing, and fires only for a newly written alert — a deduped one changes no rendered byte. The child re-checks the same condition before writing, since the operator may have switched views since the spawn.
- `garden alerts` lists full history split into unread (added since the last `⌥a` acknowledgement — `lastSeenAt`) and read, with per-level glyphs (`✖` error / `⚠` warn / `•` info) and relative age; `garden alerts clear` wipes the store.

### Worker Isolation Model
- Every worker operates in its own git worktree — no shared working directory
- The project shell (`⌥s`) stays on the main checkout for manual work
- Branch name equals the worker name (e.g., `swift-oak`)
- Worktrees persist until the worker is killed, enabling the review cycle and manual inspection
- Every agent-CLI-specific decision (the launch command dialect, the Claude settings runtime config below, headless invocation, transcript reading, prompt delivery, transient-error shapes, session identity) lives on the harness adapter registry in `src/dashboard/harness/` — `claude-code` is the default adapter; a second adapter (`codex`) is reachable as a **reviewer/resolver/ci-fix** via per-role resolution (`garden config <p> role reviewer harness codex`; see `resolveReviewRole` in `src/dashboard/roles.ts`) and as a **worker** via `garden workers new <p> --harness codex` (default and designer workflows). Session-id capture, history/continue routing, status-pane activity summaries, and plan-mode asking status for a Codex worker are wired — the hook captures Codex's self-assigned session id onto `WorkerEntry.sessionId` (feeding `codex resume <id>`), while the `⌥h` history view and status detail read the transcript through the entry's adapter (`readTurns`/`resolveTranscriptPath`/`readActivity`). The capture fills only an empty `sessionId`, since a claude-code worker's id is minted by garden at creation; a pane that switches conversations in place has its new id adopted at that session's `SessionStart` instead (below). The hook captures the transcript path onto `WorkerEntry.transcriptPath` only when the path names the worker's own session (`transcriptNamesSession`; both harnesses put the session id in the transcript filename): Codex fires the relay for the subagent threads it spawns, and a subagent's rollout path would otherwise point `⌥h`, `readActivity` and the rollout listener's asking/turn-end reconciliation at a side thread. Codex 0.147 emits no tool hook for its built-in `request_user_input`, so the watchdog watches rollout writes and maps the pending call/result pair onto the shared `asking`/`working` transitions. The same listener treats a final `task_complete` with no later `response_item` as the authoritative backstop for a missed final `Stop`, and a final `turn_aborted` (an Esc interrupt, which writes no `task_complete` and fires no `Stop`) the same way, healing a stale `working` worker to `idle` and waking its poller; live-verifying `codex resume` remains (Phase 4). `WorkerEntry.harness` names a worker's adapter and the launch/resume/bounce/loop paths thread it. The adapter splits into a light core (`harness/core.ts`, importable from the hook bundle) and the full adapter (`harness/index.ts`, adds the heavyweight `installRuntimeConfig`; CLI bundle only) so `dist/hook.js` stays lean; `package.json` sets `"sideEffects": false` to keep that split effective, which means modules must stay free of import-time side effects (only entry points execute at top level). See `docs/MULTI-MODEL.md` "Layer 3".
- Launch identity is resolved once before any command is rendered. `resolveWorkerLaunchPlan` (`src/dashboard/launch-plan.ts`) binds role, harness, backend, credential reference (never the secret value), model/effort, execution policy, runtime project view, and required capabilities into one `WorkerLaunchPlan`; `resolveHeadlessLaunchPlan` produces the trusted review-family sibling. Unknown harness/provider names and unsupported workflow/provider/resume/headless-role tuples fail closed. Spawn, attach, bounce, loop respawn, and every headless poller pass the same validated plan to the adapter and the provider-token tmux chokepoint, preventing command, sandbox, and credential paths from independently choosing different identities. Adding a provider remains configuration; adding a harness means registering its core/full adapters and declaring `workerWorkflows`, `providerProfiles`, `resume`, `sandbox`, and `headlessRoles` deliberately.
- Codex runtime refresh is repeatable across a worker's lifetime. Attach, bounce, and loop respawn rebuild the current workflow-specific rules and pass them through `installRuntimeConfig`, which composes them over the worktree's `AGENTS.md` as it stands and writes one fresh `AGENTS.override.md`, so both Garden rules and repository rules advance. Directory-trust insertion into shared `CODEX_HOME/config.toml` holds a cross-process file lock around its read/check/append, preventing concurrent worker bootstraps from writing duplicate TOML tables.
- Garden's Claude settings file configures Claude's OS-level sandbox (Seatbelt on macOS, bubblewrap on Linux) — auto-allow mode approves sandboxed bash without prompts while blocking out-of-allowlist filesystem writes and network calls at the kernel. Workers and reviewers run without `--dangerously-skip-permissions` but remain autonomous inside the sandbox. Allowlist defaults (Anthropic, GitHub, npm, the project's git remote host, plus worktree + standard subprocess caches) are built in `src/dashboard/sandbox.ts` and extended per-project via the `sandboxDomains` (network) and `sandboxWriteRoots` (filesystem) config keys. The file lives outside the worktree, under `~/.garden/control/claude-settings/` (one per directory Claude runs in, `claudeSettingsPath`), and is passed to interactive Claude launches with `--settings`. Headless launches build fresh settings from current project config into a protected `<promptFile>.settings.json` sidecar under `control/headless` before every launch, including retries. This leaves a live worker's provider-specific settings untouched while applying sandbox repairs immediately. The sidecar is swept with the corresponding prompt/result after the headless window exits. It was the worktree's `.claude/settings.json` until a repo that commits its own settings file showed the cost: garden overwrote it, `git status` reported it modified, and the clean-tree review gate held every review back, while the repo's own permissions and hooks silently stopped applying in workers. Claude Code merges `--settings` over project settings (verified 2.1.286): both sets of hooks fire, a repo's `sandbox.enabled: false` cannot disable garden's sandbox, but a repo's `allowWrite`/`allowedDomains` entries do widen it — accepted, since the repo's committed hooks already run outside the sandbox. Outside the worktree it is also outside every worker sandbox, so a worker cannot edit its own sandbox. Three constraints follow from Claude Code's behavior: a missing file stops Claude from starting, so every launch path installs immediately before launching and validation sweeps interactive settings only once their worker and project are gone and an hour has passed; only the last `--settings` flag applies, so the ultracode keyword trigger is written into this file rather than passed as a second flag; and a launch with `--settings` in a worktree still holding an older build's garden-written `.claude/settings.json` would fire every hook twice, so `installRuntimeConfig({ beforeLaunch: true })` retires that copy (recognized by garden's own SessionStart hook command: deleted when untracked, restored from git when it overwrote a tracked file) — only before a launch, because a live worker from the older build still reads it. The first two were verified against 2.1.286, like the merge. Because Claude Code merges the two files, the repo's `env` also keeps applying in workers, beside its permissions and hooks.
- Garden's own git runs unsandboxed, usually inside a worker's worktree, so it never runs what the worker can write there. Every git command garden issues goes through `runGit` (`src/dashboard/git-exec.ts`) with hooks and fsmonitor off, and with `--no-optional-locks`, since a plain `git status` takes `index.lock` to write back the stat data it refreshed and garden reads worktrees while their worker, reviewer or resolver commits there. Hooks and fsmonitor are off because the bootstrap scopes `core.hooksPath` to the worktree's own `.garden-hooks`, a git-excluded directory inside the worker's write grant, so the poller's push, fetch, rebase or checkout would otherwise run a hook the worker planted. Garden's operations on the operator's own checkout (fast-forward, base push, `worktree add`, branch cleanup) keep that checkout's hooks through `operatorGit`, because those hooks are the operator's (board keeps its beads database in sync from post-merge). Content diffs also pass `--no-ext-diff --no-textconv`, and the two fetches that precede a review launch and a merge are bounded by the runner's 60 s timeout instead of holding a project's single-threaded poller for as long as a dead connection takes to fail. The worker sandbox denies writes to every worktree's `config.worktree`, `commondir` and `gitdir` (Claude Code protects only the session's own), and the review prompt's documentation, test and spec inputs are read as committed regular-file blobs (`readCommittedFiles`) rather than from the worktree, so a planted symlink or FIFO is never followed. What garden hands git is constrained the same way (`git-refs.ts`): origin's branch is named in full (`refs/remotes/origin/<base>`, `refs/heads/<base>` in refspecs), because the abbreviated `origin/<base>` resolves through git's lookup order and a same-named tag or branch a worker created would stand in for it; revisions are commit SHAs, `HEAD` or full refs, with `--end-of-options` before them, so a registry value can never reach git as an option; branch names are read back from full refs (`symbolic-ref`, `%(refname)`), since git's short forms disambiguate and a same-named tag turns `main` into `heads/main`; and path lists are read from `-z` output, which git does not quote. `--end-of-options` is why garden needs Git 2.30, the first `rev-parse` that takes it; `reset` is the exception, spelled `reset <mode> <ref> --`, because it rejects the flag before Git 2.44. See `docs/SANDBOX-THREAT-MODEL.md`.
- Every worker launch and resume passes `--permission-mode auto`, so the worker starts in Anthropic's built-in auto mode. It has to be the flag: Claude Code ignores `auto` as a `defaultMode` in project `.claude/settings.json` (a checked-in repo must not be able to grant itself auto mode) and falls back to the plan's built-in default — auto on Pro/Max/Team, but manual on Enterprise, which left workers on an Enterprise `claudeProfile` starting in manual mode. The ignored project value also suppresses a user-level `defaultMode`, so garden writes none. The classifier auto-approves low-risk tool calls and only prompts the operator for the rest. `permissions.allow` also pre-approves `Bash(tmux:*)` plus read-only tail utilities (`echo`, `head`, `tail`, `cat`, `grep`, `wc`) since workers routinely query pane/window state and pipe or chain the output — Claude Code checks each subcommand of a compound bash call against the allow list independently, so without the tails a command like `tmux list-keys -T root | head -40` still escalates. Garden wires a `PermissionRequest` hook (no matcher — all tools) that fires **only** when a prompt is actually being shown; it flips `agentStatus` to `asking`, which renders the worker row bold-yellow in the status pane. A catch-all `PostToolUse` hook (no matcher — all tools) flips `asking` back to `working` when the approved tool completes, regardless of which tool the classifier escalated. Because Claude Code emits no event at approval itself, a long approved command (a test suite) would otherwise read `asking` until it finished: the `PermissionRequest` hook therefore spawns a detached watcher (`garden dashboard _await-permission`, `permission-prompt.ts`) that reads the pane once a second for up to 10 minutes and flips `asking` → `working` (or, for a subagent's dialog, to the status recorded with it) as soon as the caret is back in the composer (the dialog hides it), and the watchdog tick re-checks any claude-code worker still `asking` past 10 s. This is the one sanctioned pane read that drives a transition (STATUS.md "Answered permission dialogs"). Tool events carrying `agent_id` come from a subagent and never move `agentStatus`: their activity says nothing about whether the worker's main conversation is still blocked or has ended. The exception is the subagent's own dialog. Claude Code puts `agent_id` on every hook a subagent fires, `PermissionRequest` included, and that request raises `asking` even while the main thread is idle and firing nothing; no hook reports a denied or expired request (Claude Code 2.1.310's `PermissionDenied` fires only for auto-mode classifier denials). (`Notification` never carries `agent_id`.) The raise therefore records the agent, the episode's `lastStateChangeAt` stamp and the prior `idle` or `working` in `entry.subagentAsk`, and the same agent's next tool event restores that status, as does the watcher above. The record is read only while that `asking` episode stands, so it needs no clearing, and a request from a second thread within the episode disowns it, since one agent's activity cannot show that both dialogs closed. Hooks reach a worker by cwd alone, so another session in the worktree is kept out the same way when it has no transcript of its own: a `session_id` other than `entry.sessionId` whose `transcript_path` does not name it (Codex runs a `/side` conversation as its own thread in the worker's process and writes no rollout for it). Its tool events count as background activity, and its start, prompt, Stop and blocked events write nothing. The check is `isForeignSession` (`hooks/default.ts`). Before it, on burnt-mild-reed (2026-09-22), a `/side` thread's start, prompt and Stop moved the worker to `ready`, `working` and `idle` while the worker's own thread was mid-turn. A session that names its own transcript is not ignored, because it can be the pane's own conversation after an in-place switch whose `SessionStart` never arrived, and dropping its events would freeze the row. Its `SessionStart`, unless a compaction, is that switch (`/clear`, `/resume`, Claude Code's `/branch`), so its id is adopted, and the transcript-ownership guard then follows the new transcript. (Claude Code reports a `/branch` switch as a `SessionStart` with a `fork` source.) They still stamp `reviewInterruptedAt` when the completed tool mutates a worktree under review, and they stamp `subagentActivityAt` — the input to the delegating display: an `idle` worker whose subagent activity postdates its turn end renders as `working` with a dim `bg` tag in the state cell (`isDelegating`, `registry.ts`; STATUS.md "Delegated background work"), so a worker parked waiting on its background Workflow/Task agents doesn't read as finished. Display derivation only — review entry and the merge gate still see `idle`.
- The same settings file sets `tui: "fullscreen"`, Claude Code's alternate-screen renderer. The classic main-screen renderer answers a pane resize by erasing and repainting only the rows on screen (verified in 2.1.294: a viewport-height run of erase-line + cursor-down, no scrollback clear), so the rows above stay in tmux history at the old width, tmux re-wraps them, and the repaint lands below them. Each terminal resize therefore left fragments and partial duplicate copies of the reply in a worker's scrollback. Fullscreen redraws the whole screen and keeps history in its own scrollback, leaving tmux's empty, so the `WheelUpPane` binding (`hotkeys.ts`) sends the wheel to a pane on the alternate screen with mouse tracking on, and enters copy-mode for every other pane. Verified against fullscreen on 2.1.295 before shipping: draft detection, the permission-dialog caret check, bracketed paste-and-submit, and the pane title all read it unchanged. Every worker launch reads it, so new, bounced, and resumed workers start on fullscreen.
- The same settings file also declares a `statusLine`, so every worker pane persistently shows what it is running on: model, reasoning effort, and remaining context (`Opus 5 · xhigh · 62% of 200k context left`). Claude Code surfaces none of these on its own past the moment they are set, which leaves an operator scanning a fleet of panes unable to tell a worker's model apart from its neighbour's or see one approaching compaction. The command points at `statusline.mjs` beside the settings in `control/claude-settings/`, a small script `installRuntimeConfig` writes (0o555, rewritten on every refresh/bounce) that reads the session JSON Claude Code pipes it on stdin — `model.display_name`, `effort.level`, `context_window.*`. It used to sit in the worktree's `.claude/`, which the worker can rewrite, while Claude Code runs it outside the sandbox. A file rather than an inline `node -e`, because the command already sits inside a JSON string that a shell then parses. The Codex analog is a launch-time `-c tui.status_line=[…]` override (`codex-core.ts`): Codex renders a status line natively but ships only model-with-reasoning and the working directory, and the key replaces the list wholesale, so garden restates those two and adds `context-remaining` — `gpt-6-astra high · Context 100% left · /repo`. Worker launches only; a headless reviewer has no TUI.
- The `hooks` block of the same settings file is derived from one table, `CLAUDE_HOOK_EVENTS` (`harness/claude-code-hooks.ts`), which names every hook event Claude Code fires (the 33 of 2.1.310) with garden's disposition for each: the wire routes a registered event's commands end in, or the reason the event is left unregistered. `buildSettingsJson` writes the registered rows and nothing else. Eight events are registered: `SessionStart`, `UserPromptSubmit`, `Stop` and `StopFailure`, `PreToolUse` (the `AskUserQuestion` and `ExitPlanMode` dialogs, and the `Bash` review fingerprint), `PermissionRequest`, and `PostToolUse` with `PostToolUseFailure`. `test/claude-code-hooks.test.ts` keeps its own copy of Claude Code's catalog and fails when the table and the catalog name different events, when a row has neither a route the dispatcher maps nor a reason, or when the hooks the settings file registers differ from the table's rows. Bringing that catalog up to a new Claude Code release therefore forces a decision for each event the release adds; before the table, an event nobody had weighed was simply absent (`StopFailure`, until a turn that died on a usage limit left its worker `working` for 39 hours). Among the unregistered rows, `WorktreeCreate`/`WorktreeRemove` would replace how Claude Code creates and removes its own worktrees, `MessageDisplay` fires every few displayed lines, and `Elicitation`, an MCP server asking the operator for input, is not handled yet: no hook raises `asking` for it, so the row reads `working` while such a dialog waits. The table is CLI-only: the dispatcher in `dist/hook.js` keys on the route a command ends in and never reads it, and `hook-bundle.real.test.ts` fails if it reaches that bundle.

### Telemetry ledger

An append-only JSONL event ledger (`src/dashboard/telemetry.ts`) records worker lifecycle facts for cross-model / provider / harness / workflow / prompt-version analysis. It is the durable history garden otherwise lacks: `removeWorker` hard-deletes the registry entry and `dashboard.log` tail-trims at 10MB, so nothing else survives a worker's cleanup. One line per fact (never an aggregate), sharded monthly at `~/.garden/telemetry/events-YYYY-MM.jsonl` and **never truncated** — aggregation happens at read time, which keeps future questions answerable against past data.

- **Design constraints.** Best-effort throughout (every write is wrapped and swallows — a telemetry failure must never break the poller or a launch, exactly like `log.ts`) but no longer silent: the first failing write in a process logs one `telemetry` warn naming the error, then stays quiet (a process that cannot write the ledger cannot write its next event either, and garden execs a fresh CLI per poll, so per-process is the natural granularity). Silence here was a real cost — `garden` run inside an agent sandbox is denied `~/.garden/telemetry` while `~/.garden/sessions` stays writable, so a worker's whole lifecycle record could go missing while its `dashboard.log` lines landed normally, leaving `garden stats` under-counting with no evidence anywhere. The module is kept THIN (`fs`/`path`/`crypto`/`config`, plus `log.ts` — itself `fs`/`path`/`config`/`atomic-write` and already in the hook bundle) and its directory is resolved lazily inside the write, so it is safe to pull into any import graph — including the `dist/hook.js` closure that `registry.ts` reaches — without an import-time dependency. Callers construct the already-primitive payloads (harness/model/crew/`rulesHash` are resolved caller-side in CLI-only modules); the module only stamps `v`+`ts` and serializes. Every line carries a schema version `v` for read-time migration.
- **Join key.** Worker names are randomly generated slugs that collide over months, so the durable identity is `workerId = project/name/createdAt`. Every event carries it; the lean lifecycle events join back to `worker.created` on it.
- **Lifecycle events (Phase 1).**
  - `worker.created` — emitted from `newWorker` (`workers.ts`) with the full configuration snapshot frozen onto the event (config is mutable, so "what was configured when this ran" cannot be reconstructed later): `workflow`, `harness`, `provider`, `model`, `ultracode`, `crew` (the per-worker `entry.crew` when set, else the project's explicit binding; null for an unbound project, since builtin seat ladders do not apply implicitly), per-role `{harness, model}` for reviewer/resolver/ci-fix (`resolveReviewRole`, resolved with `entry.crew` so a per-worker crew's review harness is recorded, not the project's), `baseBranch`, `rulesHash` (a short hash of the composed global+project rules — the prompt-version axis), and `gardenVersion` (the build axis).
  - `state` — emitted from `transitionState` (`poller-state.ts`) on every genuine prState move (`from`/`to`/`workflow`). The lifecycle backbone: time-in-state (review/resolve/cycle durations) falls out of consecutive events' timestamps at read time.
  - `merge` — emitted from `transitionToTerminal` (`poller-merge.ts`) with the counts the pure `state` event can't carry: `terminalState` (`done`/`merged`), the cumulative `mergeCount` ordinal, and this cycle's `changedFiles`. The terminal move thus appears as both a `state` line (machine trace) and a `merge` line (enrichment), distinguished by event type.
  - `worker.removed` — the tombstone, written first by the shared removal tail (`finalizeWorkerRemoval`, `workers.ts` — the `⌥x` kill and `garden workers stop` both funnel through it), before `removeWorker` erases the entry. Unlike every other event it is not best-effort: when the append does not land (any agent sandbox is denied `~/.garden/telemetry`), the tail keeps the worker (entry, worktree, branch, bead claim) and raises a warn alert, since nothing could rebuild it afterwards. Carries the ENTIRE final `WorkerEntry` verbatim under `entry`: a kill deletes the worktree, branch, and registry entry, but the agent transcript survives on disk, so this snapshot is the one missing piece `garden resurrect` needs to rebuild the worker (see "Resurrection" below). Full fidelity over a field selection — kills are rare and the ledger is never truncated. Spawn-failure rollbacks also call `removeWorker` but deliberately do not tombstone (no session worth resurrecting).
  - `worker.resurrected` — emitted by `garden resurrect` after a rebuild, under the same `workerId` (the rebuild preserves `createdAt`). Keeps the ledger coherent — later events for a resurrected worker would otherwise trail a `worker.removed` with no explanation — and marks the tombstone consumed, so the resurrect list drops it until a re-kill writes a fresh one.
- **Review-cycle quality events (Phase 2).** The review family emits its outcome with magnitude and effort — the signal the `state` stream can't carry.
  - `review.verdict` — emitted from `handleReviewing` (`poller-review.ts`) at the single point a parseable verdict is known (every reviewing workflow, every clean/fixed/failed outcome): the verdict, the review `durationMs` (from `reviewStartedAt`), and the reviewer's **fix magnitude** — `getReviewFixNumstat` (`git.ts`), zero on CLEAN and the edit size on FIXED. Without a rebase it is the numstat of `preReviewSha..tipSha`. After the reviewer rebased onto an advanced base that range also holds every commit the base gained, which recorded a sibling merge as the fix of a CLEAN review, so it sums only the commits the reviewer added: the rebased copies of the worker's commits drop out by patch id and the base's own commits are excluded. A reviewer that squashes or conflict-resolves a worker commit has that commit counted as its own. The headline quality metric: a worker a reviewer must rewrite N lines per merge to land is not the cheap worker it appears.
  - `resolve.outcome` / `cifix.outcome` — emitted from `poller-resolve.ts` / `poller-ci-fix.ts` at the point the outcome is known: the agent's advisory `verdict`, the ground-truth `verificationPassed` (only a verified push counts), the `attempts` against the per-cycle budget, and `durationMs`. Success/failure is already inferable from the following `state` transition; these add the effort + duration it can't encode.
- **Autonomy events (Phase 3).** How much the operator has to hand-hold a config — the dimension no review score captures.
  - `continue.dispatched` — emitted from `continueWorker` (`continue.ts`) at the ordinary paste-success point for interrupt/post-merge/handoff-callback delivery, and from `seedWorker` only after `UserPromptSubmit` confirms a seed became a real user turn. Its `kind` field names the path: `interrupt`, `post-merge`, `handoff-callback` or `seed`. A corrective resend after detected truncation is another garden-authored user turn, so its verifier emits a second event only after the transcript confirms that resend landed (intact or truncated); a swallowed corrective paste emits nothing. A swallowed seed retry likewise emits nothing; several paste attempts that eventually produce one turn emit one event. Operator-typed prompts are deliberately NOT recorded, so operator-initiated work = all prompts − these: marking every real garden-authored turn here is what makes that subtraction possible.
  - `operator.action` — emitted from `holdWorker` / `bounceWorker` (`workers.ts`, shared by the CLI and the `⌥e`/`⌥b` hotkeys) and the `kick` command (`commands/kick.ts`), with the `action` name. The direct "this config needed manual intervention" signal.
- **Cost events (Phase 4).** The worker's token spend — the axis a model/provider cost comparison turns on (the review family is always strong Opus, so its cost isn't the variable under study).
  - `worker.tokens` — emitted from `transitionToTerminal` (`poller-merge.ts`) at each merge: the worker's CUMULATIVE token usage (`input`/`output`/`cacheRead`/`cacheCreation`) summed over its Claude transcript by `sumTranscriptUsage` (`conversation.ts`), plus the turn count, the transcript's ground-truth `model`, and the `mergeCount`. Cumulative because a default worker's phases share one growing session, so per-cycle cost is a read-time diff of consecutive samples for the same workerId. The sum **dedupes by `message.id`** — Claude Code re-emits each assistant message on every streaming update carrying the message's cumulative usage, so a naive per-line sum overcounts ~2.7x (measured). Best-effort: absent when the transcript can't be read, so it never blocks the merge event.
  - Deliberately deferred (documented, not built): reviewer/resolver/ci-fix token cost (their headless throwaway-session transcripts are a separate discovery problem), Codex stderr token-trailer parsing (its numeric format isn't modeled — building a parser blind would be guessing), and a usage-meter utilization time-series (`snapshotMeters` gives only fleet-level percentages, not per-config tokens).
- **Read surface (Phase 5): `garden stats`** (`src/commands/stats.ts`) aggregates the ledger into a per-config comparison — quality (clean-review rate, reviewer fix magnitude, fail rate, review duration), cost (output tokens per merge), and autonomy (operator interventions per merge). `readTelemetryEvents` (`telemetry.ts`) is the sole read path (scans every shard, tolerant of torn lines). The unit of comparison is the config group; `--by` re-keys it (`config` default → `model`/`provider`/`harness`/`workflow`/`crew`/`rules`/`version`), `--since Nd|Nh|Nm` windows it, `-p` scopes to one project. The workerId→config join is built from the FULL `worker.created` history (never time-windowed) so a worker created before a `--since` window still resolves its config; only metric events are windowed. `worker.tokens` samples are cumulative, so a window is charged each worker's highest in-window sample minus its last sample before the window (the read-time diff above), and out-tokens-per-merge divides that by the window's merges. Events whose workerId has no `worker.created` (workers predating the ledger) bucket to `(unknown)` rather than vanishing, and age out as those workers are cleaned up. JSON when piped (complete data), a table in a TTY. Deferred cost refinements (reviewer token cost, Codex trailer, usage-meter time-series) remain as noted above; the four event families plus this read surface deliver the model/provider/workflow/config comparison the ledger was built for.


### Worker git cleanup

Removing a worker deletes its registry entry; a separate step deletes its worktree, its local branch, and its origin branch. That step is dispatched, not executed inline, because the removing process was not always allowed to do it: `garden` invoked from inside an agent's sandbox (a Codex worker's pane, whose writable roots are its own worktree plus `~/.garden/sessions`) could kill the tmux window and delete the registry entry — both land in permitted paths — and then be denied every git command against the project checkout. A removal now refuses in that position (`stopWorkerByName` when tmux does not answer, `finalizeWorkerRemoval` when the tombstone cannot be written); the dispatched request still turns any other failed cleanup into a retry.

`backgroundGitCleanup` (`workers.ts`, the tail of `finalizeWorkerRemoval`) therefore writes a **cleanup request** and dispatches a detached `garden dashboard _worker-cleanup <project> <worker>` (`src/dashboard/worker-cleanup.ts`). The request file is the same per-worker path (`workerCleanupMarkerPath`, `git.ts`) that `garden resurrect` and the watchdog's orphan sweep already read as "cleanup in flight" — it just carries the parameters and an attempt count now, so their semantics are unchanged. Detached because removing a worktree holding a full `node_modules` and deleting an origin branch are seconds-to-minutes of work that must not block the `⌥x` keypress.

The pane-creation rollback uses the same path after killing the worker window, because `respawn-pane` may already have started the detached bootstrap before a later swap fails. It requests cleanup for each target that did not exist when this spawn began; a same-name worktree or branch that predates the attempt may be the only surviving copy of an older worker's unmerged work and is never adopted or deleted by the failed spawn.

- **Every step is idempotent and reports.** Each git step is skipped when its target is already gone and, when it runs, returns git's own stderr rather than a boolean (`gitCleanupStep` / `gitCleanupOutput`, `git.ts`). A retry after a partial success finishes the remainder instead of re-reporting the done half. Two git refusals mean `worktree remove` can never succeed, because git no longer tracks the directory as a working tree: its admin entry is gone ("is not a working tree"), or the tree's own `.git` file is gone while the entry remains ("'<path>/.git' does not exist"); git deletes a tree in readdir order, not `.git` last, so a removal cut off part way leaves the second. For either, cleanup deletes the directory itself and prunes. Each is matched as git's complete diagnostic (the second under the resolved path git recorded at `worktree add`), so a lock reason quoting it cannot bypass a worktree lock.
- **Cleanup reaps before it removes.** Killing a worker's tmux window kills the pane's foreground process group, not anything the worker daemonized: a backgrounded `npm run dev` reparents to init and outlives the pane, the registry entry, and the worktree removal. Its cwd is still inside the deleted directory, so its next cache flush recreates the path git just deleted — leaving a husk no registry entry claims, which the watchdog reports as an orphaned worktree an hour later. `reapAndLog` (`worker-reap.ts`) therefore SIGTERMs (then SIGKILLs, after `TERM_GRACE_MS`) every process whose cwd is inside the worktree, before `git worktree remove` runs. The test is **cwd, not ancestry**: by the time anyone can look, the process to kill has already been reparented away from the dead pane, so a descendant walk misses exactly the case that matters. It runs whether or not the directory currently exists — on the watchdog's retry the husk *is* the resurrection and its author is still holding it — and it is idempotent, so the retry re-reaps for free. Reaped pids are logged at info: a worker leaving processes behind is operator signal that was previously invisible until the orphan alert. This is how `keychange-ai/mute-wry-dove` came back 57 seconds after a clean removal, as an empty `.next/cache/webpack` tree, while its dev server held port 3333 for a day (2026-08-25).
- **The reaper is aimed, never pointed.** Its target is always the canonical worktree path the executor re-derives from a validated `(project, worker)` pair — never a path read out of the worker-writable request body, which would hand the unsandboxed watchdog a machine-wide process killer. It also spares both the process chain captured when cleanup is requested and the executor's live `ancestorPids`: `garden workers stop` run from inside the doomed worktree hands that cwd to the detached cleanup child, and the requester may exit before that child reads the process table. Capturing before detachment closes the reparenting race that would otherwise make the reaper kill the operator's shell. The request body is worker-writable, but this field only excludes pids from the canonical cwd target set, so it cannot widen the kill authority. After the TERM grace, the reaper reads cwd again and SIGKILLs only pids still selected inside the worktree, closing the PID-reuse window; it deliberately does not check liveness after SIGKILL because a zombie still answers `kill(pid, 0)`. A sandboxed caller is denied `ps`/`lsof` and reaps nothing, degrading exactly like the git steps do — the watchdog retry is the one that reaps. The cwds the reaper selects on come from `lsof -d cwd` alone: lsof ORs its selection options unless given `-a`, so adding `-u <uid>` to narrow the listing widens it to every descriptor that user holds (measured at 26s and 24x the output, against 0.24s).
- **A link at the worktree path is unlinked, never followed.** Garden only ever creates a directory at a worker's canonical path, but that entry is inside the removed worker's own write grant, so a process that outlived the worker can put a symlink there once git has removed the tree, then forge a request for the worker's now-unregistered name. Followed, the link retargets both destructive steps: once the worker's admin entry is gone, `git worktree remove` resolves the path it is given and removes whatever worktree the link lands on, uncommitted work included, and a reap that resolved the whole path swept the link's target, every process the operator owns for a link to `/`. The executor therefore lstats the path before reaping and again after, since the reap's TERM grace is time enough to swap a link in, and anything there other than a directory is unlinked, which never touches a link's target, and pruned, with neither step run on it (`unlinkNonDirectory`). The reaper itself resolves only the path's parent, so a symlinked `HOME` or `~/.garden` still matches while a link at the worktree's own name does not. Both checks precede git's own resolution of the path, so a process that keeps swapping a link and a directory there can still race that window (`docs/SANDBOX-THREAT-MODEL.md`).
- **The request cannot choose git targets.** `~/.garden/sessions` is worker-writable IPC, so the watchdog treats the JSON body as untrusted. (Because that check needs the config, the sweep returns and retires no request while `config.yml` does not load: a failure that says nothing about any one request must not delete it and strand its worktree.) Before any git command, `cleanupRequestError` binds it back to a configured project, a generated worker identity with no live registry entry, that worker's canonical `~/.garden/worktrees/<project>/<worker>` path, and its same-name branch. The executor derives the actual targets again from config and the canonical layout; a forged body cannot turn the unsandboxed retry into an arbitrary `git branch -D` or worktree removal. Invalid requests are retired with a warn log, and so is a request whose validation throws, which would otherwise throw on every tick and end the sweep before the requests after it. Stale unreadable or pre-upgrade empty markers are also retired rather than suppressing orphan detection forever. The hidden command validates its arguments before composing the marker path, closing traversal through the lookup itself.
- **A live pane defers it.** Every removal kills the worker's panes before writing the request, so a dashboard pane whose cwd is still inside the worktree means the worker is not gone: the request and the registry entry were forged. (`garden workers stop` refuses before touching anything when tmux does not answer, since `stopWorkerByName` checks `dashboardReach`, `session.ts`, first; a sandboxed stop used to reach this point after deleting the entry without killing the pane.) `executeWorkerCleanup` then returns before reaping or running any git step, and leaves the request for the next retry without counting an attempt (`paneHoldingWorktree`). Pane existence comes from tmux, which a sandbox cannot reach and so cannot fake. Three refinements make that judgment sound:
  - **Both headless windows are killed first.** The removal tail kills the review window *and* the ci-fix window (`killCiFixWindow`), which is a separate window the ci-fix agent runs in with the worktree as its cwd. Killing only the review one left that agent working for a worker that no longer existed — its 2h timeout is enforced through the registry entry removal had just deleted, and it could still push to the branch — and its pane then deferred the cleanup that used to reap it, indefinitely.
  - **Garden's own infrastructure is not a worker.** The project pollers, the usage poller, the watchdog, and the `_garden-*` views are created without an explicit start directory, so they inherit the cwd of whichever client spawned them: a `garden` command run from inside a worktree parks one there for the life of the dashboard. None of them ever holds a worker, so `isInfrastructureWindow` excludes them from the judgment. The visible `main` window's left column (title, status, growhouse slot) is excluded the same way, by tmux geometry rather than the worker-writable state file's pane ids: it inherits the cwd `garden dashboard` was launched from, and a worker is only ever shown in the right slot.
  - **An unanswered listing is not an empty one.** tmux answering that no dashboard session exists means no dashboard pane can hold the worktree, so a cleanup after `dashboard exit` still runs. But a tmux that does not answer at all (`dashboardReach` reports `unreachable`), or a session that answers `has-session` and then fails to enumerate its panes, has said nothing either way, and that defers: absence is only evidence when tmux gave it. The first case is an agent sandbox, which is denied the tmux socket but may write the shared `.git`: a cleanup run there that read the silence as "no dashboard" could not delete the worktree directory, yet removed its admin entry and then its branch from under a worker still running in it (`garden/weak-tough-lynx`, 2026-09-17). tmux also reports a pane's cwd as the kernel resolved it, so both the lexical worktree path and its `realpath` are matched — under a symlinked `HOME` or `~/.garden` the lexical one never matches and the check would silently never fire.

  A shell the operator left in the worktree defers the cleanup the same way, until it leaves, with one info line per retry naming the pane.
- **A deferral is bounded by a warning, not by destruction.** A deferral never counts an attempt, so it can never age into the give-up path below — that path deletes the worktree, and a live worker may still be using it. Instead the request records when it first deferred, and after `CLEANUP_DEFER_ALERT_AFTER_MS` (30 min) one warn alert names the pane and window holding the tree, the manual remedy, and the two things the standing request is meanwhile suppressing: the worktree is hidden from the orphaned-worktree sweep and cannot be resurrected. Said once per request, not on every 2-minute retry.
- **Failure keeps the request.** A failed run rewrites the request with `attempts + 1` and the error text, and logs a `cleanup` warn. This is the whole point: the predecessor composed the git commands inline as `sh -c` with every step ending in `2>/dev/null || true`, so a denied cleanup produced a leaked worktree, no error, no log line, and no retry — the only surviving signal was the orphan sweep an hour later, which can say "nothing owns this" but not "cleanup was attempted and denied". That is how `leadingtone-io/numb-clear-vow` leaked 351MB on 2026-08-22.
- **The watchdog is the retry.** `sweepWorkerCleanups` (`watchdog.ts`) runs on the regular 60s tick and re-dispatches any request older than `CLEANUP_RETRY_AFTER_MS` (2 min). The watchdog is the fleet's one always-unsandboxed recurring process, so its re-dispatch is the one that succeeds; a run where tmux does not answer defers without spending an attempt, and a failed run costs one attempt rather than a leaked worktree. It dispatches rather than running the git inline for the same reason the removal tail does — an overrunning watchdog iteration is read by `absorbSleep` as machine-suspend time and would shift live review timers. Selecting a due request advances its mtime before dispatch, and execution holds a per-request file lock, so the 60s tick cannot fan out duplicate cleanup children; the sweep skips that lock, its reclaim salvage, and `atomicWriteFile` temps, which share the request's name as a prefix. A failed attempt rewrites the request, so its mtime re-arms the window and the retry cadence is self-throttling. A project with no `origin` simply skips remote deletion; when an origin is configured, failure to inspect it is retryable rather than misreported as "branch absent."
- **Giving up is explicit.** After `CLEANUP_MAX_ATTEMPTS` (3) the request is deleted and a warn alert names the worktree, the branch, git's last error, and the manual `git worktree remove --force` + `prune` (with `rm -rf` in place of the remove for the two refusals above). Deleting the request is deliberate: leaving it would be worse than useless, since both resurrect and the orphan sweep read its presence as "cleanup in flight" and would stay quiet about the leak forever. Retiring it hands the standing condition to the orphan sweep, which reports size and age.

Identity is read from the request body, never parsed out of the filename — project and worker names both contain hyphens, so `worker-cleanup-<project>-<worker>` cannot be split apart.

### Resurrection

`garden resurrect` (`src/commands/resurrect.ts` + `src/dashboard/resurrect.ts`) rebuilds an accidentally killed worker from its `worker.removed` tombstone. The premise: a kill destroys the worktree, branch, and registry entry, but the agent transcript — the conversation the operator actually misses — survives on disk untouched, and the tombstone preserves everything else. Resurrection is bounded by the agent CLI's own transcript retention; a tombstone whose transcript has been reaped lists as not resurrectable.

- **List and search.** Bare `garden resurrect` lists tombstones newest-kill-first (`listTombstones`: latest `worker.removed` per workerId, superseded by `worker.resurrected`, minus workers currently alive in the registry — a hand-rebuilt worker has no resurrected marker, so the registry check is load-bearing, not belt-and-suspenders). `--search <expr>` matches name/task/branch AND raw transcript content, so "the worker that did the schema migration" is findable without remembering its slug; `-p` scopes to a project. JSON when piped.
- **Rebuild** (`resurrectWorker`). The worktree is recreated at its ORIGINAL path — session resume is cwd-keyed, so any other path would orphan the transcript and dangle every file reference in the agent's context. A per-worker cleanup marker makes resurrection refuse while the detached kill cleanup is live, so a newly adopted tree cannot be deleted from underneath it. Start-point preference: (1) a local branch or worktree left by failed cleanup is adopted as-is — a surviving worktree even preserves uncommitted files; (2) the tombstone's `lastSeenSha`, when the commit object still exists and origin/<base> hasn't absorbed it — a deleted branch's commits survive in the object store until gc, so unmerged work a kill would have destroyed is restored; (3) `origin/<base>` (the normal case: everything merged before the kill). The rebuilt tree's dependency install runs as the operator, outside any sandbox, so it runs only for a tree started from the project's own configured base on origin: (1)'s local branch, (2), a local-only branch under the base's name (which any worker can create), and a base the tombstone merely names (`baseBranch` is copied from the worker-writable registry) are all content no review saw, and install nothing — neither npm nor poetry — with a note in the resurrect output saying so; an adopted worktree is not reinstalled at all. `--ignore-scripts` is not enough on its own: it covers lifecycle scripts, while the tree's own `.npmrc` names programs npm runs itself (`git`, measured running a script from the tree three times as the operator). The registry entry is rebuilt via an allowlist (`rebuildEntry`): identity, config (harness/provider/model/effort/crew/ultracode), history counters (`mergeCount`, `holisticReviewedThroughMergeCount` — without these the poller would re-run the holistic pass over already-reviewed scope), `lastReview`, and workflow sub-objects survive; every transient state-machine field (prState, review/resolve/ci-fix machinery, handoff linkage) is dropped, so the worker re-enters the lifecycle from idle quiescence.
- **Resume.** With the dashboard live, the session respawns through the same `respawnWorkerWindow` (`create.ts`) the attach-time resume loop uses — one code path bakes runner/hook commands, which is exactly what hand-rolled recovery got wrong — and the project poller is ensured. Without the dashboard, the rebuilt entry simply resumes on the next `garden dashboard`, which is that same loop.

## Worker Status Detection

Each worker has two independent status axes:

**Process status** — what Claude is doing, written by Claude Code hooks (except `paused`, written by the operator `hold` action — a raw Escape fires no hook):
- ⏳ **loading** — worker pane started, bootstrap script running, Claude not yet launched
- ◇ **ready** — Claude launched but not yet tasked
- ⠋ **working** — Claude is processing a submitted prompt (braille spinner animation)
- ⚑ **asking** — the worker needs operator input, either mid-turn or through a recorded blocked question; row is highlighted bold-yellow in the status pane
- ◆ **idle** — turn has ended, Claude is at the prompt waiting for the next message
- ‖ **paused** — operator deliberately halted the worker mid-turn via the hold action (`⌥e` / `garden hold`); held awaiting a redirect, cleared by the next prompt; row is highlighted bold-cyan in the status pane
- ○ **exited** — process has terminated

**Lifecycle status** — where the worker's code is in the review pipeline, written by the poller:
- ◎ **reviewing** — automated reviewer is checking the worker's commits
- ◷ **merge-pending** — review passed, in the merge queue
- ◔ **resolving** — automated resolver is fixing a merge-queue rebase conflict
- ✖ **failing** — review failed, waiting for worker to fix; row is highlighted bold-red in the status pane. When the operator has prompted the failed worker and it is mid-turn (`agentStatus` = working), the icon becomes the braille spinner while the state cell and red row are unchanged — "still broken, being worked on" versus "broken and parked" (`isFailingBusy` / `iconFor`, `src/commands/status.ts`)
- ✓ **merged** — transient post-merge beat; row is uncolored (not actionable; cleared by the next auto-continue prompt)
- ✓ **done** — worker self-declared finished via `.garden-done`; row is highlighted bold-green in the status pane (operator cleanup signal)

The display combines both axes: lifecycle state normally takes priority when present, otherwise the process state is shown. A recorded blocked question is the operator-input exception: it derives the `asking` display over every lifecycle state except `failing`, without changing either stored axis. A worker that is "reviewing" therefore shows the reviewing bullseye unless it has recorded a question, while a failing worker always stays red. The animated braille spinner belongs to the "working" display state and to one crossover: a `failing` worker whose agent is working (see above), which spins in red.

**Base-branch divergence indicator**: how a worker's row flags its base depends on whether the project has an explicit `baseBranch` configured.

*Configured projects* (`baseBranch` set): the project header carries a grey `⋅<base>` token (what workers merge into, at a glance), and each worker row is judged against that configured base independently — no project-wide toggle. A worker whose pinned base matches shows nothing; one that differs shows a grey `→ <base>` (a deliberate per-worker override, e.g. `workers new --base`); one whose base has vanished from origin shows a yellow `→ <base>` — the only genuine fault, since the merge will fail. The missing-from-origin check (`branchExistsOnOrigin`) is TTL-cached per project like the checkout-branch lookup, and only configured projects pay it (`formatConfiguredBaseHint` / `collectMissingBases` in `src/commands/status.ts`).

*Unset projects* (legacy checkout-follows default): a worker whose pinned `baseBranch` differs from the branch currently checked out in the project's main directory gets a grey `→ <baseBranch>`, and when *any* worker diverges the matching siblings show their base in grey too (`projectHasBranchDivergence` / `formatBranchHint`). This keeps a mixed project unambiguous but toggles every row on one worker's divergence — the jitter the explicit `baseBranch` key retires. The pin/checkout mismatch is informational, not a warning — merging into a non-checked-out base is a fully supported workflow (the post-merge step advances that base's ref on its own) — so it wears the quiet grey of the identity cluster rather than a yellow alert color; the yellow `→ <base>` is reserved for the one genuine fault (a base gone from origin, where the merge will fail), which only the configured-base path can detect. The project's current branch itself isn't repeated next to the project name — the bottom status bar (`formatLeft` in `header.ts`) already shows it for the active project. The post-merge alert is correspondingly narrow — `notifyPostMerge` stays silent when an off-base base ref advances cleanly or a redundant local commit auto-heals, and otherwise alerts only on entry into the state: `diverged` (real local-only commits, warn), `checked-out-elsewhere` (base live in another worktree, warn), `dirty` (uncommitted changes on the on-base checkout, warn), or `stuck` (fetch failure or a wedged checkout, error).

**Worker row ordering**: rows are ordered by attention and recency rather than by name (the name is just an address handle). `compareWorkerFreshness` (`src/dashboard/registry.ts`) sorts by attention tier first — (0) blocked on the operator (`failing`/`asking`), (1) new and awaiting its first prompt (`loading`/`ready`), (2) active/recent (`working`/`idle`/`paused`/`exited`), (3) in flight under the poller (`reviewing`/`resolving`/`ci-fixing`/`merge-pending`/`merged`), (4) `done` (sinks to the bottom as a cleanup candidate) — then within a tier by freshness descending, then by name as a stable tiebreak. The bands follow a worker's life top-to-bottom: needs-you at the top, then the work descends through active → in-flight → done as it heads toward merge. The in-flight prState is classified before the new (`loading`/`ready`) agentStatus, so a worker whose turn ended and was picked up for review lands in the in-flight band even if its agentStatus is a stale `ready`/`loading` (a STATUS.md invariant). The active band's tier number is the exported `ACTIVE_SORT_TIER`, shared with `isWorkerStale` so the stale-dim follows the active band if the bands are ever renumbered. Ordering freshness (`workerSortFreshness`) is the most recent of `lastStateChangeAt` — the worker's last *meaningful* transition (an `agentStatus` change, stamped by `applyAndLog`, or a `prState` change, stamped by `transitionState`; never the 10s heartbeat) — then `lastEventAt`, then `createdAt` (stamped at `addWorker` so a brand-new worker sorts fresh before its first hook; both timestamps are backfilled on read for pre-existing entries by `migrateCreatedAt` / `migrateLastStateChangeAt`). Keying on the state-change time, not the raw `lastEventAt`, is deliberate: the 10s hook heartbeat bumps `lastEventAt` for a working agent without repainting the status pane (the refresh is gated on a real state change), so ordering by `lastEventAt` let the registry order drift silently and then snap on the next unrelated repaint — e.g. the operator navigating to another worker. Tying ordering to the transition keeps every reorder coincident with the repaint that the same transition already triggers, so the list stays fixed while you navigate and only moves when a worker genuinely changes state. Freshness is compared at 60-second granularity so a burst of state changes among co-active workers doesn't reshuffle the list. The same comparator orders the ⌥]/⌥[ cycle (`cyclePane`) and the `whoami` sibling list, so navigation matches the visible order; the default focus target on project switch is deliberately left in tmux insertion order. An active-band worker untouched for over `WORKER_STALE_MS` (24 h — far coarser than the 15-min health staleness, since this only drives a dim) is rendered faint via `dimRow`, which re-arms the faint attribute after each inner ANSI reset so embedded colored segments (the base-divergence hint, for one) don't half-brighten the row. Staleness reads `workerFreshness` (`lastEventAt`, falling back to `createdAt`) rather than the ordering key, because it asks whether the worker is alive, which the heartbeat answers. Blocked, new, in-flight, and `done` rows are never dimmed; nor is the one colored active-band state, `paused` (an explicit operator hold rendered bold cyan — a dim would fight that color and hide a deliberate state), which `isWorkerStale` excludes so `dimRow` only ever wraps an uncolored row.

**Time-in-state suffix**: in-flight and blocked rows (`reviewing`/`merge-pending`/`resolving`/`ci-fixing`/`asking`/`failing`) carry a dim elapsed suffix showing how long the worker has sat in its current state — `reviewing 12m`, `merging 47m`, `asking 2h` — computed by `formatTimeInState` (`src/commands/status.ts`). A pipeline row (`reviewing`/`merge-pending`/`resolving`/`ci-fixing`/`failing`) counts from `prStateChangedAt`, which only `transitionState` stamps, and only when the state changes: `lastStateChangeAt` is also stamped by every `agentStatus` move, so an agent turn that leaves the lifecycle alone (the operator prompting a failing worker, a read-only answer mid-review) used to restart `failing 3h` at zero and hide a review's yellow "slow" flag. An entry whose last transition predates the field falls back to `lastStateChangeAt`, and an `asking` row counts from `lastStateChangeAt` (or `blockedAt` for a recorded question). `garden queue` ages its rows from the same stamp. It reads grey by default and turns yellow once elapsed passes a soft per-state expectation (10 min for `reviewing`/`merge-pending`/`resolving`, 15 min for `ci-fixing`), well under the hard `REVIEW_TIMEOUT_MS` (120 min) kill, so "slow" is visible long before "killed". Only the otherwise-uncolored pipeline states escalate to yellow; `asking`/`failing` rows are already whole-row colored, so their elapsed stays dim rather than fight the row color. The suffix is suppressed under a minute (no `0m`) and is folded into the state column — `reviewing 12m` is one cell, one fact — so how long a worker has been reviewing sits next to *what* it is doing, not adrift at the end of the row. Because it rides the same pre-baked-file + SIGUSR1 path as the rest of the status pane, the elapsed value would otherwise freeze between state transitions; the liveness watchdog's 60 s tick re-bakes it (`refreshStatusElapsed`, `header.ts`), the one recurring driver of the otherwise event-driven pane, content-deduped so a fully idle fleet (static icons) never repaints. The `working` spinner frame is baked FIXED (`iconFor`) and animated locally by the pane at 0.12 s, so a busy fleet's baked bytes stay stable too — the dedup (a byte-compare against the file on disk, so it holds even in the one-shot hook/hotkey processes) suppresses the write and SIGUSR1 on a tick where no row's suffix actually advanced. It compares against the file rather than against the process's own last write: the watchdog and the usage poller are long-lived, every other garden process rewrites the same files between their calls, and a skip taken because a render matched the process's own last write left the pane showing whatever another process baked meanwhile (an idle pane blocks until signalled).

A question-derived `asking` row is the timestamp exception: it uses `blockedAt`, because a lifecycle move after the question can bump `lastStateChangeAt` without answering it. If `failing` outranks that question, the row displays the failure and keeps using its lifecycle stamp (`prStateChangedAt`), so `failing 2m` never misreports how long the question has existed.

**Worker row grammar (identity vs. status)**: a worker row is `<focus> <icon> <name>  <state+elapsed>  <detail>  <badges>  <model>  <flags>`, built once by `collectSegments`/`renderWorkerRow` (`src/commands/status.ts`) for both the `garden status` CLI and the baked dashboard pane. Two info classes, two treatments. *Identity* facts — a worker's base (`→ <base>` when it overrides the project base), per-worker crew (the crew name, when `entry.crew` differs from the project default — it supersedes the member badge, since the crew name already encodes the build harness), member (its build harness, when it differs from the project default — `codex` on a Claude project), model (`sonnet`/`opus`, when what the worker runs is not what the project runs), and workflow — render as quiet **grey** badges, and only when they differ from the project default: **default is invisible, override is grey**. The whole identity cluster — base, crew, member, workflow, and the model — trails the detail column as ragged tags (no shared leading column), so nothing sits between the state and the description: the description is the row's primary content and reads first (operator call, 2026-07-16). Ragged-right means each badge costs width only on the row that carries it, rather than a width-aligned leading column that would push every plain row's description to the right — the same reason the model tag already trailed. The model tag names the model the harness reports running when it reports one (else the pin) and stops there — one model, grey, like every other identity badge (see "Model drift" below). The **state column** itself is sized to the widest state cell actually on screen (`computeStatusWidth`, across every project's workers, floored at `STATUS_MIN_WIDTH`), the same way the name column sizes to the longest name — so a fleet of short `done`/`idle` rows isn't padded out to the 13 columns only the longest transient state (`reviewing 12m`) needs, which was the dead space between the state and the description. When a worker enters an elapsed-bearing state the column widens on that bake and the detail column shifts right in step (and tightens again once it clears); it is recomputed each bake off the same `now` the elapsed suffix uses, so measured and rendered widths never drift. *Status* facts — the state word, the folded-in elapsed, the CI bracket, the `gate closed` flag, and the `dirty tree` / `tree unknown` review-blocked flag (`formatReviewBlockedFlag`, rendered only on an `idle` row: a `working` worker has an agent on the problem, and every other state's cell already says more) — own the color-escalation vocabulary (grey/yellow/red). The state cell also folds in a dim `bg` tag when a row's `working` is derived from live subagent activity or a background task the last turn left running (`run_in_background`, an async Agent — tracked by `background-tasks.ts`) rather than the worker's own turn (STATUS.md "Delegated background work") — it answers why the pane sits at a prompt while the row spins. Workflow decoration is a pure `workflowRowDecor` switch on `entry.workflow` (a grow loop's `grow N/M` counter fills the detail slot; a designer gets a grey `designer` badge in the identity cluster instead, so the live activity keeps the detail slot), deliberately kept off the `src/dashboard/workflows/` import graph so `status.ts` (and thus `dist/hook.js`) never pulls in the poller graph. Truncation follows the grammar: the core (through the state cell) and the flags never drop, the identity cells (the badge cluster and the trailing model) drop as a unit next, and the detail column truncates first and absorbs the width — a narrow pane shows *what* and *where it stands* before it shows prose. A truncated detail is marked with a trailing `…` (`truncateToVisibleWidth`'s `ellipsis` flag, which reserves the marker's column so the row still fits the cap): a summary is prose, and prose stopped mid-word with no marker reads as a broken render rather than a long line (operator call, 2026-07-27). The whole-line backstop applied after the rows are built is deliberately unmarked — it only trims what the grammar already fit, so a marker there would claim a truncation that did not happen. Each project header also carries a yellow `⚠n` unread-alert count (`unreadAlertCountsByProject`, `alerts.ts`) beside the diary pencil — the count clears globally on `⌥a` (there is one `lastSeenAt`), so it answers "did anything happen here while I was away?" without switching to the alerts view.

**Where the detail text comes from (per harness)**: the detail column renders `entry.task`, the worker's own "what am I doing" summary, refreshed by the hook path (`applyAndLog`) and both status render paths, which share one `refreshWorkerTasks` (`status.ts`): the dashboard's `refreshDashboard` and `garden status`, each reading every worker's pane title with a single `list-panes -s`. `garden status` then renders every project's rows from the registry that refresh returns, so a call reads the registry once rather than once more per project. The source is the harness's, not garden's — `resolveWorkerActivity` (`harness/core.ts`) asks the harness core for a `readActivity` and only reads the tmux pane title when it has none. Claude Code rewrites its terminal title as it works, so it defines no `readActivity` and the pane title IS the summary. Codex does not: its title is configurable (`[tui].terminal_title`) but every item is metadata or a counter — verified against codex 0.144.6, `activity` is a bare spinner glyph, `task-progress` renders `Tasks 3/5`, `thread-title` renders the thread UUID even once a title exists on disk, and the default `["activity", "project-name"]` resolves `project-name` to the cwd basename, which for a garden worktree is the worker's own name (the row read `weak-brave-snow  weak-brave-snow`). So a new Codex worker starts with `awaiting task` (or the first meaningful line of a seed Garden already owns), then the Codex core derives the summary from its rollout (`codex-core.ts` `readActivity`): the opening operator prompt's first line, reported only while the task is unset and then replaced once by a model-written topic (below). Both lines pass through `condense`, which removes terminal control sequences (`stripControlSequences`, `tmux.ts`, as `cleanPaneTitle` does for a claude-code pane title) before cutting the text to one 120-character line, because a handoff seed's first line is written by the sandboxed calling worker and the status row and `garden whoami` print `entry.task` as stored. Plan steps are deliberately not read: the row names what the thread is about, and reading the newest `update_plan` step overwrote that topic mid-thread and left the row on whichever step came last. The prompt reader accepts every shape Codex has carried a prompt in — the `event_msg` ones `codexUserMessage` already reads for the history view (`user_message`, and the current `item_completed` `UserMessage`) plus the `response_item/message` record — and skips the AGENTS/environment context Codex records as injected user-role messages ahead of the operator's prompt. That skip is applied to the resolved text rather than to one shape, because which record carries the injected block moves between Codex versions. A harness that defines `readActivity` is authoritative over the field: a null return means "keep the previous summary", never "fall back to the pane title", since for such a harness the title is known-useless. That authority binds the tmux `pane-title-changed` handler too (`handleTitleChanged`, `header.ts`), which is a fourth writer of `entry.task` and the one that does NOT begin from a registry sweep: it defers entirely for such a harness, because it wrote the raw title — Codex's worker-name-shaped `project-name` — straight over the summary the other three paths had just derived, so the row showed a useful summary and then reverted to the worker's own name seconds later. The hook is a session hook, which tmux 3.7c runs only for the panes of the session's current window, `main` (measured on an isolated server: a title change in a parked worker window or a garden view never fires it), and each run cold-starts the CLI, so tmux filters first (`installTitleChangedHook`, `create.ts`, reinstalled on attach and after a rebuild): `if-shell -F` passes only the right slot of `main` (`pane_at_right`), the one pane there that holds a worker or the project shell, and drops the left column's title churn (the root shell's prompt, the logs view, the diary editor). A parked worker's title change is picked up by the next `refreshWorkerTasks`. Codex worker panes in the right slot still pass the filter and return at the `readActivity` check. For those workers the live pane-border label (`@garden_task`) is refreshed by `refreshWorkerTasks` instead, which is otherwise the title handler's job. A newly discovered task is a visible event even when the hook changes no lifecycle state: `applyAndLog` repaints it immediately, and `refreshWorkerTasks` re-bakes once with its updated registry snapshot instead of leaving the prior text visible until the next event. The opening-prompt read is bounded to the head of the transcript because it runs on the hook path; its bound clears the rollout's instruction preamble, measured at 70-90KB for a real garden worker.

**Model drift (what a worker is running vs. what it was pinned to)** (`src/dashboard/model-drift.ts`): `pinnedModel(entry)` resolves the model garden *asked* for and passes on the launch command line — normally `entry.model`, with the Codex-default fallback the launch path uses — and until now the status pane rendered it as settled fact. A harness can overrule it after launch. On 2026-09-08 codex 0.153.4, on the first session started after a Homebrew upgrade, showed its new-model notice seven seconds into a worker's boot, moved that live session from the pinned `gpt-5.6-sol` to `gpt-6-astra`, wrote the new model into `$CODEX_HOME/config.toml`, and recorded a `<model_switch>` developer message in the rollout. The worker's own pane status line read `gpt-6-astra` for the next 13 minutes of work; garden's row read `gpt-5.6-sol`, and nothing anywhere reported that the two disagreed — the pin looked honored precisely because garden was the one asserting it.

So the pin is now checked against the harness's own record. `HarnessCore.readRunningModel` is the optional seam: a harness defines it only when it can reconcile the vocabulary it launches with against the vocabulary its transcript records, because the caller compares the returned reading to the pin for exact equality. Codex qualifies — `-m` takes a concrete slug and `turn_context` reports that same slug back, one record per turn — and `readCodexRunningModel` returns the newest one it can establish from a bounded tail scan. The scan starts at 256 KB and widens to 4 MB so a later long turn does not fall through to the first turn's model. Its head fallback is load-bearing rather than defensive: a worker still on its FIRST turn has its only `turn_context` in the rollout preamble, far above any tail read (line 8 of the rollout that motivated this, still on that turn 2.3 MB later), so a tail-only read would stay blind for exactly as long as the switched turn runs — the window in which the operator can still redirect it. The fallback is used only before the first observation; after that, exhausting the tail preserves the last reading rather than misreporting a potentially stale head context as current. claude-code qualifies too, once the reader normalizes aliases: a family alias pin (`opus`) and the concrete id the backend answers with (`claude-opus-5`) reduce to the shared family token (`opus`/`sonnet`/`haiku`/`fable`), so the reader answers in the alias pin's own words when they agree. A concrete pin remains an exact comparison — `claude-opus-4-6` running as `claude-opus-4-5` is drift, not family-level agreement. A trailing context tag on either kind of pin (`opus[1m]`, the ultracode preset's) selects a context window, not a model, and the transcript records the id without it, so the comparison ignores it. An observed id with no family (`<synthetic>`, a provider's own id) returns null: the previous reading stands rather than a drift nothing substantiates. The normalization is what the harness needed to opt in; the pin had gone unverified here for as long as it had on Codex, and on 2026-09-09 four live workers whose bootstrap read `claude --rc --model opus …` were running `claude-fable-5-1` from their first assistant message, one of them having moved between the two mid-session.

`sweepWorkerModels` runs on the watchdog's 60 s tick (harness-gated, so a fleet with no such worker pays one map lookup each) and writes the reading to `WorkerEntry.runningModel` — **beside** the pin, never over it. Healing `entry.model` to match would silence the row by adopting the accident, and the next bounce would then relaunch on the drifted model deliberately. The status row renders the observation in place of the pin, under the identity cluster's override-only rule: nothing at all when the model is what the project itself runs (`projectWorkerModel`, `crew.ts` — the flat `model` key, the bound crew's builder seat, or Codex's Garden-owned launch default), and the model alone when it overrides that (`formatModelTag`, `status.ts`). It names what is RUNNING and stops there — the pin is not printed beside it. The tag appears only when the model is not the project's, so its presence already says "not what this project runs"; adding the pin gives the operator a second model to read for no decision it changes, and a pin they want back is one `⌥i` -> model away (operator call, 2026-09-09). A claude-code project that pins no model has no baseline — its workers run the account default, which Garden cannot name — so there only an explicit per-worker pin shows. An otherwise-unpinned Codex worker is different: `harnessTuning` launches it with `DEFAULT_CODEX_MODEL`, so `pinnedModel` treats that known command-line default as intent and can still report a substitution. That comparison arrived a day after the tag itself (operator call, 2026-09-09): crews stamp their builder seat onto every worker they spawn, so a crew-bound project (`claude-codex` pins `opus`) put a tag on every row that only repeated what the project header already said, which is precisely the noise the "default is invisible" rule exists to prevent. It stays **grey** — a divergence is routine, not a fault. The operator changes a worker's model often enough (`⌥i` -> model, `/model` in the pane) that a status color here would mark deliberate work as a problem; this is identity, what the worker runs, and grey is what identity wears — the same quiet treatment the base badge gives `→ <base>` (operator call, 2026-09-08). A reading that moves is **logged, deliberately not alerted** (`warn` on drift, `info` on agreement, so `garden logs -l warn` reconstructs what a branch was built on). The operator changes a worker's model routinely — `⌥i` -> model, or `/model` typed into the pane — and that produces exactly the reading a harness switching a session on its own does, with nothing in the transcript to separate the two. An alert on every model change would spend the operator-attention surface on the common deliberate case to catch the rare accidental one. The row is the surface instead: it names the running model where it used to assert the pin, so the divergence is visible the moment the operator looks at the fleet, which is precisely what was missing when a worker ran 13 minutes on a model nobody chose. A claude-code worker with no explicit pin never flags because Garden cannot name its account default.

**Thread titles for a row the harness left without one** (`src/dashboard/task-title.ts`): the fallback above — the opening prompt's first line, capped at 120 chars — is a truncated paragraph of the operator's own prose, and because `readActivity` returns it only while the task is unset, it then freezes there for the worker's whole life. Codex offers nothing better: verified across live rollouts on 2026-08-25, it writes no title record of any shape, `Reasoning.summary_text` is empty with the reasoning itself encrypted, and the `update_plan` steps some models emit name a step, not the thread. So garden writes the phrase itself — the opening prompt goes to a cheap Haiku (`generateTaskTitle`, the same model and precedent as `verdict-extract.ts`: a small model reading a subject, not forming a judgement), launched with an empty tool set so the software-engineering instruction it is naming cannot cause shell or file actions, and the reply is stamped as `entry.task`, giving the row a topic (`Erica composer autoheight`) instead of a cut-off sentence. `sanitizeTitle` removes terminal control sequences from the reply before it is stamped, since the model has just read a prompt someone else wrote. Titling is driven from the watchdog's 60 s tick (`sweepWorkerTitles`), which dispatches a detached `garden dashboard _worker-title <project> <worker>` per candidate, because a multi-second model call on the tick's own thread would be read by `absorbSleep` as machine-suspend time and shift live review timers. The cheap sweep selects, with no attempt recorded, either of two shapes: a harness that defines `readActivity` (the existing declaration that its pane title is not a summary) carrying a non-placeholder task, or — whatever the harness — a row that is **still blank** more than `BLANK_TASK_GRACE_MS` (5 min) after the worker was created, while its `agentStatus` says it has actually been prompted (`working`/`idle`/`asking`/`paused`; one still booting, parked at its first prompt, or exited has no opening prompt to title from and would otherwise cost a dispatch every tick for its whole life). That second leg is what covers **claude-code**, whose row has exactly one source: Claude Code names a thread from a prompt the operator TYPED, and a prompt delivered programmatically — another Claude session fanning work out over the cross-session socket — moves no terminal title, so such a worker's row stayed empty for its whole life with nothing in the log to say why (omi-godot, 2026-09-18: six fanned-out workers, all blank). A Haiku title is not permanent there the way it is on Codex: a pane title that does eventually appear supersedes it, which is the right order — a rolling summary beats a frozen topic. The detached route then confirms the rollout contains a real opening prompt before it claims the attempt, because a creation-time seed can populate the registry before verified delivery and should not spend a title call. It does not require the task to still equal the prompt fallback: nothing but this route writes over a set Codex task any more, and a worker whose row an older build let a plan step overwrite is exactly one that needs a topic. `WorkerEntry.titleGeneratedAt` is claimed **before** the model call and never released, so exactly one attempt runs per eligible worker: a slow call cannot be double-dispatched by the next tick, and a failing one cannot re-spend on every tick forever — the cost being an un-titled row after a transient failure, which is what shipped before. The title is generated from the transcript's WHOLE opening prompt, not the registry's already-truncated task, since a briefing routinely states its subject past the first line; the prompt is fenced and the model told not to follow it. Reading that opening prompt is per-harness (`OPENING_READERS`, a table here rather than a `HarnessCore` method for the reason `prompt-verify.ts` gives: a core method cannot be tree-shaken out of the lean hook bundle). The claude-code reader (`readOpeningPrompt`, `conversation.ts`) is the head-scanning mirror of `readLatestPrompt` with one deliberate difference: it ADMITS a peer-delivered prompt — the meta, system-sourced record whose `origin.kind` is `peer` — and returns `origin.body`, the message without its "Another Claude session sent a message:" wrapper. Delivery verification correctly ignores those records (they are not garden's paste); for titling they are the only statement of the task that exists. The claim carries the task it was taken from **in a wrapper**, because a blank row — the whole point of the second leg — is otherwise indistinguishable from a refused claim. The final write is guarded on that task being unchanged since the claim, so a concurrent writer is never silently overwritten.

### Bead intake (board→garden delegation)

The intake loop (`src/dashboard/poller-intake.ts` + the bd client in `src/dashboard/beads.ts`) converts ready, dispatch-labeled beads in a project's `.beads` store into garden workers. It is garden's half of the board→garden delegation design (board's `docs/DELEGATION.md` is the authority): bd owns the work graph and computes the ready frontier (`bd swarm status <epic> --json` — never the `--parent` family, which is empty for dependency-edge epics on both verified versions, bd 1.0.3 and 1.2.2); board steers dispatch via labels on the epic; garden subscribes to the frontier and executes. Opt-in per project via `beadIntake: true` (+ optional `beadIntakeCap`, default 3; + optional `beadsDir` pointing at a shared store — see "Shared store" below). Projects without the flag never shell out to bd.

**Where it runs.** A step at the end of each poller cycle (`poll()` in `poller.ts`), throttled to one pass per 60 s via an on-disk mtime stamp (`intake-last-<project>` in the control tree — poller processes are exec-per-wake, so any remembered state lives on disk; in the worker-writable sessions dir a worker could keep it fresh, or future-date it to hold background intake off). A stamp more than one interval ahead of now also counts as due, so a wall clock that stepped back after the write cannot hold intake off until it catches up. `garden poke [project]` bypasses the throttle: it writes an `intake-poke-<project>` marker, ensures the project's poller exists, and pokes its FIFO (`<project>-poll-signal`), so the very next cycle runs intake now — this is the fire-and-forget wake board's dispatch gate keys use. The liveness watchdog adds the one recurring beat the design needs (`INTAKE_BEAT_MS`, 5 min): it keeps a poller alive for each opted-in project even when the project has no workers, then sends a plain FIFO poke, so a gated epic can dispatch the project's first worker when no lifecycle event is arriving.

**Shared store** (DELEGATION.md Decision 15). A project may point its bd calls at another checkout's `.beads` with the `beadsDir` config key (absolute path; in practice the board repo's store, which the store audit found is the only one in the fleet — so enabling any project for cross-project delegation is two config lines: `beadIntake true` + `beadsDir` → the board store). The resolution rule exists ONCE — `resolveBeadsDir` in `src/config.ts`: `beadsDir` when set, else the checkout's own `.beads` — and every surface that names the store consumes it, so intake can never read a different store than workers write (the split-brain DELEGATION.md warns about): (a) garden's own bd shell-outs — every `beads.ts` function takes a `BeadsStore` (structurally the project config), and `runBd` keeps cwd at the project path while injecting the resolved `BEADS_DIR` into the child env (overriding a different store inherited when garden is invoked inside another project's worker); (b) worker env injection (`beadsEnvExports`) exports the same resolved dir as `BEADS_DIR`; (c) both harnesses' sandbox write grants follow the resolved dir, which makes a configured `beadsDir` a sandbox write root: it is refused and canonicalized on the same terms as a `sandboxWriteRoots` entry (`resolveBeadsWriteRoot`), when `garden config` stores it and again at every launch. With a shared store every project's pass sees every project's epics, so `runIntakeOnce` scopes its whole pass — plan consume, reaper, governor, dispatch — client-side to epics carrying the `project:<name>` label (the bd query stays broad; board's own epics carry `project:board`, so the conjunct is harmless on a single-store project too). The dangling-store check is loud and fail-closed: `beadsStoreError` (config.ts) flags a configured `beadsDir` that is relative, missing, or not a directory, `runBeadIntake` then skips the pass, stamps it as the intake error (board's liveness chip reads it), and raises an error alert — running bd against a dangling path would bootstrap a fresh divergent DB there, the exact split-brain this rule prevents. Each pass also logs which store it resolved (info when a shared store is pinned, debug otherwise), and `garden doctor` renders a `beads stores` row for any project pinning a `beadsDir`.

**The label contract** (all on the epic, except `retry` and `failed` on the bead):

- `dispatch:manual` — operator-armed authorization for ONE WAVE (the trust ramp; board's `g`; DELEGATION.md Decision 9). The arm covers the whole observed wave, not one pass: intake keeps dispatching under it across passes until the frontier it observes — unassigned ready beads not excluded by the circuit breaker — is empty, and only then consumes it by rewriting to `dispatch:dispatched`; board re-arms by restoring `dispatch:manual`. An armed epic whose frontier is empty and carries no mid-wave marker stays armed (the operator's `g` press is never silently eaten). Beads that become ready mid-wave dispatch under the same arm — accepted, one keystroke per wave is the contract.
- `dispatch:dispatching` — garden-written durable mid-wave marker: the armed wave has started but was throttled (cap/budget) before the frontier drained. It lets a later empty-frontier pass distinguish "wave dispatched, now done" (consume) from "armed, nothing ready yet" (stay armed). GC'd whenever the epic's mode is not manual.
- `dispatch:auto` — the wavefront marches unattended (board's `G`).
- `dispatch:off` — gate closed; wins over manual/auto if both are present.
- `budget:N` — operator-set cap on total dispatched sessions for the epic; retries count. Intake tracks spend in a garden-written `dispatch:spent:N` label (bd labels are the sanctioned durable channel — registry entries hard-delete on worker removal — and board can render "N sessions spent" from the same label). The counter is written fail-closed (Decision 10): the session is charged BEFORE its spawn — the incremented label is added before every old `dispatch:spent:*` straggler is removed, with all writes checked, so either partial-write order preserves/overcounts spend and never undercounts it — and any write failure aborts that epic's dispatch pass (other epics continue) with a distinct error alert (`intake-budget-write:` dedup key), so an uncounted session can never spawn; a spawn failure refunds the charge best-effort in the same fail-closed order (restore the prior non-zero count before removing the charge), and a failed refund overcounts. A spawn that throws is refunded only when no new registry entry carries the bead: newWorker registers the worker before it starts the pane and drops the entry when the pane fails, so an entry left behind may be a running session and keeps its charge. The rest of the pass still runs, and the error is rethrown at its end so the intake-error stamp still fires. All counter labels (`budget:`, `dispatch:spent:`, `dispatch:retry:`, `dispatch:failed:`) parse duplicates max-wins on both sides of the border, and garden's rewrite sites garbage-collect every matching straggler. At the cap intake halts, labels `dispatch:budget-exhausted`, and raises an error alert; in-flight workers are never killed (operator decision). Clearing the exhausted label and raising `budget:N` resumes.
- `dispatch:retry:N` — written on a bead each time the reaper recovers a crash (a worker that died mid-build). Crash recoveries only: a worker that died `failing` takes the failed counter below instead, because retries should keep dispatching and quality failures should stop it.
- `dispatch:failed:N` — garden-written quality-failure counter on a bead (Decision 8), written from the two places garden observes quality failure, both through the shared `incrementFailedLabel` in `beads.ts` (max-wins read, incremented label added before every straggler is removed — the spent counter's partial-write order, so a partial write can only preserve or raise the count): the reaper's failing branch (a bead worker that died parked in `failing`), and the review pipeline's rejection path (`dispatchDefaultVerdict`'s failed branch stamps the bead of a worker carrying `entry.bead`, folding the outcome into the existing review-failed alert; best-effort — the breaker is advisory and may fail open, unlike the budget, so a write failure logs a warning and the failing transition proceeds unchanged). At `BREAKER_THRESHOLD` (2) the frontier excludes the bead — from dispatch (before slots are computed and before the priority sort, so a tripped bead can neither hold a slot open nor outrank an eligible sibling) and from the manual-wave consume rule's frontier — its blocked descendants wait, and board renders the epic chip red.

The `plan:*` family (DELEGATION.md phase 4d + Decision 16) shares the epic as its label surface but drives a SEPARATE loop — a planner decomposes the epic into children; dispatch executes them. Unknown `plan:*` values are ignored on both sides (fail closed); never invent new ones:

- `plan:pending` — board-armed (`S`): decompose this epic. The only spawnable plan state.
- `plan:planning` — garden-written pre-spawn; a planner owns this epic. The planner worker rewrites it to `plan:ready`/`plan:failed` on completion; intake rewrites it to `plan:failed` when the spawn dies.
- `plan:ready` — planner-written: draft wisps await board's `S` promotion. Never touched by garden.
- `plan:failed` — terminal failure; board's `;plan:none` re-arms.

**Plan consume (the planner lifecycle).** The plan-consume loop runs at the top of `runIntakeOnce`, BEFORE the dispatch loop, over epics admitted by the widened `plan:*` filter (an epic carrying both families runs both loops, each keyed on its own labels). For each `plan:pending` epic the label is consumed BEFORE the spawn: remove `plan:pending` first — a failed remove aborts that epic with an error alert (`intake-plan:` dedup key), because proceeding risks duplicate planners on the next wake — then add `plan:planning` (on failure: alert + best-effort `plan:failed`), then spawn exactly ONE planner worker (`--workflow planner`, Opus/xhigh seat) through the intake spawn seam, seeded by `buildPlannerSeed` with the epic id/title, the full pinned design doc, and the empirically verified bd contract (see WORKFLOWS.md § "Planner workflow" — including the deliberate deviation from DELEGATION.md's `--graph` sketch: bd 1.2.2 now honors `--ephemeral` but silently drops `--parent`, leaving the children outside the epic's dispatch frontier). A spawn failure rewrites `planning` → `failed` with an alert. Only `pending` is spawnable, so repeated poller wakes are idempotent by construction. The planner carries no bead assignee and is deliberately EXEMPT from the intake cap/governor and the budget counter — the governor joins on bd assignees and `budget:N` caps dispatched build sessions, and a planner is neither; it is likewise invisible to the reconcile step (no `bead` field), so a planner orphaned by a board-side `;plan:none` keeps running until removed by `garden workers stop` or the dashboard kill.

**Dispatch pass.** For each open epic carrying any `dispatch:*` label: read the frontier, filter `ready[]` to beads nobody holds — neither a bd assignee (assigned-but-open beads stay in `ready[]` on both verified versions, 1.0.3 and 1.2.2, and carry an `assignee` field) nor a registry worker that has not exited carrying the bead in `entry.bead` (a worker's own claim lands only after bootstrap and boot, and it is the only claim for a `handoff --bead` worker or one whose two post-spawn claims failed) — drop beads the circuit breaker excludes (`dispatch:failed:N >= BREAKER_THRESHOLD` — before slots and before the sort), and dispatch up to `min(cap slack, budget remaining, wave size)` — highest priority first (`bd show` supplies priorities; board's reordering steers which beads win scarce slots). Each dispatch: re-check the single bead's assignee with a fresh `bd show` immediately before spawning (the frontier snapshot is stale by then — a claim that raced in skips the bead without charging the budget), pre-charge the spent counter fail-closed, write the seed file, `newWorker({background: true, seedMessageFile})`, then claim the bead AS the worker (`BEADS_ACTOR=<worker-name> bd update <id> --claim`) — one atomic bd write that sets assignee + in_progress, removes the bead from the frontier, and establishes the join. A failed post-spawn claim is retried once before falling back to the worker's own seeded claim, and the seed's protocol footer tells a worker whose claim loses to another actor to stop and mark itself done. The concurrency governor counts live intake workers via that same join (bd assignees with a live registry entry, or for an unassigned bead the registry worker carrying it — no invented registry state), and same-pass spawns count immediately.

**The join contract.** Workers of a `beadIntake` project get `BEADS_ACTOR=<worker-name>` and `BEADS_DIR=<resolved store>` (via `resolveBeadsDir` — the checkout's own `.beads`, or the shared store a `beadsDir` names) exported alongside the `GARDEN_*` vars (bootstrap + resume paths, `beadsEnvExports` in `create.ts`), and the sandbox allows writes to that resolved `.beads` dir. `BEADS_ACTOR` makes the bd assignee the garden registry key — board joins bd assignee ↔ registry entry with zero invented state. `BEADS_DIR` is load-bearing: a worktree carries the tracked `.beads` files but not the gitignored Dolt database, so bd run bare in a worktree would bootstrap a divergent local store and the worker's `bd close` would never reach board or intake. The join's registry→bd half is `WorkerEntry.bead`: the bead id stamped onto the worker's entry at creation — by the intake spawn seam (`IntakeSpawnRequest.bead` → `NewWorkerOptions.bead`) and by `garden handoff --bead <id>` for hand-run dispatches, one shared write path. Stamping makes no bd claim (intake claims post-spawn; a handoff worker's own briefed claim is the claim) — the field exists so garden can navigate worker → bead: the removal-time unclaim and reconcile step below, the review-rejection breaker writer, and board's chips before a hand-run handoff's claim lands.

**bd route-arounds** (first verified against 1.0.3 and still true on 1.2.2): `--claim` never overwrites a foreign assignee and a same-actor claim on a pre-assigned open bead is a no-op that does NOT set in_progress — so the design doc's `garden-pending` pre-assign stack is replaced by the claim-as-worker flow above, and the worker's own seeded `bd update <id> --claim` lands on the verified idempotent same-actor path. `bd human <id>` only prints a help menu — the seed's stuck path is `bd update <id> -s blocked` + `bd label add <id> human` + `bd comment <id> "<why>"` (surfaced by `bd human list`).

**Reaper.** Runs each pass over every gated epic's `active[]` (in_progress) beads, before dispatch, with two recovery branches split by what the death means. A crash — a registry entry with `agentStatus === "exited"` still in `working` prState, past a 10-min grace (`REAPER_GRACE_MS`, spanning bounce gaps), or the legacy `garden-pending` marker — is recovered with `bd reopen` + unassign + a `dispatch:retry:N` bump and a warn alert (`intake-reap:` dedup key). A quality failure — `shouldReapFailing`, a separate predicate beside the deliberately narrow `shouldReap`: entry exists, `agentStatus === "exited"`, prState exactly `failing`, past the same grace — is recovered with `bd reopen` + unassign + a `dispatch:failed:N` bump (and explicitly NO retry bump), warn-alerted under an `intake-failed:<project>:<bead>:<N>` dedup key; at the breaker threshold the bead stops dispatching. A LIVE `failing` worker keeps its bead — the operator may still redirect it; only provably-dead ones are recovered. No registry entry at all means a foreign/operator actor — never touched. Entries in pipeline states keep their beads (review/merge continues headless), and `done`-but-open beads are board's amber "missed `bd close`" divergence, not a crash. Because intake claims pre-spawn are made only after `newWorker` returns a name (a registered entry), every intake-claimed bead's assignee has an entry, so the missed-spawn and crashed-worker cases share this one recovery.

**Reconcile** (DELEGATION.md Decision 7). After the reaper and BEFORE the governor count — so a freed slot is usable in the same pass — intake walks registry workers carrying `entry.bead` (the registry→bd join; independent of the gated-epic set, so `handoff --bead` workers reconcile too, and the step runs even when no gated epic exists), batch-reads their beads, and stops (via the injectable `IntakeDeps.stopWorker`, wired to `stopWorkerByName` — the full `garden workers stop` removal) any worker whose bead is **closed** or **foreign-assigned** (a non-empty assignee that is not the worker: the operator's board-side recall, whose claim is the durable cancel marker). Two guards: an UNASSIGNED bead is skipped — the worker's own claim may still be in flight after a failed post-spawn claim, not a recall — and workers in pipeline states (`reviewing`/`resolving`/`ci-fixing`/`merge-pending`) are deferred with a log line, never yanked mid-headless-pipeline; the next pass catches them once they exit it. A closed bead's worker has a third guard, because the stop deletes its branch, origin's copy of the branch, and its worktree, and a bead can close before the work merges (an agent's early `bd close`, the operator's `x` in board, a multi-merge worker closing after its first merge) while prState cannot say whether the work landed (a merged worker that was auto-continued holds new work). Such a worker is retired only once nothing would be lost: its agent is not mid-turn (`agentStatus` `working` defers at debug, since the turn may be writing), and `describeUnlandedWork` finds neither a commit that `origin/<base>` lacks on its branch, on origin's copy, or on its worktree HEAD, which a rebase leaves detached (`countUnlandedCommits`, `git.ts`), nor uncommitted changes in its worktree (`isWorktreeDirty`, the review gate's check, so garden's own info/exclude'd files do not count). It reads the canonical worktree the removal tail deletes, never the registry's `worktreePath`. Otherwise the worker is kept and the operator is told once (warn, `intake-unlanded:<project>:<worker>` dedup key), with the closure recorded on `WorkerEntry.unlandedNoticeBead`: the condition can stand for days, and the alert dedup alone would repeat it hourly. A git failure is stated in that alert and keeps the worker; it is never read as nothing to lose. The first pass after the work lands retires the worker, and `garden workers stop` removes it at once. A recall is not held this way: the operator's claim asks for the worker to stop. Only a work-discarding recall raises an alert (warn, `intake-reconcile:<project>:<worker>` dedup key): a recall that stops a worker whose branch has NOT landed (prState other than `merged`/`done`) is discarding in-flight changes. A recall of a merged/done worker is the completion of an operator-initiated action — routine lifecycle, logged with the worker's prState but not alerted, exactly like the closed-bead sweep; the closed-bead sweep is logged but not alerted, because it is routine lifecycle: closed-bead reconcile deliberately sweeps COMPLETED intake workers (worker merges, closes its bead, goes `done` → the next pass retires it) — the intended lifecycle GC for background-spawned delegated workers, and the only one the guard above lets through. The Decision-12 guard in the removal tail makes both cases safe: a closed or foreign-assigned bead is left untouched by the removal-time unclaim, so retirement never disturbs the graph and a recall's claim survives the displaced worker's removal.

**Removal-time unclaim** (DELEGATION.md Decision 12). The registry hard-deletes worker entries on removal, and the reaper's predicate deliberately never touches a bead whose assignee has no registry entry — so removing a worker used to orphan its in_progress bead forever. Both operator removal paths — the dashboard `⌥x` kill (`killPane`) and `garden workers stop <worker>` (`stopWorkerByName`) — now funnel through one shared tail, `finalizeWorkerRemoval` (`workers.ts`): review-window kill, telemetry tombstone, the guarded unclaim, registry removal, poller-stop check, background git cleanup. The unclaim reads the bead (`bd show`) and reopens (when in_progress) + unassigns it ONLY when its status is open/in_progress AND its assignee is still this worker's name; a closed bead is finished work, and a foreign-assigned bead is the operator's board-side recall claim (or another actor's) — both are left untouched, which is exactly what preserves the recall flow. The bd shell-outs run after the dashboard state lock is released (they cost up to ~20s per call under store-lock retries) but synchronously and checked: any read or write failure raises a warn alert (`bead-unclaim:<project>:<bead>` dedup key) — the orphaned-bead hole reopening is never silent — and the removal still completes. The unclaim runs before `removeWorker` so a crash mid-unclaim leaves the entry (and its join) on disk rather than an orphaned bead. The pre-work rollback removal sites (tmux spawn failure, the two bootstrap aborts) stay on raw `removeWorker` — no bd claim exists at those points to unclaim.

**Intake liveness in `garden status`** (DELEGATION.md Decision 11): the piped `garden status --json` output carries `lastIntakeAt` (the intake stamp's mtime, ISO) and `lastIntakeError` (the message from an `intake-error-<project>` stamp in the control tree, written when a pass throws and cleared by the next clean pass) on each `beadIntake` project's entry — the transport for board's `dispatch stalled` chip, so board never reads garden's session directory. The path helpers and status reader live in `src/dashboard/intake-paths.ts`, a hook-bundle-safe leaf, because `status.ts` is reachable from `dist/hook.js` and must not import `poller-intake.ts`.

### Status tracking and the liveness watchdog

The full specification for status tracking and display lives in `docs/STATUS.md`. The registry is the single source of truth: Claude Code hooks (`SessionStart`, `UserPromptSubmit`, `Stop` — and `StopFailure`, which a turn that dies on an API error fires instead and which shares `Stop`'s route, as `PostToolUseFailure` shares `PostToolUse`'s) write `agentStatus`; the poller writes `prState`; the worker launch wrapper writes `agentStatus="exited"` when its agent exits (`dashboard _agent-exited`, `handleAgentExited`: the pane survives the agent via `exec $SHELL`, so the tmux `pane-died` hook, which tmux runs only under `remain-on-exit`, never fires for it; the route also runs the Stop hook's turn-end routine, since a turn the exit cut short fired no `Stop`, and flags `interruptedWhileWorking` when the agent was mid-turn); the operator `hold` action (`⌥e` / `garden hold`) writes `agentStatus="paused"` (the one operator-initiated writer — a raw Escape interrupt fires no hook, so a deliberate halt is otherwise invisible); and the Codex rollout listener (`codex-input.ts`) writes `agentStatus="asking"`/`"working"` around a `request_user_input` call, plus `"idle"` when the rollout's final `task_complete` proves a final `Stop` was missed or its final `turn_aborted` shows an interrupted turn (which fires no `Stop` at all), in which case it also runs the Stop hook's turn-end routine (`routeStopHookEnd`: arm the review, flag a dirty tree, apply `.garden-done`) in the worker's canonical worktree, since that hook is what arms the review for the turn's last commits. The first-launch bootstrap runs the agent as `<agent> || true`: under the script's `set -e`, a non-zero exit (a crash, a kill) would fire its ERR trap, which reports an aborted bootstrap and skips the `_agent-exited` record. There is no pgrep, no marker file, no fallback poll. Every transition is event-triggered, with one sanctioned exception: Claude Code emits no event when the operator approves a permission dialog, so the `PermissionRequest` hook spawns a bounded pane-reading watcher and the watchdog tick backs it up, flipping `asking → working` (or to the status a subagent's record names) once the caret is back in the composer (`permission-prompt.ts`; see the permission-mode bullet under "Worker Isolation Model" and STATUS.md "Answered permission dialogs"). The single recurring tick in the system is the liveness watchdog (`watchdog.ts`, `_garden-watchdog` window): every 60 s it (1) re-pokes any project holding a worker stranded in an active state past a 5 min staleness threshold, recovering dropped one-shot pokes (poller respawn gap, reboot-killed detached wake-ups), and (2) keeps each project's poller window healthy — respawning it if it died uncleanly (a poke is useless with no poller reading the FIFO) and collapsing duplicates to one if a spawn race left several (resolving windows by index, since a tmux name target is ambiguous across duplicates). It also respawns the usage poller's window when that is gone (`ensureUsagePoller`), except on a provider-only fleet, which runs no usage poller. The heal is mutual: every project `poll` re-arms the watchdog when its window is missing (`startWatchdog` collapses duplicates to one, like the poller heal, and is otherwise a no-op), because a watchdog that died stayed dead until the next attach or rebuild and took every duty listed here with it. The spawn race itself is prevented at the source: `startProjectPoller` runs its check-and-spawn under a per-project file lock (`<project>-poller.spawn.lock`), so two concurrent starters serialize and the second no-ops instead of opening a second window — the watchdog collapse is now a backstop, not the primary defense. That lock and `startWatchdog`'s `watchdog.spawn.lock` live in the control tree, since only unsandboxed processes take them: a lock is never reclaimed while its pid answers and names a process older than the lock, so one planted in the sessions dir made every respawn of that poller throw, or stalled every poll for its 2s deadline. A build from before that move takes both locks in the sessions dir, so for the seconds a deploy runs processes of both builds the two do not exclude each other, which is what the duplicate collapse in both starters covers. It also (3) re-files provably misnamed worker windows by joining pane cwd to registered worktree paths under the dashboard state lock, before orphan detection. The lock keeps the heal from observing a navigation swap between its `swap-pane` and its rename, which would look like a misfiled window, and running first lets orphan detection judge the healed names. It then (4) alerts on orphaned worker windows — a live tmux worker window with no registry entry, the casualty of the create/sweep race fixed in `dropGhostEntries` — making the detached worker visible (detection only; it never reconstructs the entry) so the operator can recover it. It (5) repairs a right slot whose pane died or whose id is missing (`healActivePane`, `validate.ts`), adopting the actual surviving occupant or recreating the missing full-height slot and refilling it from a parked worker or shell; a failed split leaves the id null and is retried on the next tick. It (6) discounts machine-sleep/clock-jump time from live review/resolve/ci-fix timeouts (`absorbSleep`): the watchdog is the fleet's one fixed-cadence process, so a loop iteration that overran a full extra tick of slack measures the suspend, and it shifts each live-windowed worker's `reviewStartedAt` forward by that slippage so a laptop that slept mid-review doesn't wake to a spurious `REVIEW_TIMEOUT_MS` kill (`isReviewTimedOut`/`isCiFixTimedOut` read that wall-clock anchor). It (7) re-reads models reported by capable harnesses, persisting `runningModel` beside the pin and repainting only when the observation moves. It (8) backstops the answered-permission-dialog watcher (`sweepAnsweredPermissionPrompts`, `permission-prompt.ts`): any claude-code worker still `asking` after 10 s whose pane shows the caret back in the composer is returned to `working`, or to the status a subagent's record names, guarded on the same `asking` episode so a newer question is never cleared. On a separate hourly throttle it (9) runs disk housekeeping (`housekeeping`): `truncateLog` enforces the 10MB `dashboard.log` cap on a recurring cadence (previously only called on fresh dashboard creation, so a long-lived session's log grew unbounded between restarts), `sweepBootstrapScripts` deletes spent `bootstrap-<project>-<branch>.sh` scripts older than 6h from `control/scripts` (and older builds' copies in the sessions dir) (each worker launch writes one, consumed by its pane within seconds and never touched again, but nothing removed them — one orphan per worker ever created), `sweepSpawnDrafts` deletes stale `spawn-draft-<project>.json` composer overrides past their 5-min TTL, and validate.ts's `cleanContextFiles`/`cleanClaudeSettingsFiles` remove the control-tree settings and context files of workers and projects that are gone (an hour's grace), which otherwise waited for the next attach. The same hourly pass detects worktree directories with no claiming registry entry, after a 1h idle grace and excluding live cleanup markers; it reports their bounded-walk sizes but never deletes them because they may contain uncommitted work. These actions only restore lost event delivery, repair or surface a window casualty, record harness observations, discount suspend time from a timeout anchor, or bound an accumulating on-disk artifact — the tick's one lifecycle-state write is the answered-permission-dialog backstop in (8), the single sanctioned pane-read transition. The watchdog *process* additionally hosts the Codex rollout listener (`startCodexInputWatcher`, `codex-input.ts`), which does write `agentStatus`: it lives here because this is the fleet's one unconditional long-lived process, but it is driven by `fs.watch` write events rather than the 60 s tick, so the no-polling invariant holds.

Before arming that listener, `startCodexInputWatcher` creates `$CODEX_HOME/sessions`, matching Codex's lazy first-run setup so a fresh workstation does not lose the watcher permanently to `ENOENT`. Before that fix, a workstation where Codex had never run left the watcher dead for the watchdog process's life (it has no retry), and every Codex worker lost its `asking` status and its missed-turn-end heal until the next dashboard rebuild (observed on a fresh machine, 2026-08-27). Each debounced batch of rollout writes runs `reconcileCodexInputRequests` (`codex-input.ts`) over two rollout-tail readers in `harness/codex-core.ts`: `readCodexInputRequestState` (the newest `request_user_input` call and its matching `function_call_output`) and `readCodexTurnState` (the turn end). Each write re-checks, inside the registry lock, the status and any freshness field its decision read unlocked, and is dropped if another writer moved either, so a `Stop` hook idling the turn in the same instant is never stomped back to `working`. The turn-end heal guards on `lastEventAt`, not `lastStateChangeAt`, which `prState` moves also stamp: a worker stalled in `merge-pending` carries a newer `lastStateChangeAt` than the turn end it waits on, so that guard would never fire for exactly the stalled workers. That is the class that held a wolf worker in `merge-pending` for 30h on 2026-08-09, `handleMergePending` deferring on a worktree it believed an agent was editing (`isWorkerClaudeWorking`) and logging the defer at debug level only, so 364 watchdog pokes produced no visible signal. The turn-end routine runs only for a worker name Garden generated, in the worktree derived from that name rather than a registry path, since the listener runs unsandboxed and the registry is worker-writable.

The same fast watchdog tick also claims and re-dispatches due worker-cleanup requests. That recovery action is described in "Worker git cleanup" above; it is detached so it does not extend the loop interval that `absorbSleep` measures, and it mutates only the cleanup request's retry mtime rather than worker lifecycle state.

The hourly housekeeping pass also removes what an interrupted write leaves behind (`sweepWriteLeftovers`, `write-leftovers.ts`). A process killed between `atomicWriteFile`'s temp write and its rename leaves `<file>.<uuid>.tmp`, one killed inside a lock reclaim leaves `<lock>.reclaiming.<uuid>`, and nothing else removed either: three intake-stamp temps sat in the sessions dir for weeks, each written the second a rebuild killed that project's poller mid-write. A rebuild no longer restarts a poller mid-poll, but any process killed mid-write leaves the same file. The sweep matches only those two name shapes (`isAtomicWriteTemp`, `isLockSalvage`, beside the code that names them), takes only regular files more than an hour old (a write renames its temp within milliseconds, and a reclaim unlinks or restores its salvage as soon as it has re-read it), and visits at most 50,000 entries in each tree, so a flooded directory cannot stretch the tick `absorbSleep` measures. It walks the whole control tree but only the top level of the sessions dir, whose subdirectories a worker could swap for links between the listing and the unlink.

Planner follows designer's status-decoration form: a grey `planner` identity badge leaves the detail slot available for live decomposition activity.

```
garden checks [project]            # Run the project's configured checks command under the
                                   # machine-wide checks semaphore (queue instead of stampede;
                                   # see "Project Configuration" → checks). Exit code passes
                                   # through. Runs in the caller's cwd (the worker's worktree).
```

Project name is auto-detected from cwd when inside a project directory. `GARDEN_PROJECT` env var overrides. Worker panes also export `GARDEN_WORKER`, `GARDEN_BRANCH`, and `GARDEN_BASE_BRANCH` so workers can self-identify via `garden whoami` and filter their own log history with `garden logs -w $GARDEN_WORKER`.

`garden health [--fix]` (`src/commands/health.ts`) lists where dashboard state and the registry disagree with tmux: a recorded pane id tmux no longer has, a missing or orphaned worker window, a worker whose pane process is dead but not marked `exited`, and a `working` worker with no hook event for 15 minutes. `--fix` marks those dead-pane workers `exited` and reconciles dashboard state through `validateAndHeal` under the dashboard state lock.

## Output Format

All read commands detect whether stdout is a TTY:
- **TTY:** pretty-printed for humans
- **Non-TTY:** JSON, one object per line

## Technology

- TypeScript, compiled via esbuild to `dist/cli.js` (plus `dist/hook.js`, a minimal entrypoint for the per-tool-call Claude hook so its node cold-start parses only the shared hook closure, not workflow/poller handlers; the minified bundle is guarded below 144KB and worker hook commands prefix it with a fleet-shared `NODE_COMPILE_CACHE` dir in the control tree (`~/.garden/control/node-compile`, out of every sandbox's write grant because the unsandboxed hook loads that bytecode) so each cold start reuses the bundle's cached V8 bytecode)
- tmux for session persistence and pane management
- `js-yaml` for config parsing
- No CLI framework — lightweight `process.argv` dispatch with aliases

### Build and deploy

How a rebuild reaches the running fleet without a restart, including why `scripts/build.mjs` swaps each bundle in by rename, is described under **postMerge** in "Project Configuration"; why the hook's compile cache lives in the control tree is in `docs/SANDBOX-THREAT-MODEL.md`. On 2026-10-24 the build wrote `dist/hook.js` at 141.4KB and `dist/cli.js` at 776.8KB, so the hook bundle is about 82% smaller.

Worker hook commands reach `dist/hook.js` through `resolveHookRunner()` (`runner.ts`). On the claude-code path, `buildSettingsJson` (`harness/claude-code.ts`) prefixes that command with `hookCompileCachePrefix()`, the `NODE_COMPILE_CACHE` assignment, which made each cold start a measured ~8% faster. Node namespaces the cache by engine version and architecture, keys each entry by the module's file path and discards it when a CRC32 of the source no longer matches, so a node upgrade or a rebuilt `hook.js` invalidates it on its own. The prefix depends on Claude Code running hook commands through a shell, and is deliberately not folded into `resolveHookRunner()`: the Codex adapter embeds that string in a TOML `command` value, whose exec semantics do not guarantee that an environment-assignment prefix survives.

A route a hook spawns runs in the CLI, not the hook bundle. `hook.js` reads its first argument as an event name, so `dashboard <route>` started through it would reach the hook dispatcher as an unknown event named `dashboard` and never run; `resolveGardenRunner()` therefore maps the hook entry point to the CLI beside it (`dist/hook.js` to `dist/cli.js`, and `src/hook-entry.ts` to `src/cli.ts` under tsx). The routes hooks spawn include the alerts-pane repaint, the Stop hook's usage refresh, the permission-dialog watcher and the delivery of owed handoff callbacks. `test/integration/claude-hook-bundled.real.test.ts` runs the built hook through a link from outside any worktree, since from inside one `resolveGardenRunner()` prefers the installed `garden` on `PATH`, and checks that the alerts repaint spawned by an alert the Stop hook raises writes the view.

## Principles

1. **Human-first.** The dashboard is for a human operator. Everything is driven by keyboard shortcuts and CLI commands.
2. **Files over databases.** YAML, JSON. All human-inspectable.
3. **Shell out, don't abstract.** Call `claude` directly. Don't wrap the API.
4. **Hotkeys over commands.** Inside the dashboard, keyboard shortcuts are the primary interface. CLI commands are for setup and scripting.
5. **Grow by adding, not changing.** New commands, new pane types, new hotkeys — avoid breaking what works.
