# Garden

Garden is a CLI orchestrator for managing interactive Claude Code sessions across multiple projects via a tmux dashboard.

**This file is the project's agent instructions, for every harness.** Claude Code reads `CLAUDE.md` and never `AGENTS.md`; Codex reads `AGENTS.md` and never `CLAUDE.md`. Garden runs both against this repo, so `AGENTS.md` is the real file and `CLAUDE.md` is a one-line `@AGENTS.md` import ([the documented pattern](https://code.claude.com/docs/en/memory#agents-md)). Edit this file; never keep a second copy of the same instructions in `CLAUDE.md`. `garden doctor` reports which registered projects have not adopted the pairing.

**Authoritative docs.** This file is a quick-start. Depth lives elsewhere — when something here disagrees with one of these, the spec wins:

- `DESIGN.md` — full architecture
- `rules.md` — coding rules loaded into every Claude session (commit/test/scope discipline)
- `WORKFLOWS.md` — workflow registry design, "how to add a new workflow", and trellis/grow workflow specs
- `docs/STATUS.md` — worker status state machine (spec)
- `docs/MULTI-MODEL.md` — multi-model / multi-harness architecture (Phases 1-3 shipped — provider layer, neutral core, harness adapter registry; Phase 4 in progress — Codex adapter shipped and reachable **as a reviewer** via per-role resolution (`config <p> role reviewer harness codex`) and **as a worker** via `workers new --harness codex`; a Codex worker's session-id capture, history/continue routing, and status-pane activity summary now ship — the remaining gaps are live-verifying `codex resume` and Codex-aware unsent-draft detection)
- `docs/TRACKS.md` — multi-track / promotion pipeline (design target, no code yet)
- `docs/` — additional design docs and behavioral specs; see `docs/README.md` for the index

## Build and run

```bash
npm install
npm run build          # esbuild → dist/cli.js + dist/hook.js
npm run dev -- help    # tsx during development
npm test               # vitest unit + integration; tsc --noEmit
```

`npm link` makes `garden` global. `dist/cli.js` is the symlink target — `npm run build` is all you need after edits. `package.json` sets `"sideEffects": false` so esbuild tree-shakes imported-but-unused modules (load-bearing for keeping `dist/hook.js` lean); modules must stay free of import-time side effects — only the entry points (`cli.ts`, `hook-entry.ts`) execute at top level. The build emits a second minimal bundle, `dist/hook.js` (from `src/hook-entry.ts`), that serves the per-tool-call Claude hook: it bundles only the hook dispatcher's import closure (~60% smaller than `cli.js`) so each fire's node cold-start is cheaper. Worker `settings.json` hook commands invoke it via `resolveHookRunner()` (`dashboard/runner.ts`), prefixed with a `NODE_COMPILE_CACHE=~/.cache/garden/node-compile` assignment (`hookCompileCachePrefix`) so each cold start reuses the bundle's cached V8 bytecode (~8% faster, measured; the dir is a sandbox-writable root shared fleet-wide, and node self-invalidates it on version/content change). The prefix is applied only on the claude-code path (`buildSettingsJson`), whose hook commands run through a shell — deliberately not folded into `resolveHookRunner()`, since the Codex adapter embeds that string in a TOML `command` value with different exec semantics. `cli.js` keeps its own `_claude-hook` route for workers whose settings predate it.

## Source layout

- `src/cli.ts` — entry point, command dispatch, help text
- `src/hook-entry.ts` — minimal second entry point for the per-tool-call Claude hook, built to `dist/hook.js` (calls `handleClaudeHook` directly, skipping the full command/dashboard graph)
- `src/commands/<name>.ts` — one async function per CLI command, registered in `commands/index.ts`
- `src/config.ts` / `src/session.ts` / `src/rules.ts` / `src/output.ts` / `src/version.ts` — config (`~/.garden/config.yml`), tmux sessions, system-prompt assembly, TTY-aware output, build version
- `src/checks-semaphore.ts` — machine-wide slot semaphore bounding concurrent checks-suite runs (`max(1, cores/8)` slots by default, overridable via the garden-level `limits.checksSlots`; pid-stamped `O_EXCL` lock files in `SESSIONS_DIR`, dead-owner steal, bounded-wait fail-open); `garden checks` (`src/commands/checks.ts`) is the consumer. The sibling fleet-wide budget is `limits.maxConcurrentReviews` (a cap on live `_<project>-review-<worker>` windows across all projects, gated at the review-launch point in `handleWorking` — defers, doesn't block; resolvers/ci-fix uncapped to avoid pipeline deadlock; 0/unset = unlimited). Both live under `limits` in `~/.garden/config.yml` (`LimitsConfig`, `config.ts`); `garden limits` (`src/commands/limits.ts`) is the operator surface. See DESIGN.md "Machine-wide limits".
- `src/dashboard/` — the dashboard. Notable modules:
  - `index.ts`, `create.ts`, `workers.ts`, `navigate.ts`, `layout.ts`, `hotkeys.ts`, `keybindings.ts`, `header.ts` — UI lifecycle and pane swapping. `keybindings.ts` is the single source of truth for the Meta-key hotkeys: `hotkeys.ts` binds each row into tmux and `garden keys` (`commands/keys.ts`) documents it, so a new hotkey is one row in `DASHBOARD_HOTKEYS` and the bound set can't drift from the documented one
  - `state.ts`, `registry.ts`, `validate.ts` — atomic state files + tmux/state reconciliation
  - `tmux.ts`, `window-names.ts`, `atomic-write.ts` — low-level helpers
  - `poller.ts` + `poller-state.ts` + `poller-{review,merge,resolve,ci,ci-fix,fifo}.ts` — per-project review/merge/resolve/ci-fix lifecycle, event-driven via FIFO. `poller-ci-fix.ts` mirrors `poller-resolve.ts` for self-healing red CI. When a reviewer's output reaches a conclusion but lacks a parseable `CLEAN`/`FIXED`/`FAILED` line (prose tail, markdown-decorated token, or verdict buried above a long test dump), `handleReviewing` first tries a cheap synchronous Haiku classifier (`verdict-extract.ts` `extractReviewVerdict`, 45s hard timeout, same first-party account as the reviewer) to recover the verdict before falling through to `handleUnparseableReview`'s re-review — default workflow only (trellis `DRIFT` carries a structured drift list a one-word extraction can't reconstruct). `launchReview` gates on `MAX_REVIEW_PROMPT_BYTES` (1MB) *before* launching: the prompt carries the whole branch diff inline, so a delta past any reviewer's context window is rejected by the agent CLI before the reviewer starts and no retry can help — the worker parks in `failing` with `failingReason: "oversized-diff"` and an alert naming the size and the remedy, instead of burning the retry ladder behind a generic "unavailable or unparseable output". Not kick-recoverable (an unchanged diff re-fails) and deliberately not an `OPERATOR_ACTION_FAILING_REASON` — reducing the branch diff changes the SHA and re-enters review through the normal failing debounce. The holistic pass (`poller-holistic-review.ts`) applies the same ceiling but leaves the worker `done` with a warn alert, matching that file's best-effort posture. Ceiling sized from measurement (median review delta 3-14KB, p95 88-155KB, largest observed 336KB across 160 commits of two repos; the motivating failure was 2.88MB)
  - `beads.ts` + `poller-intake.ts` — the bead-intake loop (board→garden delegation; board's `docs/DELEGATION.md` is the authority, DESIGN.md "Bead intake" the garden-side spec). `beads.ts` is the bd 1.0.3 shell-out client (cwd pinned to the project checkout — a worktree's `.beads` has no database); `poller-intake.ts` is a poller step (opt-in via `beadIntake: true`, cap via `beadIntakeCap`) that converts ready, dispatch-labeled beads into workers: frontier from `bd swarm status <epic> --json` (never the `--parent` family), modes/budget/spend via epic labels (`dispatch:manual|auto|off|dispatched|budget-exhausted`, `budget:N`, garden-written `dispatch:spent:N`), claim-as-worker idempotency (`BEADS_ACTOR=<worker-name> bd update --claim` post-spawn — 1.0.3's `--claim` never overwrites a foreign assignee, so the doc's `garden-pending` stack is routed around), a reaper for dead workers' beads (`dispatch:retry:N`), and a concurrency governor joined via bd assignee == registry name. Workers of opted-in projects get `BEADS_ACTOR`/`BEADS_DIR` injected (`beadsEnvExports`, `create.ts`) + sandbox write access to the canonical `.beads`. Throttled per-project on disk; `garden poke` bypasses and ensures a poller first; the watchdog keeps pollers alive for opted-in projects with zero workers and supplies the recurring `INTAKE_BEAT_MS` poke
  - `handoff-dispatch.ts` — request-file IPC the `garden handoff` CLI uses to spawn workers from inside a sandboxed worker pane; pollers process pending requests in their poll cycle. With `--expect-callback`, the dispatcher stamps parent linkage on the child entry so `transitionState`'s terminal-state chokepoint can fire a one-shot prompt back at the parent pane via `notifyHandoffCallback` (`continue.ts`) — with `handleDone`'s quiescent leg as the second dispatch site, since the Stop hook's trail-off `done` write bypasses `transitionState`; the child stages an optional reply via `garden reply`. With `--ultracode`, the child is created with the ultracode preset (Opus pin on `entry.model` + `entry.ultracode` → `--effort max` and the dynamic-workflow keyword trigger, rendered by the harness `buildAgentCommand` and threaded through spawn/resume/bounce)
  - `workflows/` — workflow registry (`default.ts`, `trellis.ts`, `grow.ts`, `botanist.ts`, `types.ts`, `index.ts`); see `WORKFLOWS.md`. `botanist.ts` is a design worker (deliverable is a doc, not code — Opus/xhigh designer seat, inverted worktree posture via the `src/rules.ts` botanist branch, reachable via `workers new --workflow botanist`; spec `docs/future/BOTANIST-WORKFLOW.md`). It sets `skipsReviewMerge: true` (the `WorkflowDefinition` flag), so the shared `handleWorking` routes it working → merge-pending directly with **no reviewer** (the operator reviewed the artifact at the human gate), after enforcing the committed diff stays under the publishable `docs/` boundary — a code-committing botanist parks in `failing` with `failingReason: "botanist-scope"`. The holistic whole-task review is NOT a workflow — it is one interposed reviewer pass on a completed default worker (`poller-holistic-review.ts`), not a spawned worker

Split registries: `core.ts` (light, safe for the hook bundle) vs `index.ts` (full adapter with `installRuntimeConfig`; CLI bundle only — its closure carries the skills/sandbox content). `codex-*` is the Codex adapter, reachable as a **reviewer/resolver/ci-fix** via `resolveReviewRole` (`roles.ts`) and as a **worker** via `workers new --harness codex` (default workflow only); its headless command splits stdout→result / stderr→sidecar (the verdict is on stdout, the token trailer on stderr). A Codex worker's lifecycle relay reuses garden's wire event names but is injected as `-c` overrides on the launch, not written as a `.codex/hooks.json` file (Codex resolves project hooks at the repo root, so a worktree file never fires); `installRuntimeConfig` instead seeds directory-trust in `CODEX_HOME/config.toml` + git-excludes, and the composed rules ride the worktree `AGENTS.md`. Both sides need it: `codex.ts` writes the composition, and `readDocSections` (`prompt-compose.ts`) undoes it, or a Codex worktree feeds garden's worker rules back into a reviewer prompt that already carries them. Session-id capture (the hook writes Codex's assigned id to `entry.sessionId` when empty), the `⌥h` history view (`readTurns`/`resolveTranscriptPath`), and the status pane's detail column (`readActivity`) now route through the Codex adapter. `readTurns` is held to the same contract for every harness — one assistant entry per operator prompt, summarized by what the turn DID rather than what the model said — so the Codex reader accumulates rollout activity between prompts and feeds `conversation.ts`'s `summarizeTurn`, mapping Codex's vocabulary onto the neutral tool names it reads and deriving Read/Grep from shell command text (Codex reads and searches by shelling out, and emits an `agent_message` per progress narration, so a reader that pushed each message verbatim produced a reformatted copy of the agent pane). Garden/handoff prompt-marker collapsing is shared by both readers via `promptTurn` (`conversation.ts`). `readActivity` is the optional core method that names a worker's activity for a harness whose terminal title carries no rolling summary — Claude Code rewrites its title as it works so it defines none and garden reads the pane title, while Codex's title items are metadata and counters only (its default `project-name` resolves to the worktree basename, i.e. the worker's own name), so the Codex core reports the step its newest `update_plan` is on, falling back to the opening prompt's first line. Defining it makes the harness authoritative: a null return means "keep the previous summary", never "read the pane title". Dispatch is `resolveWorkerActivity` (`harness/core.ts`), called from `applyAndLog` and both `refreshWorkerTasks`. Spec: DESIGN.md "Telemetry ledger"
  - `usage.ts` + `usage-poller.ts` — Claude quota meter (5h/week/model-scoped). **Two sources split by cadence** (mirrors Claude Code itself): the 5h + weekly bars come every poll from the `anthropic-ratelimit-unified-{5h,7d}-*` headers on a 1-token `/v1/messages` completion (`fetchUsageHeaders`→`parseUnifiedHeaders`; utilization is a 0..1 fraction, reset is epoch seconds) — the documented, generously-limited surface; the model-scoped bar (`fable`) + extra-usage credits come from the throttled `/api/oauth/usage` endpoint (`fetchUsageRaw`→`normalizeUsage`, gated by `scopedFetchDue`) — hourly **only while a scoped-model (Fable) worker is actively running**, else a slow 12h idle keepalive. The active check (`scopedModelInUse`, reading the registry) matches a live worker's effective model against the last-seen scoped labels (default `fable`) with a fresh `lastEventAt`, so an idle fleet stops pinging the endpoint for a 7-day figure that isn't moving. **Effective model is the model actually running, not `entry.model`** — that field records only an explicit pin, and an unpinned worker (the common case) runs the account default, which is routinely the scoped model itself; the gate resolves it per live worker from the newest assistant message in the transcript (`readLatestTranscriptModel`, `conversation.ts` — a bounded tail read, unlike `sumTranscriptUsage`'s whole-file parse; non-claude harnesses skip, since they spend no Anthropic quota) and falls back to the pin when one exists. Reading the pin alone reported "no scoped worker" for a fleet running entirely on Fable and pinned the bar to the 12h keepalive indefinitely — this is the load reduction that curbs the shared per-OAuth-token budget pressure that can collaterally 429 the primary `/v1/messages` probe. A scoped 429 never freezes the header bars (the primary bars are already live); it is surfaced as a dim `Fable meter rate-limited` health tag **only when a Fable worker was active** (`fetchScopedIfDue` gates the `scopedError` on that), staying fully silent during the idle keepalive. The primary probe's own 429 is labeled `account meter rate-limited` in the pane/log so the two sources can't be confused. `assembleSnapshot` folds both fetch outcomes + prior into the snapshot: `dataAt` tracks primary-bar freshness (drives the stale tag), `scopedAt`/`scopedAttemptedAt` track the scoped bar's freshness + cadence so it never trips the stale warning — instead the scoped row carries its own dim `· 11h old` age tag once it outlives its active cadence plus a margin (`SCOPED_AGE_TAG_AFTER_MS`, `formatScopedAge`), so a legitimately throttled row is distinguishable from a stuck one, and `scopedError` carries the surfaced scoped-fetch failure (cleared on the next scoped success). This replaced polling the throttled endpoint for all three bars, which chained hour-long freezes when fleet activity pushed request volume past the endpoint's ~10-12/hr budget. **Refresh is demand-driven with a timer floor**: the bars move only when workers spend tokens, so the Stop hook's `maybeRefreshUsage` is the primary lane (`HOOK_REFRESH_COOLDOWN_MS` 90s, deliberately *below* `POLL_OK_MS`) and the 10-min poller is the idle floor plus liveness backstop. Cost is bounded by the cooldown, not fleet size — the gate reads the shared on-disk snapshot's `fetchedAt`, so a fleet ending turns together produces one fetch, and an idle fleet spends nothing (its last reading is still true). `decideRefresh` applies the error backoffs to both lanes identically and they outrank the cooldown, so the demand lane is a healthy-path rule only and cannot route around a 429. `renderUsagePane` draws a second **Codex** meter in the empty space to the right once any Codex process has reported usage; its underlined column-label row is followed by one blank row so the first bars clear the underline: `codex-usage.ts` parses the `rate_limits` object Codex writes into its rollout JSONL (primary/secondary rolling windows + credits — same shape as Anthropic's; no new auth or endpoint, the data is already on disk). Capture is **role-agnostic** — `captureCodexUsageLatest` reads whichever rollout under `$CODEX_HOME/sessions` is newest by mtime, so a headless reviewer/resolver/ci-fix run meters exactly like a worker turn (a `claude-codex` crew spends Codex quota and fires no lifecycle hook, so the former Stop-hook capture keyed on the worker's `transcript_path` showed nothing at all). It is driven from the **watchdog** tick, the fleet's one unconditional recurring tick — the Anthropic usage poller is gated on `anyAnthropicMeteredProject()`, so an all-Codex fleet would otherwise never repaint. Codex emits `rate_limits` every turn but populates it only periodically, so both the backward line scan and the rollout choice skip all-null readings (`primary`/`secondary` null with an empty `credits` object is *not* a reading — treating it as one wrote an unrenderable windows-`[]` snapshot over a good one) and fall through up to `MAX_ROLLOUTS_TRIED` rollouts back. Reading the rollout is **passive** — only ever as fresh as the last Codex run — so `probeCodexUsage` is the active half: a minimal `codex exec` (read-only sandbox, temp cwd, stdin closed) made purely to force a quota report, the analog of the Claude meter's 1-token `/v1/messages` probe. It spends real quota, so every caller gates on `codexInFleet()` (any project with `harness: codex` or a `roles.*.harness: codex`, or any registered worker with a codex harness/crew). Call sites split by initiator: **ambient** ones go through `probeCodexUsageIfStale` (fleet gate + a 6h `CODEX_PROBE_INTERVAL_MS` snapshot-age gate) — the watchdog tick, and `garden dashboard _usage-refresh`, which is the Stop hook's usage lane (`maybeRefreshUsage`) rather than an operator command and so re-fires on that lane's 90s demand cooldown throughout active work; the **explicit** `garden usage refresh` probes outright (the operator asking is the reason), ahead of the `anyAnthropicMeteredProject` gate since Codex is a separate pool. A fleet actively running Codex is fed for free by the passive capture and never probes. `PROBE_TIMEOUT_MS` (30s) stays under the watchdog's `SLEEP_SLACK_MS` (60s) — the probe runs synchronously in the watchdog body, whose iteration overrun is read as machine-suspend time. `credits.balance` arrives as a STRING (`"0"`) and is coerced, not type-tested. Windows are labelled `5h` / `week` / `30d` and sort smaller-first (5h above 30d) to match Claude's ordering; a subscription account typically reports only the 30d (`window_minutes=43200`) window. Two-column layout is gated on Codex data existing, so a fleet that has never run Codex leaves the pane byte-unchanged — the gate is the on-disk rollout rather than the registry, so an operator running Codex outside garden sees the column too (intended: it is one quota pool).

  - `watchdog.ts` — liveness watchdog: recurring tick that recovers lost event delivery — re-pokes workers stranded in active states by a lost one-shot event, keeps each project's poller window healthy (respawns it if it died, collapses duplicates to one if a spawn race left several — resolving windows by index, since tmux name targets are ambiguous across duplicates), and alerts on orphaned worker windows (a live tmux worker window with no registry entry — the create/sweep race casualty; detection only, never reconstructs the entry). It also re-bakes the status pane each tick (`refreshStatusElapsed`, `header.ts`) so the time-in-state suffixes advance — the sole recurring driver of the otherwise event-driven status pane, content-deduped so an idle fleet never repaints. Transitions nothing (delivery-time and disk bookkeeping only).

Operator prompts are shown uncapped. (The view is "history"; the module parses the underlying conversation transcript.)

## Workers (worktrees)

Every worker runs in its own git worktree at `~/.garden/worktrees/<project>/<worker>/`, on a branch named after the worker, branched from `origin/<base>` (fetched first). Each project has a dedicated **poller** in a hidden tmux window that drives review/merge using local git — no GitHub PRs. Reviewers and resolvers run headless in hidden `_<project>-review-<worker>` / `_<project>-resolve-<worker>` windows. Multiple reviews run in parallel within a project; the merge queue is serial. Full state machine: `docs/STATUS.md`.

Per-phase review sees only one delta against base, so when a multi-phase **default** worker reaches `done` having merged `>= 2` times, the poller interposes ONE final review of the whole-task cumulative diff for cross-phase coherence defects before the worker truly finishes. This is NOT a spawned worker: it reuses the headless reviewer flow (`launchHeadlessAgent` + `resolveReviewRole`, so a Codex reviewer works) on the worker's own branch, re-opening `done` → `reviewing`. Gated per-project by `holisticReview: off|shadow|fix` (default `fix` — `DEFAULT_HOLISTIC_REVIEW` in `config.ts`; `shadow` reports findings as an alert, `fix` fixes cross-phase defects directly and rides the normal CI/merge gate — the deliberate-decision guardrail is folded into the reviewer prompt; a project opts out with an explicit `off`/`shadow`). Spec: `WORKFLOWS.md` § "Holistic-review workflow"; `garden dashboard _holistic-backtest` replays it read-only against a past worker.

Worker prompt is `rules.md` (global) + `<project>/.garden/rules.md` (project) + per-worker preamble built by `buildWorktreeRules` in `src/rules.ts`. The preamble names the project's configured `checks` command (from `garden config <project> checks`) so the worker, the reviewer, and CI all gate on the same string — keep that command aligned with `.github/workflows/test.yml` or you reintroduce the asymmetry that caused workers to push broken state and CI to email "Run failed" on every commit. Workers and reviewers run it via `garden checks`, which executes exactly that string under the machine-wide checks semaphore (see DESIGN.md "Project Configuration" → checks) so overlapping suites queue instead of stampeding the workstation; CI runs the raw command ungated on its own runner. Worker panes start in `permissions.defaultMode: "auto"` inside an OS sandbox (Seatbelt/bubblewrap) configured by `sandbox.ts`. Workers commit and push autonomously — no operator confirmation; the poller handles review and merge.

## Dashboard internals

Permanent tmux layout — content is moved between visible slots and **hidden underscore-prefixed windows** (`_<project>-worker-N`, `_<project>-shell`, `_<project>-poller`, `_garden-{growhouse,root,logs,history,diary,alerts}`, `_garden-usage-poller`, `_garden-watchdog`) via `tmux swap-pane`. Pane slots are never destroyed.

The title and status panes are passive: keyboard input, mouse selection, and wheel scrolling are disabled. The lower growhouse slot retains normal interaction for its active view.

- **Left column**: `garden` title pane (Claude quota meters), `status` pane (per-project worker list), and `growhouse` pane (cycles `⌥g` growhouse / `⌥r` root / `⌥l` logs / `⌥h` history / `⌥d` diary / `⌥a` alerts). Title and status panes refresh via SIGUSR1, replaying pre-baked files written atomically. Each project header row in the status pane carries a dimmed pencil `✎` when its diary holds non-whitespace content (`diaryHasContent` in `src/diary.ts`, stat-cached on mtime+size to stay off the refresh hot path; `formatDiaryGlyph` in `src/commands/status.ts`). Worker rows are ordered by attention/recency, not name — `compareWorkerFreshness` (`registry.ts`) sorts by tier (blocked-on-you → new/`ready` → active → in-flight → `done`; the bands descend a worker's life toward merge, so `reviewing`/`merging` sit below `working`, above `done`), then freshness (`workerSortFreshness` = `lastStateChangeAt ?? lastEventAt ?? createdAt`, 60s-bucketed to avoid jitter), then name; the same comparator drives the `⌥]`/`⌥[` cycle and `whoami` siblings. Ordering keys on `lastStateChangeAt` (the last real `agentStatus`/`prState` transition, stamped by `applyAndLog` on an `agentStatus` change and by `transitionState` on a `prState` change — never on the 10s heartbeat), NOT the raw `lastEventAt`: the 10s hook heartbeat bumps `lastEventAt` without repainting the status pane, so ordering by it let rows drift silently and snap on the next navigation-triggered repaint. `lastEventAt`/`workerFreshness` still drive the 24h stale-dim (`isWorkerStale`) — that wants heartbeat liveness. Active-band rows untouched >24h (`isWorkerStale`) render faint via `dimRow` — except the operator-held `paused`, which keeps its bold-cyan mark. In-flight/blocked rows (`reviewing`/`merge-pending`/`resolving`/`ci-fixing`/`asking`/`failing`) fold a dim time-in-state elapsed into the state cell (`reviewing 12m`, `asking 2h`) computed from `lastStateChangeAt` by `formatTimeInState` (`src/commands/status.ts`), yellow past a soft per-state expectation (the otherwise-uncolored pipeline states only; `asking`/`failing` stay dim since their row is already colored). It rides the same pre-baked-file path, so the watchdog's 60s tick re-bakes it via `refreshStatusElapsed` (`header.ts`) — the one recurring driver of the otherwise event-driven status pane — content-deduped so an idle fleet never repaints. The row grammar splits identity from status (`collectSegments`/`renderWorkerRow`, one path for CLI + baked): the description (detail) comes first after the state, and the whole grey override-only identity cluster — base `→ <base>`, per-worker crew (supersedes member), member/harness, and the **model** tag — trails *after* the detail as ragged tags, so nothing sits between the state and the description (operator call, 2026-07-16); the cluster costs width only on the rows that carry it and drops as a unit on a narrow pane. A detail shortened to fit the pane ends in `…`; the marker consumes one of the available columns, so the row remains within its width cap. Workflow self-identifies via `workflowRowDecor` — grow shows `grow N/M` and a vine its `[trellis: …]` bracket in the detail slot; a botanist takes a grey `botanist` badge in the identity cluster instead, leaving the detail slot to its live activity. Status-class flags (CI bracket, `gate closed`) never truncate. A `failing` worker whose agent is mid-turn (`isFailingBusy` — prState `failing` + agentStatus `working`, i.e. the operator prompted it about the failure) swaps its `✖` for the braille spinner and keeps everything else red and `failing`; the plot strip mirrors it with a `failing-working` state (red spinner), which tracks the failing worker specifically — a plot whose failing worker is parked stays a static `✖` even while siblings work. The **state column** is sized to the widest state cell actually on screen (`computeStatusWidth`, floored at `STATUS_MIN_WIDTH`), like the name column — so a fleet of short `done`/`idle` rows isn't padded to the 13 cols only `reviewing 12m` needs (the old dead space between state and description); it widens when a worker enters an elapsed-bearing state and tightens again when it clears. Each header also carries a yellow per-project `⚠n` unread-alert count (`unreadAlertCountsByProject`, cleared globally on `⌥a`). See DESIGN.md "Worker row grammar" + "Worker row ordering". The `⌥h` history view shows the focused worker's prompt history (operator prompts + brief verb-tagged assistant summaries), read from the worker's Claude transcript JSONL by `conversation.ts` and painted via the same pre-baked-file + SIGUSR1 path; `writeHistoryRendered` (`header.ts`) only parses the transcript when history is the active garden mode, keeping it off the hook firehose. The `⌥a` alerts view is the same shape (`writeAlertsRendered` + `renderAlertsPane` in `commands/alerts.ts`), and is the one place alerts are marked read — it acks on entry, but splits unread/read on `state.alertsSeenMark`, the pre-ack seen-time snapshotted on entry, so the view still shows what was new while the badges clear; pressing `⌥a` again re-snapshots, folding them into read. Unlike history it is deliberately NOT baked from `refreshDashboard` (that call sits in `dist/hook.js`'s closure and would pull the renderer into the lean hook bundle — measured +2.8KB vs +260 bytes tree-shaken); its CLI-bundle drivers are `focusAlerts`, the watchdog's `refreshStatusElapsed` tick, and `rebakePanesOnResize` when a terminal resize changes the wrapping width.
- **Right-pane clock**: the right pane (worker or project shell) shows a `%H:%M` clock in the right corner of its top border (mirroring the `garden` title in the top-left). The shared `pane-border-format` carries a right-aligned, bold-green segment (matching the `garden` title, capped with border dashes to the corner) gated on the `@garden_clock` pane var, set on worker panes and the right-pane shell (not the left-column garden shells); tmux strftime-expands it on each `status-interval` tick — no extra process or poll. Keep the style comma-free (`#[fg=green]#[bold]`) — a comma in the `#{?…}` conditional blanks the clock.
- **Project color dot**: the right pane's top border prefixes the worker/shell label with a `●` in the project's `logColor` (palette of 256-color indices in `src/log-palette.ts`; `logColorAnsi` / `logColorTmux` derive the ANSI and tmux renderings) — the border names the worker, never the project, so the dot is the pane's only project marker. Gated on the `@garden_color` pane var (`colour<N>`), set by `setPaneProjectColor` (`header.ts`) everywhere `@garden_clock` is applied; the format nests `#{@garden_color}` inside `#[fg=…]`, which tmux expands before parsing the style. Deliberately not echoed in the status pane or bottom bar — those already name the project in text.
- **Logs sticky filter**: `⌥/` opens `tmux command-prompt` (pre-filled with the current filter); `⌥.` clears it instantly. The typed expression persists in `~/.garden/sessions/logs.filter.json` and is honored by both the dashboard logs pane and bare `garden logs` until cleared. Syntax: `key:value` for `worker`/`src`/`level`/`project` plus bare fuzzy tokens. CLI escape hatch for metacharacter-bearing exprs: `garden logs filter <expr>` / `--clear`.
- **State of record**: registry (`dashboard.registry.json`) for workers, state file (`dashboard.state.json`) for UI runtime, alerts file for operator-visible issues. Tmux is the source of truth for pane existence; `validate.ts` reconciles on attach.
- **Status**: hooks write `agentStatus`, the poller writes `prState`, `pane-died` writes `agentStatus="exited"`, and the operator `hold` action (`⌥e` / `garden hold`) writes `agentStatus="paused"` (a raw Escape interrupt fires no hook). One deliberate crossover rides that split: a mutating tool call (Edit/Write — not Bash, so a read-only Q&A turn is free) landing while the worker's review is in flight stamps `entry.reviewInterruptedAt` on the hook side, and the poller cancels the pass — kills the reviewer window, discards any verdict (the reviewer shares the worktree, so it certified a tree being rewritten under it), resets to `working` with the review re-armed for the next Stop. Holistic passes cancel the same way. Event-driven; the only recurring tick is the liveness watchdog (`watchdog.ts`, `_garden-watchdog` window), which re-pokes projects whose workers sit in active states past a 5 min staleness threshold, keeps each project's poller window healthy (respawning a dead one, collapsing duplicates a spawn race left), and alerts on orphaned worker windows (a live tmux worker window with no registry entry) — it recovers lost event delivery or surfaces a casualty and never transitions state. Spec: `docs/STATUS.md`.
- **Auto-continue**: `continue.ts` re-prompts after interrupt (mid-turn dashboard kill / tmux crash / bounce-while-working) and after a clean merge (with the list of files changed during review). Worker opts out by writing `.garden-done` in its worktree root before ending its turn. `garden pause` / `resume` toggle the sentinel; `UserPromptSubmit` clears it. A worker whose continue prompt was blocked (global gate closed, or paste lost) parks in `merged`; the merged-state handler (`handleMerged`, `poller-merge.ts`) replays the auto-continue decision on every poke — the gate-reopen sweep — so the prompt lands on the first poke after the gate reopens. A gate-closed strand is surfaced three ways: the status pane appends a yellow `gate closed` suffix to the `merged` row (`formatGateSuffix`, `status.ts`), `garden whoami` prints the gate state (`auto-cont.` line, on/OFF + pause reason), and the sweep logs gate blocks at info. The intended in-memory per-worker throttle resets with every one-shot poll process; but the info line can appear once per poke. The gate's usage-triggered closures are per-project (see the auto-continue gate bullet under CLI surface): usage-exempt projects auto-continue through them, so their rows never show the suffix and their `whoami` line reads `on` with a separate-token-pool note — only an explicit `garden auto off` closes the gate for everyone. Before pasting, `continueWorker` also defers when the operator has an unsent draft in the worker's Claude input box (`capturePaneText` + `capturePaneCursor` + `extractOperatorDraft`) so an auto-continue can't be concatenated onto a half-typed message. The draft is the span between the `❯` prompt marker and the cursor column — Claude Code paints dimmed ghost/placeholder text into an *empty* box and `capture-pane` strips the dimming, so the marker-to-cursor bound (not the bare post-marker remainder) is what tells a real draft from a suggestion. The two primary dispatch legs re-arm a bounded 12s backoff (`rearmContinueIfDrafting`, `--attempt N`, capped at 15) until the box clears.
- **Post-merge**: advance the local base to the merged tip — `merge --ff-only` when it's the checked-out branch (also moves the working tree, so `postMerge` runs), else `git fetch origin <base>:<base>` to advance the ref alone (the many-base workflow: checkout parked elsewhere, ff-enforced + worktree-aware, postMerge skipped, silent). Then notify live siblings whose files overlap. A clean advance never alerts, and a redundant local commit whose clean tree already matches origin is auto-healed silently (`reset --hard origin/<base>`, reflog-preserved). `postMerge` is prevented from dirtying the checkout itself (`revertPostMergeChurn`, `poller-merge.ts`): tracked files the hook modified that were clean before it ran are restored, closing the trap where `npm install`'s package-lock churn eventually collides with a merged dependency bump, blocks `merge --ff-only`, and so skips the very hook that would clean it — freezing the checkout and the binary built from it. Operator edits already in flight, untracked files, and staged changes are never touched. Of the rest, `diverged`/`checked-out-elsewhere`/`dirty` warn (the operator's own checkout state, merge already on origin; the `dirty` alert names how far behind origin the checkout has fallen) and `stuck` — fetch failure or a wedged checkout — errors. The base checkout is the operator's shared working directory, not a pristine mirror, so all four are expected; each alert fires only on *entry* into the state, not every merge cycle (a diverged/dirty checkout would otherwise re-alert on every sibling merge). See `fastForwardBase` (`git.ts`) and `notifyPostMerge` (`poller-merge.ts`).
- **CI gate**: before each merge, `handleMergePending` queries `gh api repos/<owner>/<repo>/commits/<sha>/check-runs` (see `src/dashboard/poller-ci.ts`). Pending defers the merge (60 s recheck); failure dispatches a self-healing ci-fix agent (see `src/dashboard/poller-ci-fix.ts`, `_<project>-ci-fix-<worker>` hidden tmux window, budget 3 attempts per merge cycle). The agent reads `gh run view --log-failed` output, makes the minimum fix, and pushes — the gate then re-runs against the new SHA. Launch and success are routine lifecycle beats — logged (visible in `garden logs`) but not raised as operator alerts; only budget exhaustion alerts (error level), parking in `failing` with `failingReason: "ci"` for a genuinely red CI, or the kick-recoverable `failingReason: "transient-review"` when the agent only hit transient backend outages or a usage-quota cutoff. The gate passes through on projects without a GitHub remote, without `gh` installed, with `requireCiSuccess: false`, or with zero check-runs on a project with no CI; on a project that has CI, zero check-runs on a freshly force-pushed SHA are treated as not-yet-materialized and the merge defers within a bounded grace window (3 min) before passing through. **The grace stamp and the 60s-recheck dedup marker both live on disk** (`WorkerEntry.ciNoRuns`, keyed by SHA; a mtime-stamped `ci-recheck-<project>` file in `SESSIONS_DIR`) because the poller loop execs a fresh process per poll — as module-level Maps the stamp was re-created as "now" every poll, so the elapsed check measured ~0 ms and the merge deferred forever, and the poke dedup never fired, so each poke during the stall spawned another sleeper that poked again. That pair stranded two wolf workers in `merge-pending` for 5.5 h behind 43 orphaned sleepers on 2026-07-21. Any state a poll must remember belongs on disk, not in a module Map. "Has CI" reads `.github/workflows/*.yml`/`*.yaml` on disk first (`projectDefinesCi`, `poller-ci.ts`), falling back to a check-run observed earlier in this poller's life — the disk read is what makes the grace window reachable at all, since the in-memory flag could only be set by an observation the materialization race hides, leaving the gate silently open after every poller restart. This is defense-in-depth against GitHub's branch protection — the poller's force-push path bypasses the merge UI, so branch protection alone can't catch a red CI.

## Conventions

- **JSON when piped, pretty in TTY** — use `output()` / `outputLines()` from `src/output.ts` for all data output.
- **Project resolution** — use `resolveProject()` / `resolveProjectFromArgs()`. Never parse names manually. Auto-detected from cwd inside a registered project.
- **Bash escaping** — every value interpolated into a generated shell command goes through `shellEscape` (`src/dashboard/tmux.ts`). It returns a fully single-quoted bash literal — use the result without surrounding `'...'`. No inline `.replace(/'/g, "'\\''")`.
- **Atomic writes** — every persisted state file goes through `atomicWriteFile` (`src/dashboard/atomic-write.ts`). Readers pair this with an `is{ShapeName}` type guard before trusting parsed JSON. See `readDashState` / `readRegistry` / `readAlerts`.
- **Dashboard windows** — every window created in `DASHBOARD_SESSION` goes through `newDashboardWindow` (void) / `newDashboardWindowPaned` (returns the pane id) in `src/dashboard/tmux.ts`, which suppress the window name at creation. There is no global `window-status-format` default, so a raw `tmux("new-window", …)` leaks the window name into the status-bar center strip (`setupStatusBar` only blanks the `main` window).
- **Alert dedup** — `addAlert` (`src/dashboard/alerts.ts`) suppresses identical-key alerts within a 1-hour window. Default key is `${level}:${source}:${project}:${worker}:${message[:200]}`. When a message embeds time-varying detail (SHA, error string, file list), pass an explicit stable `dedupKey`.
- **Specs** — files containing the marker phrase **"the code is wrong"** in their opening paragraph are specs. The reviewer prompt-prepends a strong warning never to edit a spec to match the code. If the code disagrees, fix the code.
- **Tests** — `npm test` runs unit + integration (`test/integration/**`); the bundled-hook test catches module-init cycles vitest's source resolver misses. Don't move integration tests behind a flag. Both configs load `test/setup-home.ts`, which pins `HOME` to a throwaway dir for every test: the operator's workstation has a real `~/.garden`, a CI runner does not, so a test that reads the live config would otherwise pass locally and fail only on CI (how `resolveReviewRole`'s unconditional `loadConfig()` shipped a red main). A test needing its own writable garden uses `useTmpHome()` (`test/helpers.ts`); nothing should read the real one.

## Adding a new command

1. `src/commands/<name>.ts` — export an async `(args: string[]) => Promise<void>`
2. Register in `src/commands/index.ts`
3. Add to the help text in `src/cli.ts`
4. Use `output()` and `resolveProject*()` per Conventions

## Adding a new workflow

See `WORKFLOWS.md`. Short version: define a `WorkflowDefinition` in `src/dashboard/workflows/<name>.ts`, register in `workflows/index.ts`, reuse `default.ts`'s state handlers and `defaultHookHandlers` wherever possible. Tests: `test/workflows.test.ts` + an integration test on real fs/git. Two concrete examples in the registry: `trellis.ts` (full-spec divergence — own reviewer prompt, verdict vocab, model pinning, post-merge dispatch) and `grow.ts` (minimal divergence — reuses default's reviewer/verdicts/hooks; only the iteration counter and post-merge dispatch differ). If your workflow shares the cold-respawn-per-iteration mechanics, supply a `LoopHooks` instance (see `src/dashboard/loop.ts`) instead of forking the dance.

**Per-workflow runtime data** (the trellis pattern). Anything the workflow accumulates per worker goes under an optional sub-object on `WorkerEntry`, not as flat fields — `entry.trellis?: TrellisData` and `entry.grow?: GrowData` are the two concrete examples (`registry.ts`). `updateWorkerFields({ <subObject>: { <field>: ... } })` deep-merges that sub-object so callers don't clobber sibling fields. Add a legacy-shape migration to `readRegistry` so on-disk entries from earlier shapes get rebuilt at next read. Don't add flat per-workflow fields to `WorkerEntry`; the flat-fields path was deliberately removed (the migration in `readRegistry` exists to scrub stragglers from old on-disk entries).

## Adding a new harness

See `docs/MULTI-MODEL.md` "Layer 3". Short version: implement `HarnessCore` in `src/dashboard/harness/<name>-core.ts` (command dialects, prompt delivery, transcript reader, transient-error shapes — keep its import closure light; it is reachable from `dist/hook.js`), add `installRuntimeConfig` in `harness/<name>.ts`, and register in both `harness/core.ts` and `harness/index.ts`. Registering makes the harness a crew **member** and so a `⌥⇧N` build-dim choice for free — but the composer's **model and effort vocabularies** are per-harness and do NOT follow: `composerModels`/`composerEfforts` (`trellis-picker.ts`) branch explicitly, so an unhandled harness silently offers the Anthropic aliases and the claude-code effort rungs. Add a branch (see `codex-models.ts` for the read-the-harness's-own-catalog shape, fallback-list included) or the operator picks names the new harness cannot run. A new **provider** needs none of this — it is config, not code: `garden provider add` makes it a member and its `modelMap` keys become its model vocabulary automatically (`providerModelAliases`). A harness without a turn-end signal cannot be registered — `capabilities.turnEnd` is typed `true` because STATUS.md's no-polling invariant is preserved by refusing such harnesses, not polling around them. The event side: translate the harness's native lifecycle onto the normalized `WorkflowHookHandlers` methods (`onTurnEnded` etc.) — for claude-code that translation is `hook-dispatcher.ts`'s wire-name switch. Check what the harness's terminal title says while it works: if it is not a rolling summary of the agent's activity, implement the optional `readActivity` too, or the status pane's detail column shows whatever the title happens to be (for Codex that was the worktree basename, i.e. the worker's own name). `readTurns` owes a **summary**, not a transcript dump: accumulate activity between operator prompts and flush ONE assistant turn per prompt through `summarizeTurn` (`conversation.ts`), mapping the harness's tool vocabulary onto the neutral names it reads — and route operator prompts through `promptTurn` so garden's own continuations collapse to markers. A reader that emits one turn per assistant message produces a worse-formatted copy of the agent pane.
