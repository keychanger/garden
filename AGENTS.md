# Garden

Garden is a CLI orchestrator for managing interactive Claude Code sessions across multiple projects via a tmux dashboard.

**This file is the project's agent instructions, for every harness.** `CLAUDE.md` is a one-line `@AGENTS.md` import, so Claude Code and Codex read this one file (DESIGN.md "Agent instruction files"). Edit this file; never keep a second copy in `CLAUDE.md`.

**This file is the map, not the territory.** It loads into every Claude/Codex session in this repo, so it holds the module map, the conventions, and the "Adding X" checklists; behavior, rationale and incident history live in the docs below. When something here disagrees with one of these, the spec wins:

- `DESIGN.md` — full architecture
- `rules.md` — coding rules loaded into every Claude session (commit/test/scope discipline)
- `WORKFLOWS.md` — workflow registry design, "how to add a new workflow", and workflow specs
- `docs/STATUS.md` — worker status state machine (spec)
- `docs/MULTI-MODEL.md` — multi-model / multi-harness architecture and phase status
- `docs/SANDBOX-THREAT-MODEL.md` — what the worker sandbox enforces, and the open items
- `docs/TRACKS.md` — multi-track / promotion pipeline (design target, no code yet)
- `docs/` — additional design docs and behavioral specs; see `docs/README.md` for the index

## Build and run

Fresh-machine setup is in `README.md`. Use Node 22.12+ (22.x) or 24+,
`npm ci --include=dev`, then build, link, and initialize. `garden doctor` checks
Git, tmux, Claude Code, and the supported Node range before project setup.

```bash
npm install
npm run build          # esbuild → dist/cli.js + dist/hook.js
npm run dev -- help    # tsx during development
npm test               # vitest unit + integration; tsc --noEmit
```

`npm link` makes `garden` global; `npm run build` is all a change needs, and the live fleet picks it up with no restart (DESIGN.md "Build and deploy"). `dist/hook.js` (from `src/hook-entry.ts`) runs on every tool call: `hook-bundle.real.test.ts` caps it at 144KB and keeps the workflow registry and poller handlers out of it; raise the ceiling with a recorded reason rather than trim unrelated code. `"sideEffects": false` lets esbuild tree-shake it, so modules must stay free of import-time side effects — only `cli.ts` and `hook-entry.ts` execute at top level. Check a module's `bytesInOutput` in esbuild's metafile before assuming it is outside the bundle.

## Workers

Every worker runs in its own git worktree at `~/.garden/worktrees/<project>/<worker>/`, on a branch named after the worker, branched from `origin/<base>`. Each project has a dedicated **poller** in a hidden tmux window that drives review and merge with local git — no GitHub PRs. Reviews run in parallel; the merge queue is serial and merges only the SHA cleared for it. Full state machine: `docs/STATUS.md`; pipeline: DESIGN.md "Poller and Auto-Merge", "Merge Handling".

The worker prompt is `rules.md` + `<project>/.garden/rules.md` + the per-worker preamble from `buildWorktreeRules` (`src/rules.ts`), which names the project's `checks` command: keep it aligned with `.github/workflows/test.yml`, since the worker, the reviewer and CI all gate on that string. Workers commit and push autonomously; worker panes run in auto permission mode inside an OS sandbox (DESIGN.md "Worker Isolation Model").

## Conventions

- **JSON when piped, pretty in TTY** — use `output()` / `outputLines()` from `src/output.ts` for all data output.
- **Project resolution** — use `resolveProject()` / `resolveProjectFromArgs()`. Never parse names manually. Auto-detected from cwd inside a registered project. `tryGetProject` / `detectProjectFromPath` answer "no project" only for an unconfigured project or an uninitialized garden; a `config.yml` that exists but does not load throws `loadConfig`'s error, which names the file and the YAML fault, rather than reading as an unknown project (the watchdog also raises it as an error alert).
- **Bash escaping** — every value interpolated into a generated shell command goes through `shellEscape` (`src/dashboard/tmux.ts`). It returns a fully single-quoted bash literal — use the result without surrounding `'...'`. No inline `.replace(/'/g, "'\\''")`.
- **tmux text** — tmux expands `#` sequences in menu titles, item names and commands, `display-message` text, `run-shell` commands and `command-prompt` pre-fills, and a `#(...)` there runs a shell command as the operator, outside every sandbox; shellEscape does not stop it, because tmux expands before the shell parses. Text garden did not write (branch names, registry fields, file contents, errors) goes through `tmuxLiteral` before it reaches one of those slots. `buildMenuArgv`, `menuRunShell` and `tmuxDisplay` already do it; typed input goes through `promptArgv` / `promptCommand` (the reply reaches the route as one argument), never `%%` inside a `run-shell`. `test/integration/tmux-literal.real.test.ts` checks each against a real tmux client.
- **Running git** — garden's git runs unsandboxed, as the operator, usually inside a worker's worktree. Use `git.ts`'s helpers or `runGit` (`git-exec.ts`), which run with hooks and fsmonitor off and with `--no-optional-locks` (a plain `git status` takes `index.lock` to write back the stat data it refreshed, and garden reads worktrees while their worker, reviewer or resolver commits there, whose own lock then fails) and replace refs ignored (`GIT_NO_REPLACE_OBJECTS=1`, which the bootstrap also exports and every headless agent inherits: a worker can write `refs/replace/<sha>` into the shared refs); never `execFileSync("git", …)` against a worktree, where `.garden-hooks/` is worker-writable. `operatorGit` keeps the repository's hooks and is only for commands on the operator's own checkout. Name origin's branch in full (`remoteBranchRef`, and `branchRef` for refspecs) — an abbreviated `origin/<base>` resolves through git's lookup order, where a same-named tag or branch in the shared refs store comes first — but where the answer decides what garden *pushes to the base branch*, *advances the operator's checkout to*, or *installs from with package scripts on*, do not read a remote-tracking ref at all: those live in the shared git dir every worker sandbox can write, so `mergeToBase`, the merge queue's rebase (`handleMergePending`), `fastForwardBase`, the worker bootstrap (`baseShaStep`, `create.ts`) and resurrect's origin-base start point ask origin itself (`remoteTipSha`, over `ls-remote`) and act on the SHA it reports. A SHA start point carries no upstream, so those two worktree-creating sites restore it explicitly (`createWorktree`'s `track`) — the worker rules have every worker check `git log @{u}..HEAD` — and neither acts on a commit the object store lacks: the bootstrap aborts with a reason rather than falling back to the ref it is distrusting, while resurrect degrades to the local ref with the install skipped, since it is the emergency-recovery command and an unreachable origin is when it is most needed. All of this assumes `remote.origin.url` is fixed, which is true only where `.git/config` is write-denied — not for a Codex worker, whose git grant includes it (`docs/SANDBOX-THREAT-MODEL.md`) — and pass only commit SHAs, `HEAD` or full refs as revisions: the range helpers refuse anything else, so a registry value cannot reach git as an option (`--output=<path>` makes `git diff` write a file). Read a branch name back from its full ref (`symbolic-ref`, `%(refname)`), never `--abbrev-ref` or `%(refname:short)`, which answer `heads/main` once a tag named `main` exists. Parse path lists from `-z` output. Garden needs Git 2.30 for `rev-parse --end-of-options`; `reset` rejects that flag before 2.44, so it takes `<ref> --` instead. A base branch is validated (`isValidBranchName`) where it enters: `--base`, `garden config baseBranch`, the menus, and `resolveSpawnBase`. Read a worker's files from the commit (`readCommittedFiles`) or through `readStableRegularFile`, never with a plain `fs.readFileSync` from an unsandboxed process. See `docs/SANDBOX-THREAT-MODEL.md`.
- **Transactional shared state** — every persisted state file goes through `atomicWriteFile` (`src/dashboard/atomic-write.ts`), which flushes the temp file before rename and the parent directory afterward for durable writes, and every read-modify-write holds the corresponding cross-process lock. Config writers use `mutateConfig`; conditional registry writers use `updateWorkerFieldsIf` or `mutateRegistry`; worker creation uses `addWorkerWithUniqueName` so name allocation and insertion share one registry snapshot; dashboard pane changes use `withStateLock`. `file-lock.ts` stamps each lock with a PID plus a unique owner token, never age-evicts a demonstrably live holder, and removes a lock only when the token still matches. A lock is reclaimed unless its pid actually answers the liveness probe: only `EPERM` proves a holder exists (another user's process), so pid 1 or below, a pid past the OS range — which `kill(0)` refuses with a type error rather than `ESRCH`, and which a forged body used to step around the pid-1 rule by writing a longer number — and any other unnameable pid all read as dead. A parsable holder is never age-evicted, so reading one of those as alive held the lock forever. A pid that answers is still not the holder when `ps` reports its process started more than 30s after the lock was written: the holder died and its pid was handed out again (`pidStartedAfter`, shared with checks slots). A caller `ps` refuses, as inside a worker sandbox, keeps the pid's answer. `transitionState` validates and applies the current-state move in one registry transaction; invalid edges are rejected, with `forceTransitionState` reserved for explicit recovery paths. Readers pair persisted JSON with an `is{ShapeName}` type guard before trusting it. See `readDashState` / `readRegistry` / `readAlerts`. A registry enum such as `prState` is guarded by type, not membership, on purpose: a value this build does not know (a newer build's state read after a rollback, a hand-edit, a worker's write) is kept as written and its consumers skip that one worker (`pollWorker`, `isWatchedState`, `hasLiveWork`). Rejecting it would drop a live worker's entry, which the next write makes permanent; tightening the guard to a union check reintroduces exactly that.
- **Per-cycle worker fields** — the `WorkerEntry` fields that live for one review, resolve or ci-fix cycle are cleared by spreading a named set from `src/dashboard/cycle-resets.ts` (`FRESH_REVIEW_CYCLE`, `FRESH_RESOLVE_CYCLE`, `FRESH_CI_FIX_CYCLE`, `CLEAR_HOLISTIC`) into the transition, never by a hand-written `field: undefined` list, and a new per-cycle field goes into its set once. The per-site lists had drifted: the one-shot unparseable-verdict marker outlived worker pushes, edits, timeouts and failing parks, so the next cycle's first unparseable verdict went straight to `failing`. `test/cycle-resets.test.ts` fails on a hand-written clear of a set member. A site that sets one member itself spreads the set first.
- **Review environment recovery** — headless Claude launches regenerate protected `<promptFile>.settings.json` sidecars from current project config, preserving interactive worker settings. Claude temp grants include canonical `/tmp` and `os.tmpdir()`. After repairing test permissions, inspect `garden review <worker>` and use `garden kick <worker> --retry-review` to requeue a failed default review whose recorded tip matches its failing SHA. Active worker turns are refused; the failed report remains, and a full fresh review and normal merge gates are required. No empty commit or fabricated pass is needed.
- **Trusted vs. worker-writable state** — `~/.garden/sessions` is inside every worker's sandbox write grant (claude-code's `DEFAULT_ALLOW_WRITE` in `sandbox.ts`, Codex's `writable_roots` in `codex-core.ts`), so it holds worker request IPC and nothing a worker must not be able to forge. Control-plane files live under `~/.garden/control`, which no sandbox grants: reviewer/resolver/CI-fix prompts, results, fresh Claude settings, and harness stderr sidecars under `control/headless`, durable holistic reports under `control/reports`, and the per-directory Claude settings files (hooks, sandbox, status line) interactive Claude launches load with `--settings` under `control/claude-settings` (`claudeSettingsPath`) — outside the worktree so a worker cannot edit its own sandbox. So do the files an unsandboxed process runs or hands an agent as instructions: worker bootstrap and dashboard pane scripts under `control/scripts`, system-prompt context files under `control/contexts` (`contextFilePath`, keyed like the settings), and seed prompts under `control/seeds` (`writeSeedFile`/`readSeedFile`, `seed-files.ts`; `seedWorker` reads only through the stable regular-file reader, and accepts `SESSIONS_DIR` only for seeds an older build wrote there). The quota snapshots the auto-continue gate and the usage pane act on (`claude-usage.json`, `codex-usage.json`, the Codex probe stamp, and their locks) and the V8 compile cache the unsandboxed hook loads (`control/node-compile`) are control files as well; the snapshot readers still shape-check what they read (`isUsageSnapshot`, `isCodexUsageSnapshot`), so a malformed one reads as absent. What must stay in `sessions` is opened defensively: the pokers never block on the poll FIFO and write it only after confirming the descriptor they opened is a FIFO (`triggerProjectPoll` also refuses to open through a link; a shell cannot, so `fifoPokeShell` checks the path first and the descriptor again). Every poke garden itself runs goes through one of those two — `pollSignalSnippet` (`create.ts`), the headless-agent window, and the detached `scheduleDelayedPoke` timer all compose `fifoPokeShell`, so none can regress to the blocking `echo > fifo` form that stranded orphaned shells. The worker's own `.garden-hooks/pre-push` keeps the plain `echo` form deliberately: that hook is the worker's file and runs sandboxed as the worker on its own push, so following a link it planted writes a newline only where its sandbox already allows, and garden never runs it (`runGit` sets `core.hooksPath=/dev/null`). `ensureSignalFifo` also replaces a directory planted at the path, which `unlink` refuses and which made `mkfifo` fail in a way that stalled that project's poller, and so its whole review and merge pipeline. The usage snapshots' locks live in the control tree beside the snapshots (`USAGE_LOCK`, `CODEX_PROBE_LOCK`), as do the poller and watchdog spawn locks (`pollerSpawnLockPath`, `WATCHDOG_SPAWN_LOCK_FILE`), since `withFileLock` waits out any lock naming a live pid: one planted in a worker-writable dir would freeze the meter, hold off every ambient Codex probe, or stall every poll. The bead-intake throttle and error stamps (`intake-paths.ts`) and worker-cleanup requests with their locks (`workerCleanupMarkerPath`) are control files too. A new headless-agent role takes its paths from `src/dashboard/headless-paths.ts` (which also bounds unsafe or oversized project/worker names to a SHA-256 component) rather than composing a fresh `path.join(SESSIONS_DIR, …)`. The registry itself is still in `sessions` — see `docs/SANDBOX-THREAT-MODEL.md` for that open item.
- **Dashboard windows** — every window created in `DASHBOARD_SESSION` goes through `newDashboardWindow` (void) / `newDashboardWindowPaned` (returns the pane id) in `src/dashboard/tmux.ts`, which suppress the window name at creation. There is no global `window-status-format` default, so a raw `tmux("new-window", …)` leaks the window name into the status-bar center strip (`setupStatusBar` only blanks the `main` window).
- **Alert dedup** — `addAlert` (`src/dashboard/alerts.ts`) suppresses identical-key alerts within a 1-hour window. Default key is `${level}:${source}:${project}:${worker}:${message[:200]}`. When a message embeds time-varying detail (SHA, error string, file list), pass an explicit stable `dedupKey`.
- **Specs** — files containing the marker phrase **"the code is wrong"** in their opening paragraph are specs. The reviewer prompt-prepends a strong warning never to edit a spec to match the code. If the code disagrees, fix the code.
- **Tests** — `npm test` runs unit + integration (`test/integration/**`); the bundled-hook test catches module-init cycles vitest's source resolver misses, and `import-cycles.real.test.ts` fails when a module outside the known set joins a runtime import cycle (the list there only shrinks). Don't move integration tests behind a flag. The merge gate runs unit coverage (`test:coverage`, which excludes `test/integration/**`) and then the dedicated integration config exactly once; per-file thresholds protect lifecycle/launch/lock boundaries with ~5pp headroom. Both configs load `test/setup-home.ts`, which pins `HOME` to a throwaway dir for every test: the operator's workstation has a real `~/.garden`, a CI runner does not, so a test that reads the live config would otherwise pass locally and fail only on CI (how `resolveReviewRole`'s unconditional `loadConfig()` shipped a red main). A test needing its own writable garden uses `useTmpHome()` (`test/helpers.ts`); nothing should read the real one.
- **tmux must answer before absence counts** — tmux is the source of truth for pane existence only when it answers: a garden process inside an agent sandbox is denied the tmux socket, so every probe fails exactly as a destroyed pane does. Confirm reachability (`dashboardReach` / `dashboardExists`, `session.ts`) before treating a missing pane or window as evidence or acting on it.
- **Poll state lives on disk** — the poller execs a fresh process per poll, so anything a poll must remember (grace stamps, dedup markers, retry counts) goes in the registry or a file, never a module-level Map (DESIGN.md "Merge Handling"). `poll-module-state.real.test.ts` fails on new module-level state in any module a poll loads; state that is right to lose at exit goes on its list, with the reason.

## Adding a new command

1. `src/commands/<name>.ts` — export an async `(args: string[]) => Promise<void>`
2. Register in `src/commands/index.ts`
3. Add to the help text in `src/cli.ts`
4. Use `output()` and `resolveProject*()` per Conventions

## Adding a dashboard tmux hook

Install visual status hooks in `setupStatusBar` (`src/dashboard/header.ts`), which runs on creation and runtime refresh. Keep work tmux-native when possible; a focus hook can use `refresh-client -S` with the event client as its default target. Hooks requiring Garden logic follow the `create.ts` hooks: invoke an internal `dashboard` route through `run-shell` and shell-escape its arguments. Test command wiring and any format or redraw behavior against an isolated tmux server; `test/integration/status-focus.real.test.ts` uses a Python standard-library PTY fixture to exercise terminal focus reports.

## Adding a new project config key

Add the field to `ProjectConfig` and `VALID_CONFIG_KEYS` in `src/config.ts`. A scalar key also belongs in `SETTABLE_KEYS` and the validation/mutation switch in `src/dashboard/project-config-mutate.ts` so the CLI has one authoritative writer; a list-valued key with verbs needs a dedicated dispatch and shared mutators instead (`sandboxWriteRoots` is the example). Update `src/cli.ts` help plus DESIGN.md "Project Configuration"; add a dashboard menu row only when the key is an everyday interactive control. Cover set, clear, invalid, and read-back behavior in `test/config.test.ts`, and update `DESIGN.md` when the key changes runtime architecture.

## Adding a garden-level setting

Add an optional field or typed block to `GardenConfig` in `src/config.ts`, with a defaulting getter and a validated setter using `mutateConfig`. For a menu control, add its view field, plan builder, and apply handler in `src/dashboard/garden-menu.ts`, then wire the internal route in `src/dashboard/index.ts`. Await any live update before reopening the menu: `runMenu` blocks until the menu closes. Route all consumers through the same getter; for column split changes, use `reconcileColumnSplit`, which reuses `rebakePanesOnResize` and `presizeHiddenWindows` and records successful application under the dashboard state lock. Cover set, unset, invalid values, and live application, and update the `⌥;` menu description in DESIGN.md "Machine-wide limits".

## Adding a new workflow

See `WORKFLOWS.md`. Short version: define a poller-only `WorkflowDefinition` in `src/dashboard/workflows/<name>.ts`, register it in `workflows/index.ts`, and reuse `default.ts`'s state handlers wherever possible. Agent activity hooks are shared lifecycle plumbing; do not import the workflow registry from `hook-dispatcher.ts` or `hooks/default.ts`. Tests: `test/workflows.test.ts` + an integration test on the real external boundary the workflow drives. Concrete examples in the registry: `grow.ts` (minimal loop divergence) and the designer/planner pair (data-only definitions that reuse default handlers and invert worker posture through rules/skills). If your workflow shares the cold-respawn-per-iteration mechanics, supply a `LoopHooks` instance (see `src/dashboard/loop.ts`) instead of forking the dance.

**Per-workflow runtime data** (the grow pattern). Anything the workflow accumulates per worker goes under an optional sub-object on `WorkerEntry`, not as flat fields — `entry.grow?: GrowData` is the concrete example (`registry.ts`). `updateWorkerFields({ <subObject>: { <field>: ... } })` deep-merges that sub-object so callers don't clobber sibling fields. Add a legacy-shape migration to `readRegistry` so on-disk entries from earlier shapes get rebuilt at next read. Don't add flat per-workflow fields to `WorkerEntry`; the flat-fields path was deliberately removed (the migration in `readRegistry` exists to scrub stragglers from old on-disk entries).

## Adding a new harness

See `docs/MULTI-MODEL.md` "Layer 3". Short version: implement `HarnessCore` in `src/dashboard/harness/<name>-core.ts` (command dialects, prompt delivery, transcript reader, transient-error shapes — keep its import closure light; it is reachable from `dist/hook.js`), add `installRuntimeConfig` in `harness/<name>.ts`, and register in both `harness/core.ts` and `harness/index.ts`. Registering makes the harness a crew **member** and so a `⌥⇧N` provider choice for free; add its strong/middle pair to `SEAT_MODELS` (`crew.ts`) or its builtin crew seats stay unpinned. But the composer's **model and effort vocabularies** are per-harness and do NOT follow: `composerModels`/`composerEfforts` (`harness/vocabulary.ts`) branch explicitly, so an unhandled harness silently offers the Anthropic aliases and the claude-code effort rungs, in the `⌥⇧N` composer and the `⌥,` project menu alike, and the project effort setter and the CLI `--effort` (`workerEffortRungs`) refuse its own levels. Add a branch (see `codex-models.ts` for the read-the-harness's-own-catalog shape, fallback-list included) or the operator picks names the new harness cannot run. Launch **tuning defaults** are per-harness in the same way: `harnessTuning` (`launch-plan.ts`) is what pins codex's unpinned model/effort, and a harness with no branch there launches on whatever its own CLI defaults to. That may well be right — decide it deliberately rather than inherit it by omission. A new **provider** needs none of this — it is config, not code: `garden provider add` makes it a member and its `modelMap` keys become its model vocabulary automatically (`providerModelAliases`). Add a row to the `READERS` table in `prompt-verify.ts` too: delivery verification reads back the newest prompt from the harness's own transcript, and because that table is a hook-bundle leaf rather than a `HarnessCore` method, registering does NOT opt a harness in — an unlisted harness silently loses verification (`prompt-verify.test.ts` fails until the row exists). The reader must skip the harness's injected user-role records and return the text verbatim: the caller compares it against what garden pasted, so any condensing manufactures a mismatch. `task-title.ts`'s `OPENING_READERS` is a second such table, for the same bundle reason and with the same consequence: an unlisted harness can never be given a written thread title, so a row its own title source leaves blank stays blank (`task-title.test.ts` fails until the row exists). Its reader returns the first task prompt, including peer-delivered task messages that delivery verification skips. A harness without a turn-end signal cannot be registered — `capabilities.turnEnd` is typed `true` because STATUS.md's no-polling invariant is preserved by refusing such harnesses, not polling around them. Worker capabilities are **enforced at spawn/resume** by `resolveWorkerLaunchPlan` (`launch-plan.ts`, delegating tuple checks to `workerLaunchCompatibilityError`), so declare them deliberately rather than copying a sibling adapter: `workerWorkflows` is a fail-closed allowlist of the worker workflows whose launch/resume semantics the adapter actually implements (a workflow missing from it is refused, so registering does NOT opt a harness into future workflow protocols), and `providerProfiles` says whether the harness consumes garden's `ANTHROPIC_*` provider contract — false means a provider-backed worker is refused rather than silently launched against the harness's own backend. `sandbox` and `resume` are enforced at the same boundary; `headlessRoles` separately opts the adapter into each review-family role. The event side: translate the harness's native lifecycle onto the normalized `WorkflowHookHandlers` methods (`onTurnEnded` etc.) — for claude-code that translation is `hook-dispatcher.ts`'s wire-name switch. Check what the harness's terminal title says while it works: if it is not a rolling summary of the agent's activity, implement the optional `readActivity` too, or the status pane's detail column shows whatever the title happens to be (for Codex that was the worktree basename, i.e. the worker's own name). Check whether the harness can move a session OFF the model garden pinned with its launch flags: if it can, and if it names models in the same vocabulary the pin uses, implement the optional `readRunningModel` so `model-drift.ts` can flag the divergence — a harness that omits it is simply never checked, and garden goes on asserting a pin it cannot verify (which is what let codex 0.153.4 run a worker on `gpt-6-astra` for 13 minutes under a row reading `gpt-5.6-sol`). The caller compares the reading to the pin for exact equality, so a harness whose pin is an alias its transcript never echoes back (claude-code pins `opus`; the transcript records `claude-opus-5`) must normalize inside the reader — answer in the pin's own words when the two name the same model, and return null for an id it cannot place, rather than handing up a spelling that reads as drift on every healthy worker. Check WHEN the harness's SessionStart-equivalent fires, too: garden's seed wait treats `agentStatus` leaving `loading` as "the TUI is up", which holds only for a harness that reports boot. One that fires at the first *turn* instead (Codex) deadlocks that wait — nothing clears `loading` until a prompt lands, and the wait is what withholds the prompt — so it must implement the optional `promptReady`, which reads boot off the pane. Two call sites outside the adapter name the harness explicitly and do NOT follow from defining it: `newWorker` (`workers.ts`) stamps codex's `awaiting task` creation placeholder (or a seed's first line) so a fresh row is not blank before the first prompt, and `applyAndLog` (`hooks/default.ts`) exempts a worker still carrying that placeholder from the heartbeat throttle so the derived summary lands on the first hook rather than up to 10s later. A harness with no branch there starts blank and heals a heartbeat behind. `newWorker` also names claude-code as the only harness with the ultracode preset and the only one given a workflow's `workerModel` (the designer/planner Opus): any other harness is refused an explicit ultracode request, skips a project or crew `ultra`, and launches on its own tuning default instead of Opus. The pane's **status line** is a third such site: garden names the worker's model, effort, and remaining context on every pane, but each harness expresses that in its own dialect (claude-code: a `statusLine` command in garden's settings file; Codex: a `-c tui.status_line=[…]` launch override), so a new adapter shows whatever its CLI shows by default until it renders its own. `readTurns` owes a **summary**, not a transcript dump: accumulate activity between operator prompts and flush ONE assistant turn per prompt through `summarizeTurn` (`conversation.ts`), mapping the harness's tool vocabulary onto the neutral names it reads — and route operator prompts through `promptTurn` so garden's own continuations collapse to markers. A reader that emits one turn per assistant message produces a worse-formatted copy of the agent pane.

Two model details do not follow automatically from registering the adapter. If the harness accepts both aliases and concrete model IDs, normalize only aliases whose transcript spelling differs; concrete pins must stay exact or a substitution within one family is hidden. If `harnessTuning` supplies a Garden-owned default model, add that same default to `pinnedModel` (`model-drift.ts`) and `projectWorkerModel` (`crew.ts`), or the drift detector and override-only status badge disagree with the launch plan.
