# Garden

Garden is a CLI orchestrator for managing interactive Claude Code sessions across multiple projects via a tmux dashboard.

**This file is the project's agent instructions, for every harness.** Claude Code reads `CLAUDE.md` and never `AGENTS.md`; Codex reads `AGENTS.md` and never `CLAUDE.md`. Garden runs both against this repo, so `AGENTS.md` is the real file and `CLAUDE.md` is a one-line `@AGENTS.md` import ([the documented pattern](https://code.claude.com/docs/en/memory#agents-md)). Edit this file; never keep a second copy of the same instructions in `CLAUDE.md`. `garden doctor` reports which registered projects have not adopted the pairing.

**Authoritative docs.** This file is a quick-start. Depth lives elsewhere — when something here disagrees with one of these, the spec wins:

- `DESIGN.md` — full architecture
- `rules.md` — coding rules loaded into every Claude session (commit/test/scope discipline)
- `WORKFLOWS.md` — workflow registry design, "how to add a new workflow", and workflow specs
- `docs/STATUS.md` — worker status state machine (spec)
- `docs/MULTI-MODEL.md` — multi-model / multi-harness architecture (Phases 1-3 shipped — provider layer, neutral core, harness adapter registry; Phase 4 in progress — Codex adapter shipped and reachable **as a reviewer** via per-role resolution (`config <p> role reviewer harness codex`) and **as a worker** via `workers new --harness codex`; a Codex worker's session-id capture, history/continue routing, status-pane activity summary, and plan-mode `asking` status now ship — the remaining gaps are live-verifying `codex resume` and Codex-aware unsent-draft detection)
- `docs/TRACKS.md` — multi-track / promotion pipeline (design target, no code yet)
- `docs/` — additional design docs and behavioral specs; see `docs/README.md` for the index

## Build and run

```bash
npm install
npm run build          # esbuild → dist/cli.js + dist/hook.js
npm run dev -- help    # tsx during development
npm test               # vitest unit + integration; tsc --noEmit
```

`npm link` makes `garden` global. `dist/cli.js` is the symlink target — `npm run build` is all you need after edits. `package.json` sets `"sideEffects": false` so esbuild tree-shakes imported-but-unused modules (load-bearing for keeping `dist/hook.js` lean); modules must stay free of import-time side effects — only the entry points (`cli.ts`, `hook-entry.ts`) execute at top level. The build emits a second minimal bundle, `dist/hook.js` (from `src/hook-entry.ts`), that serves the per-tool-call Claude hook. Its dispatcher binds directly to the shared worker hook handlers and never imports the workflow registry or poller state handlers: the minified closure measures ~125KB versus ~688KB for `cli.js` (~82% smaller), and `hook-bundle.real.test.ts` enforces a 128KB ceiling plus the graph boundary. Worker `settings.json` hook commands invoke it via `resolveHookRunner()` (`dashboard/runner.ts`), prefixed with a `NODE_COMPILE_CACHE=~/.cache/garden/node-compile` assignment (`hookCompileCachePrefix`) so each cold start reuses the bundle's cached V8 bytecode (~8% faster, measured; the dir is a sandbox-writable root shared fleet-wide, and node self-invalidates it on version/content change). The prefix is applied only on the claude-code path (`buildSettingsJson`), whose hook commands run through a shell — deliberately not folded into `resolveHookRunner()`, since the Codex adapter embeds that string in a TOML `command` value with different exec semantics. `cli.js` keeps its own `_claude-hook` route for workers whose settings predate it.

## Source layout

- `src/cli.ts` — entry point, command dispatch, help text
- `src/hook-entry.ts` — minimal second entry point for the per-tool-call Claude hook, built to `dist/hook.js` (calls `handleClaudeHook` directly, skipping the full command/dashboard graph)
- `src/commands/<name>.ts` — one async function per CLI command, registered in `commands/index.ts`
- `src/paths.ts` / `src/config.ts` / `src/session.ts` / `src/rules.ts` / `src/output.ts` / `src/version.ts` — trusted runtime paths, config (`~/.garden/config.yml`), tmux sessions, system-prompt assembly, TTY-aware output, build version
- `src/checks-semaphore.ts` — machine-wide slot semaphore bounding concurrent checks-suite runs (`max(1, cores/8)` slots by default, overridable via the garden-level `limits.checksSlots`; pid-stamped `O_EXCL` lock files in `SESSIONS_DIR`, dead-owner steal, bounded-wait fail-open); `garden checks` (`src/commands/checks.ts`) is the consumer. The sibling fleet-wide budget is `limits.maxConcurrentReviews` (a cap on live `_<project>-review-<worker>` windows across all projects, gated at the review-launch point in `handleWorking` — defers, doesn't block; resolvers/ci-fix uncapped to avoid pipeline deadlock; 0/unset = unlimited). Both live under `limits` in `~/.garden/config.yml` (`LimitsConfig`, `config.ts`); `garden limits` (`src/commands/limits.ts`) is the operator surface. See DESIGN.md "Machine-wide limits".
- `src/dashboard/` — the dashboard. Notable modules:

  - `state.ts`, `registry.ts`, `validate.ts` — transactional state mutation + tmux/state reconciliation
  - `window-heal.ts` — watchdog-driven tmux window repair, run under the dashboard state lock before orphan detection so navigation swaps are never mistaken for damage
  - `tmux.ts`, `window-names.ts`, `atomic-write.ts`, `file-lock.ts` — low-level helpers
  - `headless-paths.ts` — traversal-safe, length-bounded paths for reviewer/resolver/CI-fix prompt and result exchanges under the poller-owned `~/.garden/control/headless` tree; durable holistic shadow reports live under `~/.garden/control/reports`. Handoff has an untrusted request inbox under sandbox-writable `~/.garden/sessions`, but pollers move claims, protected seed copies, and durable receipts into `~/.garden/control/handoff` before acting
  - `poller.ts` + `poller-state.ts` + `poller-{review,merge,resolve,ci,ci-fix,fifo}.ts` — per-project review/merge/resolve/ci-fix lifecycle, event-driven via FIFO. `poller-ci-fix.ts` mirrors `poller-resolve.ts` for self-healing red CI. When a reviewer's output reaches a conclusion but lacks a parseable `CLEAN`/`FIXED`/`FAILED` line (prose tail, markdown-decorated token, or verdict buried above a long test dump), `handleReviewing` first tries a cheap synchronous Haiku classifier (`verdict-extract.ts` `extractReviewVerdict`, 45s hard timeout, same first-party account as the reviewer) to recover the verdict before falling through to `handleUnparseableReview`'s re-review — default workflow only (trellis `DRIFT` carries a structured drift list a one-word extraction can't reconstruct). Every review-prompt builder composes through `composeWithinCeiling` (`prompt-compose.ts`), which measures the assembled prompt against `MAX_REVIEW_PROMPT_BYTES` (1MB) and, when it busts, recomposes ONCE with the inline diff swapped for its `git diff --stat` summary plus the command to page the delta — the reviewer runs inside the worktree with a shell, so a branch too large to carry inline is still reviewable, just shallowly (the paged block tells it to name the files it did not read, so a partial pass can't read as full coverage). The ceiling is deliberately well under the reviewer's context window: the reviewer also rebases, runs the checks suite, and reads/edits files in that window, and a prompt sized to fill it compacts mid-review — a compacted reviewer certifies a summary of the diff, not the diff. `launchReview`'s own ceiling check is now the backstop for the case degradation can't fix (non-diff context — rules, docs, test files — over the ceiling on its own): no reviewer can launch at all, so the worker parks in `failing` with `failingReason: "oversized-diff"` and an alert naming the size and the remedy. Not kick-recoverable (an unchanged branch re-fails) and deliberately not an `OPERATOR_ACTION_FAILING_REASON` — shrinking the branch changes the SHA and re-enters review through the normal failing debounce. The holistic pass (`poller-holistic-review.ts`) degrades identically and applies the same backstop, but leaves the worker `done` with a warn alert, matching that file's best-effort posture. Ceiling sized from measurement (median review delta 3-14KB, p95 88-155KB, largest observed 336KB across 160 commits of two repos; the motivating failure was 2.88MB)
  - `beads.ts` + `poller-intake.ts` — the bead-intake loop (board→garden delegation; board's `docs/DELEGATION.md` is the authority, DESIGN.md "Bead intake" the garden-side spec). `beads.ts` is the bd shell-out client (contract first verified against 1.0.3 and re-verified against 1.2.2; cwd pinned to the project checkout — a worktree's `.beads` has no database; every call takes a `BeadsStore` and a configured `beadsDir` reaches bd as `BEADS_DIR`, the same `resolveBeadsDir` rule worker env injection uses — Decision 15's one store-resolution rule); `poller-intake.ts` is a poller step (opt-in via `beadIntake: true`, cap via `beadIntakeCap`) that converts ready, dispatch-labeled beads into workers: frontier from `bd swarm status <epic> --json` (never the `--parent` family), filtered by the circuit breaker (`dispatch:failed:N >= BREAKER_THRESHOLD` excludes a bead before slots/sort; garden writes the label from its two quality-failure observation points — the reaper's failing branch and the review-rejection path in `poller-review.ts`, both via the shared `incrementFailedLabel` in `beads.ts`), modes/budget/spend via epic labels (`dispatch:manual|auto|off|dispatched|budget-exhausted`, `budget:N`, garden-written `dispatch:spent:N` charged fail-closed BEFORE each spawn, plus the `dispatch:dispatching` mid-wave marker — a manual arm covers the whole wave across passes, consuming to `dispatch:dispatched` only when the observed frontier drains; counter labels parse max-wins with straggler GC), claim-as-worker idempotency (`BEADS_ACTOR=<worker-name> bd update --claim` post-spawn with one retry and a pre-spawn assignee re-check — the behavior verified on 1.0.3 remains true on 1.2.2: `--claim` never overwrites a foreign assignee, so the doc's `garden-pending` stack is routed around), a two-branch reaper for dead workers' beads (crash while `working` → `dispatch:retry:N`; died parked in `failing` → `dispatch:failed:N` via `shouldReapFailing`, no retry bump — live failing workers keep their beads), a reconcile step (Decision 7: stop — via `stopWorkerByName` — any `entry.bead` worker whose bead is closed or foreign-assigned, i.e. recalled; unassigned beads and mid-pipeline workers are skipped/deferred; closed-bead reconcile deliberately retires COMPLETED intake workers, the lifecycle GC, made safe by the Decision-12 removal guard), and a concurrency governor joined via bd assignee == registry name, counted after reconcile so a freed slot is usable the same pass. It also hosts the **plan-consume loop** (board's `plan:*` lifecycle, DELEGATION.md Decision 16): epics labeled `plan:pending` are consumed to `plan:planning` BEFORE spawning exactly one planner worker (seeded by `buildPlannerSeed` with the epic's design doc + the verified bd contract; `plan:failed` on any failure) — the planner is cap/governor/budget-exempt and carries no bead, and only `pending` is spawnable so repeated wakes are idempotent. The join's registry→bd half is `WorkerEntry.bead`, stamped at spawn through the intake spawn seam (`IntakeSpawnRequest`) and by `garden handoff --bead`; both operator removal paths (`⌥x` and `garden workers stop`) run the guarded Decision-12 unclaim from the shared `finalizeWorkerRemoval` tail in `workers.ts` (reopen+unassign only a still-self-assigned open/in_progress bead; failures alert, never silent). Piped `garden status` reports `lastIntakeAt`/`lastIntakeError` per `beadIntake` project via `intake-paths.ts` (a hook-bundle-safe leaf — `status.ts` must not import `poller-intake.ts`). Workers of opted-in projects get `BEADS_ACTOR`/`BEADS_DIR` injected (`beadsEnvExports`, `create.ts`) + sandbox write access to the resolved canonical `.beads`. A per-project `beadsDir` (absolute path) points BOTH bd surfaces — garden's own shell-outs and worker env — at a shared store (in practice board's, the fleet's only one) via `resolveBeadsDir` (`config.ts`); each pass is then scoped client-side to epics labeled `project:<name>`, a dangling configured store skips the pass fail-closed (stamped as the intake error + error alert; `beadsStoreError`), and `garden doctor` preflights every pinned store. Throttled per-project on disk; `garden poke` bypasses and ensures a poller first; the watchdog keeps pollers alive for opted-in projects with zero workers and supplies the recurring `INTAKE_BEAT_MS` poke

The client waits 15s for claim and 75s after claim for the synchronous spawn path. With `--expect-callback`, the dispatcher stamps parent linkage on the child entry so `transitionState`'s terminal-state chokepoint can fire a one-shot prompt back at the parent pane via `notifyHandoffCallback` (`continue.ts`) — with `handleDone`'s quiescent leg as the second dispatch site, since the Stop hook's trail-off `done` write bypasses `transitionState`; the child stages an optional reply via `garden reply`. With `--ultracode`, the child is created with the ultracode preset (Opus pin on `entry.model` + `entry.ultracode` → `--effort max` and the dynamic-workflow keyword trigger, rendered by the harness `buildAgentCommand` and threaded through spawn/resume/bounce). Defining it also opts the harness into thread titling (`task-title.ts`), which reads that declaration as "this harness's pane title is not a summary" and gives workers still showing their opening-prompt fallback one Haiku-written topic; an existing plan step is already live activity and is never replaced. ## Workers (worktrees)

Every worker runs in its own git worktree at `~/.garden/worktrees/<project>/<worker>/`, on a branch named after the worker, branched from `origin/<base>` (fetched first). Each project has a dedicated **poller** in a hidden tmux window that drives review/merge using local git — no GitHub PRs. Reviewers and resolvers run headless in hidden `_<project>-review-<worker>` / `_<project>-resolve-<worker>` windows. Multiple reviews run in parallel within a project; the merge queue is serial. Full state machine: `docs/STATUS.md`.

Before merging, the queue rebases onto the current `origin/<base>` through
`rebaseBranch` (`git.ts`). It skips the rebase when the branch already contains
the base tip, uses `--rebase-merges` when a genuinely behind branch contains
merge commits, and uses a plain rebase for an ordinary linear branch. Reviewer
prompts apply the same selection; resolver prompts preserve merge topology when
re-attempting a conflicted rebase.

Per-phase review sees only one delta against base, so when a multi-phase **default** worker reaches `done` having merged `>= 2` times, the poller interposes ONE final review of the whole-task cumulative diff for cross-phase coherence defects before the worker truly finishes. This is NOT a spawned worker: it reuses the headless reviewer flow (`launchHeadlessAgent` + `resolveReviewRole`, so a Codex reviewer works) on the worker's own branch, re-opening `done` → `reviewing`. Gated per-project by `holisticReview: off|shadow|fix` (default `fix` — `DEFAULT_HOLISTIC_REVIEW` in `config.ts`; `shadow` reports findings as an alert, `fix` fixes cross-phase defects directly and rides the normal CI/merge gate — the deliberate-decision guardrail is folded into the reviewer prompt; a project opts out with an explicit `off`/`shadow`). Spec: `WORKFLOWS.md` § "Holistic-review workflow"; `garden dashboard _holistic-backtest` replays it read-only against a past worker.

Worker prompt is `rules.md` (global) + `<project>/.garden/rules.md` (project) + per-worker preamble built by `buildWorktreeRules` in `src/rules.ts`. The preamble names the project's configured `checks` command (from `garden config <project> checks`) so the worker, the reviewer, and CI all gate on the same string — keep that command aligned with `.github/workflows/test.yml` or you reintroduce the asymmetry that caused workers to push broken state and CI to email "Run failed" on every commit. Workers and reviewers run it via `garden checks`, which executes exactly that string under the machine-wide checks semaphore (see DESIGN.md "Project Configuration" → checks) so overlapping suites queue instead of stampeding the workstation; CI runs the raw command ungated on its own runner. Worker panes start in `permissions.defaultMode: "auto"` inside an OS sandbox (Seatbelt/bubblewrap) configured by `sandbox.ts`. Workers commit and push autonomously — no operator confirmation; the poller handles review and merge.

## Dashboard internals

Permanent tmux layout — content is moved between visible slots and **hidden underscore-prefixed windows** (`_<project>-worker-N`, `_<project>-shell`, `_<project>-poller`, `_garden-{growhouse,root,logs,history,diary,alerts}`, `_garden-usage-poller`, `_garden-watchdog`) via `tmux swap-pane`. Normal navigation never destroys pane slots; `healActivePaneInState` is the single repair exception, recreating a right slot only after its pane has already died.

The title and status panes are passive: keyboard input, mouse selection, and wheel scrolling are disabled. The lower growhouse slot retains normal interaction for its active view.

- **Left column**: `garden` title pane (Claude quota meters), `status` pane (per-project worker list), and `growhouse` pane (cycles `⌥g` growhouse / `⌥r` root / `⌥l` logs / `⌥h` history / `⌥d` diary / `⌥a` alerts). Title and status panes refresh via SIGUSR1, replaying pre-baked files written atomically. Each project header row in the status pane carries a dimmed pencil `✎` when its diary holds non-whitespace content (`diaryHasContent` in `src/diary.ts`, stat-cached on mtime+size to stay off the refresh hot path; `formatDiaryGlyph` in `src/commands/status.ts`). Worker rows are ordered by attention/recency, not name — `compareWorkerFreshness` (`registry.ts`) sorts by tier (blocked-on-you → new/`ready` → active → in-flight → `done`; the bands descend a worker's life toward merge, so `reviewing`/`merging` sit below `working`, above `done`), then freshness (`workerSortFreshness` = `lastStateChangeAt ?? lastEventAt ?? createdAt`, 60s-bucketed to avoid jitter), then name; the same comparator drives the `⌥]`/`⌥[` cycle and `whoami` siblings. Ordering keys on `lastStateChangeAt` (the last real `agentStatus`/`prState` transition, stamped by `applyAndLog` on an `agentStatus` change and by `transitionState` on a `prState` change — never on the 10s heartbeat), NOT the raw `lastEventAt`: the 10s hook heartbeat bumps `lastEventAt` without repainting the status pane, so ordering by it let rows drift silently and snap on the next navigation-triggered repaint. `lastEventAt`/`workerFreshness` still drive the 24h stale-dim (`isWorkerStale`) — that wants heartbeat liveness. Active-band rows untouched >24h (`isWorkerStale`) render faint via `dimRow` — except the operator-held `paused`, which keeps its bold-cyan mark. In-flight/blocked rows (`reviewing`/`merge-pending`/`resolving`/`ci-fixing`/`asking`/`failing`) fold a dim time-in-state elapsed into the state cell (`reviewing 12m`, `asking 2h`) computed from `lastStateChangeAt` by `formatTimeInState` (`src/commands/status.ts`), yellow past a soft per-state expectation (the otherwise-uncolored pipeline states only; `asking`/`failing` stay dim since their row is already colored). It rides the same pre-baked-file path, so the watchdog's 60s tick re-bakes it via `refreshStatusElapsed` (`header.ts`) — the one recurring driver of the otherwise event-driven status pane — content-deduped so an idle fleet never repaints. The row grammar splits identity from status (`collectSegments`/`renderWorkerRow`, one path for CLI + baked): the description (detail) comes first after the state, and the whole grey override-only identity cluster — base `→ <base>`, per-worker crew (supersedes member), member/harness, and the **model** tag — trails *after* the detail as ragged tags, so nothing sits between the state and the description (operator call, 2026-07-16); the cluster costs width only on the rows that carry it and drops as a unit on a narrow pane. A detail shortened to fit the pane ends in `…`; the marker consumes one of the available columns, so the row remains within its width cap. Workflow self-identifies via `workflowRowDecor` — grow shows `grow N/M` and a vine its `[trellis: …]` bracket in the detail slot; a botanist takes a grey `botanist` badge in the identity cluster instead, leaving the detail slot to its live activity. Status-class flags (CI bracket, `gate closed`, the review-blocked `dirty tree`) never truncate. An `idle` worker with commits ahead of base whose review the clean-tree gate refuses to arm carries a yellow `dirty tree` (or `tree unknown`) flag — that stall sets no `prState`, so without it the row is indistinguishable from a worker that finished with nothing to review, and the only evidence is one info line in the log; the reason is persisted as `entry.reviewBlockedReason` by the Stop hook and both poller deferral points, and cleared at review arm/launch (`formatReviewBlockedFlag`, `status.ts`). A `failing` worker whose agent is mid-turn (`isFailingBusy` — prState `failing` + agentStatus `working`, i.e. the operator prompted it about the failure) swaps its `✖` for the braille spinner and keeps everything else red and `failing`; the plot strip mirrors it with a `failing-working` state (red spinner), which tracks the failing worker specifically — a plot whose failing worker is parked stays a static `✖` even while siblings work. The **state column** is sized to the widest state cell actually on screen (`computeStatusWidth`, floored at `STATUS_MIN_WIDTH`), like the name column — so a fleet of short `done`/`idle` rows isn't padded to the 13 cols only `reviewing 12m` needs (the old dead space between state and description); it widens when a worker enters an elapsed-bearing state and tightens again when it clears. Each header also carries a yellow per-project `⚠n` unread-alert count (`unreadAlertCountsByProject`, cleared globally on `⌥a`). See DESIGN.md "Worker row grammar" + "Worker row ordering". The `⌥h` history view shows the focused worker's prompt history (operator prompts + brief verb-tagged assistant summaries), read from the worker's Claude transcript JSONL by `conversation.ts` and painted via the same pre-baked-file + SIGUSR1 path; `writeHistoryRendered` (`header.ts`) only parses the transcript when history is the active garden mode, keeping it off the hook firehose. The `⌥a` alerts view is the same shape (`writeAlertsRendered` + `renderAlertsPane` in `commands/alerts.ts`), and is the one place alerts are marked read — it acks on entry, but splits unread/read on `state.alertsSeenMark`, the pre-ack seen-time snapshotted on entry, so the view still shows what was new while the badges clear; pressing `⌥a` again re-snapshots, folding them into read. Unlike history it is deliberately NOT baked from `refreshDashboard` (that call sits in `dist/hook.js`'s closure and would pull the renderer into the lean hook bundle — measured +2.8KB vs +260 bytes tree-shaken); its CLI-bundle drivers are `focusAlerts`, the watchdog's `refreshStatusElapsed` tick, `rebakePanesOnResize` when a terminal resize changes the wrapping width, and the `dashboard _refresh-alerts` route that `addAlert` spawns (`refreshAlertsPane`, `alerts.ts`) when a new alert lands while the view is the active garden pane — out of process for the same bundle reason plus the header→alerts import cycle a direct call would close, so an alert raised under an open view repaints immediately instead of on the next 60s tick.
- **Right-pane clock**: the right pane (worker or project shell) shows a `%H:%M` clock in the right corner of its top border (mirroring the `garden` title in the top-left). The shared `pane-border-format` carries a right-aligned, bold-green segment (matching the `garden` title, capped with border dashes to the corner) gated on the `@garden_clock` pane var, set on worker panes and the right-pane shell (not the left-column garden shells); tmux strftime-expands it on each `status-interval` tick — no extra process or poll. Keep the style comma-free (`#[fg=green]#[bold]`) — a comma in the `#{?…}` conditional blanks the clock.
- **Project color dot**: the right pane's top border prefixes the worker/shell label with a `●` in the project's `logColor` (palette of 256-color indices in `src/log-palette.ts`; `logColorAnsi` / `logColorTmux` derive the ANSI and tmux renderings) — the border names the worker, never the project, so the dot is the pane's only project marker. Gated on the `@garden_color` pane var (`colour<N>`), set by `setPaneProjectColor` (`header.ts`) everywhere `@garden_clock` is applied; the format nests `#{@garden_color}` inside `#[fg=…]`, which tmux expands before parsing the style. Deliberately not echoed in the status pane or bottom bar — those already name the project in text.
- **Logs sticky filter**: `⌥/` opens `tmux command-prompt` (pre-filled with the current filter); `⌥.` clears it instantly. The typed expression persists in `~/.garden/sessions/logs.filter.json` and is honored by both the dashboard logs pane and bare `garden logs` until cleared. Syntax: `key:value` for `worker`/`src`/`level`/`project` plus bare fuzzy tokens. CLI escape hatch for metacharacter-bearing exprs: `garden logs filter <expr>` / `--clear`.
- **State of record**: registry (`dashboard.registry.json`) for workers, state file (`dashboard.state.json`) for UI runtime, alerts file for operator-visible issues. Tmux is the source of truth for pane existence; `validate.ts` reconciles on attach.
- **Status**: hooks write `agentStatus`, the poller writes `prState`, `pane-died` writes `agentStatus="exited"`, and the operator `hold` action (`⌥e` / `garden hold`) writes `agentStatus="paused"` (a raw Escape interrupt fires no hook). Claude Code's catch-all `PostToolUse` moves `asking`/stale `idle` back to `working` only for the worker's main conversation thread: subagent tool events carry `agent_id` and never move `agentStatus`, because they can arrive while the main thread remains blocked or has already stopped. They do stamp `entry.subagentActivityAt`, from which the status renderer derives a `working` + dim `bg` display for an `idle` worker whose background Workflow/Task agents are still running (`isDelegating`, `registry.ts`) — display-only, so `asking` keeps its yellow flag and review/merge gating still sees `idle`; the display clears when the resumed main thread's own events bump `lastStateChangeAt` past the stamp, bounded by a 30-min freshness window for subagents that died silently. One deliberate crossover rides that split: a mutating tool call (Edit/Write — not Bash, so a read-only Q&A turn is free) landing while the worker's review is in flight stamps `entry.reviewInterruptedAt` on the hook side even when a subagent made the edit, and the poller cancels the pass — kills the reviewer window, discards any verdict (the reviewer shares the worktree, so it certified a tree being rewritten under it), resets to `working` with the review re-armed for the next Stop. Holistic passes cancel the same way. Event-driven; the only recurring tick is the liveness watchdog (`watchdog.ts`, `_garden-watchdog` window), which re-pokes projects whose workers sit in active states past a 5 min staleness threshold, keeps each project's poller window healthy (respawning a dead one, collapsing duplicates a spawn race left), and alerts on orphans in the two places a resource can outlive its registry entry — a live tmux worker window, and (on the hourly housekeeping throttle) a worktree directory nothing claims — it recovers lost event delivery or surfaces a casualty and never transitions state. The same process also hosts the `fs.watch`-driven Codex rollout listener (`codex-input.ts`), which writes `asking`/`working` for a `request_user_input` Codex fires no hook for — event-driven, not part of the tick. Spec: `docs/STATUS.md`.
- **Auto-continue**: `continue.ts` re-prompts after interrupt (mid-turn dashboard kill / tmux crash / bounce-while-working) and after a clean merge (with the list of files changed during review). Worker opts out by writing `.garden-done` in its worktree root before ending its turn. `garden pause` / `resume` toggle the sentinel; `UserPromptSubmit` clears it. A worker whose continue prompt was blocked (global gate closed, or paste lost) parks in `merged`; the merged-state handler (`handleMerged`, `poller-merge.ts`) replays the auto-continue decision on every poke — the gate-reopen sweep — so the prompt lands on the first poke after the gate reopens. A gate-closed strand is surfaced three ways: the status pane appends a yellow `gate closed` suffix to the `merged` row (`formatGateSuffix`, `status.ts`), `garden whoami` prints the gate state (`auto-cont.` line, on/OFF + pause reason), and the sweep logs gate blocks at info. The intended in-memory per-worker throttle resets with every one-shot poll process; but the info line can appear once per poke. The gate's usage-triggered closures are per-project (see the auto-continue gate bullet under CLI surface): usage-exempt projects auto-continue through them, so their rows never show the suffix and their `whoami` line reads `on` with a separate-token-pool note — only an explicit `garden auto off` closes the gate for everyone. Every garden-initiated prompt is delivered by `pasteAndSubmit` (`tmux.ts`), which pastes **bracketed** (`paste-buffer -p`) and waits for the composer to hold the paste before tapping Enter. Both halves are load-bearing: unbracketed, `paste-buffer` turns every LF into a CR (so a blank line between prompt paragraphs submits) and the TUI has only an arrival-timing heuristic to recognize a paste, while the fixed 300ms Enter it replaced fired mid-burst — together they truncated prompts to an arbitrary mid-sentence **suffix**, 7 of 11 post-merge continues across four workers on 2026-08-29, one down to 20 characters, leaving merged workers acting on a decontextualized fragment. The settle wait polls `capturePaneCursor` (100ms, 3s ceiling) for a caret that moved off its pre-paste position and then held; every exit submits, so an unreadable caret or a blown deadline degrades to the old fixed delay rather than losing the prompt. Delivery is then **content-verified**: `continueSentAt` is cleared by any `UserPromptSubmit`, so a truncated prompt used to read as delivered, and after a successful paste `continueWorker` polls the worker's transcript (1.5s, 20s ceiling) and classifies what landed via `classifyPromptDelivery` (`prompt-verify.ts`) — `intact` / `truncated` (a proper fragment of what we sent) / `pending`. A truncated landing re-pastes the full prompt ONCE behind a "that was a fragment, disregard it" preamble, bypassing `continueWorker` (the fragment already submitted, so the worker reads `working` and would be refused); a second truncation alerts instead of pasting a third copy, and an operator draft blocks the resend. `pending` is the catch-all, so only the observed failure shape ever re-delivers. See DESIGN.md "Paste delivery". Before pasting, `continueWorker` also defers when the operator has an unsent draft in the worker's Claude input box (`capturePaneText` + `capturePaneCursor` + `extractOperatorDraft`) so an auto-continue can't be concatenated onto a half-typed message. The draft is the span between the `❯` prompt marker and the cursor column — Claude Code paints dimmed ghost/placeholder text into an *empty* box and `capture-pane` strips the dimming, so the marker-to-cursor bound (not the bare post-marker remainder) is what tells a real draft from a suggestion. The two primary dispatch legs re-arm a bounded 12s backoff (`rearmContinueIfDrafting`, `--attempt N`, capped at 15) until the box clears. The guard carves out garden's *own* stuck paste — a prior `pasteAndSubmit` whose Enter taps were eaten leaves the message sitting unsent, and deferring on it starved every retry forever (bead workers missed their seeded `bd close`): when `entry.continueSentAt` is outstanding (stamped at the paste, cleared by `UserPromptSubmit` — so no prompt has landed since garden last pasted) AND the draft's head bears a garden-paste signature (`[garden]` / `[handoff` / the collapsed `[Pasted text …]` placeholder), `continueWorker` re-submits it with `pressEnter` instead of deferring (`isOwnStuckPaste`, `continue.ts`); the loop workflows' mirrored gate (`paneHasBlockingOperatorDraft`) applies the same carve-out. Those signatures cover every prompt garden composes itself but NOT an operator-authored single-line seed, so the guard takes a second, signature-free route when the caller knows what it is about to paste (`continueWorker` always does — a retry re-sends the same text): under an outstanding stamp, a whitespace-normalized draft **equal** to the pending message in full is our own paste, since a partial compose cannot equal the whole text; a **wrapped** draft (caret below the marker, so only its first row is visible — `extractDraftInfo` carries that bit, which the `extractOperatorDraft` string return discards) accepts an exact *prefix* instead, safe without a length floor precisely because wrapping requires the operator to have retyped a full visual row verbatim. See DESIGN.md "Stuck-paste recovery". A **seed** (a spawned worker's first prompt — handoff briefings, `workers new --seed`, each loop iteration's cold-respawn prompt) is delivered *verified* rather than fire-and-forget: `seedWorker` waits out the cold boot (a readiness wait bounded at 180s), pastes, then confirms the prompt registered as a real user turn by watching `continueSentAt` change (`classifySeedDelivery` — the `UserPromptSubmit` hook is that field's only clearer), re-pasting up to 3 times and finally raising an error alert while **keeping** the seed file so the operator can re-deliver. A lost seed is the one continuation with no recovery leg — it leaves a live worker with no task at all. The readiness half of that wait is harness-specific: `agentStatus` leaves `loading` on its own only for a harness whose SessionStart fires at BOOT (claude-code), while Codex fires it at the first *turn* — so a Codex worker stayed `loading` until something prompted it and this wait was what withheld the prompt, deadlocking every handoff for the full 180s backstop. A harness in that position implements the optional `HarnessCore.promptReady`, read off its own pane (Codex: the `›` glyph paired with its empty-composer placeholder — the glyph alone also marks startup-dialog menu rows); the wait consults it via `harnessSignalsPromptReady` (`harness/core.ts`) whenever `agentStatus` still says `loading`, and a harness that omits it keeps the pure-`agentStatus` wait with no `capture-pane` fork. See DESIGN.md "Verified seed delivery".
- **Post-merge**: advance the local base to the merged tip — `merge --ff-only` when it's the checked-out branch (also moves the working tree, so `postMerge` runs), else `git fetch origin <base>:<base>` to advance the ref alone (the many-base workflow: checkout parked elsewhere, ff-enforced + worktree-aware, postMerge skipped, silent). Then notify live siblings whose files overlap. After writing `merged`/`done`, `transitionToTerminal` re-reads `agentStatus`; if a prompt landed mid-finalization and the worker is already `working` or blocked in `asking`, it clears the terminal lifecycle state back to `working` so the row renders the live process status instead of a phantom terminal signal. A clean advance never alerts, and a redundant local commit whose clean tree already matches origin is auto-healed silently (`reset --hard origin/<base>`, reflog-preserved). `postMerge` is prevented from dirtying the checkout itself (`revertPostMergeChurn`, `poller-merge.ts`): tracked files the hook modified that were clean before it ran are restored, closing the trap where `npm install`'s package-lock churn eventually collides with a merged dependency bump, blocks `merge --ff-only`, and so skips the very hook that would clean it — freezing the checkout and the binary built from it. Operator edits already in flight, untracked files, and staged changes are never touched. Of the rest, `diverged`/`checked-out-elsewhere`/`dirty` warn (the operator's own checkout state, merge already on origin; the `dirty` alert names how far behind origin the checkout has fallen) and `stuck` — fetch failure or a wedged checkout — errors. The base checkout is the operator's shared working directory, not a pristine mirror, so all four are expected; each alert fires only on *entry* into the state, not every merge cycle (a diverged/dirty checkout would otherwise re-alert on every sibling merge). See `fastForwardBase` (`git.ts`) and `notifyPostMerge` (`poller-merge.ts`).
- **CI gate**: before each merge, `handleMergePending` queries `gh api repos/<owner>/<repo>/commits/<sha>/check-runs` (see `src/dashboard/poller-ci.ts`). Pending defers the merge (60 s recheck); failure dispatches a self-healing ci-fix agent (see `src/dashboard/poller-ci-fix.ts`, `_<project>-ci-fix-<worker>` hidden tmux window, budget 3 attempts per merge cycle). The agent reads `gh run view --log-failed` output, makes the minimum fix, and pushes — the gate then re-runs against the new SHA. Launch and success are routine lifecycle beats — logged (visible in `garden logs`) but not raised as operator alerts; only budget exhaustion alerts (error level), parking in `failing` with `failingReason: "ci"` for a genuinely red CI, or the kick-recoverable `failingReason: "transient-review"` when the agent only hit transient backend outages or a usage-quota cutoff. The ci-fix prompt carries the branch diff like a review prompt, so it composes through the same `composeWithinCeiling` (degrading an oversized delta to a file summary the agent pages itself) with the same launch-point backstop: a prompt still over the ceiling parks the worker in `failing`/`"ci"` **without** incrementing `ciFixAttempts`, since nothing ran and all three attempts would fail identically. The gate passes through on projects without a GitHub remote, without `gh` installed, with `requireCiSuccess: false`, or with zero check-runs on a project with no CI; on a project that has CI, zero check-runs on a freshly force-pushed SHA are treated as not-yet-materialized and the merge defers within a bounded grace window (3 min) before passing through. **The grace stamp and the 60s-recheck dedup marker both live on disk** (`WorkerEntry.ciNoRuns`, keyed by SHA; a mtime-stamped `ci-recheck-<project>` file in `SESSIONS_DIR`) because the poller loop execs a fresh process per poll — as module-level Maps the stamp was re-created as "now" every poll, so the elapsed check measured ~0 ms and the merge deferred forever, and the poke dedup never fired, so each poke during the stall spawned another sleeper that poked again. That pair stranded two wolf workers in `merge-pending` for 5.5 h behind 43 orphaned sleepers on 2026-07-21. Any state a poll must remember belongs on disk, not in a module Map. "Has CI" reads `.github/workflows/*.yml`/`*.yaml` on disk first (`projectDefinesCi`, `poller-ci.ts`), falling back to a check-run observed earlier in this poller's life — the disk read is what makes the grace window reachable at all, since the in-memory flag could only be set by an observation the materialization race hides, leaving the gate silently open after every poller restart. This is defense-in-depth against GitHub's branch protection — the poller's force-push path bypasses the merge UI, so branch protection alone can't catch a red CI.

## Conventions

- **JSON when piped, pretty in TTY** — use `output()` / `outputLines()` from `src/output.ts` for all data output.
- **Project resolution** — use `resolveProject()` / `resolveProjectFromArgs()`. Never parse names manually. Auto-detected from cwd inside a registered project.
- **Bash escaping** — every value interpolated into a generated shell command goes through `shellEscape` (`src/dashboard/tmux.ts`). It returns a fully single-quoted bash literal — use the result without surrounding `'...'`. No inline `.replace(/'/g, "'\\''")`.
- **Transactional shared state** — every persisted state file goes through `atomicWriteFile` (`src/dashboard/atomic-write.ts`), which flushes the temp file before rename and the parent directory afterward for durable writes, and every read-modify-write holds the corresponding cross-process lock. Config writers use `mutateConfig`; conditional registry writers use `updateWorkerFieldsIf` or `mutateRegistry`; worker creation uses `addWorkerWithUniqueName` so name allocation and insertion share one registry snapshot; dashboard pane changes use `withStateLock`. `file-lock.ts` stamps each lock with a PID plus a unique owner token, never age-evicts a demonstrably live holder, and removes a lock only when the token still matches. `transitionState` validates and applies the current-state move in one registry transaction; invalid edges are rejected, with `forceTransitionState` reserved for explicit recovery paths. Readers pair persisted JSON with an `is{ShapeName}` type guard before trusting it. See `readDashState` / `readRegistry` / `readAlerts`.
- **Trusted vs. worker-writable state** — `~/.garden/sessions` is inside every worker's sandbox write grant (claude-code's `DEFAULT_ALLOW_WRITE` in `sandbox.ts`, Codex's `writable_roots` in `codex-core.ts`), so it holds worker request IPC and nothing a worker must not be able to forge. Control-plane files live under `~/.garden/control`, which no sandbox grants: reviewer/resolver/CI-fix prompts, results, and harness stderr sidecars under `control/headless`, durable holistic reports under `control/reports`. A new headless-agent role takes its paths from `src/dashboard/headless-paths.ts` (which also bounds unsafe or oversized project/worker names to a SHA-256 component) rather than composing a fresh `path.join(SESSIONS_DIR, …)`. The registry itself is still in `sessions` — see `docs/SANDBOX-THREAT-MODEL.md` for that open item.
- **Dashboard windows** — every window created in `DASHBOARD_SESSION` goes through `newDashboardWindow` (void) / `newDashboardWindowPaned` (returns the pane id) in `src/dashboard/tmux.ts`, which suppress the window name at creation. There is no global `window-status-format` default, so a raw `tmux("new-window", …)` leaks the window name into the status-bar center strip (`setupStatusBar` only blanks the `main` window).
- **Alert dedup** — `addAlert` (`src/dashboard/alerts.ts`) suppresses identical-key alerts within a 1-hour window. Default key is `${level}:${source}:${project}:${worker}:${message[:200]}`. When a message embeds time-varying detail (SHA, error string, file list), pass an explicit stable `dedupKey`.
- **Specs** — files containing the marker phrase **"the code is wrong"** in their opening paragraph are specs. The reviewer prompt-prepends a strong warning never to edit a spec to match the code. If the code disagrees, fix the code.
- **Tests** — `npm test` runs unit + integration (`test/integration/**`); the bundled-hook test catches module-init cycles vitest's source resolver misses. Don't move integration tests behind a flag. The merge gate runs unit coverage (`test:coverage`, which excludes `test/integration/**`) and then the dedicated integration config exactly once; per-file thresholds protect lifecycle/launch/lock boundaries with ~5pp headroom. Both configs load `test/setup-home.ts`, which pins `HOME` to a throwaway dir for every test: the operator's workstation has a real `~/.garden`, a CI runner does not, so a test that reads the live config would otherwise pass locally and fail only on CI (how `resolveReviewRole`'s unconditional `loadConfig()` shipped a red main). A test needing its own writable garden uses `useTmpHome()` (`test/helpers.ts`); nothing should read the real one.

1. `src/commands/<name>.ts` — export an async `(args: string[]) => Promise<void>`
2. Register in `src/commands/index.ts`
3. Add to the help text in `src/cli.ts`
4. Use `output()` and `resolveProject*()` per Conventions

## Adding a new project config key

Add the field to `ProjectConfig` and `VALID_CONFIG_KEYS` in `src/config.ts`, then add it to `SETTABLE_KEYS` and the validation/mutation switch in `src/dashboard/project-config-mutate.ts` so the CLI has one authoritative writer. Update `src/cli.ts` help plus the Projects summary above; add a dashboard menu row only when the key is an everyday interactive control. Cover set, clear, invalid, and read-back behavior in `test/config.test.ts`, and update `DESIGN.md` when the key changes runtime architecture.

## Adding a new workflow

See `WORKFLOWS.md`. Short version: define a poller-only `WorkflowDefinition` in `src/dashboard/workflows/<name>.ts`, register it in `workflows/index.ts`, and reuse `default.ts`'s state handlers wherever possible. Agent activity hooks are shared lifecycle plumbing; do not import the workflow registry from `hook-dispatcher.ts` or `hooks/default.ts`. Tests: `test/workflows.test.ts` + an integration test on the real external boundary the workflow drives. Concrete examples in the registry: `trellis.ts` (full-spec divergence — own reviewer prompt, verdict vocab, model pinning, post-merge dispatch), `grow.ts` (minimal loop divergence), and the botanist/planner pair (data-only definitions that reuse default handlers and invert worker posture through rules/skills). If your workflow shares the cold-respawn-per-iteration mechanics, supply a `LoopHooks` instance (see `src/dashboard/loop.ts`) instead of forking the dance.

**Per-workflow runtime data** (the trellis pattern). Anything the workflow accumulates per worker goes under an optional sub-object on `WorkerEntry`, not as flat fields — `entry.trellis?: TrellisData` and `entry.grow?: GrowData` are the two concrete examples (`registry.ts`). `updateWorkerFields({ <subObject>: { <field>: ... } })` deep-merges that sub-object so callers don't clobber sibling fields. Add a legacy-shape migration to `readRegistry` so on-disk entries from earlier shapes get rebuilt at next read. Don't add flat per-workflow fields to `WorkerEntry`; the flat-fields path was deliberately removed (the migration in `readRegistry` exists to scrub stragglers from old on-disk entries).

## Adding a new harness

See `docs/MULTI-MODEL.md` "Layer 3". Short version: implement `HarnessCore` in `src/dashboard/harness/<name>-core.ts` (command dialects, prompt delivery, transcript reader, transient-error shapes — keep its import closure light; it is reachable from `dist/hook.js`), add `installRuntimeConfig` in `harness/<name>.ts`, and register in both `harness/core.ts` and `harness/index.ts`. Registering makes the harness a crew **member** and so a `⌥⇧N` build-dim choice for free — but the composer's **model and effort vocabularies** are per-harness and do NOT follow: `composerModels`/`composerEfforts` (`trellis-picker.ts`) branch explicitly, so an unhandled harness silently offers the Anthropic aliases and the claude-code effort rungs. Add a branch (see `codex-models.ts` for the read-the-harness's-own-catalog shape, fallback-list included) or the operator picks names the new harness cannot run. Launch **tuning defaults** are per-harness in the same way: `harnessTuning` (`launch-plan.ts`) is what pins codex's unpinned model/effort, and a harness with no branch there launches on whatever its own CLI defaults to. That may well be right — decide it deliberately rather than inherit it by omission. A new **provider** needs none of this — it is config, not code: `garden provider add` makes it a member and its `modelMap` keys become its model vocabulary automatically (`providerModelAliases`). Add a row to the `READERS` table in `prompt-verify.ts` too: delivery verification reads back the newest prompt from the harness's own transcript, and because that table is a hook-bundle leaf rather than a `HarnessCore` method, registering does NOT opt a harness in — an unlisted harness silently loses verification (`prompt-verify.test.ts` fails until the row exists). The reader must skip the harness's injected user-role records and return the text verbatim: the caller compares it against what garden pasted, so any condensing manufactures a mismatch. A harness without a turn-end signal cannot be registered — `capabilities.turnEnd` is typed `true` because STATUS.md's no-polling invariant is preserved by refusing such harnesses, not polling around them. Worker capabilities are **enforced at spawn/resume** by `resolveWorkerLaunchPlan` (`launch-plan.ts`, delegating tuple checks to `workerLaunchCompatibilityError`), so declare them deliberately rather than copying a sibling adapter: `workerWorkflows` is a fail-closed allowlist of the worker workflows whose launch/resume semantics the adapter actually implements (a workflow missing from it is refused, so registering does NOT opt a harness into future workflow protocols), and `providerProfiles` says whether the harness consumes garden's `ANTHROPIC_*` provider contract — false means a provider-backed worker is refused rather than silently launched against the harness's own backend. `sandbox` and `resume` are enforced at the same boundary; `headlessRoles` separately opts the adapter into each review-family role. The event side: translate the harness's native lifecycle onto the normalized `WorkflowHookHandlers` methods (`onTurnEnded` etc.) — for claude-code that translation is `hook-dispatcher.ts`'s wire-name switch. Check what the harness's terminal title says while it works: if it is not a rolling summary of the agent's activity, implement the optional `readActivity` too, or the status pane's detail column shows whatever the title happens to be (for Codex that was the worktree basename, i.e. the worker's own name). Check WHEN the harness's SessionStart-equivalent fires, too: garden's seed wait treats `agentStatus` leaving `loading` as "the TUI is up", which holds only for a harness that reports boot. One that fires at the first *turn* instead (Codex) deadlocks that wait — nothing clears `loading` until a prompt lands, and the wait is what withholds the prompt — so it must implement the optional `promptReady`, which reads boot off the pane. Two call sites outside the adapter name the harness explicitly and do NOT follow from defining it: `newWorker` (`workers.ts`) stamps codex's `awaiting task` creation placeholder (or a seed's first line) so a fresh row is not blank before the first prompt, and `applyAndLog` (`hooks/default.ts`) exempts a worker still carrying that placeholder from the heartbeat throttle so the derived summary lands on the first hook rather than up to 10s later. A harness with no branch there starts blank and heals a heartbeat behind. `readTurns` owes a **summary**, not a transcript dump: accumulate activity between operator prompts and flush ONE assistant turn per prompt through `summarizeTurn` (`conversation.ts`), mapping the harness's tool vocabulary onto the neutral names it reads — and route operator prompts through `promptTurn` so garden's own continuations collapse to markers. A reader that emits one turn per assistant message produces a worse-formatted copy of the agent pane.
